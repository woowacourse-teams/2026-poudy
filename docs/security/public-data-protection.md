# 공개 데이터 수집 억제

이 문서는 Issue #340의 범위에서 공개 데이터 무단 수집을 억제하기 위한 현재 정책과
후속 작업을 기록한다. Nginx 요청 제한과 백엔드 `:8080` 직접 접근 제한은 Issue #297의
소유 범위이므로 이 문서에서 구현하거나 중복 관리하지 않는다.

## 목표와 한계

Poudy의 카탈로그는 회원가입 없이 브라우저에서 조회할 수 있다. 따라서 브라우저에 전달된
데이터를 사용자가 한 번 저장하는 것까지 기술적으로 막을 수는 없다. 이 문서의 목표는 다음과
같다.

- robots.txt를 따르는 검색 엔진이 원본 API를 직접 순회하지 않게 한다.
- 화면에 필요하지 않은 데이터가 공개 응답에 추가되는 것을 방지할 기준을 만든다.
- 자동 수집 패턴을 발견했을 때 증거를 남기고 대응할 수 있게 한다.
- 보호가 필요한 데이터는 익명 브라우저에 직접 제공하지 않는 설계로 전환할 수 있게 한다.

robots.txt, CORS, Referer, User-Agent 검사와 JavaScript 난독화만으로 비협조적인 수집기를
막을 수 있다고 간주하지 않는다.

## 현재 공개 데이터 표면

현재 백엔드 컨트롤러 기준의 읽기 전용 공개 API는 다음과 같다. 실제 운영 경로와 응답은 배포
환경과 API 계약 검증 결과를 기준으로 다시 확인한다.

| 경로                                  | 용도                       | 대량 수집 위험 | 보호 방향                        |
| ------------------------------------- | -------------------------- | -------------- | -------------------------------- |
| `GET /api/categories`                 | 전체 카테고리와 제품 수    | 낮음           | 짧은 캐시와 요청 제한            |
| `GET /api/brands`                     | 전체 브랜드와 제품 수      | 중간           | 요청 제한, 필요 필드 점검        |
| `GET /api/brands/{brandId}`           | 브랜드 상세                | 중간           | ID 순회 탐지                     |
| `GET /api/products`                   | 필터·검색 제품 목록        | 높음           | page size 상한, 페이지 순회 탐지 |
| `GET /api/products/count`             | 조건별 제품 수             | 중간           | 반복 조건 조회 탐지              |
| `GET /api/products/suggestions`       | 제품 검색 제안             | 중간           | 검색어 반복·자동화 탐지          |
| `GET /api/products/{productId}`       | 제품 상세와 전체 성분      | 높음           | ID 순회 탐지, 응답 필드 점검     |
| `GET /api/ingredients`                | 성분 목록                  | 높음           | page size 상한, 페이지 순회 탐지 |
| `GET /api/ingredients/suggestions`    | 성분 검색 제안             | 중간           | 검색어 반복·자동화 탐지          |
| `GET /api/ingredients/{ingredientId}` | 성분 상세                  | 높음           | ID 순회 탐지, 응답 필드 점검     |
| `GET /api/exclude-codes`              | 빠른 필터용 성분군         | 낮음           | 필요 필드 점검                   |
| `GET /api/products/share-matches`     | 공유 텍스트 제품 식별      | 중간           | 입력 길이·반복 조회 점검         |
| `GET /api/storage`                    | 전달받은 제품 ID 상세 목록 | 높음           | 요청 ID 개수 상한 검토           |

피드백과 제품 등록 요청 API는 변경 요청이므로 이 문서의 공개 읽기 API 목록에서는 제외한다.

## 정책

### robots.txt

운영 환경에서는 공개 화면과 상세 페이지를 색인 대상으로 유지하되, `/api/`는
`robots.txt`에서 `Disallow`한다. staging은 전체 경로를 차단한다. 운영 색인을 허용한 공개
페이지라도 API 응답 자체를 보호한다는 의미는 아니며, robots.txt를 따르지 않는 수집기는
Issue #297의 요청 제한과 별도 탐지 대상이다.

Sitemap에 넣을 화면은 색인 정책과 함께 결정한다. 현재 `client/lib/seo/sitemap.ts`에는 검색·
보관함 경로도 포함되어 있으므로, 이 경로를 색인할지 여부는 별도 SEO 검토에서 sitemap과
페이지 metadata를 함께 조정한다. 제품·성분 상세 URL을 검색 결과에 노출할 필요가 있는지는
SEO 정책으로 결정하고, robots.txt의 API 차단과 혼동하지 않는다.

### 데이터 최소 공개

각 API 변경 시 다음을 확인한다.

- 화면에 필요한 필드만 응답하는가
- 내부 운영 정보나 원본 수집 메타데이터를 불필요하게 노출하지 않는가
- 목록 조회의 page size와 요청 ID 개수에 명확한 상한이 있는가
- 전체 데이터를 한 번에 내려받는 export 경로가 없는가
- 보호가 필요한 원본 데이터가 익명 브라우저에 전달되지 않는가

필드·page size·요청 ID 상한을 실제로 바꾸는 작업은 백엔드 API 계약 변경이므로 별도 이슈와
테스트로 진행한다. 현재 인프라 작업에서는 Spring Boot 코드와 애플리케이션 메모리 캐시를
수정하지 않는다.

### 탐지와 대응

단일 IP 제한을 우회할 수 있는 분산 수집까지 고려해 다음 패턴을 운영 신호로 삼는다.

- 제품·성분 ID 또는 페이지를 짧은 시간에 연속 순회하는 패턴
- 여러 IP에서 같은 User-Agent, 경로 순서, 시간 간격이 반복되는 패턴
- 검색 제안과 상세 조회를 기계적으로 결합한 패턴
- 429, 404, 5xx 비율이 특정 IP·경로·시간대에 함께 증가하는 패턴

User-Agent나 Referer 하나만으로 자동 차단하지 않는다. 운영자는 신호가 확인되면 요청 원문과
시간 범위를 보존하고, 임시 차단·해제 기준과 담당자 알림 절차를 기록한다. 현재 운영은
CloudWatch Agent 중심이며 Nginx access log 중앙 수집 범위가 제한적이므로, 중앙 집계가
필요하면 별도 모니터링 작업으로 다룬다.

### 비기술적 억제

서비스 이용약관에는 자동화된 수단으로 자료를 대량 수집·복제하거나 영리 목적으로 재배포하는
행위를 금지한다고 명시한다. 무단 수집이 확인되면 대상 URL·시간·IP·User-Agent·요청 패턴과
서비스 데이터의 출처를 함께 보존해 문의와 중단 요청에 사용할 수 있어야 한다.

## CloudFront·AWS WAF 도입 조건

CloudFront와 AWS WAF는 이 문서의 구현 대상이 아니다. 다음 조건이 확인될 때 플랫폼 권한과
비용을 포함해 별도 인프라 이슈로 검토한다.

- Nginx 요청 제한만으로 자동 수집이 지속된다.
- 분산 IP·국가·봇 유형별 정책이 필요하다.
- 원본 EC2 직접 접근을 차단하고 CloudFront 경유만 허용할 수 있다.
- AWS 계정에 기존 Web ACL 또는 중앙 Firewall Manager 정책이 있는지 확인했다.
- 도입 비용과 캐시·DNS·TLS·원본 우회 방지 운영 복잡성을 감수할 근거가 있다.

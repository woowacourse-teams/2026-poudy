## 보완 시나리오 — 7~56 req/s 부하 (2026-10-15)

**실제 화면의 8종 API로 바꿔 시험했다.** 56 req/s까지 오류·누락은 없었고 DB CPU가 먼저 높아졌다. 이 기록은 2차 수정 전의 결과다.

### 조건

스테이징 `https://staging.poudy.site/api`에 GET만 보냈다. 비율은 본문과 같다. 상품 필수 정보·페이지·상세 성분·큐레이션 내용·자동완성 강조 범위도 검사했다. 모든 필터의 정답을 검증하는 기능 테스트를 대체하지는 않는다.

소스·이미지는 `ab6c0186f073485f407bf2a9ee2b8ada32ff5d8e`. 시험 중 앱·스키마는 바꾸지 않았다. 검색어 `토너`, 첫 페이지·고정 ID, 기존 캐시를 사용했다. 약 15초마다 두 환경의 상품 상세를 별도 확인했다.

로컬 k6 2.2.0은 VU(동시 작업자) 50개를 준비하고 최대 100개까지 허용했다. 44·56 구간에는 AWS k6 2.3.0도 사용했다(0.5 CPU·256MiB, swap 추가 불가). 각각 22 또는 28 req/s씩 5분간 실행했고 시작 차이는 약 4초였다. 기존 IP별 제한은 유지했다.

### DB와 백엔드 상태

| 목표 req/s | DB CPU 최대 | BE 호스트 CPU 최대 | DB 가용 메모리 최저 | Hikari pending 최대 |
|---:|---:|---:|---:|---:|
| 7 | 16.6% | 7.1% | 993MiB | 0 |
| 15 | 34.8% | 8.8% | 975MiB | 0 |
| 22 | 44.6% | 17.0% | 914MiB | 0 |
| 44 | 73.3% | 20.4% | 924MiB | 0 |
| 56 | 91.5% | 25.9% | 912MiB | 0 |

DB CPU는 약 10초 표본, 백엔드 호스트 CPU는 2분 구간으로 계산한 값을 약 15초마다 읽었다. 서로 측정 방식이 다르고 순간 최대값이 빠질 수 있다. pending은 DB 연결을 기다리는 요청 수다.

**44 → 56에서 로컬 p95가 약 94 → 180ms로 늘고 DB CPU가 90%에 가까워졌다.** 연결 부족과 swap은 관측하지 않았다. CPU 90%가 2분 지속되지는 않았지만, 예정한 56 단계를 마친 뒤 증가는 멈췄다. 최대 처리량을 찾은 것은 아니다.

**캡처 정정:** 이 구간에 첨부했던 DB CPU·API p99 원본 이미지가 모두 비어 있어 제거했다. 아래 시간은 시험 기록이며, 빈 이미지로 수치를 확인한 것은 아니다. 압축 파일에 남은 두 빈 캡처도 증거에서 제외한다.

UTC 기준 7 req/s는 약 01:14–01:24, 15는 01:29–01:34, 22는 01:39–01:44, 44는 01:44–01:49, 56은 01:50–01:55다. 위 DB CPU 표는 약 10초 간격 측정값, p95·p99 표는 k6 원본을 근거로 한다.

### SQL 비용

`pg_stat_statements`에서 스테이징 DB OID와 `poudy_user`만 골라 **시험 전후 증가분**을 구했다. queryid는 같은 형태의 SQL을 구별하는 번호다.

15 req/s의 통계 창은 01:29:02–01:34:57 UTC이며 health·주변 요청도 포함한다. 통계 초기화 시각은 10/13 00:56:47 UTC로 같았고, 22 이후 확인한 통계 항목 제거(`dealloc`)는 0이었다.

마지막 조회는 약 **211만 행을 반환**했다. 코드에서 자동완성이 화면에 필요 없는 성분까지 읽는 것을 확인해 개선 후보로 골랐다. 211만 행과 17.31초 전체가 자동완성 때문이라는 뜻은 아니다.

주요 SQL의 디스크 읽기(`shared block read`)와 임시 파일 쓰기(`temp block write`) 증가가 0이었다. 기존 캐시가 있는 조건에서 SQL 처리와 데이터 조립 비용부터 확인했다. 특정 SQL의 CPU 점유율이나 인덱스 부족을 확정한 것은 아니다.

### 오류와 회복

시험 창(01:10–01:56 UTC)의 API 5xx는 staging 0/46,089건, 운영 FE 합산 0/1,056건이었다. 운영 로그에는 DataHub도 포함돼 Poudy 단독 비율은 아니다. 두 환경 health 표본은 200이었다. 기존 오류는 [자체 점검](https://github.com/woowacourse-teams/2026-poudy/issues/679#issuecomment-6182183585)과 구분했다.

56 단계의 컨테이너 단일 표본은 CPU 57.5%, 메모리 348.4MiB/1GiB였다. DB swap은 전 구간 0이었다. 종료 후 DB CPU 약 0.6%, PostgreSQL 접속 정상, pending 0을 확인하고 임시 프로세스를 종료했다.

## 성분 필터 진단 — 실제 SQL 실행 (2026-10-15)

**필터가 비어 있어도 검사를 반복하는 비용을 확인했다.** 다만 검사 하나만 없애면 다른 경로가 느려져, 포함 성분 처리도 함께 바꿨다. 이후 #749에 적용했다.

### 발견한 문제

DRY 1페이지에서 제외할 성분이 없는데도 아래 조회가 실행됐다. loops는 같은 작업을 반복한 횟수다.

| 연산 | 관측 |
|---|---:|
| 상품 후보 | 1,242개 |
| `product_component` 인덱스 조회 | 1,242 loops |
| 제외 검사의 `product_ingredient` 인덱스 조회 | 1,298 loops |
| 성분 조회의 필터 제거 행 | loop당 평균 약 37행 |
| shared block read | 0 |

빈 제외 조건의 검사를 생략하자 이 반복이 사라졌다. 하지만 성분 6 포함 조건은 **21.73 → 32.04ms**로 오히려 느려졌다. DB가 성분 연결 48,235행을 읽는 계획을 선택했기 때문이다.

대안은 **필요한 성분을 가진 상품을 먼저 찾는 것**이었다. 기존 인덱스로 성분 연결 11행을 찾은 뒤, 요청한 성분을 모두 가진 상품만 남겼다. 중복 ID는 `count(distinct ingredient_id)`로 처리했다.

### SQL 실행시간

각 3회 중앙값, custom plan, 1페이지다. 마지막 행은 별도의 포함 조건 비교다.

| 조건 | 기존 SQL | 선택한 대조안 | 변화 |
|---|---:|---:|---|
| 토너 검색 | 48.83ms | 33.24ms | 빈 제외 검사 생략 |
| DRY | 34.94ms | 16.81ms | 빈 제외 검사 생략 |
| 카테고리 2 | 28.08ms | 11.40ms | 빈 제외 검사 생략 |
| 성분 6 포함 | 21.95ms | 1.82ms | 포함 상품 선별 + 빈 제외 검사 생략 |

이 표는 **SQL 하나를 실행한 시간**이다. API p95나 혼합 부하 개선율과는 다르다. 검색 함수 비용도 남아 있다.

### 결과 보존과 제외한 안

기본 8조건과 복수 `[6,155]`·중복 `[6,6]`·포함+제외 ID·포함+제외 성분군을 대조했다. **수정안 26건에서 전체 개수·페이지·브랜드/카테고리/피부별 개수가 같았다.** 페이지 위치도 비교했고, 순서가 없는 집계 결과는 정렬 후 비교했다.

조회수 결과를 따로 저장하는 MATERIALIZED CTE는 채택하지 않았다. DRY generic plan에서 22.45 → 24.57ms로 늘어 이득이 없었다.

<summary>DB 설정·입력값·실행 방법</summary>

| 항목 | 조건 |
|---|---|
| 접속 | DB EC2 SSM, PostgreSQL 18.6, `poudy_staging`, 상품 1,242개 |
| 권한 | 앱과 같은 `poudy_user`, 읽기 전용 트랜잭션 |
| SQL | 소스 `ab6c0186`의 CANDIDATES/PAGE 재구성. 검토한 `e638b89b`도 같은 구현 |
| 바인딩 | 이름 있는 파라미터가 등장할 때마다 별도 `$n` 사용. JDBC 방식 유지 |
| 입력 | 토너 / DRY / 카테고리 2 / 포함 성분 6, 각 1·2페이지, size 20, 기본 정렬 |
| 나머지 입력 | 다른 배열은 비움. 조회수 기간 2026-09-15~10-14 |
| 실행 | `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`. 각 조건·방식당 3회, 실행 순서 교차 |
| 진단 세션 제한 | statement_timeout 5초, lock_timeout 500ms |
| 서버 설정 | `plan_cache_mode=auto`, JIT on, work_mem 4MiB. 변경 없음 |

custom/generic plan은 입력값별 계획과 공통 계획이다. 진단 세션에서 둘 다 강제해 확인했고 generic에서도 개선됐다. **실제 앱이 어느 계획을 택했는지는 확인하지 않았다.** [PostgreSQL 계획 선택](https://www.postgresql.org/docs/18/sql-prepare.html)

성분군·정렬·검색어·데이터 크기의 모든 조합을 확인한 것은 아니다. 이후 CI에서 활성 필터·중복 입력·대표 옵션·필터별 개수를 추가 검증했다. DB 데이터·스키마·인덱스·전역 설정은 바꾸지 않았다.

진단 후 두 환경의 공개 상세 API는 모두 200이었고 임시 프로세스는 종료했다.

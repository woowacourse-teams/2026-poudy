## 구현과 기능 확인

사용자가 조회 패턴 방식의 이전 구현을 폐기하고 상품 검색용 표준형 저장을 선택했다.
표준형 도입 당시 V34(현재 V40)를 추가했으며 적용된 V1~V33은 변경하지 않았다. 규칙은
`search_product_spelling_rules()`의 `[대체 표기, 표준형]` 배열에 선언한다.
현재는 `[['썬크림','선크림']]`뿐이며 상품 원문·기존 정규화 열·공유·성분 검색은 보존한다.

기존 materialized view 끝에 표준형 열을 추가하고 표준 문서 GIN 인덱스 두 개를 만든다.
원래 값과 같은 표준값은 NULL로 저장하고 비교 시 원래 값으로 대체해 중복 저장을 줄였다.
완성 표현이 있는 조건만 표준값을 쓰며, 나머지 부분 토큰은 원래 값으로 비교한다.
이름 검색은 토큰 판정과 브랜드 분리 준비를 한 번 계산하고, 메타데이터 후보가 없으면
기존 이름 hit를 그대로 사용한다. 기존 page와 공개 함수의 인자·타입·JSON은 유지한다.

API 테스트는 양쪽 전체 ID 집합·개수, 붙여쓰기·브랜드·속성·표식 AND, 필터·정렬·전체 페이지,
실제 원문 강조·UTF-16·교정·인기 검색어 결과 존재 판단을 확인한다. 입력 간 페이지 순서는
비교하지 않는다. 현재 선반 경로 `/api/users/me/shelf/product-suggestions`와 기존 제안 API도
검증한다. `선크/썬크`는 실제 원문 부분 문자열이며, `선크리/썬크리`의 리→림은 기존 교정과
구분한다. 미완성 입력을 표준화 규칙으로 완성시키지 않는다.

추가 규칙 테스트는 임시로 `['검증짧','검증긴표기']` 한 행과 문서 갱신만 적용해 이름·붙여쓰기·
개수·존재 확인·다른 길이의 원문 강조가 동작하고 core 정의가 바뀌지 않는지 검사한다.
이 테스트 표현은 운영 규칙에 등록하지 않는다. 업그레이드 테스트는 V33 정의를 복원한 뒤
V34를 적용하고 원래 열·함수 OID·소유자·SELECT 권한·5개 인덱스·1~4인자 호출·공유·성분을 확인한다.
빈 스키마 전체 적용은 SpringBootTest의 clean/migrate로 확인한다. MV 재생성에 CASCADE는 사용하지 않는다.

## V34 구현 시점 성능 결과

PostgreSQL 18.6, UTF8/C.UTF-8, shared_buffers=128MB, work_mem=4MB,
max_parallel_workers_per_gather=2, statement_timeout=0이다. 양쪽 환경과 상품 수 1,029개가 같다.
호스트는 Apple M5 Pro·macOS 26.6.2이며 Gradle Java 21 toolchain을 사용했다.
버전별 4,800개 표본에서 사전 고정한 48개 조합 중 **44개 통과, 4개 초과**다.

이 시점에는 **#703 전체 성능 기준을 통과하지 못했다.** 아래 공통 본체 전환 후 같은 기준으로 재측정했다.
확장 입력의 실행 계획에서는 표준값 GIN 두 개가 실제 실행됐다. shared hit 281~297,
shared read·임시 블록 읽기/쓰기는 0이다. 일반 입력은 기존 원문 인덱스를 계속 사용한다.

원시 표본·구간별 p50/p95·전체 요약·고정 한계·환경·실행 계획·측정 코드는 하나의
[최종 측정 자료](product-equivalent-spelling-797.json.gz)에 보관한다. `benchmark_source`를
server/src/test/java/com/poudy/product/controller/Search797BenchmarkTest.java에 추출한 뒤
동일 fixture를 기준 커밋과 최종 코드에 넣고, server/에서 각각
`POUDY_797_PHASE=before sh ./scripts/test.sh --tests '*Search797BenchmarkTest'`와
`POUDY_797_PHASE=after sh ./scripts/test.sh --tests '*Search797BenchmarkTest'`로 재현한다.
출력 디렉터리 `/private/tmp/poudy-797-standard`를 먼저 만들고, 측정 후 임시 Java 파일은 제거한다.
일반 검증에는 이 측정 코드를 포함하지 않는다. 중간 구현·중간 실험 자료는 최종 diff에 넣지 않았다.

로컬 합성 데이터·동시 호출 1개·jit=off의 결과다. 측정 fixture에서는 메타데이터 후보가 없어
이름 hit를 재사용하는 경로를 사용한다. 속성·표식 혼합 검색의 정확성은 별도 API 회귀로 검증했지만
그 부하의 성능은 아래 추가 측정에서 비교한다. 운영 자료·HTTP 왕복·기본 JIT·동시 부하·문서 재생성 비용은 측정하지 않았다.

## 공통 검색 본체 전환 후

구조 변경 기준은 `7c7a9161`이다. V34를 수정하지 않고 V35에서 기존 두 core를
이름 전용/메타데이터 포함 공통 본체의 진입점으로 교체했다. 입력 해석은 공통 함수로
모으고, 후보별 토큰 일치에 메타데이터 충족 여부를 함께 집계해 이름 재검사를 없앴다.
`eligibility/accepted`에서 조건 충족 여부를 판정한 뒤 `rank_values/ranked`에서 기존 등급을
계산한다. 기존 부분 일치 등급과 표시 우선순위·페이지·함수 인자·반환형은 유지한다.
질의 준비 함수는 이름 본체와 메타데이터 함수가 각각 호출하며, 요청 전체의 단일 실행을 뜻하지 않는다.

같은 1,029개 상품·12개 입력·4개 경로·20회 워밍업·5구간×20회로 변경 전후 각각 4,800개를
측정했다. 환경·JIT·페이지·필터는 위 기준과 같다. **최종 변경 후 48개 조합 모두 기존에 고정한
#703 한계를 충족했다.** 허용 시간을 변경하거나 표본을 제외하지 않았다.
직전 V34와 비교하면 `닥터지 블랙검증` 추천 p95는 2.582→3.169ms로 증가했다.
따라서 모든 요청이 빨라졌다고 해석하지 않는다.
네 표기 확장 입력의 실행 계획에서 기존 표준값 GIN 두 개가 모두 실제 실행됐다.
루트 shared hit는 281~297, shared read·임시 블록 읽기/쓰기는 모두 0이었다.

추가로 SERIALIZABLE 트랜잭션에서 상품 90101에 무기자차와 검증표식을, 90107에 검증표식을
연결했다. 동일 fixture에서 V34 함수 복원/최종 함수로 각각 4개 입력×4개 경로×100개,
버전별 1,600개 표본을 비교했다. 혼합 검색은 최종 구현을 먼저 측정하고 V34를 복원해 측정했다.
이 16개 조합의 p95는 22.7~42.4% 감소했으며 전체 개수는 동일했다. 별도 합격 한계는 만들지 않았다.

| --- | ---: | ---: |
| 무기자차 | 4.959 | 3.834 |

최종 자료의 `structure_refactor`에 일반·혼합 표본 12,800개, 환경·계획·요약·측정 소스와 V35

일반 비교의 before는 기준 커밋에서 실행한다. 측정 후 임시 테스트를 제거한다.

## 전체 검증

`server/`에서 `sh ./scripts/verify.sh` 통과(1분 16초). API 생성물 드리프트 없이 전체 빌드·Spotless·
Checkstyle·구조 검사를 완료했다. 테스트 1,702개, 실패·오류·건너뜀 0개이며, 동등 표기 33개와
업그레이드 1개, 구조 변경 2개를 포함한다. 37개 입력×두 core의 전체 행·등급·강조를 V34와
직접 비교했고 함수 OID도 보존했다. 임시 성능 측정 테스트는 제거했고 검증을 우회하거나
약화하지 않았다. 독립 읽기 전용 코드 검토에서도 확정 결함은 없었으며 DB 실행은 본 검증으로 수행했다.

## PR 게시 전 통합 검증

최신 dev `cf10c6f2`를 병합하고 검색 마이그레이션을 V40/V41로 옮긴 뒤 `./gradlew clean`,
`sh ./scripts/verify.sh`를 실행했다. 전체 검증은 1분 20초에 통과했으며 테스트 1,715개,
실패·오류·건너뜀은 모두 0개다. SQL 본문 해시는 기존 측정값과 같고 성능 재측정은 하지 않았다.
표기 확장 입력의 구조 변경 요약에는 원시 직접 입력 기준 대신 기존 검증의 대응 입력
(차단·닥터지차단·수분)과 허용 시간을 연결하도록 메타데이터를 바로잡았다. 원시 표본과
미리 고정한 기준은 그대로이며 48개 통과 결론도 같다.

별도 [성능 개선 보고서](product-search-797-performance-report.md)에 구조 변경·전후 비교·한계를 정리했다.

## 후속: 연관검색어 동등 표기 강조

실제 검색 입력 화면의 `/api/products/related-keywords`가 상품 후보를 받은 뒤 원문만으로
표시명·강조 구간을 다시 계산하던 누락을 발견했다. 직접 표현이 없으면 브랜드 접두와 전체
브랜드 강조로 넘어갔다. 기존 후보 검색은 정상이며 연관검색어의 후처리 연결 누락이다.
API 회귀 네 사례를 먼저 실패로 재현했다. 후속 수정은 상품 전용 토큰·저장 표준값을 표시명
판정에도 사용하고, 최종 강조 직전에 기존 함수로 실제 원문 조각을 복원한다. 완성 표기와
미등록 토큰이 섞이면 토큰별로 원문을 강조해 부분 입력까지 표준화하지 않는다. 화면과 DB
마이그레이션·HTTP 형식은 변경하지 않았다.

6개 입력×전후×100회, 1,200개 표본을 같은 연결에서 교차 측정했다. 상품은 1,029개,
limit=5, maxLength=100, jit=off이며 입력·버전별 20회 워밍업, 5구간×20회다. 결과 개수는 같고
표시명·강조는 버그 수정에 따라 달라진다. 별도 합격 시간을 만들거나 기존 #703 한계를 바꾸지 않았다.

## 리뷰 반영: 나눠 쓴 미등록 토큰의 접두어 유지

PR #925의 [접두어 생략 리뷰](https://github.com/woowacourse-teams/2026-poudy/pull/925#issuecomment-6336669905)는
`5662204a`를 기준으로 한다. `썬 크림` 입력의 전체 표준값 `선크림`이 상품명과 같으면,
미등록 토큰 `썬`을 브랜드나 표식에서 충족했어도 그 접두어를 생략했다.

접두어 생략 전에 상품명만으로 모든 필수 토큰을 충족하는지 확인하도록 수정했다. 각 토큰의
`has_spelling`에 따라 저장된 표준값 또는 원래 값을 비교하며, 영문 읽기와 초성도 인정한다.
상품명 밖에서 충족한 토큰이 있으면 기존 브랜드·표식 접두어 계산으로 이어진다.

브랜드·표식 각각에 `선/썬` 양방향 API 회귀를 추가해 수정 전 네 실패를 재현했다. 수정 후에는
`썬브랜드 선크림` 또는 `썬크림 선크림`을 반환하며 실제 일치한 원문을 강조한다. 상품명이
모든 토큰을 충족하는 나눠쓰기·영문 읽기·초성 네 사례도 추가해 불필요한 접두어를 생략하는
기존 동작을 확인했다. 새 API 테스트 8개가 모두 통과했다.

`server/`에서 `sh ./scripts/verify.sh`를 통과했다. 전체 테스트 1,743개,
실패·오류·건너뜀 0개이며 API 생성물 드리프트 없이 빌드·Spotless·Checkstyle도 통과했다.

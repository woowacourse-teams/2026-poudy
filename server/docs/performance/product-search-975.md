# 제품 검색 책임 분리 성능 비교 (#975)

이 보고서와 보관한 표본은 **dev 병합 전 `705bda11`의 2026-10-27 결과**다.
2026-10-29 dev의 V46 마크 통합을 반영하면서 검색 V46·V47을 V47·V48로 옮기고 마크 인자를 연결했다.
아래 표의 V46·V47은 당시 검색 구현을 가리킨다. 병합 후 성능은 다시 측정하지 않았다.

V47의 목록·개수는 표시 없는 검색 점수 행을 필터에 연결하고, 제안·연관검색어는 페이지 상세만 만든다.
V43(리팩터링 전), V46(중간 구현), V47(후속 구현)을 같은 트랜잭션·자료에서 교대로 측정했다.
기능 동등성과 로컬 DB 비용을 확인한 결과이며 운영 응답 시간을 보장하는 자료는 아니다.

## 측정 조건과 경로

- PostgreSQL 18.6, aarch64 Docker, JIT off, `work_mem=4MB`, `shared_buffers=128MB`.
- 기존 테스트 자료 44개에 같은 접두어의 제품을 1,000개 또는 10,000개 추가했다.
  메타데이터 연결과 오타 교정 자료도 포함한다. 만든 자료·함수는 측정 뒤 롤백했다.
- 1,044개 자료: 입력 9개 × 경로 6개 × 버전 3개, 각 20회 준비 후 50회 측정(8,100개 표본).
- 10,044개 자료: 넓은 입력 2개 × 경로 6개 × 버전 3개, 각 10회 준비 후 30회 측정(1,080개 표본).
- 버전 실행 순서를 매회 뒤집었다. 시간은 서버 안에서 동적 SQL을 계획·실행한 시간이다.
  HTTP·JDBC 왕복, 카드·브랜드 로딩, 운영 자료와 동시 요청은 포함하지 않는다.
  필터 SQL의 개선 폭에는 매 호출 계획 비용 감소도 포함되므로 JDBC의 준비된 문장 재사용 환경과 다를 수 있다.

| 경로 | V43·V46 | V47 |
| --- | --- | --- |
| SEARCH | `search_products_v2(query,0,null,2)` | `search_product_results(query,2)` |
| SUGGEST | 상위 20개의 v2 JSON | 상위 20개의 `search_product_suggestions` 행 |
| RELATED | 기존 Repository SQL / V46 함수 | 상위 5개, 길이 100의 연관검색어 함수 |
| LIST_FILTERED | 기존 전체 JSON을 펼친 뒤 필터·순위·페이지·선택지 | 점수 행에 같은 조건을 적용 |
| COUNT_FILTERED | 같은 후보·필터의 개수 | 같은 후보·필터의 개수 |
| COMPAT_ALL | `search_products_v2(query,0,null,2)` | 같은 전체 JSON 반환 계약 |

필터 측정은 브랜드 90000, 기본 정렬, 첫 페이지 20개와 선택지 집계를 사용한다.
포함·제외 성분 조건은 이 성능 자료에서 비워 두며, 동작은 기존 통합 테스트로 검증했다.

## 확인한 비용과 남은 회귀

- 이름 경로의 중복 ID를 복합 값으로 확장하기 전에 줄이고, 다중 토큰의 불필요한 결합 문서 조회를 막았다.
  전체 후보의 상세 배열·반복 분석 배열을 전달하던 비용은 관계형 사실과 간결한 점수로 줄였다.
  10,000개에서 커진 이름 근거의 ID 배열 비교 비용은 ID 집합과 문서의 조인으로 줄였다.
- 복잡한 단계 조합의 요청별 재계획 때문에 작은 검색에도 고정 비용이 붙었다.
  `search_product_evaluate` 안에만 `plan_cache_mode=force_generic_plan`을 적용했다.
  다른 요청의 설정은 유지한다. 위 측정은 이 설정을 포함한다.
- 표시 함수가 이름·메타데이터 선택을 페이지에서 수행하면서 일부 작은 제안·연관검색어에는 V46 대비 비용이 남는다.
  표의 입력별 p50·p95를 함께 봐야 하며 모든 입력이 빨라졌다고 해석하지 않는다.
- 10,000개 `성능 검증 젤` 제안은 p50이 개선됐지만 p95는 V43의 96.517ms에서 101.214ms로 늘었다.
  넓은 검색에서도 모든 경로의 지연 상위 구간이 개선된 것은 아니다.
- `COMPAT_ALL`은 모든 제품의 표시 상세와 JSON을 만들어야 하므로 V43 대비 회귀가 남는다.
  API 목록·개수는 이 경로를 사용하지 않는다. 호환 호출의 속도를 위해 별도 검색 정책을 복제하지 않았다.
- 10,000개 자료는 같은 접두어가 많은 합성 자료다. 다양한 브랜드·속성 분포, 운영 자료 규모,
  동시 요청, 캐시 상태에 따른 인덱스 선택은 배포 환경에서 추가로 확인해야 한다.

실행 계획에서 10,000개 `성능 검증 젤`은 필드 사실 50,033행과 점수 10,021행을 만들고,
상품 제안 페이지를 20개로 제한했다. 요약 요청의 임시 기록은 1,003블록, 페이지 상세 포함 요청은
1,508블록이었다. `work_mem=4MB`에서 사실 공유와 정렬의 임시 파일 비용이 남는다는 뜻이며,
전체 후보의 상세 배열 전달을 없앴다고 모든 중간 자료의 비용이 사라지는 것은 아니다.

## 근거와 재현

과거 수치를 재현할 때는 `705bda11`의 스크립트·마이그레이션·테스트 자료를 함께 사용한다.
현재 [측정 스크립트](product-search-975/benchmark.py)는 dev V46 마크 통합·검색 V47·최종 V48을
현재 마크 정의와 연결 자료로 비교한다. 기준 함수는 별도 이름으로 복원한다. 새 비교는 아직 실행하지 않았다.
[1,000개 원자료](product-search-975/stages-1000/measurements.json.gz)와
[10,000개 원자료](product-search-975/stages-10000/measurements.json.gz)에 환경, 9,180개 표본과 실행 계획 80개를 보관했다.

후보와 호환 근거 외에 실제 점수·페이지 상세 단계, 목록·개수·제안 경로의 실행 계획을 포함한다.
`evaluate` 내부 SQL은 함수와 같은 generic plan을 쓰는 PREPARE/EXPLAIN으로 펼쳐 확인한다.
내부 SQL의 설명용 준비는 시간 표본을 수집한 뒤에 수행한다.

공유 개발 DB를 사용하지 않는다. 테스트의 clean/migrate를 버려도 되는 전용 DB에서 실행한 후,
테스트와 측정을 동시에 실행하지 않고 다음 명령을 실행한다.

```sh
# server/에서 실행. 아래 psql 인자는 자신의 전용 DB 연결로 대체한다.
python3 docs/performance/product-search-975/benchmark.py /tmp/search-975-1000 \
  psql -U postgres -d poudy_search_975
SEARCH_BENCH_PRODUCTS=10000 SEARCH_BENCH_WARMUP=10 SEARCH_BENCH_ITERATIONS=30 \
  SEARCH_BENCH_QUERIES='ㅂ,성능 검증 젤' \
  python3 docs/performance/product-search-975/benchmark.py /tmp/search-975-10000 \
  psql -U postgres -d poudy_search_975
```

병합 전 최종 `verify.sh`: 테스트 1,792개, 실패·오류·생략 0개, OpenAPI/TypeScript 생성물 드리프트 없음.
기존 284개 비교 스냅샷에 관계형 점수 비교 51개를 추가했다.
이전 V46 측정 2,700개 표본은 기존 [요약](product-search-975/summary.tsv)과
[원자료](product-search-975/measurements.json.gz)에 남긴다.

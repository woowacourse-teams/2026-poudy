# 제품 검색 근거 분리 성능 비교 (#975)

V46은 기존 결과를 유지하면서 검색·연관검색어가 필드별 일치 근거를 공유하도록 바꾼다.
대표 입력의 목록 검색·상품 제안은 빨라졌고, 연관검색어는 중복 판정을 없앤 효과가 더 컸다.
다만 후보가 많이 잡히면 근거를 모으고 전달하는 비용이 남는다. 모든 입력의 성능이 개선된 것은 아니다.

## 측정 조건

- 기준: `origin/dev`의 `323a9ffa`. V40 표기 판정·토큰, V41 공통 함수,
  V43 검색 본체와 기존 V33 페이지·교정 진입점을 별도 이름으로 복원해 같은 트랜잭션에서 비교했다.
  연관검색어는 기존 Repository SQL을 비교 기준으로 보관했다.
- PostgreSQL 18.6, aarch64 Docker, JIT off, `work_mem=4MB`, `shared_buffers=128MB`.
  개발 DB와 분리한 로컬 전용 DB에서 측정했다.
- 검색·표준 표기·연관검색어 테스트 자료에 같은 이름 접두어를 가진 제품 1,000개를 더해 총 1,044개.
  실제 연결된 속성값·마크 조건도 포함했다. 자료와 측정용 함수는 마지막에 롤백했다.
- 입력 9개 × 경로 3개 × 전후 2개. 각 조합은 20회 준비 호출 뒤 50회 측정했다(총 2,700개 표본).
  전후 실행 순서를 매회 바꿨다. 시간은 서버 안에서 호출을 계획·실행하는 데 걸린 시간이다.
- `SEARCH`: 목록·개수 API가 사용하는 `search_products_v2(query,0,null,2)`.
  `SUGGEST`: 같은 함수의 상위 20개. `RELATED`: 상위 5개, 표시 길이 100 제한.
  HTTP, JDBC 왕복, 제품 카드 로딩, Repository의 후속 필터·선택지 집계는 포함하지 않는다.

대표 입력 7개에서 목록 검색 p50은 약 10~28%, 상품 제안은 8~23%, 연관검색어는 40~71% 줄었다.
반면 `ㅂ`의 목록 검색은 1.8ms(18%), 1,000개가 일치하는 입력은 4.0ms(37%) 늘었다.
후자의 p95도 10.908→14.938ms로 늘어 단일 이상치에 의한 차이로 볼 수 없다.
이번 측정은 구조 변경의 비용을 확인한 것으로 운영 응답시간이나 처리량을 보장하지 않는다.
운영 카탈로그 크기·토큰 분포·동시 요청으로 이 두 경우를 다시 확인해야 한다.

## 실행 계획에서 확인한 점

이름 후보 수집은 기존 정규형·읽기·표준형·초성 인덱스 경로를 유지한다.
속성값·마크는 정의를 먼저 비교한 뒤 연결 인덱스로 제품을 찾는다.
이름 일치 근거는 제품별로 준비한 필드를 입력 토큰과 비교해 모으고, 순위 단계에서 그 근거를 읽는다.
기존의 토큰 집계보다 자료가 많아 넓은 검색의 비용은 증가한다.

분리 과정에서 입력 분석이 반복 평가되는 문제는 요청당 한 번 준비하는 CTE로 해결했다.
필드 준비를 토큰 반복 밖으로 옮기고 후보 중복 제거를 한곳에 모았다.
이름 필수 토큰의 미사용 등급 계산과 이름이 맞은 제품의 메타데이터 표시 선택도 생략했다.
페이지가 있는 요청은 선택한 페이지의 근거만 다음 단계에 넘긴다.

최종 실행 계획에서 `성능 검증 젤`의 후보 수집은 2.475ms, 필드 근거 조립까지는 10.575ms였다.
이는 단일 `EXPLAIN ANALYZE` 실행값이며 위 반복 측정의 p50과 직접 합산할 값은 아니다.
측정 환경·모든 표본·8개 실행 계획은 [measurements.json.gz](product-search-975/measurements.json.gz)에 보관했다.

## 재현

V46까지 적용한 **전용 테스트 DB**에서 실행한다. 스크립트는 고정 ID의 테스트 자료를 넣으므로
운영 DB나 개발 데이터를 보관한 DB에 실행하지 않는다.

```sh
cd server
python3 docs/performance/product-search-975/benchmark.py /tmp/product-search-975 \
  psql -U postgres -d poudy_search_975
```

`psql` 앞에 `docker exec -i <전용 컨테이너>`를 붙일 수도 있다.
스크립트는 측정 SQL, 표본 JSON, p50/p95 표와 실행 계획 출력을 지정한 디렉터리에 남긴다.
전용 DB의 테스트·마이그레이션 실행과 동시에 돌리지 않는다.

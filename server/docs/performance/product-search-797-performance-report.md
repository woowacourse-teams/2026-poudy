# 상품 검색 #797 성능 개선 보고서

이 보고서는 선크림·썬크림 동등 검색과 검색 구조 변경을 검토하는 백엔드 개발자를 위한 자료다.
무엇을 바꿨는지, 같은 조건에서 얼마나 달라졌는지, 어떤 결과까지 확인했는지를 정리한다.
측정일은 2026-10-22이며 수치는 저장소에 보존한 원시 표본에서 계산했다.

## 확인한 결과

공통 검색 본체로 전환한 뒤, 이름 중심 검색 48개 조합 중 47개에서 p95가 낮아졌다.
속성·마크를 함께 찾는 혼합 검색은 16개 조합 모두 p95가 낮아졌고 감소율은 22.7~42.4%였다.
이름 중심 검색의 48개 조합은 #703에서 변경 전에 고정한 허용 시간도 모두 충족했다.

`닥터지 블랙검증` 추천은 2.582→3.169ms로 22.7% 느려졌다. 모든 검색이 빨라졌다고
평가할 수는 없다. 이 요청도 고정 허용 시간 3.351ms 이내였으며, 표본을 제외하거나 기준을 바꾸지 않았다.

수치 비교에는 두 기준을 구분해서 사용했다. **개선율은 같은 상품 집합을 찾는
`7c7a9161`과 `a72e2794`의 측정값으로 계산했다.** #703 통과 여부는 `66f6c093`에서
미리 정한 허용 시간과 비교했다. 상품 집합이 넓어진 선크림·썬크림 검색을 기능 변경 전의
작은 결과 집합이나 빈 결과 시간과 직접 비교하지 않았다.

## 비용을 줄인 변경

### 상품별 토큰 판정을 공통 본체로 통합

기존 현재 버전 검색은 이름 core의 결과를 받은 뒤 속성·마크 결과를 합치면서 이름의 토큰
일치를 다시 검사했다. 새 `search_product_hits()`는 이름·브랜드에서 맞은 토큰과 메타데이터에서
맞은 토큰을 같은 후보에 대해 집계한다. `token_matches`에서 계산한 판정을 `token_summary`가
개수와 표시 대상 선택에 함께 사용하므로, 바깥 core가 이름 조건을 다시 검사하지 않는다.

기존 이름 전용 core와 메타데이터 포함 core는 공통 본체를 호출하는 진입점으로 남겼다.
서로 다른 필수 조건이 같은 상품에서 모두 충족되는지 확인하는 기준과 기존 DB 반환형을 유지했다.

### 붙여쓰기 준비와 반복 문자열 변환을 모음

브랜드+제품 붙여쓰기 후보를 만들 때 브랜드 집합과 분리한 제품 조각의 영문 읽기 값을
미리 계산한다. 제품마다 같은 제품 조각을 다시 변환하던 작업을 줄이는 구조다.
입력 해석 정의는 `search_product_queries()`로 모았지만, 이 함수는 이름 본체와
메타데이터 함수가 각각 호출한다. 한 요청에서 입력 해석이 한 번만 실행된다는 뜻은 아니다.

### 표준형을 저장하고 인덱스로 후보 수집

상품 검색 문서와 입력에 같은 `썬크림 → 선크림` 규칙을 적용한다. 표준형 검색값은
문서 갱신 때 만들어 저장하고, 조회 시 기존 `LIKE` 비교와 표준값 GIN 인덱스로 후보를 모은다.
검색 요청마다 전체 상품의 표기를 변환하는 구조를 피했다.

표준값이 기존 값과 같으면 추가 열에 NULL을 저장하고 조회 시 기존 값으로 대체한다.
문자열 중복 저장을 줄이려는 설계이며, 디스크 용량이나 갱신 시간의 절감량은 측정하지 않았다.
새 표준값 인덱스 두 개의 저장 비용과 문서 갱신 비용도 별도로 측정하지 않았다.

### 조건 충족과 순위 계산 분리

`eligibility/accepted`가 검색 조건 충족 여부를 정하고 `rank_values/ranked`가 기존 등급을 계산한다.
이 구분으로 조건을 추가할 때 순위 숫자에 포함 정책을 섞지 않도록 했다. 기존 내부 DB 호출의
부분 일치 등급 3은 남기고, HTTP 추천·목록에서는 기존 기준대로 제외한다.

이 변경들은 함께 적용해 측정했다. 각 변경을 하나씩 켜고 끈 실험은 하지 않았으므로,
전체 개선율을 특정 함수나 최적화 하나의 효과로 나누어 설명할 수는 없다.

이름 중심 검색은 12개 입력 × 4개 경로 × 100회로 버전별 4,800개를 수집했다.
혼합 검색은 상품 90101에 무기자차와 검증표식을, 90107에 검증표식을 연결한 자료로
4개 입력 × 4개 경로 × 100회, 버전별 1,600개를 수집했다. 혼합 자료 쓰기는
기존 DB 제약에 맞춰 SERIALIZABLE 트랜잭션에서 실행했다.

구조 변경 비교 표본은 총 12,800개다. HTTP 왕복 시간은 포함하지 않았으며 수집한 표본을
잘라내지 않았다. 혼합 검색은 최종 구현을 먼저 측정하고 같은 스키마에서 V34 함수를 복원해
기준 구현을 측정했다. 두 버전을 번갈아 실행한 무작위 교차 실험은 하지 않았다.

## 인덱스와 버퍼 확인

`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`으로 실행 계획을 기록했다.
선크림·썬크림·닥터지썬크림·수분썬크림의 최종 core 계획에서 다음 두 인덱스가
실제로 실행된 것을 `Actual Loops`로 확인했다.

- `ix_product_search_document_key`
- `ix_product_search_document_read_key`

네 계획의 루트 shared hit는 281~297이었다. shared read와 임시 블록 읽기·쓰기는 모두 0이었다.
워밍업 후 캐시에 올라온 자료를 조회한 결과이므로, 첫 요청이나 디스크 읽기 비용을 설명하는 수치는 아니다.

## 정확성과 호환성 확인

구조 변경 전후 37개 입력 × 두 core의 전체 결과 행을 직접 비교해 상품 ID·등급·토큰 비율·
표시 필드·강조 구간이 같은지 확인했다. 함수 OID도 유지했다.
별도 API 회귀는 표기별 전체 상품 집합·개수, 브랜드·붙여쓰기·필터, 모든 페이지의 중복·누락,
원문 강조·오타 교정·초성·영문 읽기와 속성·마크 AND 조건을 확인했다.
입력 두 개의 페이지별 순서가 같아야 한다는 조건은 추가하지 않았다.

성능 측정 시점의 전체 `verify.sh`는 1,702개 테스트를 통과했다.
최신 dev 통합 뒤에는 `./gradlew clean` 후 전체 `verify.sh`를 다시 실행해 1,715개 테스트를
통과했다. 실패·오류·건너뜀은 없었고 API 생성물에도 드리프트가 없었다. 두 검증의 테스트 수 차이는
dev에서 통합된 별도 변경에 따른 것이다.

## 해석의 한계와 후속 확인

로컬 합성 데이터, 동시 호출 1개, jit=off, 워밍업 후의 결과다. 운영 자료·HTTP 왕복·기본 JIT·
동시 부하·첫 요청·검색 문서 갱신 비용은 측정하지 않았다. 실행 순서에 따른 환경 변화나
구간별 변동의 원인도 분리하지 않았으므로, 관측한 감소율이 운영에서도 그대로 나올 것으로 보지 않는다.

느려진 `닥터지 블랙검증` 추천은 같은 조건의 후속 측정 대상으로 남긴다. 운영 반영 후에는
실제 입력 분포와 데이터 크기에서 추천·목록 지연, DB 부하, 문서 갱신 잠금 시간을 확인해야 한다.

## 후속 수정: 실제 입력 화면의 강조 경로

앞선 검증은 동등 표기의 연관검색어 강조 조합을 놓쳤다. 상품 후보를 받은 뒤 표시명과 강조

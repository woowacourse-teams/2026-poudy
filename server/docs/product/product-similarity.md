# 성분 유사 제품 조회와 수동 계산 연결

서버는 유사도를 계산하지 않는다. 데이터 담당자가 제품 적재 후 private 저장소의
`product-similarity/calculate.py`를 수동 실행해 동일 DB에 결과를 저장한다.
서버 빌드·기동·요청 시 Python을 호출하거나 계산 작업을 예약하지 않는다.

## 저장 계약

Flyway V6가 결과 테이블을 생성했다. private 스크립트의 별도 schema.sql은 실행하지 않는다.

- `product_similarity(component_id, similar_component_id, similarity_score)`: 방향이 있는
  구성 요소 간 결과. 점수는 0~1이다. 두 구성 요소 ID가 복합 PK이고, 두 ID 모두
  `product_component`를 참조하며 구성 요소가 지워지면 결과도 함께 지운다.
- V6의 `product_similarity_calculation(component_id)`는 V36에서 삭제했다. 어떤 구성 요소를 계산했는지는
  계산 작업이 관리할 기록이고 서비스는 결과만 읽으면 되기 때문이다. V36 배포 전에 private 계산 스크립트와
  수집 제품 적재 스크립트가 이 테이블을 잠그거나 쓰지 않고 기준 구성 요소의 결과 행만 교체하도록 바꿔야 한다.
- 기준 구성 요소마다 동일 최하위 카테고리의 다른 제품을 비교한다. 제품명에서 확인된
  필수 성분군을 만족해야 한다. 한 대상 제품에서는 최고 점수 구성 요소 하나만 저장한다.
- 최종 점수 0.25 이상인 서로 다른 제품을 점수 내림차순, 제품 ID 오름차순으로 최대 10개 저장한다.
  대상 제품 내 구성 요소가 동점이면 구성 요소 ID 오름차순으로 선택한다.
- 원천 데이터는 정식 DB ID를 사용한다. 로컬 검증 보고서의 임시 ID를 적재하지 않는다.
- 계산 중 입력이 바뀌면 반영을 중단한다. 기준 구성 요소의 결과 행은 한 트랜잭션으로 교체한다.
  중복 실행을 막고 실패하면 이전 결과를 유지한다.

## 조회 계약

`GET /api/products/{productId}/similarities?partId={componentId}&size=10&sort=UNIT_PRICE_ASC`

partId는 기존 상세 API와 같은 용어다. 생략하면 표시 순서가 가장 앞선 구성품을 선택한다.
다른 제품에 속한 partId 또는 없는 partId는 PRODUCT_PART_NOT_FOUND(404)다.

`size`는 1~10이고 생략하면 기존 상세 미리보기와 같은 3이다. `sort`는 기본 `SIMILARITY` 또는
`UNIT_PRICE_ASC`다. 판매 상태·점수·카테고리 조건과 제품 중복 제거를 적용한 뒤 유사도 상위
size개를 확정하고, 그 안에서만 정렬한다. 가격순으로 바꿔도 후보 집합은 같고, 11번째 이후의
저렴한 제품을 가져오지 않는다. 가격 동점과 비교 불가 후보끼리는 기존 유사도·제품 ID 순서를 유지한다.

응답은 `partId`, `calculated`, `items`다. 구성품이 없으면 partId는 null이고 calculated는 false다.
calculated는 기준 구성품의 결과 행이 하나라도 저장돼 있는지를 뜻한다. 미계산과 후보 없음은 둘 다
결과 행이 없어 구분하지 않는다. 결과 행이 있어도 판매 상태·점수 조건에서 모두 걸러지면 items는 비어 있다.
현재 판매 옵션이 하나 이상 active이고 최종 점수가 0.25 이상인 후보를 기본 3개, 최대 10개 반환한다.
자기 제품과 다른 카테고리는 제외하고, 제품 중복 제거와 판매 상태 필터링을 size 제한 전에 한다.
API는 DB에 저장된 후보 범위에서만 조회하므로 상위 10개 밖의 후보를 다시 계산해 채우지 않는다.

각 항목은 제품 ID·이름·브랜드·이미지, 계산 대상 구성품 partId,
containsExcludedIngredient(대상 구성품에 빠른 제외 6종 중 하나라도 포함)를 제공한다.
가격·용량은 대표 용량 옵션(표시 순서가 가장 앞선 옵션) 값이고, priceDifference는 추천 제품 가격에서
기준 제품 대표 옵션 가격을 뺀 값이라 양수면 추천 제품이 더 비싸다. 유수분은 제품 상세와 같은 값이라
향수·클렌징은 null이다.

추가 가격 정보는 기존 클라이언트와 함께 사용할 수 있도록 선택 필드로 문서화하며, 서버는 다음 값을 제공한다.

- `unitPrice`: 대표 옵션 가격을 용량으로 나눈 값의 정수 반올림. 용량 0이면 null이다.
- `unitPriceDifferencePercent`: `(대상 단가 / 기준 단가 - 1) × 100`을 소수 둘째 자리까지 반올림한 값이다.
  음수는 더 저렴한 뜻이다. 비교 불가이거나 기준 가격이 0이면 null이다.
- `unitPriceComparison`: 반올림 전 단가로 판정한 `CHEAPER`, `SAME`, `MORE_EXPENSIVE`, `UNAVAILABLE`이다.
  비율이 반올림으로 0이 돼도 실제 가격 관계는 이 값을 따른다.

대표 옵션은 기준·대상 모두 기존과 같이 표시 순서가 가장 앞선 옵션이다. 단위가 다르거나 어느 쪽 용량이
0이면 가격 비교 불가이며 가격순 목록 뒤에 둔다. 기준 용량을 모르면 후보의 유사도 순서를 유지한다.
단위의 대소문자는 같은 것으로 보지만 단위 간 환산은 하지 않는다. DB의 허용 단위는 ml, g, ea다.
가격 비교와 정렬은 나눗셈·반올림 전에 분자·분모를 교차 곱해 수행한다. 기준 가격 0에서는 비율만
비워 두고 가격 관계와 정렬은 제공한다. 유사도 점수나 높음·보통 등급은 추가하지 않는다.

나만의 필터 성분 포함 여부는 회원마다 달라 이 응답에 넣지 않는다. 회원별 제품 정보
(`/api/users/me/products/{productId}`)가 같은 partId·size·sort 기준 추천 제품마다 `containsMyFilterIngredient`를 주고,
클라이언트는 이 값과 containsExcludedIngredient 중 하나라도 true면 주의로 표시한다.
회원별 조회도 기본 3개이며, size=10이면 4~10번째 후보까지 판정하고 응답을 공유 캐시하지 않는다.
점수는 공개하지 않는다. 기존 상세는 items가 0개면 영역을 숨기고, 1~2개면 그만큼 표시한다.
별도 결과 화면은 빈 결과와 조회 실패를 구분한다.

## 배포 순서

1. Flyway V6와 조회 API를 배포한다. 최초 계산 전에도 빈 결과로 동작한다.
2. 데이터 담당자가 카탈로그와 성분군을 적재한다.
3. private 저장소 chore/db-scripts 브랜치의 `product-similarity` 운영 버전을 배치하고 미리보기를 실행한다.
   기본 policy.json은 release_ready=true, minimum_score=0.25이며 다른 노출 임계값은 null이다.
   운영 정책 변경이 포함된 `af8128b` 이후 버전을 배포한다. 과거 검토용 파일은 apply를 막는다.
4. 결과와 정식 ID를 확인한 뒤 수동으로 `--apply`를 실행한다.
5. API에서 기준 구성품, 주의 판정, 기본 3개·최대 10개와 두 정렬, 미계산/후보 없음 상태를 확인한다.

DB 접속은 스크립트의 PostgreSQL 연결 환경으로 제공한다. 비밀번호를 코드나 명령 인수에 넣지 않는다.
카테고리 빈도를 사용하는 계산이므로 제품·전성분·성분군이 바뀌면 전체 재계산한다.
입력 변경과 재계산 사이에는 저장된 점수가 이전 입력 기준일 수 있다.
운영 데이터 적재와 계산 스크립트의 staging/운영 실행은 별도 수동 작업이다.

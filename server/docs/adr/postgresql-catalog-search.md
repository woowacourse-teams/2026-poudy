## 배경

- Poudy의 상품·성분 검색은 짧고 구조화된 이름 검색과 카테고리, 브랜드, 유수분, 포함·제외 성분 등의 관계형 필터를 함께 처리한다.
- 이름 검색에는 정확·접두·부분 일치, 별칭, 초성, 영문 읽기, 오타 교정과 결과 순위가 필요하다. 필터가 적용된 목록과 전체 개수는 같은 조건을 사용해야 한다.
- 현재 Java 메모리 검색을 PostgreSQL 조회로 전환하고 있다. 검색 SQL과 통합 테스트 구현을 바탕으로 API 연결을 진행하는 단계다.
- `poudy-private`의 `db-script` 브랜치에는 JSON과 유수분 CSV로 초기 적재 SQL을 만드는 `db-load`가 있다. 원본 적재와 검색용 뷰 갱신을 한 트랜잭션으로 처리한다.
- 검색 규칙은 사용자 요구에 따라 조정될 수 있다. 규칙의 변경 용이성, 적재 일관성, 운영 책임과 구현 완료 비용을 함께 고려해 책임 경계를 결정한다.

# 결정

- 상품·성분 검색은 **PostgreSQL 중심 구조**로 구현한다. 검색용 데이터와 입력 검색어의 변환 규칙은 DB 공통 함수가 소유한다.
- Java와 PostgreSQL의 책임을 다음과 같이 구분한다.
    - Java
        - 검색 요청, 필터, 정렬과 페이지 조건을 검증한다.
        - Repository에서 검색어와 조건을 전달하고 조회 결과를 매핑한다.
        - 최종 결과를 API 응답으로 조립한다.
    - PostgreSQL
        - 검색용 이름과 입력 검색어에 공통 정규화·초성·영문 읽기 규칙을 적용한다.
        - 검색용 뷰와 인덱스를 관리하고 상품명·브랜드명·성분명·별칭의 일치를 판정한다.
        - 일반 검색 결과에 따라 오타 후보를 찾고 교정 검색의 적용 여부를 결정한다.
        - 검색과 관계형 필터를 결합해 순위, 최종 정렬, 페이지, 전체 개수와 집계를 계산한다.
        - 최종 반환할 결과에 대해 일치한 원문의 강조 위치를 계산한다.
- SQL 호출과 저장 표현은 Repository 내부에 캡슐화한다. Service와 Controller는 검색용 뷰와 DB 함수의 구체적인 구조 대신 조회 결과를 사용한다.
- 기존 초기 적재 경로를 사용한다. 원본 적재 후 `product_search_document`, `ingredient_search_term`, `search_vocabulary`를 순서대로 갱신하고 함께 커밋한다.
- 상품·성분 검색의 정규화 규칙은 DB에서 단일하게 관리한다. 인기 검색어 사전의 대표어·표현 생성은 별도 책임으로 구분하며, 실제 검색과 같은 의미를 요구하는 사례는 양쪽의 일치 여부를 테스트한다.
- 검색 동작은 사례별 기대 결과로 검증한다. 테스트는 정규화, 일치 판정, 순위, 교정, 강조 구간 및 필터·페이지의 일관성을 다룬다.
- 이 결정을 현재 구현의 기준으로 채택한다. 검색 데이터 생성 주체나 적재 경로의 전환은 비용과 효과를 검토해 팀 합의로 결정한다.

## 이유

- 관계형 필터와 검색을 같은 DB에서 처리하면 필터 적용부터 최종 정렬·페이지·개수 계산까지 하나의 일관된 조회로 구성할 수 있다.
- 검색용 데이터와 검색어가 같은 DB 함수를 사용하므로 이름을 저장할 때와 조회할 때의 변환 기준을 함께 유지할 수 있다.
- 기존 적재기의 원본 저장과 검색 뷰 갱신을 함께 커밋하는 구조를 활용할 수 있다. 데이터 준비부터 검색 반영까지의 책임이 명확하다.
- 현재 구현한 검색 SQL과 테스트를 API 연결의 기반으로 활용해 변경 범위와 완료 시점의 불확실성을 줄인다.
- Java 전처리 구조는 적재 실행, 검색 데이터 생성, 재생성과 규칙 버전 전환까지 관리 범위를 넓힌다. 현재는 검색 전환의 완료와 기존 적재 경로의 일관성에 우선순위를 둔다.
- SQL 유지보수 비용을 인정하고 Repository 경계와 동작 테스트로 관리한다. 검색 규칙의 안정성보다 현재 팀이 소유할 구현·운영 비용을 선택 근거로 삼는다.

# 대안

### 대안 1: Java에서 검색용 데이터를 생성하고 PostgreSQL에서 조회

#### 장점

1. 정규화·초성·영문 읽기 규칙을 Java 공통 코드와 단위 테스트로 관리할 수 있다.
2. 입력 검색어와 적재할 이름에 같은 변환 코드를 적용할 수 있다.
3. PostgreSQL의 인덱스, 관계형 필터와 페이지 처리를 활용하면서 문자열 가공 책임을 Java에 모을 수 있다.

#### 단점

1. 원본을 저장하는 모든 경로가 Java 변환을 거쳐 검색용 데이터도 갱신하도록 적재 체계를 연결해야 한다.
2. 규칙 변경 시 검색 데이터 재생성과 검색 서버의 규칙 버전을 함께 전환해야 한다.
3. 초기 적재 도구와 실행 환경의 관리 책임이 서버 코드까지 확대된다.

#### 선택하지 않은 이유

- 기존 적재 경로와 검증한 DB 검색 구현을 활용하는 편이 현재 전환의 범위와 완료 비용을 관리하기에 적합하다. Java 중심의 적재·검색 데이터 관리는 팀이 운영 책임까지 합의할 때 평가한다.

### 대안 2: Elasticsearch 또는 Lucene 기반 검색

#### 장점

1. 전문 검색, 분석기와 관련도 계산을 위한 검색 엔진 기능을 활용할 수 있다.
2. Elasticsearch는 검색 부하를 원본 DB와 독립적으로 확장할 수 있고, Lucene은 애플리케이션과 함께 색인을 운영할 수 있다.

#### 단점

1. PostgreSQL 원본과 검색 색인의 동기화, 재색인과 장애 복구를 관리해야 한다.
2. 검색 엔진 운영 또는 서버별 로컬 색인 관리가 추가된다.
3. Poudy의 별칭·초성·영문 읽기와 교정 정책은 도메인에 맞게 설계해야 한다.

#### 선택하지 않은 이유

- 현재의 이름 검색과 관계형 필터는 PostgreSQL에서 함께 처리하는 구성이 적합하다. 검색 전용 시스템의 운영 비용은 검색 품질과 독립 확장의 필요성이 구체화될 때 평가한다.

### 대안 3: Java 메모리 검색 확장

#### 장점

1. 기존 검색 규칙과 Java 테스트를 직접 활용할 수 있다.
2. 문자열 처리와 검색 결과의 원인을 애플리케이션 코드에서 추적하기 쉽다.

#### 단점

1. 전체 카탈로그의 메모리 유지와 갱신, 서버별 상태 일치를 관리해야 한다.
2. 데이터 증가에 따라 전체 순회 비용과 메모리 사용량이 커진다.
3. DB의 관계형 필터와 Java 검색 결과를 결합하면 정확한 정렬·페이지·개수 처리가 복잡해진다.

#### 선택하지 않은 이유

- 전체 카탈로그 로딩 의존을 줄이고 관계형 조건과 검색 결과를 같은 조회에서 처리하는 방향을 선택한다.

# 결과

## 기대 효과

- 기존 초기 적재부터 검색 반영까지 PostgreSQL 트랜잭션으로 일관성을 유지한다.
- 검색용 이름과 입력 검색어의 변환 규칙을 한곳에서 관리한다.
- 필터, 순위, 페이지와 전체 개수를 DB에서 처리하고 Java는 필요한 결과만 받는다.
- Repository 경계와 사례별 테스트를 통해 검색 구현을 교체할 때 비교할 기준을 확보한다.

## 감수할 점

- 검색 정책과 문자열 처리 SQL의 복잡도를 관리해야 하며, DB 함수 변경에는 스키마 적용과 PostgreSQL 통합 테스트가 필요하다.
- 변환 규칙이나 원본이 바뀌면 검색용 뷰를 갱신해야 한다. 현재 갱신 방식은 검색 읽기에 잠금 대기를 발생시킬 수 있다.
- 검색과 일반 서비스 조회가 DB 자원을 공유하므로 실행 계획과 운영 부하를 살펴야 한다.
- 인기 검색어 사전의 Python 처리와 DB 검색의 의미가 겹치는 부분은 일치 여부를 관리해야 한다.
- Java 전처리 구조로 전환할 경우 적재 경로와 검색 데이터 생성 방식을 함께 변경해야 한다.

## 재검토 조건

- 약어·별칭·오타·순위 규칙의 변경이 잦아져 SQL 수정과 검증 비용이 기능 개발의 병목이 되는 경우
- 적재 체계를 개편하면서 Java 공통 변환과 원본·검색 데이터의 저장을 함께 소유할 수 있게 되는 경우
- 쿼리와 인덱스 조정 후에도 목표 응답시간이나 DB 자원 사용 기준을 충족하기 어려운 경우
- 긴 자연어 검색, 복잡한 분석기 또는 검색 부하의 독립 확장이 핵심 요구가 되는 경우
- 팀이 전환의 효과와 적재·재생성·운영 비용을 검토하고 책임 주체에 합의한 경우

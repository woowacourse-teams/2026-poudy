## 목표와 배경

#480에서 카탈로그의 원천을 PostgreSQL로 옮겼지만 상품과 성분은 기동 시 전체를
메모리에 올려 기존 Java 검색, 필터, 정렬과 집계를 수행한다. DB 검색을 구현하고 관련
조회 경로를 전환해 상품과 성분의 전체 카탈로그 로딩 의존을 제거한다.

조회수, 인기 검색어 집계, 피드백, 정정 요청과 등록 요청의 DB 저장은 기준 브랜치에
구현되어 있다. 이 작업에서는 해당 저장 기능을 다시 구현하지 않는다.

## 확인한 근거와 제약

- #480은 `search_products`, `search_ingredients`로 전환하며 검색 순위 변경을 허용한다.
  상품 목록은 검색을 필터로 사용하고 모든 토큰이 맞는 결과만 남긴다(`p_max_tier = 2`).
- API 요청과 응답 형식, 클라이언트와 모바일 코드는 유지한다. 오타 교정어를 위한 새
  응답 필드나 화면은 이번 범위에 포함하지 않는다.
- 전달받은 `poudy-full-schema.sql`은 기존 테이블과 검색용 구체화 뷰 3개, 인덱스,
  정규화, 초성, 라틴 읽기, 오타 교정, 검색 순위와 UTF-16 일치 구간 함수를 포함한다.
  구현 후보이며 실행 정확성과 성능이 검증된 것으로 취급하지 않는다.
- 첨부 파일의 현재 위치는 `C:/Users/WM/Downloads/poudy-full-schema.sql`이다.
  구현 시 검증한 SQL을 저장소 스키마에 반영해 개인 경로 의존을 없앤다.
- private repo의 `db-script` 브랜치와 `db-load`가 초기 데이터 적재 경로로 전달되었다.
  저장소 URL, 실행법과 실제 스키마 호환성은 아직 확인하지 않았다.
- Spring과 PostgreSQL은 로컬에서 실행한다. 테스트 DB는 `poudy_test`다.
  현재 기본 프로필은 `dev`이며 #480의 `local` 표기와 다르므로 실제 설정 기준으로
  실행 문서를 정리한다. Docker 도입과 운영 인프라 구성은 범위에서 제외한다.
- DB 환경 문제는 원인을 확인하고 설치, PATH, 권한 등 근본 해결책을 먼저 제안한다.
  사용자 적용 동의 없이 우회하지 않는다.

- [ ] 로컬 PostgreSQL 버전, 인코딩, 로케일, 접속과 `pg_trgm` 사용 가능 여부를 확인한다.
- [ ] 개발용 `poudy`와 테스트용 `poudy_test`를 분리한다.

- [ ] 초기 데이터를 적재하고 기존 서버 및 테스트의 기준 결과를 기록한다.

완료 조건: 다른 개발자도 문서에 따라 적재, 기동과 테스트를 재현할 수 있다.
기존 데이터 삭제나 DB 재생성은 별도 확인 없이 수행하지 않는다.

### 2. 검색 계약과 기대 결과 정의

- [ ] 기존 테스트와 실제 검색어로 정규화, 초성, 영문 읽기, 별칭과 브랜드 조합 사례를 정리한다.
- [ ] 전체 일치, 접두, 포함, 전체 토큰과 일부 토큰의 적용 범위를 정리한다.
- [ ] SQL의 오타 교정, 최근 30일 조회수, 이름 길이와 동점 처리 결과를 검증한다.
- [ ] 상품 목록의 이름순과 대표 옵션 가격순, 제안의 관련도 순위를 구분한다.
- [ ] 성분 제안 최대 5개, 일치 필드와 UTF-16 강조 구간 계약을 보존한다.

완료 조건: 의도한 순위 변경과 회귀를 구분하는 기대 결과가 테스트 사례로 남는다.
기존 순위의 완전 일치는 요구하지 않지만 변경 결과에 근거를 남긴다.

### 3. 검색 SQL 검증과 스키마 통합

- [ ] 검증 DB에서 검색 함수와 스키마를 실행하고 오류 및 계약 불일치를 수정한다.
- [ ] 신규 DB 생성과 기존 DB의 검색 구조 추가 절차를 각각 마련한다.
- [ ] 빈 질의, 정규화 후 빈 질의, 짧은 질의, 긴 토큰, 한글 조합과 전각 문자를 검증한다.
- [ ] 검색 결과, total, 빈 페이지와 강조 구간을 검증한다.
- [ ] 적재 트랜잭션 마지막에 `product_search_document`, `ingredient_search_term`,
  `search_vocabulary` 순서로 갱신하도록 적재 경로를 연결한다.
- [ ] 테스트 데이터 삽입 후에도 검색 뷰를 갱신한다.

완료 조건: 적재 원본과 검색 문서가 함께 반영되며 신규, 기존, 테스트 DB 경로가 재현된다.
첨부 SQL 전체를 기존 DB에 그대로 재실행하지 않는다.

### 4. 성분 검색과 조회 전환

- [ ] 한글명, 영문명, 별칭 검색과 제안을 DB 검색 결과에 연결한다.
- [ ] 검색 결과의 순서, 필드와 강조 구간을 기존 API에 매핑한다.
- [ ] 상세, ID 목록, 페이지 조회를 필요한 데이터만 조회하도록 전환한다.
- [ ] 사용 중인 성분 조건, 포함 상품 수와 제외 성분군 조회를 연결한다.

완료 조건: 전체 성분 로딩 없이 성분 API가 동작하며 입력 ID 순서 등 기존 계약을 유지한다.

### 5. 상품 검색, 필터와 집계 전환

- [ ] DB 검색에 상품과 브랜드 조합 및 제안을 연결한다.
- [ ] 카테고리, 브랜드, 피부타입, 수분감, 유분감, 성분 포함과 제외 조건을 구현한다.
- [ ] 목록과 count가 같은 조건을 사용하도록 구현한다.
- [ ] 정렬과 페이지 처리를 DB에서 수행하고 해당 페이지의 관계 데이터만 조회한다.
- [ ] 대표 옵션 가격, 동점 ID 순서와 관계 조인에 따른 중복을 검증한다.
- [ ] 필터 선택지는 해당 축의 필터만 제외하는 기존 집계 규칙을 보존한다.
- [ ] 검색 함수의 전체 JSON 결과를 Java로 가져와 다시 필터링하는 구조를 피한다.
  필터와 결합 가능한 행 결과 또는 쿼리 경계를 검토한다.

완료 조건: 목록, count와 선택지 집계가 일치하며 검색과 필터 적용 뒤 페이지를 자른다.

### 6. 연관 기능의 전체 로딩 의존 제거

- [ ] 브랜드와 카테고리 상품 수, 성분 사용 집계를 DB 조회로 전환한다.
- [ ] 보관 목록과 큐레이션을 필요한 상품 ID 조회로 전환한다.
- [ ] 공유 텍스트 식별의 기존 계약을 유지하며 전용 조회 경계를 마련한다.
- [ ] 조회수 기록과 정정 요청의 상품 존재 확인을 전환한다.
- [ ] 인기 상품 랭킹의 단종 제외와 정렬 규칙을 유지한다.
- [ ] `CatalogKeywordSearch`의 검색 결과 존재 확인을 DB 경계에 연결한다.
- [ ] DB 검색 결과와 기동 시 캐시가 서로 다른 시점의 데이터를 쓰지 않는지 검증한다.

완료 조건: 상품과 성분의 전체 로딩 없이 연관 기능이 동작한다.
작은 사전 데이터의 캐시까지 일괄 제거하지 않고 갱신 정책을 명시한다.

### 7. 도메인, 엔티티와 설정 정리

- [ ] 최종 조회 경계를 기준으로 `Product`, `Ingredient`와 중복 엔티티의 통합을 검토한다.
- [ ] 직접 JPA 매핑 시 전성분의 순서와 중복, 옵션 순서, 태그 근거 규칙을 보존한다.
- [ ] 검색 점수와 강조 구간은 조회 결과 모델로 분리한다.
- [ ] 불필요해진 변환, 전체 로딩 생성자와 메모리 검색 인덱스를 제거한다.
- [ ] `SnapshotReader`, `Products`, `IngredientCatalog`와 Config는 남은 사용처를 확인한다.
  인기 검색어 랭킹 스케줄러 등 필요한 설정은 유지한다.
- [ ] 패키지 순환 금지와 도메인 책임을 유지하고 아키텍처 문서를 갱신한다.

완료 조건: 중복 상태와 전환 전 코드가 정리되고 기능 및 계층 의존 검증을 통과한다.
엔티티 통합은 검색 구현의 기술적 선행 조건이 아니다. 현재 문서는 복합 도메인의 별도
엔티티를 허용하므로 채택한 설계와 문서를 함께 맞춘다.

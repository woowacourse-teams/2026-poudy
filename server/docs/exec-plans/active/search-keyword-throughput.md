# 검색어 버킷 처리량 측정

## 목적

1분 버킷을 선택할 수 있는 현재 구현이 집계·조회·스냅샷 생성이 동시에 실행되는 조건에서 버틸 수 있는지 확인한다. 이 측정은 인프로세스 도메인 저장소의 결과이며 HTTP 처리량이나 여러 JVM이 같은 파일을 쓰는 상황을 의미하지 않는다.

## 재현 방법

측정기는 저장소에 두지 않는 로컬 프로브 `KeywordThroughputProbe`로 수행한 과거 측정이다.
프로브 원본은 저장소에 보관하지 않으므로 아래 명령은 당시 재현에 사용한 형태를 기록한 것이다.
현재 체크아웃에서 그대로 실행할 수 있는 명령은 아니다.

```bash
javac -cp build/classes/java/main -d /tmp/issue414-throughput-classes KeywordThroughputProbe.java
java -Xms256m -Xmx768m \
  -cp /tmp/issue414-throughput-classes:build/classes/java/main \
  KeywordThroughputProbe 10 10000
```

하네스는 4개 writer와 1개 reader를 동시에 실행한다. writer는 지정된 목표 요청률로 정규화 가능한 한국어 키를 기록하고, reader는 10ms마다 `view()`와 `snapshotIfDirty()`를 호출한다. 모든 writer와 reader Future를 회수해 예외를 숨기지 않는다. 버킷당 키는 80개로 유지해 용량 거절이 측정에 섞이지 않도록 했다.

## 해석

이 조건에서는 1분 버킷과 30초 버킷 모두 약 5,000 req/s에서 집계 누락이나 용량 거절이 없었다. 5만 개 이력에서도 최종 합계가 프리필+성공 집계와 일치했다. 1분 버킷의 168시간 전체 보관은 10,080개 버킷, 30초 버킷은 20,160개 버킷이므로, 501개 버킷까지 채운 이 측정과 `KeywordBudgetProbe`의 전체 기간 최악 조건을 함께 봐야 한다.

표의 지연은 요청이 `record()`에 들어온 시점부터 반환될 때까지의 인프로세스 서비스 시간이다. 예약 시각 대비 지연이나 HTTP 대기열은 측정하지 않았고, paced loop의 catch-up 및 warm-up 효과가 포함될 수 있으므로 이 수치로 운영 상한을 주장하지 않는다.

이 측정만으로 운영 HTTP 처리량, GC 영향, 실제 2,016개 버킷의 순위 계산 시간까지 보장할 수는 없다. 따라서 1분 선택은 가능하되, 최종 운영값은 전체 기간을 채운 순위·스냅샷·복원 측정과 함께 판단해야 한다.

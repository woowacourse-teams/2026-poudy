# 파우치 성분 분석 개선 (#1120, #1121)

작성일: 2026-11-06. 상태: 회원 기능과 공통 분석 기반 구현 완료, 비회원 실사용 연동은 후속.

후속 사용자 결정에 따라 #1118은 이번 구현에서 제외한다. 회원 기능은 끝까지 구현하고,
비회원은 후보 계산·응답·표시의 공통 기반까지만 준비한다. 공개 API, 세션 파우치와 비회원
실사용 연동은 후속 작업이며, 이 조건이 남아 있는 #1120·#1121은 전체 완료로 닫지 않는다.

- 서버: [#1120](https://github.com/woowacourse-teams/2026-poudy/issues/1120)
- 클라이언트: [#1121](https://github.com/woowacourse-teams/2026-poudy/issues/1121)
- 연동 대상: [#1118 비로그인 파우치 구현](https://github.com/woowacourse-teams/2026-poudy/issues/1118)
- 근거: [2026.11.06 원온원 후 팀회의](https://app.notion.com/p/2026-11-06-41088d945cf0809092f4c3257986dfc6)와 후속 사용자 결정

## 도메인 리팩터링 후속 작업

PR #1126의 점검 결과에 따라 생성 경계, 제품 집계와 분석 결과 캡슐화를 정리한다.
API 필드·선정 근거 순서·후보 정렬·새 성분 판단·예외·저장 규칙은 유지한다.

1. 후보의 근거별 인덱스 조립을 정적 팩토리로 옮기고 성분군 조회 변수의 의미를 드러낸다.
2. 평가 제품 집합에 성분 포함 빈도와 위치 집계를 옮기고 후보 컬렉션에는 선별·정렬을 남긴다.
3. 분석 결과를 불변 클래스로 만들고, 파우치·후보·분석 항목이 자기 상태의 판단을 맡게 한다.
   서비스의 중첩 탐색과 DTO의 내부 성분 탐색을 제거한다.

세 단계의 리팩터링을 완료했다. 후보 생성 입력과 평가 제품 목록의 변경에도 분석이 유지되고,
필터에 든 새 성분은 표시되지 않는 행동을 테스트로 확인했다. 전용 PostgreSQL 18.6에서
`scripts/verify.sh`가 통과했으며 서버 테스트 1,987개가 모두 성공했다. 전체 패키지·기능·계층의
순환 검사도 통과했고 OpenAPI와 공통 TypeScript 생성물의 변경은 없다. 커밋은 위 세 단계로 나눴다.

## 이번 구현 결과

- 회원의 좋은 평가 성분 제외와 평가 취소·제품 삭제·되돌리기에 따른 복원을 구현했다.
  이미 나만의 필터에 저장한 성분은 유지한다.
- 선정 근거를 `reasons: [{ code, name }]`로 제공하고 성분별 복수 근거를 보존한다.
  회원은 기존 프로필 조건만 적용하며, 피부 정보 없는 조건별 분석에는 `SkinCautions.all()`을 쓸 수 있다.
- 피부 타입이 있는 회원은 나쁜 평가 한 개의 결과를 고르고 검색 제외에 저장할 수 있다.
  피부 정보 없는 회원과 평가 0개의 조건은 유지한다.
- 화면은 근거별로 후보를 나누고 선택 화면은 성분별 한 행과 한 ID를 사용한다.
  읽기 전용 카드에서는 회원의 필터·피부 설정 동작을 숨긴다.
- #1118의 공개 API, 비회원 담기·평가·세션 저장·기록 이관과 실제 비회원 연동은 구현하지 않았다.
  이 때문에 두 이슈의 비회원 완료 조건은 남아 있다.

### 검증 결과

- 전용 PostgreSQL 18.6 DB에서 `server/scripts/verify.sh`를 통과했다.
  API 생성물 드리프트가 없으며 서버 테스트 1,983개가 모두 성공했다.
- `pnpm --dir client check`를 통과했다. 포맷·린트·Next.js 경로 타입·TypeScript·빌드와
  클라이언트 테스트 1,808개가 성공했다. 수정한 파일의 별도 린트 검사에는 경고가 없다.
- Chromium과 모의 API 응답으로 320·360·390·1024px의 파우치 가로 넘침이 없는 것을 확인했다.
  복수 근거의 성분 세 개를 한 번씩 선택하고 두 개만 저장하는 흐름, 나쁜 평가가 없어져도
  기존 검색 제외 성분이 유지되는 흐름을 확인했다. 페이지 스크립트 오류는 없었다.

### 후속 연동 지점

#1118에서 공개 분석 API를 구현한 뒤 `SkinCautions.all()`의 `ingredientGroupCodes()`로
`ShelfCautionRepository.findIngredientIdsByGroup()`을 조회하고, `candidatesWith()`에 빠른 제외
성분과 성분군별 조회 결과를 전달한다. 회원과 같은 `RatedProducts`·`SuspectIngredients`·분석 응답 변환을
재사용한다. 비회원 화면은 결과 카드의 `canManageFilter`를 false로 넘겨 연결한다.

## 목표와 확정 범위

비회원은 첫 나쁜 평가부터 피부 조건별 예상 후보를 확인한다. 피부 타입이 있는 회원은
나쁜 평가 한 개로 결과를 확인하고 검색에서 제외할 성분을 고를 수 있다. 잘 맞은 제품에
한 번이라도 포함된 성분은 의심 후보에서 제외한다.

| 조건 | 결과 |
| --- | --- |
| 비회원, 나쁜 평가 한 개 이상 | 제품에 실제로 있는 빠른 제외·건성·지성·민감성 후보를 근거별로 표시 |
| 피부 타입이 있는 회원, 나쁜 평가 한 개 이상 | 기존 프로필 기준으로 후보를 고르고 검색 제외 선택까지 제공 |
| 피부 정보 없는 회원 | 기존 후보 선택과 검색 제외 노출 조건 유지 |
| 나쁜 평가 없음 | 피부 정보와 관계없이 분석 결과 없음 |
| 잘 맞은 제품에 같은 성분 존재 | 모든 후보 분류에서 해당 성분 제외 |
| 좋은 평가 취소·제품 삭제 | 남은 평가에 따라 후보 재계산 |
| 후보에서 빠졌지만 이미 나만의 필터에 저장됨 | 저장된 필터 유지 |

로그인 후 비회원 기록 이관은 다른 팀원의 후속 작업이다. 평가 0개의 피부 타입 기반 분석,
기존 필터 자동 정리, 랜딩·비교함 개편, 첫 방문 온보딩과 별도 애니메이션 제작은 포함하지 않는다.

## 현재 구현과 의존성

- 회원 서버는 이미 나쁜 평가 한 개로 후보를 계산하며, `ShelfScreen`도 해당 카드를 표시한다.
  두 개 미만을 막는 곳은 `pickLabelOf`의 검색 제외 버튼 조건이다.
- 좋은 평가에 따른 후보 숨김은 현재 포함 비율의 차이로 판단한다. 이번에는 동일 성분의
  포함 여부를 우선하는 규칙으로 바꾼다.
- `SkinCautions.ingredientIdsWith`와 `SuspectCandidates`는 피부 조건별 성분을 합쳐 보관한다.
  결과를 분류하려면 합치기 전에 각 조건의 선정 근거를 보존해야 한다.
- `groupCodes`는 기존 빠른 제외 성분군 코드다. 새 후보 분류와 의미를 섞지 않는다.
- 계획 작성 시 현재 체크아웃에는 비회원 파우치 코드가 없으며 #1118은 OPEN이다.
  확인한 열린 PR 목록에는 비회원 파우치 PR이 없었다. 구현 착수 시 다시 확인한다.
- #1118의 공개 분석 경로는 `POST /api/shelf/ingredient-analysis`다. 제품 ID와 호불호를 받고,
  분석 결과와 `possiblyUnsuitableProductIds`를 돌려주는 계약을 기준으로 연동한다.
- #1118의 초기 설명은 비회원 피부 조건 후보를 제외하지만, #1120은 최신 합의에 따라 이를
  조건별 후보로 확장한다. 공개 엔드포인트를 중복 생성하지 않는다.

## 구현 순서

### 0. 작업 공간과 계약 정리

현재 체크아웃은 `feat/1039-1040-similar-products-client`다. 실제 구현은 최신 `dev`를 기준으로
`feat/1120-1121-shelf-analysis` 같은 별도 브랜치·작업 공간에서 시작한다. 기존 미추적 파일과
다른 기능의 변경을 이 작업에 섞지 않는다. 계획 작성 단계에서는 브랜치를 전환하지 않는다.

착수 시 #1118의 브랜치·PR과 실제 응답 계약을 확인한다. 먼저 확정할 계약은 다음과 같다.

- 기존 `items`를 성분 ID별 한 항목으로 유지한다.
- 각 항목에 `reasons: [{ code, name }]` 형태의 선정 근거를 추가하는 안을 기본으로 한다.
  코드는 빠른 제외·건성·지성·민감성을 구분하고 표시 이름은 서버가 제공한다.
- 한 성분은 여러 근거를 가질 수 있지만 성분·제품 개수와 선택 ID에는 한 번만 반영한다.
- 기존 `groupCodes`, `products`, `inFilter`, `isNew`의 의미를 유지한다.
- 비회원의 `inFilter`·`isNew`는 #1118의 계약대로 false이며, 피부 정보를 입력받거나 저장하지 않는다.

완료 기준: 회원·비회원의 응답 예시, 복수 근거 예시, 빈 결과 예시를 문서나 테스트 픽스처로
고정한다. 경로와 공개 요청 검증은 #1118의 구현을 따른다.

### 1. 좋은 평가에 따른 후보 제외 규칙 변경

`SuspectIngredients`, `SuspectIngredient`, `SuspectEvidence`의 현재 책임을 확인한 뒤,
잘 맞은 제품의 성분 ID를 기준으로 후보를 제외한다. 피부 조건 가산점이나 나쁜 평가 수가
제외된 성분을 되살리지 않게 한다. 후보 제거 이후의 기존 정렬·동률 규칙은 유지한다.

먼저 도메인 테스트로 다음 행동을 고정한다.

- 나쁜 평가 여러 개와 좋은 평가 한 개에 같은 성분이 있어도 제외된다.
- 같은 성분군의 다른 성분은 함께 제외하지 않는다.
- 여러 구성품에 같은 성분이 있어도 한 번만 계산한다.
- 좋은 평가를 취소하거나 해당 제품을 빼면 남은 나쁜 평가의 후보가 복원된다.
- 나쁜 평가가 없으면 좋은 평가나 피부 정보만으로 후보를 만들지 않는다.

완료 기준: 회원 분석의 최종 성분 ID와 제품별 `possiblyUnsuitable`이 같은 규칙을 사용한다.
이 단계는 #1118의 공개 API가 아직 없어도 진행할 수 있다.

### 2. 후보 선정 근거 보존과 회원·비회원 API 연결

기존 `SkinCaution`의 성분 정의를 재사용하고 `SuspectCandidates`가 성분의 선정 근거를
답할 수 있게 한다. 성분군 조회 결과를 건성·지성·민감성의 원래 조건과 연결한 뒤 합친다.
모든 조건의 성분을 먼저 합쳐 놓고 각 조건에 같은 집합을 붙이지 않는다.

- 회원은 빠른 제외와 저장된 피부 조건에 해당하는 근거만 사용한다. 복합성은 기존처럼
  건성·지성을 함께 적용하고 민감성 여부는 별도 축으로 처리한다.
- 비회원은 빠른 제외와 세 피부 조건의 후보를 모두 사용하되 조건별 근거를 보존한다.
- 두 경로 모두 1단계의 좋은 평가 제외 규칙을 사용한다. 한 번 제외되면 모든 근거에서 빠진다.
- #1118의 공개 API가 준비되면 기존 경로에 연결한다. 준비 전에는 공통 분석 도메인과
  회원 응답·픽스처까지 진행하고 공개 엔드포인트를 임시로 복제하지 않는다.
- 공개 분석은 사용자 데이터를 읽거나 저장하지 않는다. 중복·없는 제품 등의 검증은
  #1118의 동작을 유지한다.
- `AnalysisSnapshot`은 기존대로 성분 ID를 기준으로 새 성분을 판단한다. 근거만 달라졌다고
  새 성분으로 표시하지 않는다. 평가 변경·삭제·되돌리기의 갱신도 확인한다.
- `ARCHITECTURE.md`, OpenAPI와 공통 생성물을 갱신한다. 이번 정책을 위해 새 DB 테이블이나
  마이그레이션을 만드는 작업은 계획하지 않는다.

완료 기준: 회원과 비회원 API에서 실제 평가에 맞는 근거를 조회할 수 있고, 같은 성분은
중복 항목 없이 반환된다. 공개 API 연동에는 #1118의 해당 API 구현만 필요하며 기록 이관은
선행 조건이 아니다.

### 3. 후보별 결과 표시와 단일 평가 동작 연결

클라이언트 코드를 작성하기 전에 설치된 Next.js의 관련 로컬 가이드를 확인한다.
생성된 API 타입을 사용하고 분류별 성분 목록을 클라이언트에 복제하지 않는다.

- 결과 카드에서 아직 검색 제외하지 않은 후보를 서버의 근거별로 묶는다. 빈 분류는 숨긴다.
- 같은 성분이 여러 분류에 보여도 전체 개수는 평면 성분 목록으로 계산한다.
- 검색 제외 선택 화면은 성분별 행을 한 번만 두고 필요한 근거를 함께 표시한다. 선택 상태는
  성분 ID를 기준으로 관리한다.
- 기존 검색 제외 중 목록과 결과 밖에 남아 있는 필터 안내를 유지한다.
- `summarizeAnalysis`가 회원의 피부 타입 여부를 알 수 있게 하고, 피부 타입이 있는 회원은
  나쁜 평가 한 개여도 고를 성분이 있으면 검색 제외로 진행하게 한다. 무조건 두 개 제한을
  삭제해 피부 정보 없는 회원까지 범위를 넓히지 않는다.
- #1118의 비회원 상태에서 같은 결과 UI를 사용하되 검색 제외·필터 관리 동작은 노출하지 않는다.
- 분석 결과가 바뀌면 모든 분류와 제품 표시를 함께 갱신한다. 기존 비동기 요청 순서 보장도 유지한다.
- 목 응답과 기존 분석 이벤트의 성분 개수·선택 가능 개수를 맞춘다. 분류 중복을 이벤트 수치에
  중복 반영하지 않는다. 새로운 분석 대시보드나 이벤트 체계를 추가하지 않는다.

완료 기준: 회원의 첫 나쁜 평가 → 후보 확인 → 검색 제외 저장과 비회원의 첫 나쁜 평가 →
분류 결과 확인을 각각 화면에서 검증한다.

### 4. 통합 검증과 리뷰

| 시나리오 | 확인할 결과 |
| --- | --- |
| 회원·피부 타입 있음·BAD 1개 | 후보와 검색 제외 선택·저장이 가능 |
| 회원·피부 정보 없음 | 기존 선택과 버튼 조건 유지 |
| 피부 타입만 있음·BAD 0개 | 분석 결과 없음 |
| 비회원·BAD 1개 | 제품에 포함된 후보를 조건별로 표시, 필터 동작 없음 |
| BAD 여러 개·GOOD 1개에 같은 성분 | 모든 분류에서 해당 성분 제외 |
| GOOD 취소·제품 빼기·되돌리기 | 후보와 제품 포함 표시가 다시 계산됨 |
| 성분이 복수 조건·복수 구성품에 포함 | 근거 보존, 성분 수와 선택 ID 중복 없음 |
| 후보가 전부 사라짐 | 빈 상태 표시, 저장된 나만의 필터 유지 |
| 비회원 새로고침·상세와 파우치 이동 | #1118의 세션 평가와 결과 일치 |

서버는 변경한 도메인·API·스냅샷 관련 테스트를 먼저 실행하고, API 생성물을 갱신한 다음
`server/`에서 `sh ./scripts/verify.sh`를 통과시킨다. 클라이언트는 관련 화면·도메인 테스트 후
`pnpm --dir client check`로 포맷·린트·타입·전체 테스트·빌드를 확인한다. 필요한 환경 변수가
없어 검증하지 못한 항목은 별도로 기록한다. 브라우저에서는 위 표의 핵심 회원·비회원 흐름을 확인한다.

API 필드 추가는 `common` 생성물을 통해 클라이언트 픽스처에도 영향을 준다. 이슈는 두 개로
유지하되 기본 구현은 같은 기능 브랜치에서 서버 → 생성물 → 클라이언트 순서로 진행하고,
완료된 기능 전체가 CI를 통과하는 단위로 PR을 만든다. 반쯤 적용된 타입 변경을 먼저 병합하지 않는다.
커밋을 생성할 때는 사용자 신원과 `CONTRIBUTING.md`의 규칙을 확인한다.

## 착수 지점

별도 작업 공간에서 계약 예시를 고정하고, 1단계의 좋은 평가 성분 제외 테스트와 구현부터 시작한다.
이어 선정 근거를 보존하는 구조를 추가한다. #1118의 공개 API·비회원 UI가 준비되는 시점에
연결하며, 로그인 후 기록 이관을 기다리지는 않는다.

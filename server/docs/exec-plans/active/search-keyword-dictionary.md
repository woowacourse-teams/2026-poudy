# 인기 검색어 대표어 사전 사용 계획

> 2026-09-08 범위 조정: JSON은 private output에서 resources로 직접 복사한다.
> 배포 스크립트는 이번 작업에서 변경하지 않는다.
> 2026-09-08 구현 조정: 사용자 요청에 따라 인기 검색어 전용 환경 변수는 추가하지 않는다.
> 칸 크기·순위 기간·최소 횟수·저장 주기는 `SearchKeywordPolicy`의 정책 상수로 관리한다.
> 개발 상태 경로는 `./var/search-ranking/buckets.json`, 운영은
> `/opt/poudy/state/search-ranking/buckets.json`을 기본으로 사용한다.
> 아래 초안의 환경 변수·필수 경로 설정 요구는 이 결정으로 대체한다.
> 기능 비활성 스위치는 두지 않는다. 내부 보고서 내보내기만 필요할 때 애플리케이션 속성으로 명시한다.


## 상태와 사용 흐름

서버 기능을 구현했다. 최신 데이터와 별칭 검증은 [구현 검증 기록](search-keyword-verification.md)을 따른다. 제공된 `search_keywords.json`을 읽기 전용으로 사용한다.
서버와 이 저장소에서 사전 항목·표현·ID를 추가·수정·삭제하지 않는다.
집계·기간·저장·관찰·API 계약은 [인기 검색어 계획](search-keyword-rankings.md)이 소유한다.

```text
정규화 입력별 횟수 → ACTIVE expressions 정확 조회 → 대표어별 합산 → 최소 횟수·정렬·노출 차단
                  → 공개 적격성 및 재검색 확인 → 상위 10개와 완성 표시명
```

| 입력 예시 | 제공된 사전 조건 | 처리 |
| --- | --- | --- |
| ` 라운드랩 ` | 정규화 키가 브랜드 표현에 존재 | 내부 입력 `라운드랩` 집계, 브랜드 완성어로 노출 가능 |
| `토너` | ACTIVE·ranking_eligible=true인 TERM | 일반어 `토너`로 노출 가능 |
| `독도` | 일치하는 표현 없음, 제품 검색 결과는 존재 | 내부 입력 `독도` 집계, 공개 노출 제외 |
| `ㄷㄷㅌㄴ` | 특정 제품에 연결된 표현이 실제 사전에 존재 | 검색 결과가 있으면 해당 완성 제품명으로 노출 가능 |

이 예시는 계약 설명용이며 현재 사전에 해당 별칭이 존재한다고 가정하지 않는다.
노출 가능 항목도 상위 계획의 최소 횟수와 노출 필터를 통과해야 한다.

## 로딩 계약

개발은 `server/src/main/resources/search_keywords.json`, 운영은 기존 카탈로그 외부 데이터
디렉터리의 같은 파일을 읽는다. 기동 시 불변 인덱스를 구성하고 교체 파일은 재시작 시 읽는다.
운영 데이터는 커밋하지 않으며 테스트용 fixture로 계약을 검증한다.

기존 `JsonDataReader.readList`는 `at("/" + 파일명)`으로 최상위 배열 하나만 읽으므로 이 파일에
쓸 수 없다. schema_version·normalizer_version·dictionary_version이 배열의 형제 필드다.
문서 전체를 나타내는 DTO와 사전 전용 엄격 매퍼로 읽는다. 공용 MAPPER는
`FAIL_ON_UNKNOWN_PROPERTIES`가 꺼져 있어 오타 필드가 조용히 무시되지만, 이 설정을 공용
매퍼에서 켜면 다른 카탈로그 파일의 읽기가 함께 바뀌므로 건드리지 않고 분리한다. 스네이크케이스
필드명 전략은 기존 리더와 같게 맞춘다. 전용 매퍼가 거절해야 하는 것은 알 수 없는 필드만이
아니다. 필수값 누락, 명시적 null, 중복 JSON 키, 정의되지 않은 enum 값, 지원하지 않는 버전,
그리고 아래의 표현 충돌까지 모두 기동 실패로 처리한다.

`server/.gitignore`의 `**/resources/**/*.json` 때문에 main resources의 데이터 JSON은 추적되지
않는다. 새로 클론한 환경에는 사전뿐 아니라 다른 카탈로그도 없으므로 사전만 특별 취급하지 않는다.

- 테스트는 추적되는 `src/test/resources`의 사전 fixture로 계약을 검증한다.
- 개발은 기존 카탈로그와 같은 데이터 준비 절차에 사전을 포함한다.
- 사전 누락·손상은 프로필과 무관하게 오류다.

파일이 없다는 이유로 자동으로 빈 사전으로 전환하지 않는다. 그렇게 하면 설정 누락이 정상 기동으로
보이고, 순위가 비어 있는 원인이 데이터 부족인지 사전 부재인지 구분되지 않는다.

| 필드 | 소비 계약 |
| --- | --- |
| schema_version | 지원 값 3 |
| normalizer_version | 지원 값 search-keyword-v1 |
| dictionary_version | 제공된 사전 버전 식별자 |
| search_keywords | 대표어 목록 |
| id | 불투명한 대표어 식별자. 공개 순위 합산에 사용하며 입력 집계 키와 구분 |
| kind | BRAND / PRODUCT / TERM. kind만으로 순위 제외하지 않음 |
| keyword | 표시·재검색용 완성 이름. PRODUCT는 브랜드를 포함 |
| expressions | 입력 전체를 연결할 수 있는 제공된 표현 |
| expression_types | 정규화 표현 키 → CATALOG / REVIEWED_ALIAS |
| status | ACTIVE / INACTIVE |
| ranking_eligible | 명시된 공개 순위 적격 여부. TERM도 true이면 포함 |
| catalog_refs | 참조 정보 배열. 빈 배열·복수 참조를 허용하며 검색 필터로 사용하지 않음. 서버는 형식만 검증하고 보관하지 않음 |

dictionary_version은 불투명한 제공 버전이다. 표시명이나 표현 연결이 바뀔 수 있으므로 갱신 시
엄격 검증을 수행하고, 재검색은 대표어가 순위 후보에 오를 때 한다. 버전 변경만으로 입력 횟수를 초기화하지 않는다.
별도 dictionaryRevision은 도입하지 않는다.
시간별 입력 집계에 사전 버전을 붙여 집계 귀속을 고정하지도 않는다. 지원하지 않는 버전은
명시적으로 거절하며 존재하지 않는 이전 운영 데이터의 자동 이전 규칙은 미리 정의하지 않는다.

## 정규화와 해석 검증

1. 기존 `SearchKeyword.value()`로 각 expressions 값을 정규화한다.
2. 재계산한 키 집합이 제공된 expression_types 키 집합과 정확히 같은지 검증한다.
   키 자체도 동일 정규화 함수 적용 전후가 같아야 한다. 누락·여분·불일치는 기동 오류다.
3. 동일 ID의 정규화 중복은 합치고 서로 다른 ACTIVE ID가 같은 키를 소유하면 기동을 실패시킨다.
4. 입력 전체 키로 정확 조회한다. keyword를 expressions에 자동 추가하지 않는다.
5. 초성·부분어·오타는 해당 표현이 실제 인덱스에 있을 때만 연결한다.
   `SearchKeyword.rank()`의 유일 최고 점수나 첫 제품 결과는 사용자 의도를 보장하지 않는다.
6. schema·필수 필드·ID 중복·enum과 표현 출처를 검증한다. 오류를 빈 사전으로 우회하지 않는다.
7. 기동 시 활성 항목 수·입력 키 수·빈 표현 항목 수를 요약한다. 이전 배포의 관측치와 비교해
   키 감소·미해석률 상승을 운영에서 확인한다. 소비 파일만으로 표현 누락 원인을 확정하지 않는다.
8. ACTIVE인데 expressions가 비어 있으면 기동 시 항목 ID·사전 버전과 요약 건수를 경고한다.
   인덱스에는 연결할 키가 없으므로 노출되지 않는다. 표현을 자동 보충하거나 상태를 수정하지 않는다.
   빈 표현 자체는 경고이며 실제 ACTIVE 키 충돌은 위 규칙대로 기동 오류다.

정규화 fixture에는 NFC/NFD 한글, 호환·분해 자모, 쌍자음, 공백·NBSP, U+0085,
İ와 결합점, 그리스 문자, 영문 대소문자를 포함한다. 명시된 기대 키를 Java 정규화 결과와
비교해 문자의 처리 차이를 탐지한다. 이 검증은 현재 정규화 장애가 있다는 전제가 아니라
사전·검색 구현 변경에 따른 회귀를 막기 위한 것이다. 불일치가 없는 표본 검증도 모든 Unicode
조합의 동치를 증명하지 않으므로 기동 검증과 fixture를 유지한다.

## 표시·재검색·사전 교체

- 같은 입력의 결과 제품이 여러 개여도 하나의 연결된 대표어에 한 번만 합산한다.
- 브랜드가 다른 제품 대표어는 별도 ID로 취급한다. 모호한 입력은 임의로 배분하지 않는다.
- 일반어(카테고리명·상품 공통 용어 포함)·브랜드명·상품명은 각각 독립된 검색 의도다. 제품 입력을 브랜드에 추가 합산하지 않는다.
- 순위 후보에 오른 대표어만 제공된 keyword로 재검색한다. 기동 시 사전 전체를 재검색하지 않고,
  후보를 순위순으로 확인하다 10개가 차면 멈춘다. 결과는 사전 인스턴스에 캐시한다.
  이 확인은 집계·관찰을 증가시키지 않는다. `ProductService.findProducts`를 쓰지 않는다.
  그 메서드는 keyword가 있고 첫 페이지이면 검색 로그와 집계 기록을 타기 때문이다. 대신 구성
  계층의 읽기 전용 어댑터 `CatalogKeywordSearch`가 도메인 `Products.hasResults(keyword)`를 호출해
  첫 일치에서 멈춘다. 사전 도메인은 `KeywordSearch` 인터페이스만 알고 `ProductRepository`·Spring·
  검색 구현에 직접 의존하지 않는다. 어댑터는 생성할 때 카탈로그를 한 번 받아 보관하므로
  재검색마다 파일을 다시 읽지 않는다.
- 재검색 0건 항목은 공개에서 제외하지만 입력별 기록과 해석 인덱스는 유지한다.
- 제품 표시명은 브랜드를 포함하며 실제 검색에서 브랜드 의도가 유지되는지 fixture로 검증한다.
- 참조 배열로 결과를 강제 제한하거나 일반어를 categoryIds 조건으로 바꾸지 않는다.
- 사전 교체 후에는 보존된 입력을 현재 인덱스로 다시 해석한다. 표현 추가·삭제·연결 변경은
  최근 기간의 공개 순위에도 반영된다. 같은 ID의 표시명 변경은 현재 표시명으로 응답한다.
  ID는 불투명하게 다루며 이름 변경 전후의 ID 연속성을 가정하지 않는다.
  집계 키가 대표어 ID가 아니라 정규화 입력이므로 ID가 바뀌어도 과거
  기록은 그대로 재해석된다. ID의 연속성을 전제한 저장·캐시 키를 만들지 않는다.
- 비활성·부적격·미해석 입력도 상위 계획의 보관 기간까지 유지한다. 재활성화되면 기간 내 기록을 다시 반영한다.
- 사전 파일에는 횟수·순위·발견한 입력을 쓰지 않는다. 개선 근거 확인은 상위 계획의 내부 보고서가 담당한다.

## 현재 사전의 제약

제공된 사전은 카탈로그 이름과 검증된 별칭을 연결한다. 아래 제약은 공개할 수 있는
입력 표현의 범위를 제한하므로 상위 계획의 출시 판정에서 함께 읽는다.
표현 개수만으로 실제 요청 가중 연결률이나 출시 기준 통과 여부를 확정하지 않는다.

- 2026-09-09 확인한 제공 사전은 총 599개 항목(BRAND 23, PRODUCT 460, TERM 116)이며 표현은 1,759개다.
  TERM은 카테고리 파생 23, 성분 파생 21, 브랜드 라인 57, 설정 지정 15로 구성된다.
  설정 지정에는 파생 규칙이 닿지 않는 제형·통칭 4개, 효능·고민어 9개, 한 제품으로 확정할 수 없어
  일반어로 돌린 결합어 2개가 들어간다. 승인 별칭 12개 중
  문자 별칭이 10개, 초성 별칭이 2개다. 제품명과 접미 부분어에서 파생한 초성 표현 271개가 별도로 있다.
  실제 배포본의 범위는 dictionary_version별로 확인하며 이 수치를 로더의 고정 조건으로 사용하지 않는다.
- 브랜드의 영문 이름이 제공되지 않아 BRAND 항목의 표현이 한글 하나뿐이다. 영문 브랜드 입력은
  구조적으로 미해석이다. 서버가 영문 표기를 만들어 보충하지 않는다.
- 성공 검색의 미해석 입력은 제공 사전의 별칭 연결을 검토할 대상이다. 결과 0건 입력은 순위
  저장소에 없으므로 표시용 별칭을 연결해도 순위 횟수가 생기지 않는다. 원인별 개선 경로와
  검토 근거의 전달은 [상위 계획](search-keyword-rankings.md)의 소비 화면과 커버리지 검증 절을 따른다.

ranking_eligible은 현재 제공 항목에서 모두 true다. false도 소비 계약상 유효하며 공개에서 제외한다. 지금 작동하는 차단 수단은 사전의 status INACTIVE와 서버의 노출 차단 정책뿐이다.
서버 노출 차단 정책과 역할이 중복되는지 다음 스키마 개정에서 검토한다. 검토 전까지 현재 필수
boolean 소비 계약과 false 항목 비노출은 유지한다.

## 검증 항목

- 지원 버전·필수값·표현 출처·정규화 드리프트·ACTIVE 충돌에 대한 기동 실패.
- 전용 매퍼가 알 수 없는 필드·필수값 누락·명시적 null·중복 JSON 키·잘못된 enum을 거절하는지.
  공용 매퍼로는 통과하는 입력으로 검증하고, 공용 매퍼의 기존 카탈로그 읽기가 바뀌지 않았는지 확인한다.
- 사전 누락·손상이 오류인지. 파일 부재가 빈 사전으로 대체되지 않는지.
- 순위 계산 중 재검색이 검색 로그와 입력 집계를 늘리지 않는지. 재검색 횟수만큼 카탈로그를 다시 읽지 않는지.
  사전 도메인이 검색 구현·Spring에 직접 의존하지 않는지.
- BRAND·PRODUCT·TERM의 적격 항목 포함 및 false 항목 비노출.
- 모호한 부분어의 입력 집계 유지와 공개 제외, 제공된 별칭의 완성 표시명 연결.
- 서로 다른 브랜드 제품의 분리, 복수 참조로 인한 횟수 증폭 방지.
- 사전 교체 후 과거 입력 재해석, 재검색 0건 처리, 내부 재검색 미집계.
- ACTIVE·빈 expressions의 기동 경고와 미매칭, 파일 및 status 불변.
- 로딩·검색·조회·복원 전후 사전 파일 바이트 불변.

## 별칭 보완 및 갱신 사전 적용

관련 이슈: [#414](https://github.com/woowacourse-teams/2026-poudy/issues/414).

제품 초성 검색 지원과 완성어 연결은 별개다. 검색이 성공해도 사전에 표현이 없으면 내부
입력 집계만 유지하고 공개 순위에는 연결하지 않는다. 서버는 사전을 읽기 전용으로 사용한다.

1. 백엔드 담당자가 초성·부분어 표본을 실제 검색 경로의 읽기 전용 어댑터로 검증한다.
   검증 요청은 검색 로그와 집계 횟수를 증가시키지 않는다.
2. 성공했지만 미해석인 표현을 보완 요청으로 정리한다. 입력, 대상 ID·표시명, 결과 수와 제품 ID,
   대상 포함 여부·순위, 대표어 재검색 결과, 검증 시각, 카탈로그·검색 구현·사전 버전,
   필터·정렬 조건을 접근 제한된 검토 자료에 남긴다.
3. 기존 제한된 전달 경로로 사전 검토 담당자에게 요청한다. 결과와 대표어의 대응이 명확한
   표현만 반영 대상으로 삼는다. 0건은 검색·카탈로그·필터 조사로 분리하고 모호한 입력은
   보류 사유를 기록한다. 검색 첫 상품에 임의 귀속하거나 자동 승인하지 않는다.
4. 갱신 사전을 엄격 로더와 재검색으로 검증한 뒤 적용한다. 새 별칭, 기존 표현, 충돌,
   노출 적격성과 보관 중인 성공 입력의 대표어별 합산 결과를 회귀 검증한다.

현재 `독도 토너`와 `ㄷㄷㅌㄴ`은 모두 상품 295로 연결된다. 초성 표현은 그 초성으로 검색했을 때
한 제품만 나올 때만 넣는다. `ㄷㄷㅌㄴ`은 한 글자 브랜드 접두가 허용되던 동안 닥터지 제품까지
불러 통과하지 못했고, 두 글자 미만 접두를 브랜드로 인정하지 않도록 검색을 고친 뒤 통과했다.
서버에서 표현을 생성하거나 사전을 수정하지 않는다. 표본 검증은 실제 요청 가중 연결률을 대신하지 않는다.

- [ ] 초성·부분어의 검색 결과와 사전 연결 여부 검증
- [ ] 성공 미해석 표현의 별칭 보완 요청과 검증 근거 정리
- [ ] 0건·모호한 입력의 보류 사유 기록
- [ ] 갱신 사전 적용 후 새 별칭과 기존 표현의 연결 회귀 검증

## 공개 표시 구성

카테고리명·상품 공통 용어를 포함한 일반어(TERM), 브랜드명(BRAND), 상품명(PRODUCT)을
하나의 인기 검색어 목록에 표시한다. schema 3을 유지하며 별도 CATEGORY 유형·순위는 만들지 않는다.
사전에 제공된 keyword를 그대로 표시·재검색에 사용한다. 상품은 브랜드를 포함한 정식명으로 표시한다.

| 사용자 입력 예시 | 메모리·집계 JSON의 키 | 사전 연결 후 API keyword |
| --- | --- | --- |
| ` 독도  토너 ` | `독도토너` | `라운드랩 1025 독도 토너` |
| ` 라운드랩 ` | `라운드랩` | `라운드랩` |
| `토너` | `토너` | `토너` |
| `pdrn` / `PDRN` | `pdrn` | `PDRN` |
| `ㄷㄷㅌㄴ` | `ㄷㄷㅌㄴ` | `라운드랩 1025 독도 토너` (파생 초성 표현) |

집계 키 예시는 검색 성공·최종 결과 1건 이상·수집 허용 조건을 통과한 경우에만 적용한다.
초성 검색 결과가 0건이면 순위 저장소에 기록하지 않는다. 표의 API 표시는 최소 횟수와
공개 적격성·재검색 조건도 충족한 경우다.

- 일반어에는 제공된 카테고리명과 PDRN 같은 독립된 의미의 상품 공통 용어를 포함한다.
  여러 상품이 검색되어도 정상이며, 단순히 겹치는 글자나 잘린 음절은 서버에서 새 일반어로 만들지 않는다.
- 세 종류의 대표어별 횟수를 통합해 상위 10개를 고른다. 종류별 할당량이나 별도 집계 목록은 없다.
- `PDRN` 검색과 PDRN이 포함된 상품명 검색은 각자 연결된 대표어에만 기여한다.
  상품명에 브랜드·일반어가 포함됐다는 이유로 횟수를 중복 가산하지 않는다.
- 카테고리명도 keyword 검색을 사용하며 categoryIds로 치환하지 않는다. 클릭 재검색 0건이면 비노출한다.
- 사전 자체에는 검색 횟수·기간·순위를 쓰지 않는다. 저장 및 복원 계약은 상위 계획이 소유한다.

검증에는 세 종류 통합 순위, PDRN 대소문자 병합, 상품명과의 합산 분리, 복수 상품 검색,
미등록 초성·조각 비노출, 클릭 재검색, 사전 교체 후 과거 성공 입력 재해석을 포함한다.

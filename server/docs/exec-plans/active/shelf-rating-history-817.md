# 선반 평가 이력 (#817)

2026-10-19 설계, 2026-10-20 기록 규칙 확정. 기준은 `origin/dev`의 `bdc5450b`이고 작업 브랜치는
`feat/817-shelf-rating-history`다.
이슈: https://github.com/woowacourse-teams/2026-poudy/issues/817

## 목표

선반 평가가 바뀔 때마다 그 값과 평가한 회원의 당시 프로필을 한 줄씩 쌓는다. 평가를 고치거나 선반에서
빼거나 회원이 프로필을 바꿔도 이전 기록은 남는다. 쌓은 기록은 유수분 분석 고도화의 학습 데이터로 쓴다.

## 결정

- 이력 테이블 하나만 추가한다. `user_shelf_product`, 선반 API, 성분 분석은 바꾸지 않는다(사용자 결정).
- 전성분은 따로 저장하지 않고 제품 ID만 남긴다(사용자 결정). 리뉴얼한 제품은 새 제품 ID로 적재하고,
  제품 행은 지우거나 ID를 바꿀 수 없으므로(V1 트리거) 제품 ID가 곧 그 처방이다. 같은 제품 ID의
  전성분이 재적재로 바뀌는 경우는 데이터 정정뿐이라 고친 값을 쓰는 편이 맞다. 이슈 체크리스트 2번은
  이 결정으로 대신한다.
- 성별·나이대·피부 타입·민감성 피부 여부를 기록 행에 값으로 복사한다. 회원 행을 참조하지 않는다(사용자 결정).
- 기록 시각은 한국 시간 날짜까지만 저장한다(사용자 결정). 탈퇴 회원의 기록을 익명으로 남기려면
  정확한 시각이 다른 기록과 맞춰 볼 단서가 되지 않아야 하기 때문이다.
- 탈퇴 회원을 파기할 때 기록의 회원 ID만 비우고 나머지 값은 남긴다(`ON DELETE SET NULL`, 사용자 결정).
- 분석에는 회원·제품·프로필마다 최신 평가 하나만 쓴다(사용자 결정). 평가를 여러 번 고친 사람의 의견이
  여러 번 세어지지 않게 하려는 것이다. 나이가 들거나 피부 타입이 바뀐 뒤 다시 평가한 것은 다른 맥락의
  기록이라 따로 센다. 각 줄에 최신 여부를 두므로 회원 ID를 지운 뒤에도 이 규칙이 지켜진다.
- 다른 프로필로 다시 평가해도 그 제품의 마지막 기록에서 30일이 지나기 전이면 새 표가 아니라 고친 것으로
  본다(사용자 결정). 프로필을 바꿔 가며 표를 늘리는 것을 사용자 API에서 막지 않고 기록 규칙으로 제한한다.
  API에서 막으면 피부 타입을 잘못 골라 고치려는 회원까지 막히기 때문이다.
- 선반에서 빼거나 프로필만 바꿀 때는 기록하지 않는다(사용자 결정). 뺀 제품의 이전 기록은 그대로 남는다.
- 백필하지 않는다. 운영에서 선반을 쓴 회원이 없으므로 배포 뒤 평가부터 쌓으면 된다(사용자 결정).
- 조회 API를 만들지 않는다. 분석은 DB를 직접 읽는다(사용자 결정).
- 이력 기록에 실패해도 선반 평가는 저장한다(사용자 결정). 이력은 분석용이라 사용자의 평가를 막을 만큼 중요하지
  않다. 같은 트랜잭션 안에 세이브포인트를 두고 이력 쓰기만 되돌린 뒤 오류 로그를 남긴다. 비동기 처리는 트랜잭션과
  연결이 하나 더 들고, 같은 회원의 연속 수정 순서와 평가 순간의 프로필을 따로 보장해야 해서 택하지 않았다.

## 1. 스키마

새 Flyway 마이그레이션 `V25__user_shelf_product_history.sql`로 `user_shelf_product_history`를 추가한다.
병합 전에 dev에 같은 번호가 생기면 다음 번호로 옮긴다.

| 열 | 타입 | 내용 |
| --- | --- | --- |
| `id` | BIGINT IDENTITY | 기본 키. 같은 회원·제품 기록의 순서를 정한다 |
| `user_id` | BIGINT NULL | `"user"(id)` FK, `ON DELETE SET NULL` |
| `product_id` | BIGINT NOT NULL | `product(id)` FK |
| `usage_status` | VARCHAR(20) NOT NULL | 사용 상태 |
| `rating_preference` | VARCHAR(20) NULL | 호불호 |
| `rating_moisture_level` | DOUBLE PRECISION NULL | 수분감 |
| `rating_oil_level` | DOUBLE PRECISION NULL | 유분감 |
| `gender` | VARCHAR(10) NULL | 기록할 때의 성별 |
| `age_range` | VARCHAR(20) NULL | 기록할 때의 나이대 |
| `skin_type` | VARCHAR(20) NULL | 기록할 때의 피부 타입 |
| `is_sensitive_skin` | BOOLEAN NULL | 기록할 때의 민감성 피부 여부 |
| `recorded_on` | DATE NOT NULL | 한국 시간 기록 날짜 |
| `is_current` | BOOLEAN NOT NULL | 회원·제품·프로필의 최신 평가인지 |

- 사용 상태와 평가 값의 CHECK는 `user_shelf_product`와 같은 범위를 쓴다.
- 프로필 열에는 CHECK와 FK를 두지 않는다. V17에서 피부 타입 `SENSITIVE`를 없앴듯 코드가 바뀌어도
  과거 기록은 당시 값 그대로 남아야 한다. 값은 Java enum에서만 들어온다.
- `created_at`·`updated_at`을 두지 않는다. 정확한 시각을 남기지 않기로 했고, 줄을 쓴 뒤 바뀌는 값은 최신
  여부와 회원 ID뿐이다. 날짜 열은 `_at`으로 끝나지 않으므로 `ErdCloudSchemaTest`의 시각 타입 규칙에
  걸리지 않는다.
- `(user_id, product_id)` 인덱스를 둔다. 마지막 기록 조회, 최신 표시 끄기, 회원 행을 지울 때의 `SET NULL`이
  이 인덱스를 쓴다.
- 회원 ID가 있고 최신인 줄은 (회원, 제품, 성별, 나이대, 피부 타입, 민감성)마다 하나만 있도록 부분 유일
  인덱스를 둔다. 프로필 열의 NULL도 같은 값으로 본다(`NULLS NOT DISTINCT`). 회원 ID가 빈 줄은 서로 다른
  회원의 기록일 수 있으므로 인덱스에서 뺀다.

## 2. 기록 규칙

`ShelfService`의 담기·수정이 회원 행을 잠근 트랜잭션 안에서 기록한다. 프로필 변경도 같은 회원 행을
잠그므로, 기록한 프로필은 평가를 저장한 순간의 값이다. 기록은 세이브포인트 안에서 하므로 실패하면 이력 쓰기만
되돌리고 평가는 저장하며 오류 로그를 남긴다. 배치는 없다.

### 새 줄을 쓰는 때

| 요청 | 기록 |
| --- | --- |
| 담기·수정 성공 | 새 줄. 사용 상태·평가 값·프로필이 그 회원·제품의 마지막 기록과 모두 같으면 쓰지 않는다 |
| 이미 담은 제품 담기(409), 선반에 없는 제품 수정(404) | 없음 |
| 선반에서 빼기 | 없음. 이전 기록은 남는다 |
| 프로필 변경 | 없음. 이전 기록은 당시 프로필로 남는다 |

### 최신 표시

새 줄은 늘 최신이다. 새 줄을 쓸 때 이전 줄의 최신 표시를 다음 규칙으로 끈다. 둘 다 해당하면 둘 다 끈다.

1. 같은 프로필의 최신 줄이 있으면 끈다. 같은 프로필로 다시 평가한 것은 이전 평가를 고친 것이다.
2. 프로필이 달라도 그 제품의 마지막 기록 날짜와 오늘의 차이가 30일 미만이면, 마지막 기록의 최신 표시를
   끈다. 프로필을 바꾼 직후의 다시 평가는 같은 의견을 고친 것으로 본다.

어느 규칙에도 해당하지 않으면 이전 줄은 그대로 최신으로 남고, 새 줄이 새 프로필의 표가 된다.

| 경우 | 결과 |
| --- | --- |
| 20대 지성으로 평가하고, 5년 뒤 30대 건성으로 다시 평가 | 두 표가 모두 남음 |
| 피부 타입을 잘못 골라 평가하고, 그날 고친 뒤 다시 평가 | 고친 값으로 한 표 |
| 프로필을 매일 바꿔 가며 다시 평가 | 계속 한 표 |

표를 늘리려면 그 제품 평가를 30일 넘게 멈췄다가 다른 프로필로 평가해야 하므로, 한 사람이 한 제품에서
한 달에 한 표 넘게 늘릴 수 없다.

## 3. 코드 배치

- `shelf.domain`: 기록 한 줄(`ShelfRatingRecord`)과, 새 줄을 쓸지와 어느 줄의 최신 표시를 끌지 정하는
  규칙(`ShelfRatingHistory`)을 둔다. 두 기록의 날짜 차이가 30일 미만인지는 `ShelfRatingRecord`가 판단하고, 이력은 마지막
  기록 선택과 교체 대상 결정을 맡는다. 정렬과 입력 복사는 `ShelfRatingHistory.of`에서 끝내고 내부에는 정렬된 Map
  하나만 둔다. 동일 프로필 비교는 불변 클래스 `RaterProfile`이 소유한다. 평가한 순간의 프로필은 `User`에서
  꺼내되, 코드가 나중에 바뀌어도 과거 기록을 읽을 수 있게 당시 코드를 문자열로 둔다. `shelf`는 이미
  `user.domain.User`에 의존하므로 기능 사이 의존 방향이 새로 생기지 않는다.
- `shelf.repository`: 이력 저장소(`ShelfRatingHistoryRepository`)가 회원·제품의 최신 기록 조회, 새 줄 추가,
  최신 표시 끄기를 맡는다. `ShelfRatingRecord`의 저장용 스칼라 값만 읽고 내부 `Rating`·`RaterProfile`은 탐색하지
  않는다. 스칼라 접근자는 영속성 경계에 필요하므로 유지하며 도메인 판단에는 사용하지 않는다. SQL 타입과 열 매핑은
  저장소에 둔다.
- `ShelfRatingHistoryService`: 회원 프로필과 그 제품의 기록을 읽어 도메인 규칙에 넘기고 결과를 저장한다.
  `Propagation.NESTED`로 평가 트랜잭션 안에 세이브포인트를 둔다. 오늘 날짜는 `Clock`으로 정한 한국 시간 날짜를
  쓴다. 30일 비교와 저장이 같은 날짜를 쓰고, 테스트에서 날짜를 고정할 수 있다.
- `ShelfService`: 담기·수정에서 `ShelfRatingHistoryService`를 부르고, 실패하면 예외를 잡아 오류 로그만 남긴다.
  같은 빈 안의 호출은 프록시를 거치지 않아 세이브포인트가 생기지 않으므로 기록을 별도 서비스로 나눴다. 빼기는
  이력을 건드리지 않는다.
- `user` 패키지와 `UserRetentionService`는 바꾸지 않는다. 파기는 FK의 `ON DELETE SET NULL`이 처리하므로
  `user`가 `shelf`를 알 필요가 없다.

## 4. 개인정보

- 회원으로 있는 동안 기록은 회원 ID와 이어져 있고, 선반에서 빼도 남는다. 회원이 삭제를 요구하면
  운영자가 회원 ID로 찾아 지운다.
- 탈퇴 30일 뒤 파기 작업이 회원 행을 지우면 기록의 회원 ID가 빈다. 최신 표시는 남으므로 한 표 규칙은
  유지되고, 그 뒤로는 특정 회원의 기록을 찾을 수 없다.
- 개인정보 처리방침(`client/app/privacy/page.tsx`)과 `client/README.md`의 법정 문서 절도 같은 브랜치에서
  고친다(사용자 결정). 탈퇴 후 보관을 처리방침에 공개하기 전에는 이 기능을 운영에 배포하지 않는다.
- nginx 접속 기록(3개월 보관)에는 IP 주소, 요청 시각, 제품 ID가 든 경로가 남아, 파기 직전 기록은 날짜와 제품
  ID로 IP 주소와 맞춰 볼 여지가 있다. IP 주소만으로는 사람을 알 수 없고 기간도 짧아 위험이 작다고 보고
  처리방침의 "개인을 알아볼 수 없는 통계 자료" 문구를 유지한다(사용자 결정).

   행으로 넣을 수 없다. 적재기가 이런 리뉴얼을 어떻게 넣는지 확인해야 "제품 ID가 곧 처방"이라는 전제가 선다.

   이 날짜를 쓰므로, 배포 전에 새 시행일과 사전 안내 여부를 정해야 한다.

## 하지 않는 것

- 전성분 스냅샷, 기존 평가 백필, 조회 API
- 선반에서 빼기와 프로필 변경 자체의 기록
- 프로필 변경을 막는 사용자 API 제한. 기록 규칙의 30일 기준으로 대신한다.
- 프로필 변경 횟수 기록. 악용이 보이면 그때 추가한다.
- 성분 분석 직전 결과(`user_shelf_analysis_ingredient`)의 이력

## 검증

- 도메인: 마지막 기록과 같을 때 생략, 같은 프로필 덮기, 30일 직전·당일의 다른 프로필 평가, 두 규칙이
  함께 해당하는 경우
- 저장소: 저장 값과 날짜, 최신 표시 끄기, CHECK와 부분 유일 인덱스 위반 거절
- 서비스: 담기·수정에서 기록, 409·404·빼기·프로필 변경에서 기록 없음, 기록 중 SQL 오류가 나도 평가는 저장되고
  이력만 되돌아가며 오류 로그가 남는지
- 프로필을 바꾼 뒤에도 이전 기록의 프로필 값이 그대로인지
- `deleteWithdrawnBefore`로 회원 행을 지운 뒤 회원 ID만 NULL이고 나머지 값과 최신 표시가 남는지, 익명이 된
  줄끼리 부분 유일 인덱스에 걸리지 않는지
- 기존 `ShelfServiceConcurrencyTest`, `ArchitectureTest` 통과
- `ErdCloudSchemaTest`의 테이블·열·기본 키 목록에 새 테이블 추가
- `ARCHITECTURE.md`의 Shelf·User 절 갱신
- `sh ./scripts/verify.sh`. API가 바뀌지 않으므로 OpenAPI와 common 생성물도 바뀌지 않아야 한다.

## 기록 실패 처리 변경 (2026-10-20)

- 이력 기록 실패가 선반 평가까지 막지 않도록 바꿨다. `ShelfRatingHistoryService.record`가 `NESTED`로 세이브포인트를
  두고, `ShelfService`가 예외를 잡아 오류 로그를 남긴다.
- 서비스 테스트는 같은 프로필의 최신 표시 끄기를 막아 최신 평가 유일 인덱스 위반이라는 실제 SQL 오류를 낸다. 평가가
  커밋되고 이력은 이전 줄만 남으며 오류 로그가 찍히는지 확인한다. `NESTED`를 빼면 이 테스트가 실패하는 것도 확인했다.

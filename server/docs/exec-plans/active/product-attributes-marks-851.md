## 범위

속성 정의를 여러 대분류에서 공유하고, 제품의 속성값은 필터에만 사용한다.
제품별 응답은 직접 부여한 Mark만 `marks`로 제공한다. **표식 필터·선택지·개수 집계는 만들지 않는다.**
SNS 핫템, 복수 표식 탐색, 관리 API, 속성·표식 이름의 검색어 매칭(#853)은 제외한다.

## 현재 코드에서 유지할 계약

- `ProductQueryRepository`는 검색 후보, 목록, count, 선택지를 공통 SQL로 계산한다.
- 첫 페이지에만 `filterOptions`를 제공하고, 기존 최상위 집계 필드는 유지한다.
- 최신 dev의 피부 타입·민감성 그룹 내부 OR 규칙을 유지한다. 새 속성 그룹과는 AND다.
- 목록은 `ProductCard`, 상세는 전체 제품 로더를 사용한다. 목록을 위해 상세 로더를 호출하지 않는다.
- 표식은 목록·상세뿐 아니라 검색 제안·유사 제품·위시리스트·선반에서도 공통 조회 경로를 쓴다.

## 저장 구조와 초기 데이터

이슈의 ERD대로 `attribute`, `category_attribute`, `attribute_value`,
`product_attribute_value`를 추가한다. 대분류 소유 FK를 `attribute`에 두지 않는다.

| 항목 | 결정 |
| --- | --- |
| 속성 식별 | `attribute.code` 전역 UNIQUE, 값은 `(attribute_id, value_code)`로 식별 |
| 제품별 값 | PK `(product_id, attribute_id)`, 허용값에 복합 FK |
| 적용 범위 | `(제품 소분류의 parent_id, attribute_id)`가 `category_attribute`에 존재 |
| 미등록 | 제품별 연결 행 없음. YES/NO 선택값을 추가하지 않음 |
| 표시 순서 | `category_attribute`, `attribute_value`에 각각 `display_order >= 0`, 기본값 0 |
| 시각·이름 | 기존 한국 시간 저장 규약 유지. 표시명 내부 공백 허용, 공백뿐인 이름 금지 |

초기 정의는 다음 세 가지다. 대분류별로 정의를 복제하지 않는다.

| 속성 | 값 |
| --- | --- |
| `UV_FILTER_TYPE` | `MINERAL`, `ORGANIC`, `HYBRID` |
| `WASHABILITY` | `EASY_WASH` |
| `WATER_RESISTANCE` | `WATERPROOF` |

고정 정의·값은 마이그레이션으로 등록하고, 선케어 연결과 제품별 값은 검증된 데이터 적재로 처리한다.
테스트용 선케어 ID를 운영 ID로 사용하지 않는다. 테스트 카테고리는 `afterMigrate` 콜백에서 생성되므로
속성 연결용 테스트 데이터도 카테고리 생성 이후에 넣는다.

카테고리 적용 범위는 Java 검증에만 맡기지 않고 DB 검증 트리거로 보장한다.
제품값 등록, 제품 카테고리 변경, 소분류 부모 변경, 허용 속성 연결 변경·해제를 검증한다.
무효값이 남는 변경은 거절하고, 삭제·재등록이 필요하면 같은 트랜잭션에서 명시적으로 처리한다.

동시 적재의 기본안은 관련 쓰기를 `SERIALIZABLE` 트랜잭션으로 제한하고 DB에서도 이 조건을 검사하는 것이다.
대상은 제품별 속성값·카테고리 허용 관계 쓰기, 제품 카테고리·카테고리 부모 변경이다.
최종 적용 범위는 지연 제약 트리거로 확인하고, 직렬화 실패(`40001`)는 적재 트랜잭션 전체를 재시도한다.
일반 제품 읽기는 현재 `REPEATABLE_READ`를 유지한다. 초기 데이터 적재와 테스트도 같은 쓰기 규칙을 따른다.
근거: [PostgreSQL 트랜잭션 격리](https://www.postgresql.org/docs/15/transaction-iso.html#XACT-SERIALIZABLE).

## API 설계안

기존 `GET /api/products`, `GET /api/products/count`에 `attributes` 반복 파라미터만 추가한다.

```http
GET /api/products?attributes=UV_FILTER_TYPE:MINERAL&attributes=WASHABILITY:EASY_WASH&page=1
```

- HTTP 경계에서 `속성코드:값코드`를 쌍으로 파싱한다. 코드는 공백·구분자 `:`를 허용하지 않는다.
- 속성 그룹 안은 OR, 서로 다른 그룹과 기존 필터는 AND다. 카테고리 미지정 상태에서도 사용할 수 있다.
- 생략은 조건 없음이다. 빈 값·형식 오류·동일 쌍 중복·존재하지 않는 속성/값은 400 `INVALID_QUERY_PARAMETER`다.
- 유효한 속성이 선택 카테고리에 적용되지 않는 경우는 정상적인 0개 결과다.
- 서버가 속성 코드를 내부 ID로 일괄 해석한다. 목록과 count에서 같은 검증·판정 경로를 사용한다.
- `ProductQuery.hasFilters()`에도 속성 조건을 반영해 검색 로그의 필터 여부를 유지한다.

`filterOptions`에는 `attributes`만 추가한다. 기존 브랜드·카테고리·피부 필드는 유지한다.

```json
{
  "attributes": [
    {
      "attributeCode": "UV_FILTER_TYPE",
      "name": "자외선 차단 유형",
      "values": [
        { "valueCode": "MINERAL", "name": "무기자차", "productCount": 12 }
      ]
    }
  ]
}
```

기존 `badges` 필드는 `marks: [{code, name}]`로 변경한다. 속성값을 표식으로 변환하거나
제품별 속성 표시 배열을 추가하지 않는다. `filterOptions.attributes`는 필터 선택지로 유지한다.

## 필터 SQL과 선택지 집계

`ProductQueryRepository`의 후보 단계에서 선택한 속성 그룹별 일치 여부를 계산한다.
속성 조건을 후보의 WHERE에서 먼저 적용하지 않는다. 그 경우 자기 조건을 제외한 집계가 불가능해진다.

- 목록/count: 선택한 모든 속성 그룹이 일치하는 제품만 포함한다.
- 속성 A 선택지: A 조건만 제외하고 나머지 검색·필터를 유지한 후보에 각 값을 적용해 센다.
  `productCount`는 해당 값의 제품 수이며, 현재 OR 선택에 추가한 뒤의 전체 결과 수는 아니다.
- 브랜드·카테고리·피부 선택지를 계산할 때는 모든 속성 조건을 유지한다.
- 공유 속성은 코드 기준으로 한 그룹만 반환한다. 같은 속성·값 집계에서 제품을 중복 계산하지 않는다.
- 양수 후보와 현재 선택값을 합쳐 응답한다. 선택값은 0개여도 이름과 함께 유지한다.
- 단일 대분류 문맥은 연결의 `display_order`, 복수 대분류·전체 검색은 속성 코드순이다.
  값은 `display_order`, 동률은 값 코드순이다.
- 기존처럼 첫 페이지에서만 선택지를 계산한다. 정렬과 검색 관련도는 유지한다.

속성 선택값은 조인으로 목록 행을 늘리지 않도록 그룹별 EXISTS 또는 일치 그룹 집계로 판정한다.
`(attribute_id, value_code, product_id)` 인덱스를 기본 후보로 두고 실제 실행 계획으로 확정한다.

## 표식 조회

`product` 기능 안에 속성 선택·그룹화 모델을 두고 공통 제품 로더에서 직접 표식을 조회한다.
별도 최상위 기능 패키지나 관리용 서비스는 만들지 않는다.

- `ProductFilterRequest` → 속성 선택 모델 → `ProductQuery`: HTTP 경계에서 쌍으로 파싱하고 SQL에는 검증된 선택값을 전달한다.
- 속성 정의 조회 저장소: 코드·값의 일괄 존재 검증과 선택지 메타데이터 조회를 담당한다.
- 공통 표식 로더: 페이지 대상의 `mark/product_mark`만 일괄 조회한다.
  카드·상세·검색 제안 경로가 같은 `ProductLoader`의 조회를 사용한다.
- 직접 표식은 기존 `DAISO` 코드와 표시명을 유지한다. 알 수 없는 기존 데이터는 임의로 버리지 않는다.
- 표식은 코드의 C 정렬순으로 반환하고, 표시명이 같은 다른 코드는 유지한다.
- 도메인은 `Mark`, 응답 DTO는 `MarkResponse`로 표현하고 표시명 내부 공백을 허용한다.

## 기존 배지의 전환과 배포

현재 최대 마이그레이션은 V25다. 첫 변경은 V26부터 시작하되 구현 시 번호 충돌을 다시 확인한다.
운영 배지 코드·제품 연결 목록은 저장소에 없으므로 실제 이관 매핑을 추정하지 않는다.

1. 첫 배포: 속성 테이블을 추가하고 기존 `badge/product_badge`를 원본으로
   `mark/product_mark` 조회 뷰를 제공한다(`badge_code AS mark_code`). 새 서버의 읽기를 새 이름으로 전환한다.
   기존 서버와 적재 경로는 원래 테이블을 계속 사용해 데이터 원본을 하나로 유지한다.
2. 구버전 종료 후: 적재 경로 전환을 확인하고 별도 배포의 마이그레이션에서 뷰를 제거한 뒤
   실제 테이블·컬럼을 `mark/product_mark/mark_code`로 변경한다. 두 단계를 같은 배포에 넣지 않는다.
3. 기존 속성 배지의 제품값 이관은 코드 매핑·속성당 값 충돌·카테고리 적용 범위를 먼저 확인한다.
   구버전 종료 후 제품값으로 옮기고 기존 속성 표식 연결을 정리한다. 다이소 연결과 시각은 보존한다.

뷰는 우선 조회 계약이다. `ON CONFLICT` 등을 사용하는 기존 적재를 뷰로 자동 전환하지 않는다.
표시를 바꾸는 값·연결·표시명 변경은 영향 제품의 `updated_at`을 같은 적재 트랜잭션에서 갱신한다.

## 구현 순서·검증

1. 저장 제약·초기 정의·호환 조회 뷰와 마이그레이션 검증을 먼저 추가한다.
2. 요청 파싱·일괄 검증, 목록/count 조건과 속성 선택지 집계를 추가한다.
3. 공통 표식 로더를 연결하고 `marks` 응답과 속성 필터의 분리를 확인한다.
4. OpenAPI·공용 타입·저장 계약 문서를 갱신하고 `sh ./scripts/verify.sh`를 실행한다.

필수 검증은 속성당 단일 값·복합 FK, 여러 대분류 공유·잘못된 대분류,
카테고리 변경/허용 해제와 값 등록의 동시 실행, 같은 그룹 OR·그룹 간 AND,
기존 피부 OR·성분 포함/제외와의 조합, 목록/count 일치, 자기 조건 제외·0개 선택 유지·후속 페이지 생략,
속성값 미표시·기존 다이소 데이터 보존·구버전 DB 조회 호환성이다.
쿼리 수는 페이지 제품 수에 따라 증가하지 않아야 하며 실행 계획도 확인한다.

## 검증 결과

- 로컬 PostgreSQL 18.3, UTF-8 한국어 로케일의 작업 전용 DB를 사용했다.
- 최종 sh ./scripts/verify.sh 통과: 전체 테스트 1,522개, 실패·오류·건너뛰기 0개.
- 클라이언트는 응답 계약에 필요한 참조·fixture·mock만 변경했다. 전체 타입·린트·포맷 검사와
  테스트 170개 파일 1,508개, 로컬 테스트 API를 사용한 프로덕션 빌드를 통과했다.
- OpenAPI·공용 타입 드리프트, Spotless·Checkstyle, 전체 빌드를 함께 확인했다.
- 이관 정의 누락 거절, 기존 연결 시각 보존, 실제 표식 테이블 전환도 통과했다.
- 페이지 크기 1과 20에서 조회 횟수가 같은 것을 검증했다.
  초기 실행계획 점검에서는 소규모 테스트 데이터에서 3.717ms였으며 운영 성능으로 일반화하지 않는다.
  실행계획 점검은 수동 진단으로 남기고 회귀 테스트에서는 조회 횟수만 검증한다.
- OpenAPI·TypeScript 생성물은 생성 태스크로 갱신했고 직접 편집하지 않았다.
- 리뷰 후 속성 존재 확인은 저장소, API 오류 판단은 서비스로 분리했다.
  잘못된 입력은 목록에서 전체 사례, count에서 대표 사례만 확인해 요청을 14회에서 8회로 줄였다.
- 전체 테이블·컬럼 순서·PK 목록을 복제하는 검증은 제거했다. 공통 시각 타입 검사는
  `TimestampSchemaTest`로 옮기고, 실제 PK·FK 제약 동작 테스트는 유지했다.

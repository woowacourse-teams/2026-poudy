## 상태와 범위

서버 기능을 구현했다. 최신 검증 결과는 [구현 검증 기록](search-keyword-verification.md)을 따른다. 이 문서는 집계·저장·노출 계약을 소유한다.
제공된 사전의 읽기 전용 사용 계약은 [대표어 사전 사용 계획](search-keyword-dictionary.md)을 따른다.

정규화된 검색 입력을 집계하고, 조회 시 사전으로 완성어에 연결한다. 사전에서 해석되지 않은
입력도 내부 집계에 남기며 공개 노출에서만 제외한다. 카테고리명과 상품 공통 용어를 포함한 일반어·브랜드명·상품명을 함께 제공한다.
사용자별 제출 식별과 중복 카운트 방지는 이번 수정에서 보류한다.

## 사전·메모리·집계 JSON의 역할

| 대상 | 내용 | 서버의 처리 |
| --- | --- | --- |
| search_keywords.json | 입력 표현과 대표어 ID·표시명·적격성 | 읽기 전용 로딩·검증 |
| `bucketSeconds` 버킷별 ConcurrentHashMap | 정규화 사용자 입력 → 횟수 | 요청에서 증가, 조회에서 스냅샷 취득 |
| 집계 JSON(buckets.json) | 시간 버킷별 정규화 입력·횟수 및 저장/복원 메타데이터 | 단일 작성자로 비동기 저장, 시작 시 복원 |

집계 JSON은 사용자 원문이나 대표어별 집계 결과를 저장하지 않는다. 메모리와 같은 정규화
입력 키를 저장한다. 예를 들어 ` 독도  토너 `는 `독도토너`, `PDRN`은 `pdrn`이다.
대표어 ID·상품명으로 키를 치환하거나 사전 해석 결과를 영구 고정하지 않는다.
정규화된 입력 자체가 상품 정식명과 같을 수는 있지만, 이는 입력이 그 이름이었던 경우다.

```text
시작: 사전 형식 검증 → 집계 JSON 검증 → 만료 기록 제외 → 버킷별 ConcurrentHashMap 복원 → 순위 스레드의 첫 계산을 지연 없이 예약 → 요청 수집 시작 (첫 계산 완료 전에는 빈 순위 반환)
수집: 성공한 첫 페이지 검색 → 입력 정규화·수집 허용 확인 → 해당 칸/입력 횟수 +1
저장: 60초마다 메모리 스냅샷(변경 여부와 무관) → 단일 작성자 → 집계 JSON 원자적 교체
조회: 마지막 순위 캐시 반환; 10분 칸 경계마다 완결된 최근 168시간 칸 합계 → 후보 정렬 → 적격 후보 상품 존재 검증 → 상위 10개 게시
```

복원은 저장된 횟수를 초기 상태로 넣는 작업이며 검색 요청을 재실행하거나 횟수에 1을 더하지 않는다.
최대 관측 버킷도 함께 복원한다.
집계 파일이 없을 때만 빈 상태로 시작하고, 손상된 파일은 원본을 보존하며 기동 실패한다.
사전 누락은 별도의 로딩 계약을 따른다.

순위는 일반어(카테고리명·상품 공통 용어 포함), 브랜드명, 상품명을 한 목록에 표시한다. 첫 갱신 전에는 빈 캐시를 반환한다.
대표어 표시 예시와 사용 규칙은 [사전 사용 계획](search-keyword-dictionary.md#공개-표시-구성)을 따른다.
사전에서 미해석인 성공 입력도 내부에 보관하며, 사전 갱신 후 남은 기간의 기록을 다시 해석한다.

## 검색 요청 집계 기준 — 기존 정책 유지

1. `GET /api/products`의 keyword가 있고 `SearchKeyword.value()` 결과가 비어 있지 않아야 한다.
   이 조건은 이미 `ValidSearchKeywordValidator`가 400으로 막으므로 새로 생기는 제약이 아니라
   컨트롤러를 거치지 않는 호출 경로를 위한 방어다.
2. 첫 페이지(`page=0`, 생략 시 기본값 포함)에서 검색이 성공하고 최종 `totalElements > 0`이면 요청당 한 번 기록한다.
3. 필터가 있으면 모든 필터가 적용된 결과 수로 판단한다. 결과 제품 수만큼 횟수를 늘리지 않는다.
4. 후속 페이지, count, suggestions, 상세, 성분, 공유 매칭, 순위 조회는 집계하지 않는다.
5. 동일 사용자의 반복 요청·새로고침·정렬 및 필터 변경에 따른 첫 페이지 재요청은 각각 센다.

`ProductService.findProducts`에서 결과가 완성된 뒤 기록한다. 검색을 다시 실행하거나 로거에
영속화 책임을 넣지 않는다. 클라이언트 `search_submitted` 분석 이벤트와 mode는 현재 제품
API에 전달되지 않으므로 이 집계는 실제 제출 수나 고유 사용자 수를 보장하지 않는다.
자동완성의 상세 바로가기도 검색 집계에 포함되지 않는다. 재검증에서 후속 페이지까지 모두
카운트되는 것은 아니지만 첫 페이지 재요청에 의한 중복은 남는다.

## 입력 집계와 공개 순위의 분리

```text
성공한 첫 페이지 검색 → 기존 SearchKeyword 정규화 → 입력별 메모리 집계 (60초마다 버킷 JSON 저장)
10분 칸 경계 → 완결된 칸 합계 → 대표어별 합산 → 최소 횟수 → 정렬 → 노출 차단
             → 공개 적격성·재검색 확인 → 상위 10개 → 순위 캐시 교체
순위 조회 → 마지막으로 계산한 캐시 반환
```

- 집계 키는 `normalizedQuery`다. 원래 공백·대소문자 표기는 보존하지 않는다.
- 정규화는 표기를 통일한다. 초성 확장·오타 교정·제품 의미 추론으로 집계 키를 바꾸지 않는다.
- 대표어에 연결되지 않은 입력도 성공 검색이면 기록한다. 사전의 누락이 검색 데이터 누락으로 이어지지 않는다.
- 조회에서는 현재 사전의 ACTIVE expressions 전체 일치만 사용한다. 승인된 표현이 제공되어 있으면 그 연결을 따른다.
- 하나의 입력은 최대 하나의 대표어에만 귀속한다. 제품 검색을 브랜드에 추가 합산하지 않는다.
- BRAND·PRODUCT·TERM을 kind만으로 배제하지 않는다. `ranking_eligible=true`인 일반어도 순위에 포함한다.
- 짧은 부분어의 검색 결과가 유일하거나 대표어 검색 점수가 가장 높다는 이유만으로 의도를 확정하지 않는다.
- 미해석·비활성·부적격·재검색 불가 입력은 공개 합산에서 제외한다. 입력 문자열을 응답의 대체 표시명으로 쓰지 않는다.
- 현재 사전의 완성 표시명으로 응답한다. 사전 변경 시 보존 기간 내 입력을 다시 해석한다.
  따라서 별칭 연결 변경은 과거 기간의 공개 순위에도 영향을 준다. 원래 입력별 횟수는 변하지 않는다.

## 기간·정렬·API 계약

- 주입한 `Clock`에서 현재 UTC 시간을 `bucketSeconds` 단위 epoch 경계로 내린 H를 구한다. 애플리케이션에는 이미 `feedbackClock`과
  `productRequestClock` 두 개의 `Clock` 빈이 있고 소비 측이 `@Qualifier`로 고른다. 이 기능의
  Clock도 `searchKeywordClock`으로 등록하고 주입 지점에서 한정자로 지정한다. 무자격 `Clock` 빈을
  추가하지 않는다. 순위는 진행 중인 칸을 빼고 완결된 최근 168시간의 칸으로 집계한다.
  저장소는 여기에 진행 중인 칸 하나를 더해 보관한다. 개별 요청 시각 대신 버킷별 횟수를 보존한다.
- 기본 운영 해상도는 `SearchKeywordPolicy.BUCKET_SECONDS=600`초다. 30초·60초·180초도 테스트
  생성자에서 지원한다. 새 검색은 진행 중인 칸이 끝나는 다음 10분 경계에 순위에 들어간다.
- 공개 가능 대표어별로 연결된 입력의 횟수를 합산한다. 별칭과 정식 표현의 횟수는 이 단계에서 합친다.
- 최소 노출 횟수는 `SearchKeywordPolicy.MIN_COUNT`의 5회다. 미달 기록도 만료까지 보존하고 노출만 제외한다.
- 5회는 초기 노출 정책이다. 통계적 유의성·익명성·고유 사용자 수·조작 방지를 보장하지 않는다.
- 횟수 내림차순, 동률이면 정규화 표시명 오름차순, 마지막으로 대표어 ID 오름차순이다.
- 상위 10개에 1부터 연속 순위를 부여한다. 없으면 `{"items":[]}`를 반환한다.
- `GET /api/search-keywords/rankings`는 요청 파라미터 모델 없이 최대 10건을 고정 반환한다.
- 응답은 필수 `items`와 각 항목의 필수 `Integer rank`, `String keyword`만 가진다.
  횟수·입력·내부 ID·사전 버전은 공개하지 않는다. `limit`으로 크기를 바꾸지 않는다.
- 예상하지 못한 요청 처리 오류는 기존 `GlobalExceptionHandler`의 500 / `INTERNAL_SERVER_ERROR` 계약을 따른다.

## 기간·칸 크기·갱신 시점

| 값 | 설정 |
|---|---|
| 칸 크기 | 10분 |
| 순위 기간 | 완결된 최근 7일(1,008칸) |
| 보관 | 7일 + 진행 중인 1칸(1,009칸) |
| 순위 계산 | 기동 직후 한 번, 이후 10분 칸 경계마다 |
| 파일 저장 | 60초마다(변경 없음) |

- **완결된 칸으로만 계산한다.** 진행 중인 칸까지 넣으면 순위가 검색마다 바뀌어 갱신 주기를
  30초나 1분 같은 근거 없는 숫자로 골라야 한다. 완결된 칸만 쓰면 순위는 칸 경계에서만 바뀌므로
  경계마다 한 번 계산하면 된다. 칸 크기가 곧 갱신 주기다. 대가로 새 검색은 최대 10분 늦게 반영된다.
- **칸은 10분이다.** 올리브영 급상승 검색어가 10분마다 갱신되고, 구글 트렌드도 평균 10분 단위로
  집계한다. 10분은 1시간과 24시간을 모두 나눠떨어뜨려, 이후 24시간 전 순위와 비교하거나 최근
  1시간 급상승을 볼 때 칸 단위로 정확히 자를 수 있다. 최근 1시간을 6칸으로 나눠 한 번에 몰아친
  검색을 거를 여지도 남는다. 1시간 칸은 이 조건을 걸 수 없다.
- **기간은 7일로 시작한다.** 하루 검색량을 아직 모르므로 10위까지 최소 5회를 채우기 쉬운 쪽을 고른다.
  운영 로그로 하루 검색량이 충분한지 확인되면 1일로 줄이는 것을 검토한다. 줄이는 방향은 이미 보관한
  칸으로 바로 계산된다. 다만 지금 복원은 보관 범위보다 오래된 칸이 파일에 있으면 거부하므로,
  기간을 줄일 때는 범위 밖 칸을 버리도록 복원 규칙을 함께 바꾼다.
- **다음 계산은 매번 시계로 다시 예약한다.** 고정 주기 예약은 단조 시계로 돌아 벽시계와 어긋나면
  경계를 놓친 채 한 주기를 통째로 늦을 수 있다. 계산이 끝날 때마다 현재 시각에서 다음 경계까지
  남은 시간을 구해 예약한다. 경계보다 일찍 깨면 같은 칸으로 한 번 더 계산하고 곧바로 다시 예약된다.

검색어 5,000개를 인기 순으로 치우치게 넣은 가상 분포에서 7일치 흐름을 재면 다음과 같다
(로컬 측정, 10분 칸은 보관 193시간 기준이라 실제 1,009칸보다 조금 크다).

| 분당 검색 | 칸 | 저장 항목 | 힙 | 파일 | 파일 쓰기 | 기동 복원 |
|---|---|---|---|---|---|---|
| 10 | 60초 | 93,394 | 9.8MB | 1.88MB | 24.4ms | 216ms |
| 10 | 10분 | 82,790 | 7.8MB | 1.37MB | 16.2ms | 112ms |
| 100 | 60초 | 720,723 | 66.9MB | 11.92MB | 63.6ms | 817ms |
| 100 | 10분 | 540,922 | 50.5MB | 8.92MB | 48.6ms | 589ms |

## 보관·관찰·노출 필터

정규화 입력도 민감한 내용을 포함할 수 있는 검색 데이터다. 신규 집계 파일에는 정규화 입력·시간 버킷·횟수만
보존하고 사용자·세션·IP를 추가하지 않는다. 운영 파일은 서비스 계정으로 접근을 제한하고
Git·배포 산출물·일반 로그에서 제외한다. 메모리는 시간 버킷 경계에서 만료시키고 디스크는 다음 성공 스냅샷 저장에서 만료분을 제거한다.
논리적 보존 기간과 물리적 삭제 지연을 구분하며,
백업을 운용한다면 백업에도 동일한 보존 정책을 적용한다. 저장 실패 중에는 디스크의 만료
기록이 남을 수 있으므로 마지막 저장 성공 시각과 만료 반영 지연을 감시한다.

검색 실행은 `ProductService`가 갖고, 어떻게 끝났는지도 거기서 한 번만 가른다. 로거와 집계기는
판정하지 않고 결과를 받아 각자 기록한다. 두 기록은 모두 예외를 삼켜 응답을 막지 않는다.
`ProductSearchLogger`는 정규화·제어문자 제거·길이 제한을 적용한 검색어를 기록한다.
입력의 생김새로 기록 여부를 가르지 않는다. 이메일·전화번호 패턴 검사는 검색어를 가려 조사 근거만
없애면서 상품번호 검색 같은 정상 입력을 함께 잘랐고, 무엇이 민감한지 판단하지도 못한다.
검색어 수집과 보유 기간은 개인정보 처리방침에 명시하고, 취급 범위는 접근 권한과 만료로 제한한다.
분석 이벤트와 브라우저 최근 검색에도 입력이 존재한다. 이 설계는 시스템 전체의 검색어
미저장을 주장하지 않는다. 기존 로그·분석·브라우저 저장의 보존 정책은 이 파일의 만료와 별개다.

- 결과가 없는 입력은 저장하지 않는다. 결과 1건 이상 조건과 사전 연결 조건이 공개 경로를 막고,
  저장되는 값은 정규화 입력뿐이다. 개인정보 패턴 검사는 두지 않는다. 숫자 아홉 자리 이상을
  전화번호로 보던 검사는 상품번호 검색을 함께 잘랐고, 패턴 목록이 민감 여부를 판정하지도 못한다.
- 보이지 않는 문자는 정규화가 제거한다. 공백과 함께 제어문자·형식문자를 버리므로 `토\u200B너`가
  `토너`와 같은 키가 된다. 거절하지 않고 지우는 이유는, 사용자가 보이지도 않는 문자를 지울 수 없고
  그 입력의 검색 의도는 멀쩡하기 때문이다. 전부 보이지 않는 문자면 정규화 결과가 비어 요청 검증에서 400이 된다.
- 요청 경로에는 형태 검사를 두지 않는다. 빈 값과 길이는 요청 검증이 400으로 막고, 보이지 않는 문자는
  정규화가 지운다. 집계 진입점에는 결과 0건 검사만 남는다.
- 파일 경계에서만 형태를 다시 본다. 집계 스냅샷이 칸 경계·보관 범위·키·횟수를 스스로 검증하고,
  파일을 읽을 때와 복원할 때 같은 검증을 쓴다. 저장 시점의 중복 훑기는 두지 않는다.
- 기존 제품 검색 응답은 그대로 반환한다.
- 공개 직전에는 사전 적격성·재검색 가능성과 별도의 노출 차단 정책을 적용한다.
  차단된 대표어는 대표어별 합산과 정렬 뒤, 상위 10개를 채우기 전에 제거한다. 차단 정책은 사전 파일을 수정하지 않는 별도 설정이다.
- 요청 경로에는 계측을 두지 않는다. 이 저장소에는 메트릭 수집 경로가 없고 Actuator 웹 노출도
  `health,info`뿐이라, 요청·수집·조회 카운터는 인메모리 레지스트리에 쌓이기만 하고 읽을 방법이 없었다.
  해석률과 0건 비율은 검색 로그에서 뽑고, 사전 공백은 내부 보고서의 미해결 입력 목록으로 본다.
  비율보다 어떤 표현이 몇 번 들어왔는지가 사전 확장에 바로 쓰인다.
  수집 경로가 실제로 생기면 그때 읽을 곳을 정하고 다시 넣는다.
- 검색이 예외로 끝나면 집계를 호출하지 않는다. 같은 사실이 검색 로그의 `outcome=ERROR`와
  Actuator의 `http.server.requests` 5xx에 이미 남으므로 별도 실패 카운터를 두지 않는다.
- 결과 0건 요청은 입력을 집계 저장소에 보관하지 않는다. 후속 페이지와 내부 재검색은 관찰에서도 제외한다.
- 저장소 상태와 저장 실패는 60초 maintenance 작업이 숫자 전용 로그로 남긴다. 등록한 gauge는
  수집 경로가 생겼을 때를 위한 것이고, 지금 읽는 경로는 이 로그다.
  검색 입력과 ID는 메트릭 라벨로 사용하지 않는다.
- 미해석 입력의 개선 우선순위는 성공 검색 집계의 조회 스냅샷으로 만든 내부 읽기 전용 보고서로 확인한다.
  미해석 성공 검색을 목록으로 표시한다. 보고서 최소 요청 횟수는
  `SearchKeywordPolicy.REPORT_MIN_COUNT`의 20회로
  노출 임계값과 분리한다. 1 이상의 정수로 검증하고 목록별 상위 100개로 제한한다.
  높은 임계값도 익명성·고유 사용자 수를 보장하지 않으며 보고서 잡음을 줄이는 운영 기준이다.
  보고서는 사전 공백을 찾는 근거이므로 입력을 가리지 않고 들어온 그대로 싣는다. 취급 범위는
  보고서 접근 권한과 보관 기간으로 제한한다.
  공개 API나 일반 로그로 내보내지 않고 보고서도 원본 기간을 넘겨 보관하지 않는다.
- 같은 보고서에 사전을 거치지 않은 상위 목록을 함께 남긴다. 정규화 입력을 대표어로 합치지 않고
  그대로 세어 순위를 매긴 것으로, 사전이 흩어진 표기를 모으고 있는지 아니면 커버리지만 깎고
  있는지 비교할 근거다. 비교가 성립하도록 최소 횟수와 개수는 보고서 임계값이 아니라 공개 순위와
  같은 값을 쓴다. 이 목록은 공개 API로 나가지 않는다.
- 보고서는 검토 근거다. 서버가 발견된 표현을 사전에 추가하거나 자동 승인하지 않는다.
- 보고서는 공개 API·일반 로그로 내보내지 않으므로 제한된 전달 경로를
  정해 둔다. 서버 운영자가 제한된 내부 보고서를 내보내고 사전 관리자가 검색 대조 결과와 함께
  검토한다. 보고서에는 관찰 시작·종료 기간, 카탈로그 버전과 검색 구현 버전, 입력별 횟수,
  관찰 기간과 집계 상태를 포함해 서로 다른 기간의 값을 그대로 비교하지 않게 한다. 내보낸 사본에도
  같은 접근 권한과 보관 기간을 적용하고 저장소에 커밋하지 않는다.
- 표현의 검색 결과 동등성은 실사용 로그 없이도 카탈로그와 검색 구현만으로 기계적으로 확인할 수
  있다. 두 저장소 사이에 본질적인 순환 의존은 없다. 보고서가 제공하는 것은 어떤 표현을 먼저
  검토할지에 대한 우선순위와 실제 사용 근거다. 서버가 발견된 표현을 사전에 추가하거나 자동
  승인하는 경로는 만들지 않는다.

## 시간 버킷 메모리 저장소

순위는 168시간을 `bucketSeconds` 단위 UTC 버킷으로 사용한다. 각 버킷의
`ConcurrentHashMap<String, Long>`이 정규화 입력별 횟수를 소유한다. 요청별 이벤트·시각·로그 큐는
보존하지 않는다.

- 같은 시간·같은 입력이면 기존 Long 횟수만 증가한다. 버킷 추가·만료·횟수 증가는 저장소의
  짧은 ReentrantLock으로 원자적으로 처리한다. 조회는 잠금 안에서 입력별 합계 스냅샷을 얻고
  밖에서 사전 해석·정렬한다. ConcurrentHashMap 자체가 복합 연산 원자성을 보장하지는 않는다.
- 요청과 조회 전에 만료 버킷을 제거하고 60초 주기 작업도 만료를 반영한다. 누적 합계 Map과
  `(버킷, 입력)` 엔트리 수를 저장소 잠금 안에서 갱신하고, 조회는 누적 합계 복사본에서 진행 중인
  칸의 횟수를 뺀 값을 사용한다.
- 시간 변경은 버킷 전체로 처리한다. 같은 요청의 여러 결과 상품 수만큼 횟수를 늘리지 않는다.
- Clock은 저장소 잠금 안에서 읽고 epoch 기준 `bucketSeconds` 경계로 내린 관측 버킷 H를 구한다.
  버킷 기준은 `maxObservedBucketStart = max(이전 값, H)`로 전진만 한다. 잠금 밖에서 미리 읽은
  요청 시각을 비교하지 않고 Instant 단위 요청 순서로 역행을 판정하지 않는다.
- H가 최대 관측 버킷보다 작으면 실제 버킷 역행 경고를 남기고 신규 수집을 잠시 중단한다.
  기존 순위는 최대 관측 버킷 기준으로 계속 제공하고 운영에 기준 시각 지연을 표시한다.
  H가 따라잡으면 재개한다. 같은 시간 안의 작은 시각 역행은 버킷 횟수에 영향을 주지 않는다.
- 복원 시 저장된 최대 관측 버킷을 이어받는다. 이미 만료된 과거 버킷을 시계 역행으로 복구하지 않는다.
  요청별 시각이 없으므로 역행 동안의 응답은 실제 now 기준의 정확한 시간창이라고 주장하지 않는다.

## 자원과 산술 계약

기간 전체 엔트리 수, 버킷별 엔트리 수, 집계 JSON 크기에 임의의 상한을 추가하지 않는다.
실제 비용은 입력 유입과 보관 버킷 수에 따라 달라진다. 파일은 임시 파일에 완전히 기록한 뒤
원자적으로 교체한다. 정규화 키는 UTF-16 300단위까지 검증하고, Long 증가·합산 및 복구 파일의
비정상 횟수 검증은 checked arithmetic으로 처리한다.

## 결과 0건 검색 — 저장하지 않고 로그로 조사한다

결과가 없는 입력은 집계 저장소에 보관하지 않는다. 조사에 필요한 원본은 이미 검색 로그가 갖고
있다. 모든 검색은 `event=search_completed`로 남고 결과 없는 요청은 `outcome=NO_RESULT`로 구분된다.

메모리 저장소를 따로 두지 않는 이유는 둘이다. 같은 정보를 두 곳에 들고 있을 이유가 없고,
데이터 변경마다 프로세스가 재시작되는 배포에서는 메모리 저장소가 보고서 임계값에 닿기 전에
비워진다. 로그는 재시작을 넘어 남고 journald 보존 기간을 그대로 따른다.

조사는 로그를 집계해서 한다. 기간은 필요에 따라 정한다.

```bash
journalctl -u poudy-backend --since '7 days ago' \
  | grep 'outcome=NO_RESULT' \
  | grep -o 'keyword="[^"]*"' | sort | uniq -c | sort -rn | head -20
```

0건 입력은 원인 조사 자료다. 필터 조건을 저장하지 않으므로 제품 부재·필터·오타를 이 자료만으로
확정하지 않는다. 표시용 별칭 추가만으로 검색 엔진의 0건 결과가 해결되지는 않는다.

## 운영 메트릭과 메모리 관찰

검색어 기능은 저장소별 엔트리 수·고유 키 수를 Micrometer gauge로 등록하고, 버킷 수는
maintenance 관찰 로그에 포함하며,
스냅샷 저장 실패 횟수·마지막 성공 시각도 등록한다. Spring Boot Actuator가
제공하는 JVM binder가 있으면 `jvm.memory.*`와 `jvm.gc.*` 메트릭을 함께 사용한다. 애플리케이션은
JVM 메트릭을 별도로 다시 등록하지 않는다.

현재 `application.yml`의 Actuator 웹 노출은 `health,info`만 포함하므로 JVM과 검색어 gauge는
기본 HTTP 엔드포인트로 공개되지 않는다. 운영 메트릭 수집 경로와 노출 범위는 운영 설정에서
결정하며, 이 기능은 임의의 heap 임계값이나 자동 OOM 방지를 약속하지 않는다. 실제 heap 사용량,
GC 증가 추세, 버킷·엔트리·고유 키 증가, 저장 실패와 마지막 저장 성공 시각을 함께 관찰해 용량을 판단한다.
기존 60초 maintenance 작업은 heap used/committed/max, GC 횟수·누적 시간, snapshot failure와
마지막 저장 성공 시각(epoch 초, 성공 전에는 -1)을 숫자 전용 INFO 로그로 남긴다. heap과 GC는 검색어 저장소만이 아니라 JVM 전체 값이며
`event=jvm_resources`로 구분한다. 저장소별 관찰 줄에는 시계 역행 여부를 함께 남겨 역행이
지속되는 동안에도 상태가 드러나게 한다. 로그는 애플리케이션 stdout과 로컬 journal에서
관찰할 수 있지만 중앙 수집·알림은 이 작업 범위에 포함하지 않는다. 무손실 영속성이 필요하면
파일 스냅샷이 아니라 DB 등 별도 저장소로 전환해야 한다.

## 단일 비동기 JSON 스냅샷

순위의 버킷별 횟수만 한 파일에 저장한다. 이벤트별 append·압축·부분 줄 복구·미저장 큐는
필요하지 않다. 전체 스냅샷 쓰기는 남지만 대상은 요청 수 N이 아닌 현재 보관된 E개 항목이다.

- 기본 저장 주기는 60초 fixed-delay다. 바뀐 게 없어도 매번 전체를 다시 쓴다. 한 작성자가
  버킷과 최대 관측 버킷을 같은 잠금 안에서 복사하고 savedAt도 그 잠금 안에서 읽는다.
  savedAt은 max(Clock.instant(), 최대 관측 버킷 시작)으로 두어 역행 중에도 복원 계약을 만족시킨다.
  복사 후 잠금 밖에서 JSON을 스트리밍한다.
- 변경 여부를 세는 번호는 두지 않는다. 전체 쓰기 비용이 항목 1만·5만·20만 개(당시 1분 칸으로 측정)에서
  0.17MB·8ms, 0.85MB·10ms, 3.4MB·14ms라 바뀐 것만 골라 쓸 이유가 없다. 저장 중 들어온 변경은
  다음 주기의 전체 쓰기에 들어간다. 파일 크기는 상품 수가 아니라 검색어 종류와 분산에 따라 커진다.
- 같은 디렉터리의 임시 파일에 직렬화 → 파일 force → 원자적 교체 → 디렉터리 동기화 순서다.
  교체 전 실패는 원본을 보존한다. 교체 후 동기화 실패는 실패로 세고 다음 주기에
  최신 스냅샷을 다시 쓴다. 전체 상태 교체이므로 append 중복 복구 로직이 없다.
- 실패를 작성자 경계에서 처리해 후속 주기를 유지한다. 기존 검색 응답·메모리 집계는 계속
  제공하며 저장 실패·마지막 성공 시각을 관찰한다. 작업을 요청 수만큼 쌓지 않는다.
- 순위 결과는 불변 캐시로 보관하고 파일로 남기지 않는다. 기동 직후 순위 스레드에 복원한 집계의
  첫 계산을 지연 없이 예약한다. 기동은 계산 완료를 기다리지 않으므로 첫 계산 전에는 빈 순위를 반환한다.
  이후 10분 칸 경계마다 바뀐 게 있든 없든 다시 계산한다. 갱신 실패 시 직전 정상
  캐시를 반환한다.
- 변경 감지 번호와 순위 파일은 두지 않는다. 둘 다 계산을 아끼려던 장치인데 아낄 크기가 아니다.
  다시 계산하는 비용은 고유 입력 1천·1만·5만 개에서 0.15ms·0.31ms·2.2ms였고, 재검색 확인까지 포함한
  기동 직후 첫 계산은 상품 472개와 10,384개에서 모두 20ms 안팎이었다. 첫 계산이 상품 수에 비례해
  늘지 않는 것은 재검색 확인이 정렬된 상위 후보에서 10개가 찰 때까지만 돌고, 결과가 나오는 검색어는
  첫 일치에서 멈추기 때문이다. 결과가 없는 검색어의 전체 훑기는 상품 수에 비례해 472개 1ms 안팎,
  10,384개 13ms 안팎이다. 판정은 캐시하므로 같은 대표어를 다시 훑지 않는다.
- 저장량은 매 주기 전체 스냅샷이다. 원본과 임시 파일의 동시 공간 및
  파일시스템 부가 비용은 별도다. 버킷 방식이 무조건 작은 파일이나 O(신규 요청) 쓰기를
  보장한다고 주장하지 않는다.
- 비정상 종료 시 마지막 성공 저장 이후 횟수가 유실될 수 있다. 저장 실패가 이어지면 유실
  구간도 길어진다. 만료 항목의 디스크 삭제 역시 다음 저장 성공까지 지연될 수 있다.
- 현재는 재시작·종료 시 미저장 집계의 유실을 감수한다. 종료 시 최종 저장과 종료 순서·시간
  예산 보강은 이번 범위에서 제외한다. 기존 주기적 JSON 저장·복원은 유지하며, 추후 DB로
  전환할 때 영속성과 집계 보장 수준을 다시 설계한다.

```json
{
  "schemaVersion": 1,
  "savedAt": "2026-09-06T10:34:12Z",
  "bucketSeconds": 600,
  "maxObservedBucketStart": "2026-09-06T10:30:00Z",
  "buckets": [
    {"start": "2026-09-06T10:20:00Z", "counts": {"토너": 42, "독도토너": 7}},
    {"start": "2026-09-06T10:30:00Z", "counts": {"pdrn": 3}}
  ]
}
```

## 경로·복원·배포 계약

- 개발은 server 실행 기준 `./var/search-ranking/buckets.json`, 운영은
  `/opt/poudy/state/search-ranking/buckets.json`을 사용한다. 별도 환경 변수는 추가하지 않는다.
- 보고서 경로가 집계 파일과 겹치면 기동을 거부한다.
- prod에서 상대 경로, resources·카탈로그·애플리케이션 배포 디렉터리 아래 경로를 거절한다.
  WorkingDirectory의 실제 경로도 확인한다. ../와 기존 조상의 심볼릭 링크를 해석하고 사전과
  같은 파일인지 검사한다. 재배포로 교체되는 디렉터리에 런타임 상태를 두지 않는다.
- 기동 시 사전 검증 후 스냅샷을 한 번 복원한다. 파일 없음만 빈 상태다. 잘못된 JSON·버전·
  필수 필드, 중복 JSON 키/버킷, 시작 시각이 칸 경계(10분)에 맞지 않는 버킷, 음수/0/범위 초과 횟수, 비정규화 키,
  구조 오류와 읽기 오류는 기동 실패로 처리하고 원본을 보존한다. 임의 일부 복원은 하지 않는다.
- savedAt보다 뒤 시간의 버킷은 형식 오류다. 현재 H가 maxObservedBucketStart보다 이전이면 앞의 버킷
  역행 정책을 적용한다. 최대 관측 버킷도 칸 경계에 맞고 savedAt 이하인지 검증한다. 보관 칸 수(1,009)를
  넘거나 보관 범위보다 오래된 칸이 있어도 거부한다.
- 대상 파일 검증 후 남은 임시 파일을 정리한다. 손상된 대상 대신 임시 파일을 자동 채택하지 않는다.
  운영 파일시스템의 원자적 이동·force·디렉터리 동기화 지원을 실제 환경에서 검증한다.
- 사용자 요청으로 이번 작업에서는 배포 스크립트·환경 변수를 변경하지 않는다.
  private/output의 검증된 7개 JSON을 개발 resources로 직접 복사했다.
  운영 배포를 실제로 수행할 때의 사전 검증 순서, 서비스 계정의 외부 상태 디렉터리 권한,
  데이터 교체·롤백 전후 상태 보존은 별도 운영 확인 사항이며 완료했다고 주장하지 않는다.
- 단일 JVM과 단일 작성자 배포를 전제로 한다. 다중 인스턴스의 전역 집계는 별도 저장소가 필요하다.
  운영 파일은 Git·JAR에서 제외하고 테스트·API 생성은 임시 디렉터리를 사용한다.
- 스냅샷은 버킷별 집계만 저장한다. 이 형식은 한 번도 배포되지 않은 상태에서 정한 첫 형식(스키마 1)이라
  과거 형식을 읽는 호환 규칙을 두지 않는다. 스키마가 다른 파일은 손상 파일과 같이 기동을 거부한다.

## 구현·성능 검증 기준

실제 배포 설정의 JVM·컨테이너 메모리는 운영 환경 기준으로 별도 관리한다. 순위 저장소와
저장 중 복사본을 포함한 실제 메모리 사용량은 측정해 관찰한다. 이 기능 문서에서 임의의 추가
heap·RSS 예산을 정의하지 않는다.

1. 진행 중인 칸 제외, 완결된 168시간 포함, 한 칸 더 지나면 만료, 칸 경계 전후, UTC 날짜 변경,
   큰 시각 전진·역행과 재개를 Clock 기반으로 검증한다.
2. 같은 쌍에 100만 번 더해도 항목은 하나이고 횟수는 정확한지 확인한다. 동시 기록·조회·만료와
   저장 스냅샷 생성이 버킷/합계/버킷별 항목 사용량의 일관성을 유지해야 한다.
3. 새 시간의 기존 키·기존 쌍 증가·만료 후 회복과 재시작을 검증한다.
4. 저장을 지연시킨 채 새 검색을 기록해 검색이 저장을 기다리지 않고, 저장 중 다시 불린 작성자는
   건너뛰며, 저장 실패는 세고 다음 주기에 다시 쓰는지 검증한다. 저장소는 목으로 대신한다.
   파일 교체의 원자성은 JDK·파일시스템 동작이라 테스트로 재현하지 않고 운영 환경에서 확인한다.
5. 잠금 경합 시 미리 읽은 시각을 쓰지 않음, 버킷 단위 역행/복구와 savedAt 일관성을 검증한다.
   손상·중복 파일의 기동 실패와 원본 보존, 만료 복원·사전 교체 재해석,
6. 실제 입력 및 최대 길이 입력을 채우고 반복 요청률
   1·10·100건/초를 부하 시나리오로 시험한다. 반복 요청률과 새로운 키 유입률을 분리한다.
7. 복사 잠금 p99 10ms 이하, 순위 요청 p95 50ms 이하, 60초 저장 주기 내 정상 저장 완료를
   초기 기준으로 삼는다. 실제 서버 조건에서 기존 검색 p95의
   증가도 기준 대비 5% 이내인지 반복 비교한다. 이는 구현 전 목표이며 달성을 주장하지 않는다.
8. E·K, 추가 live heap/GC·RSS, JSON 크기, 주기당 실제 쓰기량·force 시간·임시 공간,
   복원 시간과 처리량을 기록한다. 결과는 운영 용량 판단 자료로 남긴다.
   파일 제한 안이라는 이유로 메모리·응답 지연 기준을 생략하지 않는다.

## 소비 화면과 커버리지 검증

소비 화면의 제안 위치는 제품 검색 패널의 입력 전 영역이다. 선택 시 응답 keyword로 기존
제품 목록 검색을 수행한다. 이 문서에서는 UI를 구현하지 않으며 서버 구현 후 클라이언트
연결 작업에서 빈 목록·로딩·실패·클릭 재검색을 검증한다. 빈 목록이면 인기 검색어 영역을
숨긴다. 별도 추천어를 제공한다면 “추천 검색어”로 구분하고 가짜 순위·횟수를 만들지 않는다.

정확 일치 사전만으로 짧은 제품 검색의 공개 커버리지가 충분하다고 가정하지 않는다.
제공 사전에는 일반어 116개와 승인 별칭 12개(문자 10, 초성 2)가 있고 카탈로그에서 파생한 초성
표현 271개가 함께 있다. 브랜드의 영문
이름이 없어 영문 브랜드 입력은 구조적으로 미해석이다. 제품 정식 이름으로 연결되는 검색도
있으므로 브랜드·일반어 개수만으로 실제 연결 가능한 수요를 한정하지 않는다. 출시 기준 50%의
통과 여부는 실제 요청 가중 측정으로 판단하며, 사전 키 수나 합성 후보 수로 예측을 확정하지 않는다.

완성어 연결률이 낮으면 먼저 결과 1건 이상인 미해석 입력의 별칭 연결을 검토한다. 그 검토는
실사용 로그를 기다리지 않고도 카탈로그와 검색 구현으로 시작할 수 있다. 보고서는 검토 순서를
정하는 근거이며, 결과가 유일하다는 사실만으로 자동 승인하지 않는다. 서버가 표현을 임의로
보충하지 않는다. 일반어를 포함해도 미등록 부분어는 여전히 숨겨진다.

| 최종 검색 결과 | 사전 연결 | 개선 경로 |
| --- | --- | --- |
| 1건 이상 | 실패 | 완성어에 연결할 별칭 검토 후 성공 검색 표본으로 재측정 |
| 0건 | 무관 | 검색 동작·카탈로그·필터 원인 조사. 표시용 별칭 승인만으로 순위에 반영되지 않음 |
| 1건 이상 | 성공 | 최소 횟수·재검색 가능성·노출 차단 조건 확인 |

0건 입력은 집계 저장소에 기록되지 않고 검색 로그에만 남는다. 이후 검색 동작이나 카탈로그가 개선되어 성공 검색이
발생해야 횟수가 쌓인다. 완성어 연결률의 모집단은
최종 결과 1건 이상인 요청이며, 0건 비율은 별도 지표로 평가한다.

출시 전 브랜드·일반어·완성 제품명·부분어·초성·오타·모호한 입력 표본으로 성공 검색 대비
사전 해석률 및 공개 가능 비율을 측정한다.
총 요청 수/고유 정규화 입력 수를 요청 집중도로 측정하되 이를 실제 중복 요청 배수라고
부르지 않는다. 같은 입력을 여러 사용자가 제출할 수도 있기 때문이다. 별도의 통제된
브라우저 시나리오에서 제출·상세 왕복·캐시 만료·정렬 및 필터 변경별 서버 요청 수를 측정해
실제 제출당 요청 증폭을 확인한다. 식별자 수집이나 런타임 중복 제거는 추가하지 않는다.
합성 표본과 실제 검색 데이터를 구분한다. 합성 고유 입력 해석률을 실제 요청 가중 해석률로
표현하지 않는다. 실제 트래픽이 없으면 공개 커버리지 수치를 주장하지 않는다.

출시 후 7일 단위로 수집 누락률, 성공 요청 중 완성어 연결 비율, 임계값 통과 대표어 수,
빈 응답 비율을 먼저 확인한다. 클라이언트 연동 시에는 노출 대비 클릭률과 클릭 재검색의 0건
비율도 측정한다. 초기 7일을 기준선으로 두고 다음 기간과 비교하되 검색량·사전 변경을 함께
표시한다. 기준선이 없는데 성공률 목표를 달성했다고 표현하지 않는다.

출시 판정의 초기 운영 기준은 다음과 같다. 통계적 보장 대신 출시 보류·재검토의 조건이다.

- 출시 전 최근 실제 성공 검색 표본 200건 이상에서 요청 가중 완성어 연결률 50% 미만이면
  공개 출시를 보류하고 결과 1건 이상인 미해석 입력의 별칭 연결을 검토한 뒤 재측정한다.
  0건 입력은 위 개선 경로로 별도 조사하며 별칭 승인으로 연결률이 개선된다고 판단하지 않는다. 표본이 없으면
  계측/내부 시험만 진행한다. 합성 후보 통과율로 이 기준을 대체하지 않는다.
- 운영에서는 수집·저장 실패와 메모리 사용량을 관찰한다.
  문제가 확인되면 원인과 처리량을 별도로 분석하며 검색어를 조용히 버리지 않는다.
- 출시 첫 7일에 순위 요청이 100건 이상이고 빈 응답 비율이 50% 이상이면 완성어 연결률과
  임계값 통과 항목 수를 함께 점검한다. 성공 검색의 표현 연결 부족이면 별칭을 검토하고,
  0건 검색 증가는 검색 동작·카탈로그·필터 원인으로 분리한다. 연결은 충분하나 횟수가
  부족하면 min-count를 검토한다. 자동 임계값 하향이나 미등록 입력 공개는 하지 않는다.
- 기준 미달이면 이유·개선 조치·재측정 결과를 남긴 뒤 노출 확대를 결정한다. 0건 진단은
  검색 로그의 실제 보존·조회 기간을 기준으로 평가한다.

긴 제품명은 UI에서 줄바꿈/말줄임하되 접근 가능한 전체 이름과 실제 재검색 keyword를 유지한다.
표시만 짧게 자른 문자열로 검색하지 않는다. 같은 브랜드의 여러 항목이 상위에 있어도 현재
횟수순 API에서 임의로 제거하지 않는다. 다양성이나 표시/검색어 분리는 별도 API 정책 변경이다.
완성어로 해석되지 않은 입력의 그대로 노출, 제출 헤더·봇 판별·버킷별 기여 제한은 이번에 추가하지 않는다.

현재 API는 완결된 10분 칸 기준의 7일 누적 인기 순위이며 새 검색은 최대 10분 늦게 반영된다.
칸별 횟수로 구간 비교는 가능하지만
급상승 지표는 최소 모수·비교 구간·0분모 처리가 필요한 별도 기능이며 이번 응답에 섞지 않는다.

## 별칭 보완 작업 범위

[#414](https://github.com/woowacourse-teams/2026-poudy/issues/414)는 API 구현과 함께 초성·부분어의
검색 성공 여부와 사전 연결 여부를 대조하고, 성공 미해석 표현의 별칭 보완을 요청하는 작업을 포함한다.
검증 근거 작성, 0건·모호한 입력 보류, 갱신 사전 적용과 연결 회귀 검증은
[사전 사용 계획](search-keyword-dictionary.md#별칭-보완-및-갱신-사전-적용)을 따른다.
서버는 사전을 읽기 전용으로 사용하며, 제품 초성 검색 지원만으로 완성어 연결이 된다고 판단하지 않는다.

## 구현 순서와 검증

1. 읽기 전용 사전 loader와 해석기를 구현하고 [사전 검증 계약](search-keyword-dictionary.md)을 검증한다.
   최상위 객체를 읽는 경로와 엄격 매퍼, dev 파일 부재 처리, 구조적 사전 검증이 여기에 포함된다.
2. 입력별 메모리 집계·만료·복구를 구현한다. 미해석 입력도 보존되며 0건 검색은 집계 저장소에 들어가지 않고 검색 로그에만 남는지 확인한다.
3. 버킷 JSON 스냅샷의 단일 작성자·복원과 위 동시성·성능 검증을 완료한다.
   정규화 입력 키·횟수 그대로 복원, 복원 중 재집계 없음, 사전 파일 불변을 검증한다.
4. 백그라운드에서 현재 사전으로 공개 순위를 갱신한다. 일반어 포함, 별칭 합산, 모호한 입력 비노출,
   교체 사전으로 과거 입력 재해석, 10분 칸 경계, 4/5회 경계, 동률·빈 목록·상위 10개를 검증한다.
5. 저장 형태 검증, 노출 필터와 내부 보고서를 검증한다. 빈 값·길이 초과·제어문자와 형식문자를 담은
   키가 집계 파일 복원에서 거부되는지 확인한다. 168시간 순위 기간과 진행 중인 칸 보관에 따른 버킷 만료, 결과 0건 입력 미보관,
   보고서 19/20회 경계, 노출 임계값 변경이 보고서에 영향을 주지 않음,
   검색어가 로그와 보고서에 들어온 그대로 남는지 확인한다.
6. ProductService와 연결한다. 기존 첫 페이지 정책과 반복 요청 각각 +1을 유지하고
   count·suggestions·상세·후속 페이지·순위 조회가 집계되지 않음을 확인한다.
7. Controller의 200·500, 필수 필드·최대 10개·횟수 비노출과 설정·경로 검증을 수행한다.
8. 서버 구현 시 API 산출물을 갱신하고 `sh ./scripts/verify.sh`를 통과시킨다.

기능 패키지 `searchkeyword`에 Controller·Service·도메인·저장소·백그라운드 작성자를 둔다.
도메인은 Spring·Jackson·파일 API에 의존하지 않는다. 사전 읽기와 변경 상태 저장을 분리한다.
순위 계산 중 적격성 확인은 도메인의 `KeywordSearch`로 추상화하고, `config`의
`CatalogKeywordSearch`가 제품 카탈로그 검색으로 구현한다. 기동 시에는 호출하지 않는다.
`searchkeyword`와 `product`는 서로 import하지 않는다.
집계 기록은 `ProductService.findProducts`가 결과를 얻은 뒤 호출하는 단방향 연결로 둔다.
저장 실패는 기존 검색 응답과 메모리 집계를 되돌리지 않으며 다음 주기에 재시도한다.
관찰 실패도 제품 검색에 전파하지 않는다. 초기 사전·스냅샷의 형식 오류는 기동 실패로
처리하고 기존 파일을 보존한다. 운영 배포는 외부 상태 디렉터리의 권한과 재배포 후 보존을 확인한다.

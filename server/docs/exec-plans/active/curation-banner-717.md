# 큐레이션 배너 분리 (#717)

2026-10-15 설계, 2026-10-16 구현. 기준은 `origin/dev`의 `8b0c74bb`,
작업 브랜치는 `feat/717-curation-banner`다.
이슈: https://github.com/woowacourse-teams/2026-poudy/issues/717

## 범위

서버에서 배너를 분리하고 슬롯별 조회 API를 만든다. 구 큐레이션 목록 API는 제거한다.
큐레이션 상세 URL·본문·게시 상태·메타데이터와 서버 사이트맵은 유지한다.
클라이언트 화면은 추가하지 않는다. 구 목록 제거로 필요한 API 호출·응답 타입·큐레이션 이동·
사이트맵과 관련 테스트만 전환한다. 새 target의 화면 이동과 STRIP 구현은 별도 작업이다.

## 1. 스키마와 데이터 이전

한 번의 Flyway 마이그레이션으로 다음을 수행한다. 최신 dev 병합 후 다음 버전은 V20이다.

- `banner` 추가: id, slot, title, description, image_url, target JSONB,
  display_order, visible, created_at, updated_at.
- 기존 큐레이션의 배너 정보를 MAIN으로 복사한다. target은
  `{ "type": "CURATION", "curationId": 기존 ID }`이고 기존 순서를 유지한다.
  비노출·이미지 없는 기존 행도 비노출 배너로 옮긴다.
- 이전한 `curation.position`, `banner_visible`, `banner_thumbnail_image_url`과
  관련 제약을 제거한다. 큐레이션 ID·제목·요약·본문·게시 상태·시각은 보존한다.

DB 제약은 필수 값, MAIN/STRIP, target의 객체 형태, 0 이상 순서와 노출 시 이미지 존재를
보장한다. 이미지가 없던 비노출 데이터는 그대로 허용한다. 순서 중복에는 id를 보조 정렬로
사용하며, 연속 순서·DEFERRABLE 순서 제약이나 세부 JSON 검증 함수는 추가하지 않는다.
두 테이블 사이 FK는 두지 않는다.

현재 운영용 배포 스크립트는 기존 서비스를 중지한 뒤 새 서비스를 시작한다.
배너 정보 이전과 구형 컬럼 제거는 같은 마이그레이션에서 처리한다.
이는 동일 DB를 읽는 구형 서버가 모두 중지된다는 전제다. 스크립트만으로 실제 인스턴스 수나
다른 환경의 DB 공유 여부는 알 수 없으므로, 배포 전 이 전제와 구 목록 호출부 전환을 확인한다.

## 2. 배너 모델과 target

`Banner`가 홍보 문구·이미지·슬롯·노출 여부·이동 대상을 소유한다.
`Curation`에서는 배너 필드·검증·목록 조회를 제거하고 게시물 책임만 남긴다.
저장 JSON은 Repository의 codec으로 해석하고 도메인에서 값의 유효성을 검사한다.
기존 큐레이션 코드와 같은 방식이며, 별도 범용 링크 계층은 만들지 않는다.

| target.type | 값과 검증 |
| --- | --- |
| CURATION | 양의 정수 curationId. 노출 시 존재하고 PUBLISHED인 대상만 포함 |
| PRODUCT_LIST | query. 기존 PRODUCT_LINK의 검색 조건 모델·참조 검증을 재사용 |
| EXTERNAL | 절대 HTTP(S) url. 서버는 URL에 접속하지 않고 응답으로 전달 |

PRODUCT_LIST의 query는 기존과 같은 keyword, brandIds, categoryIds,
includeIngredientIds, includeGroupCodes를 사용한다. 새 필터 규칙은 만들지 않는다.

현재 저장 API가 없으므로 저장 서비스를 새로 만들지 않는다.
대신 이슈가 명시한 **저장 시 큐레이션 존재 확인**만 INSERT/target UPDATE 트리거로 검사한다.
공개 상태는 저장 제약으로 묶지 않는다. 다른 target의 세부 검증까지 DB 트리거로 확장하지 않는다.

조회에서 없거나 미게시인 큐레이션과 참조가 무효인 제품 조건의 배너는 제외한다.
제품 검색 결과가 0개라는 이유로는 제외하지 않는다.
저장 JSON 구조 오류는 기존 큐레이션과 동일하게 인프라 오류로 처리한다.
DB 장애를 빈 목록으로 바꾸지 않는다.

## 3. 조회 API

`GET /api/banners?slot=MAIN|STRIP`

- slot 필수, 잘못된 값은 400.
- visible이고 대상이 유효한 배너만 display_order, id 순서로 반환.
- 응답은 `{ items: [{ id, title, description, imageUrl, target }] }`.
- target은 세 타입의 판별 유니온으로 문서화·생성한다. 내부 href는 만들지 않는다.
- `GET /api/curations`와 전용 목록 DTO·사용하지 않는 목록 코드는 제거한다.
- `GET /api/curations/{id}`는 유지한다. 게시 상태로만 접근 여부를 판단한다.

새 banner 패키지에 Controller·Service·Repository와 필요한 도메인을 둔다.
배너 목록 조회에서 큐레이션 blocks를 읽지 않는다.
기존 제품 링크 참조 조회기는 query를 재사용할 수 있을 만큼만 수정한다.
현재 메서드는 블록 UUID에 묶여 있으므로 검색 조건의 참조 조회 부분을 재사용한다.
배너를 가짜 큐레이션 블록으로 변환하지 않는다.

상세 하단은 MAIN을 재사용하고 현재 curationId를 가리키는 항목을 제외한다.
STRIP 위치는 홈 피부타입 메뉴 아래로 정했지만 이번 서버 작업에 화면 구현은 포함하지 않는다.

필수 클라이언트 전환은 기존 MAIN·상세 하단의 CURATION 항목 표시까지다.
목록 키는 banner.id, 이미지 필드는 imageUrl, 상세 경로와 현재 항목 제외는
target.curationId를 사용한다. PRODUCT_LIST·EXTERNAL은 후속 화면 이동 구현 전까지
기존 카드에 표시하지 않는다. 구 응답을 흉내 내는 별도 호환 계층은 만들지 않는다.

## 4. 구현과 확인

1. 스키마·기존 데이터 이전, 배너 모델·target 해석·슬롯별 조회를 구현한다.
2. 기존 큐레이션의 배너 책임과 구 목록 API를 제거한다.
3. 서버 OpenAPI와 common 생성물을 갱신하고 위의 필수 클라이언트 전환을 수행한다.
   사이트맵 전환에는 기존 `/api/sitemap`의 curations를 쓴다.
4. 데이터 이전·본문 보존, 슬롯/순서/숨김, 세 target의 검증, 저장 시 큐레이션 존재 검사,
   배너 없는 공개 상세 200·미게시/미존재 상세 404를 테스트한다.
   기존 카드에서는 banner.id와 curationId가 서로 다른 사례로 이동·제외가 올바른지 확인한다.
5. 서버 저장 문서·아키텍처를 변경 내용에 맞게 갱신하고 `sh ./scripts/verify.sh` 및
   필요한 클라이언트 계약 검사를 수행한다.

  함께 사용한다. 필수 필드·자료형·중복 키 검증과 도메인 불변식을 유지했다.

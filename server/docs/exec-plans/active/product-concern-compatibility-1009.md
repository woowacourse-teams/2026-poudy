# 제품 고민별 성분 계약 전환 (#1009)

## 이번 범위

서버의 고민 정의·계산과 `concernGroups` 응답, OpenAPI/공통 생성물, 기존 화면·SEO의
새 응답 사용, 고민별 아코디언과 전성분 바텀시트까지 구현한다.

고민명 아코디언은 서버의 고민·효능 순서와 고민 단위 항목을 그대로 표시한다.
성분군 시트에는 누른 항목의
실제 구성 성분을 넘기고, 구성품이 바뀌면 이전 시트 상태를 초기화한다.

## 전환 계약과 배포

- 서버는 기존 `skinEffectGroups`와 새 `concernGroups`를 함께 제공한다.
- 전환 중 두 필드는 OpenAPI에서 선택 필드다. 실제 새 서버는 둘 다 배열로 제공한다.
  프론트는 `concernGroups`가 있으면 빈 배열도 그대로 사용하고, 없을 때만 구 필드로 표시한다.
  고민 정의와 효능 매핑을 프론트에 복제하지 않는다.
- 서버를 먼저 배포하고 프론트를 배포한다. 구 `skinEffectGroups` 응답은 계속 지원한다.
- 공통 상세 fetch에 계약 버전 쿼리를 붙여 기존 하루 캐시와 분리한다. 회원별 요청은 바꾸지 않는다.
- 새 프론트 배포와 공통 상세 캐시의 24시간 경과, 구 클라이언트의 전환을 확인한 뒤
  #1009 최종 계약 단계에서 `skinEffectGroups`와 프론트 fallback을 제거하고
  `concernGroups`를 필수로 바꾼다. 이번 호환 단계에서 제거하지 않는다.
- 모바일은 웹뷰를 사용하며 저장소 안에서 구 필드를 직접 소비하는 코드는 발견되지 않았다.

## 검증

- 7개 고민·9개 연결, 전체 효능, 중복·묶음·정렬과 빈 결과를 도메인 테스트로 검증한다.
- DTO의 개별/그룹 직렬화, 고정 type과 oneOf/discriminator 생성물을 확인한다.
- 프론트에서 구/신/혼합 응답, 빈 새 결과, SEO와 기존 성분 시트 동작을 검증한다.
- 서버 verify, 클라이언트 타입 검사·린트·관련 테스트·빌드를 실행한다.

## 고민 단위 성분 병합 (2026-11-04)

- 응답은 `ConcernGroupResponse { code, name, effects: [{code, name}], items: ConcernItemResponse[] }`다.
  성분은 고민 직하의 `items` 한 곳에 제공하고 `effects[].items`는 제거한다.
- 매핑 효능의 성분 ID 합집합을 전성분 순서로 정렬하고 중복을 제거한 후 기존 성분군 묶음 정책을 적용한다.
  서로 다른 효능에 연결된 성분도 같은 고민의 성분군으로 묶을 수 있다. 고민의 순위·최대 3개 선택은 유지한다.
- 프론트는 헤더에 효능명 목록을 표시하고 본문에는 서버의 `items`를 한 목록으로 표시한다.
  성분군 시트의 피부 작용은 실제 구성 성분의 전체 정보에서 구해, 고민의 효능을 모든 성분에 잘못 붙이지 않는다.
- 상세 fetch의 계약 쿼리를 `concerns-v3`로 올려 이전 효능별 응답 캐시와 분리한다.
  서버·프론트의 새 고민 계약은 함께 전환하며, 이미 배포된 구 `skinEffectGroups` 소비자는 그대로 지원한다.
- `sh ./scripts/verify.sh`와 서버 전체 1,817개 테스트 통과(실패·오류·스킵 0).
  프론트 관련 121개 테스트·타입 검사·변경 파일 린트·포맷 검사·프로덕션 빌드 통과.
  실제 API·Swagger와 브라우저에서 고민 단위 목록, 중복 제거, 성분군의 실제 구성 성분 표시를 확인했다.

## 노출 정책 변경 (2026-11-03)

- 모든 성분·매핑 효능을 계산한 뒤 고민별 고유 성분 ID 수 내림차순으로 최대 3개를 반환한다.
  효능 간 같은 성분은 한 번만 세며 성분군 내부의 실제 성분도 각각 센다.
  동률은 `Concern` 정의 순서를 유지한다. 빈 효능·고민 제외와 효능·항목의 내부 순서는 그대로다.
- 정렬·개수 제한은 도메인 정책으로 유지하고 OpenAPI에는 명시하지 않는다.
  공통 생성물에서도 배열 개수 제한을 제거한다.
- 서버를 먼저 배포한다. 상세 fetch의 계약 쿼리를 `concerns-v2`로 올려 고민 전체를 반환하던 하루 캐시와 분리한다.
- 당시에는 단일 효능의 본문 제목만 생략했다. 이후 2026-11-04 기획에서 효능 개수와 관계없이 고민 단위 목록으로 바꿨다.
- 변경 후 `sh ./scripts/verify.sh`와 서버 전체 1,816개 테스트 통과(실패·오류·스킵 0).
  프론트 관련 87개 테스트, 변경 파일 린트, 타입 검사와 프로덕션 빌드 통과.
  로컬 API·Swagger에서 최대 3개와 정렬을 확인하고 단일 효능의 중복 제목 제거도 브라우저에서 확인했다.

## 리뷰 후 리팩토링

- 전체 working tree와 직접 연결된 소비자를 독립 리뷰한 결과 실행 가능한 결함 없음.
- `Concern`이 자신의 효능 매핑 순서와 존재하는 효능의 선택을 처리한다.
  호출자가 `effectCodes` 목록을 꺼내 선택하던 코드를 제거했다.
- 항목 DTO의 `type`은 생성자 입력에서 제거하고 DTO 종류에 따라 고정 직렬화한다.
  잘못된 discriminator를 만드는 경로와 중복 검증을 제거했다.
- SEO의 효능명 조회는 칩 DTO를 만들지 않는다. 화면과 같은 중복 제거 기준을 공유한다.
  성분군 시트는 화면에서 이미 계산한 효능 목록을 재사용한다.
- 생성 OpenAPI를 이전 결과와 대조했다. 고정 enum과 중복되는 정규식 제거 외에
  JSON 필드·필수 여부·허용값·oneOf/discriminator의 계약 변화는 없다.
- 리팩토링 후 `sh ./scripts/verify.sh`와 서버 전체 1,815개 테스트 통과.
  프론트 관련 106개 테스트, 타입 검사, 변경 파일 린트·포맷 검사와 프로덕션 빌드 통과.
- OpenAPI에는 고민·효능·성분·성분군의 구체적인 예시와 두 항목을 함께 보여 주는 `items` 예시를 제공한다.
  개별 성분·성분군 모두 `type`을 첫 번째 필드로 직렬화하며, 생성 스키마와 실제 로컬 응답에서 확인했다.
  보완 후에도 `sh ./scripts/verify.sh`와 서버 전체 1,815개 테스트를 통과했다.

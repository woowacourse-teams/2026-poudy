### 2. 찾은 이유의 순서와 집계

- 순서(`match_reason`): 0 직접 일치(붙여 쓰기·자모 분리 포함) > 1 표기 변형·브랜드 별칭 > 2 미완성 해석 > 3 카테고리.
  한 방법이 여러 규칙을 함께 썼다면 순서가 가장 뒤인 규칙의 이유를 쓴다.
- 한 논리 단위를 여러 방법으로 찾았다면 가장 좋은 이유를 고른다. 상품의 이유는 맞은 단위들의 이유 중 가장 약한 것이다.
  일부 단위만 맞은 상품은 맞은 단위만으로 정한다.
- tier는 채택한 대체 표현과 실제 이름을 비교해 정한다. 원래 입력(`썬크림`)과 상품명(`선크림`)은 비교할 수 없기 때문이다.
  예외는 둘이다.
  - 미완성 패턴은 이름 전체와 맞아도 tier 0을 받지 않는다(가장 좋아도 1).
  - 카테고리만으로 맞은 단위는 모든 단위가 맞으면 tier 2, 일부면 3이다.
- 기본 순서: 전체 일치(tier ≤ 2) → `match_reason` → tier → token_ratio ↓ → 최근 조회수 ↓ → 정규화 이름 길이 → product_id.
  이유를 tier보다 먼저 비교하므로, 대체 표현이 tier 0을 받아도 직접 일치보다 앞에 오지 않는다. #795에서는 이유가 모두 0이라
  기존 순서와 같다.

### 3. 가짜 일치를 막는 방식: 경계 표현

자모열 자체에 역할과 음절 끝을 표시해, 자모열의 부분 문자열 일치가 곧 판정이 되게 한다.

- 초성·중성·종성을 서로 다른 조합형 자모(U+1100~, U+1161~, U+11A8~)로 쓴다. 받침 ㄹ과 초성 ㄹ이 다른 글자가 되어
  `닭`이 `달고`에 맞지 않는다.
- 음절마다 끝에 음절 끝 표시(U+3164)를 붙인다. `크리`가 `크림`에, `고`가 `과`에, `달`이 `닭`에 맞지 않는다.
  이 문자는 정규화가 지우는 글자라 입력에 나타나지 않고, 이 DB의 로케일에서 트라이그램 단어 문자다.
- 후보 수집용 `doc_jamo`는 필드 사이에 `|`를 넣어, 서로 다른 이름의 경계에서만 맞는 후보(`지블`)를 만들지 않는다.
  등급과 토큰 판정은 지금처럼 이름 필드 안에서만 한다.
- 자모마다 원문 UTF-16 시작 위치(`*_jamo_pos`)를 함께 저장하고, 맞은 자모 구간을 그대로 강조 구간으로 쓴다.
  자모의 역할과 복합 자모 안의 순서는 코드포인트와 순서로 이미 드러나므로 따로 저장하지 않는다.
- 후보를 넓게 모은 뒤 위치 배열로 다시 확인하는 원문 검증 방식은 고르지 않았다. 후보가 넓어지고 후보마다 절차적 확인이 든다.
- #796은 마지막 음절의 끝 표시만 풀면 된다. 아래에서 `(끝)`은 음절 끝 표시다. `크리`는 `크(끝)리` 뒤에 무엇이 와도 맞고,
  `고`는 `고` 뒤에 자모가 더 오는 `과`와, `달`은 `달…`(`닭`) 또는 받침을 다음 초성으로 옮긴 `다(끝)ㄹ…`과 맞는다.

### 4. 분해 수준: 복합모음과 겹받침을 나눈다

- 복합모음 ㅘㅙㅚㅝㅞㅟㅢ는 ㅗㅏ·ㅗㅐ·ㅗㅣ·ㅜㅓ·ㅜㅔ·ㅜㅣ·ㅡㅣ로, 겹받침 11개 ㄳㄵㄶㄺㄻㄼㄽㄾㄿㅀㅄ은 두 자모로 나눈다.
- 쌍자음(ㄲㄸㅃㅆㅉ, 받침 ㄲ·ㅆ)과 ㅐ·ㅔ·ㅒ·ㅖ는 나누지 않는다. 서로 다른 모음과 쌍자음을 같게 만들지 않는다.
- 그래서 `고ㅏ`=`과`, `달ㄱ`=`닭`이다. #796의 `고→과`, `달→닭`도 3번의 끝 표시 풀기 하나로 처리된다.

### 5. 초성과 음절이 섞인 입력: 지원하지 않는다

- 입력은 두벌식 자판이 조합하는 방식대로 묶는다. `ㅋㅡㄹㅣㅁ`→`크림`, `크리ㅁ`→`크림`, `수ㅂㅜㄴ크림`→`수분크림`,
  `ㄷㅏㄹㄱ`→`닭`, `닭ㅣ`→`달기`. 모음 없이 남은 자모(`ㅋ림`의 ㅋ)는 호환 자모 그대로 두어 이름 자모열과 맞지 않는다.
- 토큰 전체가 초성일 때만 기존 초성 검색을 쓴다. 섞인 토큰에 초성 검색을 적용하지 않는다.
- 자판 규칙이므로 `크ㄹ`은 `클`이 되어 두 모드 모두 `클렌징` 같은 이름을 찾는다. `크ㄹ`로 `크림`을 찾는 것은 #796의 받침 이동이다.

## DB 구조

#795가 만든 구조다. 뒤 이슈는 이 구조에 더한다.

| 객체 | 역할 |
|---|---|
| `product_search_analyze(text, read boolean)` | 정규화·두벌식 조합·자모열·원문 위치. OUT 인자 `norm`, `jamo`, `pos` |
| `product_search_compose(text)` | 조합한 정규 문자열. 사전 표현(#797·#798)도 이 함수로 통일해 저장한다 |
| `product_search_jamo(text)` | 자모열 |
| `product_search_query_tokens(text)` | 상품 검색 토큰(원래 순서, 원문, 정규·읽기·자모, 초성 여부) |
| `product_search_matches(text)` | 검색 본체. 반환 타입 `product_search_match`에 찾은 이유와 위치를 담는다 |
| `product_search_range(jamo, pos, needle)` | 자모열에서 맞은 구간을 UTF-16 원문 구간으로 바꾼다 |
| `product_search_document`의 `*_jamo`, `*_jamo_pos`, `doc_jamo`, `doc_read_jamo` | 이름 필드별 자모열·위치와 후보 수집용 자모열(GIN 트라이그램 인덱스) |
| `ux_product_search_document_product`, `ix_product_search_document_brand` | 상품 ID 고유 인덱스, 브랜드 ID 인덱스 |

- `search_products`(값 1~4개), `search_products_page`, `search_products_core`는 시그니처와 반환 모양을 유지하고 본문만
  `product_search_matches`를 따른다. `product_search_hit`은 이전 함수의 반환 타입으로 남긴다.
- 이름 필드의 읽기 자모열(`product_read_jamo`, `brand_read_jamo`)은 낱자 읽기로 펼칠 영문이 없어 원형과 같으면 NULL이다.
  NULL이면 원형 자모열과 질의의 읽기 형태를 비교해 V2의 원형·읽기 네 가지 비교와 같은 결과를 낸다. 후보 수집용 `doc_read_jamo`는
  늘 채운다.
- 초성 토큰은 이름 자모열과 비교하지 않는다. 초성 열은 음절만 초성으로 바꾸고 호환 자모는 그대로 두므로, 이름에 그 초성
  문자열이 그대로 있으면 초성 열에도 있다. 영문 브랜드명은 초성 열이 없어 V2처럼 그대로 비교한다.
- `REFRESH MATERIALIZED VIEW`는 PostgreSQL 17부터 `search_path`를 `pg_catalog, pg_temp`로 고정한다. 검색 문서가 부르는 함수는
  SQL 표준 본문(`RETURN`, `BEGIN ATOMIC`)으로 쓰거나, `$$` 본문 안에서 사용자 정의 타입·함수를 이름으로 찾지 않아야 한다.
  처음에 `product_search_form` 복합 타입으로 결과를 돌려주다 갱신이 `type "product_search_form" does not exist`로 실패해 OUT 인자로 바꿨다.
- `search_norm`, `search_jamo`, `search_query_tokens`, `search_correct_query`, `search_match_range`, `search_product_names`와
  `product_search_document`의 기존 열·인덱스는 바꾸지 않는다. 성분 검색과 공유 텍스트 매칭이 쓴다.
- 오타 교정에는 토큰마다 조합한 검색어(`product_search_query_text`)를 넘긴다. 자모를 나눠 쓴 토큰을 오타로 보지 않게 하고,
  세 글자 미만 판단도 조합한 길이로 한다.
- 검색 뷰는 이름을 유지한 채 다시 만들었으므로 카탈로그 적재기의 `REFRESH` 절차는 바뀌지 않는다. 새 materialized view는 없다.

`setup.sh`는 V1·V2 → 스냅샷 적재 → V3부터 지정한 버전까지 적용한다. 기존 DB에 새 마이그레이션을 더하는 경로와 같다.
`upgrade-check.sh <poudy-private 경로> <이전 버전> <새 버전> <out-dir>`은 이전 버전 DB의 검색 결과를 받아 두고 새 마이그레이션을
더한 뒤 다시 받아, 결과가 바뀐 질의만 보여 준다. 회차별 p95는 `summarize.py`, 실행 계획 요약은 `summarize_plans.py`로 본다.
dev 기준선 측정은 스냅샷 7분, 20배 29분이 걸렸다. 뒤 이슈에서 모드 함수로 호출이 바뀌면 `make_sql.py`의 `SUGGEST`·`CATALOG`만 고친다.

### 질의 세트와 허용 시간

`queries.tsv`의 25개 질의 × 5개 호출이다. 허용 시간은 회차별 p95 중 가장 큰 값이다. 바꾼 뒤의 p95가 스냅샷과 20배 모두
이 값을 넘지 않아야 한다. 전에는 못 찾던 입력은 예전에 빈 결과를 빨리 돌려준 시간과 비교하지 않고, `limits.tsv`에 적은
완성형 질의의 허용 시간을 쓴다. 뒤 이슈가 새 입력을 더하면 대응하는 완성형 질의도 질의 세트에 있어야 하고, 없으면
바꾸기 전 코드에서 그 질의를 먼저 잰다(#795에서 `수분크림`·`토너`를 이렇게 더했다).

### JIT

로컬 PostgreSQL 18.6은 JIT를 켜 두면(`jit = on`, `jit_above_cost` 100000) dev의 `search_products('크림', 0, 20, 3)`도 약 0.9초가
걸린다. 검색 SQL의 예상 비용이 기준을 넘어 실행마다 JIT 컴파일을 하기 때문이다. 끄면 13ms다. staging 진단 기록
(`load-tests/results/search-facets-diagnostic-2026-10-15`)은 JIT를 켠 서버에서 쟀지만 실행 계획 요약의 JIT 항목이 비어 있다.
운영·staging DB에서 JIT가 실제로 동작하는지는 확인하지 않았다. 동작한다면 지금도 상품 검색마다 큰 지연이 생긴다.

  15개와 3개로 달랐다. 측정 중에는 같은 PC에서 테스트나 빌드를 돌리지 않는다.

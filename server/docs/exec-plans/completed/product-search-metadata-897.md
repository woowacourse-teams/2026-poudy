# 속성값·마크 검색 구현 설계 (#897)

- 상태: 구현·로컬 검증 완료. 실제 배포와 운영 데이터 적재는 수행하지 않았다.
- 기준: `feat/897`, `origin/dev`의 `7ac09478897b10fb0248f3c6aa1b98362e3d84c8`
- 이슈: https://github.com/woowacourse-teams/2026-poudy/issues/897
- 관련: #853, #888, #886

## 검색 계약

기존 `keyword`에 제품명·브랜드명과 같은 검색 근거로 속성값 표시명과 마크 이름을 추가한다.
검색어의 각 조건은 네 종류의 필드 중 어디에서든 만족할 수 있고, 모든 조건은 **동일 제품에서 AND**로 충족해야 한다.

| 입력 | 필요한 조건 |
| --- | --- |
| `무기자차` | 기존 이름 검색으로 일치하거나 실제 연결된 속성값 이름으로 일치 |
| `라운드랩 무기자차` | 브랜드 등에서 `라운드랩` 일치 AND 속성값 등에서 `무기자차` 일치 |
| `다이소 무기자차 선크림` | 마크 등에서 `다이소` AND 속성값 등에서 `무기자차` AND 기존 이름에서 `선크림` 일치 |

- 제품명에 `무기자차`가 있는 기존 결과도 유지한다. 검색어를 발견했다고 특정 필드로 강제 해석하지 않는다.
- 새 매칭은 `product_attribute_value → attribute_value`, `product_mark → mark`의 실제 연결을 사용한다.
  속성 그룹명·내부 코드·카테고리 허용 관계는 새 검색 대상이 아니다. 제품 연결이 없는 정의는 결과를 만들지 않는다.
- 기존 정규화·부분 일치·초성·영문 읽기와 단독 검색의 브랜드+제품명 붙여쓰기 규칙을 유지한다.
  새 필드를 섞은 복합 검색은 공백으로 구분한 조건을 각 필드에서 찾는다.
  `라운드랩검증독도 무기자차`처럼 붙여쓴 브랜드·제품명을 다시 분해해 조합하는 지원은 이번 범위에 추가하지 않는다.
  `다이소무기자차`의 임의 분해도 추가하지 않는다.
- `선크림`의 카테고리·동의어 확장은 #799의 범위다. 이 작업에서는 현재 제품명 검색 기준을 사용한다.
- 명시적 필터는 검색과 AND다. 같은 속성 필터 안의 OR는 유지한다.
  검색어 `무기자차 유기자차`는 두 필수 조건이고, 필터에서 두 값을 선택한 OR와 구분한다.

## 변경 경계

현재 `ProductQueryRepository.find/count/suggest`와 `ProductRepository.hasSearchResults`는
`search_products(..., 2)`를 공유한다. Java에서 검색어를 나누거나 결과를 사후 필터링하지 않고,
DB의 공통 후보 판정을 확장한다. Controller·요청 파라미터와 기존 필터 집계 구조는 유지한다.

### 속성값·마크 조회

새 SQL 뷰 `product_search_metadata_term`은 표시명 하나당 한 행을 제공한다.
종류(`ATTRIBUTE_VALUE`/`MARK`), 연결 키, 원문, 정규화·읽기·초성을 담고 제품 연결은 검색 시 조인한다.
속성값은 복합 키 `(attribute_id, value_code)`, 마크는 코드로 연결한다.

일반 뷰로 소수의 정의를 먼저 매칭하고 제품 연결을 조회한다. 제품별 이름을 거대한 문자열로 합치지 않는다.
기존 `product_search_document`와 인덱스는 유지한다. 새 데이터는 검색 시 읽으므로
속성값·마크 이름과 연결의 등록·변경·삭제에 별도 REFRESH가 필요하지 않다.
제품명·브랜드명은 기존 검색 뷰 갱신 절차를 계속 따른다.

### 후보·AND 판정·정렬

1. 기존 `search_query_tokens()`로 공백·유니코드 공백을 처리하고 중복 토큰을 제거한다.
2. 기존 이름 후보와 새 속성값·마크 후보를 제품 ID로 합친다.
3. 각 제품의 각 토큰이 이름 또는 실제 연결된 속성값·마크에 맞는지 판정한다.
   토큰별로 한 번만 세어 `matched = token_count`를 검사한다.
4. 기존의 질의 전체 일치·유효한 브랜드+제품명 조합 경로를 보존하고,
   새 복합 일치는 모든 토큰이 충족된 경우에만 등급 2로 포함한다.
5. 최종 후보를 확정한 뒤 정렬·페이지·전체 개수·선택지를 계산한다. 제품 ID는 중복되지 않는다.

현재 완전/접두/포함 일치의 0/1/2 등급을 새 표시명에도 적용한다.
전체 질의가 단일 필드에서 맞으면 해당 등급, 여러 필드에 걸친 전체 토큰 일치는 2다.
등급 뒤의 조회수·제품명 길이·ID 순서를 유지해 기존 이름 결과끼리의 순서가 바뀌지 않게 한다.
기존 등급 3 내부 호출의 일부 일치 호환성은 유지하되, 공개 제품 검색 경로는 계속 최대 등급 2를 사용한다.

### 오타 교정

제품 전용 교정 함수에서 정의된 속성값·마크 이름에 맞는 토큰도 보존한다.
해당 값의 제품 연결이 없다고 `무기자차`를 `유기자차`로 교정해 다른 제품을 반환하지 않는다.
기존 PRODUCT 어휘와 현재 연결된 새 표시명의 공백 토큰을 교정 후보로 사용한다.
새 어휘도 실시간 조회해 연결 삭제 뒤 교정 후보만 남지 않도록 한다.
일반 검색에서 전체 일치가 없을 때만 교정하며, 교정 뒤에도 같은 AND 판정을 적용한다.
성분 검색과 공통 정규화 규칙은 바꾸지 않는다.

### 제품 제안과 배포 호환성

- `ProductMatchField`에 `ATTRIBUTE_VALUE`, `MARK`를 추가한다.
  `match.text`는 실제 표시명, 범위는 해당 원문 기준 UTF-16 반열림 구간이다.
- 복합 검색의 `match`는 기존처럼 대표 일치 하나만 제공한다.
  기존 이름 검색의 대표 일치 정보를 우선 유지하고, 이름 일치가 없으면 속성값 → 마크 순으로 선택한다.
  같은 종류에서는 긴 일치 토큰, 입력 순서, 정의 키 순으로 결정한다.
  속성값에만 맞았는데 제품명에 가짜 강조 구간을 만들지 않는다.
- 기존 서버는 새 `matchField`를 `ProductMatchField.valueOf()`로 읽지 못한다.
  새 Flyway 마이그레이션은 기존 함수를 덮어쓰지 않고 `search_products_v2`와 전용 core/page/교정 함수를 추가한다.
  새 서버의 네 조회 경로를 함께 v2로 전환한다. 기존 함수·반환 타입·검색 뷰는 유지한다.
- OpenAPI와 `common/api.zod.*`를 재생성한다. client의 enum 검증도 새 계약을 받아야 하므로
  생성 계약을 포함한 client 배포를 서버 전환과 조율한다. 기존 UI의 제품명 강조 분기는 유지할 수 있다.
- #886은 현재 브랜치에 미구현이다. 먼저 병합되면 연관검색어와 이동한 선반 제안 경로도 같은 검색 함수를 사용하고,
  제안어를 다시 검색했을 때 결과가 나오는지 검증한다.

## 구현 순서와 검증

1. 현재 다음 버전은 V33이다. 구현 시 최신 버전을 재확인하고 새 마이그레이션에 뷰·v2 함수를 추가한다.
   운영 제품별 속성값을 추정해 적재하거나 V2/V26을 수정하지 않는다.
2. SQL 통합 테스트로 속성값·마크 단독 및 이름과 섞인 AND 검색을 먼저 검증한다.
3. Repository 호출과 match enum·API 설명을 갱신하고 생성물을 재생성한다.
4. 제품 API 통합 테스트로 아래 결과·개수·집계·강조·갱신 동작을 검증한다.
5. 검색 문서와 `ARCHITECTURE.md`의 기존 검색 대상 설명을 갱신하고 `sh ./scripts/verify.sh`를 통과한다.

| 검증 사례 | 확인할 결과 |
| --- | --- |
| 이름에 단어가 없는 무기/유기/혼합자차 제품 | 실제 연결된 값으로만 새 결과에 포함 |
| `다이소 무기자차 선크림`과 조건 순서 변경 | 세 조건을 모두 만족하는 같은 제품만 반환 |
| 조건별로 서로 다른 제품만 존재 | 빈 결과, count 0, 존재 확인 false |
| 같은 토큰이 이름·여러 마크에 중복 일치 | 한 조건을 여러 번 세지 않고 제품도 한 번만 반환 |
| 미등록·그룹명·내부 코드·이름에만 있는 단어 | 새 연결 매칭은 제외하고 기존 이름 매칭은 유지 |
| 초성·부분 입력·오타 교정 뒤 복합 검색 | 기존 입력 규칙과 모든 조건 AND 유지 |
| 검색+명시적 필터, 여러 페이지 | 목록/count 일치, 중복·누락 없음 |
| 속성 선택지 자기 그룹 해제 | 명시적 필터만 해제하고 keyword 조건은 유지 |
| 표시명/연결 등록·변경·삭제 | REFRESH 없이 새 검색·교정·제안에 반영 |
| 새 필드로만 일치하는 제품 제안 | 실제 표시명과 유효한 UTF-16 범위 반환 |
| 마이그레이션 후 기존 함수 호출 | 구버전 enum에 없는 필드가 나오지 않음 |

기존 `MarkQueryTest.doesNotSearchByMarkCodeOrName`은 이름 검색을 허용하는 요구로 분리·갱신하고,
코드만으로 매칭되지 않는 검증은 유지한다. 기존 `PostgresSearchTest`와
`ProductSuggestionAndSearchTest`를 회귀 기준으로 사용한다.
제품 수·연결 수를 반영한 대표 데이터의 후보 조회·count·페이지 쿼리는 `EXPLAIN (ANALYZE, BUFFERS)`로 확인하고,
추가 인덱스는 실행 계획에서 필요가 확인될 때 도입한다.

## 구현 결과와 검증

- V33에 일반 메타데이터 뷰와 v2 검색·교정 함수를 추가했다. 기존 core를 재사용해
  이름 검색의 조합·등급·강조 판정을 복제하지 않는다. 구버전 함수도 유지한다.
- 메타데이터의 토큰 일치와 대표 표시 정보를 제품별로 한 번 집계한다.
  초기 구현의 제품별 반복 CTE 조회는 실행 계획 측정 후 제거했다.
- 후속 마크 테이블 전환은 검색 뷰를 해제·재생성하도록 보완하고, 전환 전후 동일한 마크 검색을 검증한다.
- 신규 검색 테스트는 19개로 정리했다. AND 조합·실제 연결·교정·중복·집계·갱신·강조를 검증한다.
  단어 순서·공백·빈 입력 등 공통 검색 규칙은 기존 테스트에 맡긴다.
  목록/count/제안/존재 확인의 일관성은 대표 복합 검색의 성공·실패 사례에서 확인한다.
- 전용 PostgreSQL 17.11에서 제품 1,240개와 속성값·마크 연결을 임시 생성해
  `EXPLAIN (ANALYZE, BUFFERS)`로 확인했다. 개선 후 한 차례 측정은 기존 이름 검색 126ms,
  새 이름 검색 88ms, 속성값 검색 56ms, 네 단어 복합 검색 112ms였다.
  로컬 합성 데이터의 단일 측정이며 운영 지연이나 부하 처리량을 보장하는 수치는 아니다.
- OpenAPI·공통 생성 계약을 재생성했다. `sh ./scripts/verify.sh` 통과:
  최신 `dev` 반영 후 서버 테스트 1,625개, 실패·오류·스킵 0개.
  생성물 드리프트·Spotless·Checkstyle·구조 검사·빌드 통과.
- client의 경로 타입을 재생성한 뒤 `tsc --noEmit --incremental false`가 통과했다.
  client 소스는 변경하지 않았으며, 새 match enum을 담은 공통 생성 계약은 배포 시 함께 반영한다.

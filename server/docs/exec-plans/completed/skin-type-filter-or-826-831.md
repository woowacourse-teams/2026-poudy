# 피부 타입 다중 선택과 민감성 후보 계산

## 확정한 동작

- #826과 #831을 함께 구현한다. 건성·지성·복합성과 민감성을 하나의 필터 그룹으로 보고 OR로 결합한다.
- 검색어·브랜드·카테고리·성분·유수분 등 다른 필터 그룹은 기존처럼 AND로 결합한다.
- 기존 `skinType` 파라미터를 반복해 여러 값을 받고, `sensitiveSkin=true`도 같은 OR 조건에 넣는다.
  아무 타입도 고르지 않고 민감성도 선택하지 않으면 피부 조건을 적용하지 않는다.
- 목록·개수·페이지·결과 집계는 같은 제품 집합을 사용하고 중복 제품을 만들지 않는다.
- 피부 선택지를 구할 때는 피부 타입과 민감성 조건을 모두 제외한다. 다른 선택지는 피부 OR 조건을 지킨다.
- 첫 페이지의 `filterOptions.sensitiveSkin`은 피부 선택지 범위에 민감성 제품이 있는지를 나타낸다.
- #832의 피부 타입 시트도 서버 후보에 맞춘다. 민감성 후보 표시, 빈 상태, 후보에서 빠진 선택의
  개별 해제를 구현하고, 테스트·목 응답을 같은 계약으로 정리한다.

## 커밋 단위

1. 피부 타입 다중 입력과 민감성 OR 검색, 목록·개수·페이지 회귀 검증, 관련 문서와 생성 API 계약.
2. 민감성 후보 응답, 피부 그룹을 제외한 후보 계산 회귀 검증, 관련 문서와 생성 API 계약.
3. 프론트의 피부 후보 표시·빈 상태·선택 해제, 목 API와 테스트 데이터, 화면 명세와 검증 기록.

## 검증

- 단일·다중·미선택, 민감성 단독·다른 타입과 혼합, 겹치는 제품, 잘못된 입력.
- 검색어·브랜드·카테고리·성분·유수분과의 AND, 페이지·목록·개수의 일치.
- 민감성 선택 전후 피부 후보 유지, 다른 필터로 좁힌 후보, 민감성 후보 없음과 빈 결과.
- 각 단계의 관련 테스트와 API 재생성, 최종 `sh ./scripts/verify.sh`.

## 진행

- OR 검색과 입력 계약 테스트 54개 통과. OpenAPI·공유 타입 재생성, Spotless와 Checkstyle 통과.
- 검증은 개발 DB와 볼륨을 공유하지 않는 임시 PostgreSQL 18 컨테이너에서 실행한다.
- 민감성 후보 응답과 피부 그룹 전체를 제외한 선택지 계산을 구현했다. 일반 피부 타입이 없는
  민감성 제품, 결과가 비어도 남는 후보, 다른 필터와의 결합을 회귀 테스트로 확인했다.
- 최종 `sh ./scripts/verify.sh` 통과: 서버 테스트 1,417개, 빌드·Spotless·Checkstyle·API 생성물 드리프트 검사.
- 실제 로컬 서버와 연결한 브라우저에서 지성·복합성·민감성 선택의 예상 개수와 적용 결과 3개가
  일치함을 확인했다. 민감성 제품이 없는 브랜드에서 기존 민감성을 따로 해제할 수 있고,
  피부 정보가 없는 제품 검색에서는 빈 상태를 표시한다.
- 프론트 전체 테스트 164개 파일·1,459개 통과. 전체 린트 오류 없음, 변경 파일 린트 경고 없음,
  포맷·타입 검사와 실제 로컬 API를 사용하는 프로덕션 빌드 통과.

# 요청 데이터 PostgreSQL 전환 안전성 보강 계획

- 상태: **완료**
- 범위: 피드백·제품 등록 요청의 보유기간, S3 이력 이관, 운영 DB 배포 준비

## 목표

PostgreSQL 전환 뒤에도 기존 S3 접수 이력을 잃지 않고, 피드백 원문과 최종 이미지를
정해진 기간 안에 함께 삭제하며, 표준 CodeDeploy 경로가 DB 설정 누락을 배포 전에
탐지하도록 한다.

## 구현

1. `received_at` 기준 만료 피드백을 작은 배치로 읽고 S3 최종 이미지를 먼저 삭제한 뒤
   DB 행을 삭제하는 예약 작업을 둔다. 중간 실패 시 DB 행을 남겨 재시도 가능하게 한다.
2. 기존 피드백·제품 등록 요청 S3 문서를 읽는 일회성 importer를 둔다. importer는 ID 기준
   insert-only로 동작해 재실행할 수 있고, 웹 서버가 리스닝하기 전 단일 트랜잭션으로 실행한다.
   잘못된 문서나 FK 불일치는 전체 rollback과 기동 실패로 드러낸다.
3. 운영 프로필에서는 보유기간 작업을 켜고, importer는 명시적인 환경 변수로만 켠다.
4. 배포 산출물에 스키마와 DB 검증 스크립트를 포함한다. CodeDeploy는 서비스 재시작 전에
   DB 환경 변수, 연결, 필수 스키마와 초기 카탈로그 데이터를 검증한다.
5. 최초 전환 절차에는 스키마 적용, 초기 데이터 적재, importer 실행·건수 검증, importer
   비활성화 순서를 문서화한다.

## 검증

- 저장소 통합 테스트로 만료 경계, 두 피드백 종류, 이미지 메타데이터의 삭제를 검증한다.
- 단위 테스트로 S3 이미지 삭제 실패 시 DB 행이 남고 재시도되는지 검증한다.
- importer 테스트로 v1/v2 문서, 관리 상태, 이미지 메타데이터, 중복 실행을 검증한다.
- 배포 스크립트 정적 검사와 `server/scripts/verify.sh`를 통과한다.

## 결정 기록

- 2026-09-19: S3 삭제 뒤 DB 삭제 순서를 선택했다. 반대 순서는 S3 장애 때 이미지 소유
  메타데이터를 잃어 고아 이미지를 복구하기 어렵다.
- 2026-09-19: dual-read 대신 기동 전 insert-only importer를 선택했다. 전환 뒤 쓰기·상태
  변경의 단일 원천을 PostgreSQL로 유지하면서도, importer가 완료되기 전에는 웹 서버가
  리스닝하지 않게 해 이력이 일부만 보이는 배포를 막는다.
- 2026-09-19: CodeDeploy DB 준비 스크립트를 실제 PostgreSQL에 연결해 스키마·초기 데이터
  검증까지 확인했고, `server/scripts/verify.sh`로 전체 테스트와 정적 검사를 통과했다.

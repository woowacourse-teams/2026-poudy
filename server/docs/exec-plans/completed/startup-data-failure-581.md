# 데이터 오류로 서버 기동 실패 해결 계획

- 이슈: [#581 데이터 오류로 서버 기동 실패](https://github.com/woowacourse-teams/2026-poudy/issues/581)
- 기준: `origin/dev`의 `351086b1`에서 만든 `fix/581-startup-data-failure`
- 상태: 구현 및 검증 완료

## 목표와 범위

제외 성분군과 검색어 사전은 일부 기능의 데이터다. 두 데이터의 오류가 해당 기능의 실패로
끝나고 Spring 전체 기동과 무관한 API를 막지 않게 한다. 오류를 빈 정상 결과나 잘못된 4xx로
숨기지 않고 원인을 로그에 남긴다. 공통 DB 연결·스키마 장애의 기동 정책은 이 이슈에서 바꾸지 않는다.

## 현재 실패 경로

1. `ExcludeCodeRepository.validateDefinitions()`가 `@PostConstruct`에서 정의 0건,
   구성원 없는 성분군, 조회 오류를 전파해 빈 생성과 서버 기동을 실패시킨다. 기존 [#57](https://github.com/woowacourse-teams/2026-poudy/issues/57)의
   기동 시 검증을 요청 시 실패로 옮겨야 한다.
2. `SearchKeywordRankingService.initializeDictionary()`가 `@PostConstruct`에서 사전을 읽는다.
   조회·데이터 검증 오류가 빈 생성 실패로 전파된다. 현재 `SearchKeywordSnapshot`의 초기 빈
   상태는 정상적으로 로드한 빈 사전과 구별되지 않아, 단순히 예외만 삼키면 순위 API가
   잘못된 200/빈 목록을 반환할 수 있다.

## 구현 순서

1. 성분군의 기동 시 검증을 제거하고, 성분군 데이터에 의존하는 조회 시 정합성을 검사한다.
   `findAll()`의 도메인 검증을 유지하며 `codesOf()`와 성분군 필터가 지정된 `containsAll()`도
   정의 누락·빈 성분군을 정상적인 빈 목록이나 잘못된 요청 400으로 취급하지 않는다. 성분군
   필터가 없는 제품 목록 등 무관한 경로는 성분군 검증 없이 동작하게 한다. 요청 때마다 DB를
   읽으므로 데이터가 복구되면 다음 요청에서 회복된다.
2. 검색어 사전의 `@PostConstruct` 로딩을 제거하고, 기동 완료 후 기존 안전한 순위 갱신
   경로에서 첫 로딩을 시도한다. 스냅샷에 미로딩 상태를 명시해 초기 실패와 유효한 빈 사전을
   구분한다. 사전이 미로딩이면 순위 조회는 명시적인 서버 오류를 반환하고 원인을 로그에
   남긴다. 원시 검색어 집계는 사전 없이도 가능하므로 유지하되, 미로딩 상태를 모든 검색어가
   미해석인 것으로 기록하지 않는다. 다음 10분 갱신에서 복구하고, 이후 갱신 실패 때는 이미
   유효한 이전 스냅샷을 보존한다.
3. 영향을 받는 HTTP 응답은 기존 `GlobalExceptionHandler`의 5xx 계약을 사용한다. 성분군
   목록·제품 상세·성분 상세·성분군 필터와 검색어 순위에서 실패가 빈 정상 결과로 보이지
   않도록 확인한다. 오류 원인을 추적할 수 있는 로그를 남기고, 정상 데이터의 기존 응답 계약은
   유지한다.

## 검증

- [x] 모의 저장소를 사용한 Spring 컨텍스트 테스트에서 성분군 정의 누락과 검색어 사전 조회
      실패에도 컨텍스트가 기동하고, 무관한 요청은 200, 영향받는 요청은 500을 반환한다.
- [x] 성분군 정의 누락·구성원 누락 시 오류를 반환하고, 필터가 없는 제품 조회는 영향을 받지 않는다.
- [x] 검색어 사전 첫 로딩 실패와 유효한 빈 사전을 구별한다. 이후 갱신으로 복구하고,
      기존 스냅샷이 있을 때의 갱신 실패는 이전 결과를 유지한다.
- [x] `server/`에서 `sh ./scripts/verify.sh`를 통과했다. 전체 테스트 794개가 성공했다.

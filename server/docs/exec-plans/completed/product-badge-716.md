# 제품 배지 추가 (#716)

## 목표와 범위

- 이슈: https://github.com/woowacourse-teams/2026-poudy/issues/716
- 기준: `origin/dev`의 `ab6c0186f073485f407bf2a9ee2b8ada32ff5d8e`.
- PR 준비 시 최신 `origin/dev`의 `366bf382`를 반영했다. 이후 #751 병합으로 V16·V17도 선점되어 배지는 V18을 사용한다.
- 작업 브랜치: `feat/716-product-badge`.
- 기존 브랜드를 유지하면서 한 제품에 여러 배지를 연결하고 제품 응답에 코드와 표시명을 제공한다.
- 사용자 결정: 관리자 API를 만들기 전까지 운영자가 DB에 직접 접속해 데이터를 적재한다.
  이번 작업은 테이블과 공개 조회만 구현하며 관리용 SQL 스크립트는 제공하지 않는다.
- 배지 관리/필터 API, 검색어 자동 해석, 클라이언트 표시와 실제 운영 데이터 등록은 이번 범위에서 제외한다.
- 공통 생성 타입 변경에 필요한 클라이언트 fixture·mock 호환 작업은 UI 구현과 별개의 연계 작업으로 관리한다.
  사용자가 범위 예외를 승인해 이번 변경에 클라이언트 테스트·목 데이터의 호환 수정도 포함한다.

## 현재 구현에서 이어갈 경계

- `ProductLoader`가 제품 ID 묶음으로 옵션·구성품·성분을 읽고 `Product`를 조립한다.
  상세·랭킹·위시리스트·큐레이션·유사 제품·선반이 이 경로를 사용한다. 최신 dev의 목록 카드와 검색 제안은
  경량 표시 조회를 유지하고 같은 로더의 배지 일괄 조회만 공유한다.
- 페이지와 정렬은 배지 로딩 전에 SQL로 결정한다. 배지 연결 때문에 제품 행이나 개수가 늘어나면 안 된다.
- 제품 저장소와 조회 서비스는 읽기 전용 REPEATABLE READ 트랜잭션으로 여러 조회의 일관성을 보장한다.
- 제품 카탈로그 쓰기 API는 없다. 새 관리 Controller/Service/Repository나 관리용 SQL 스크립트를 만들지 않는다.
- `ProductResponse.updatedAt`과 사이트맵은 `product.updated_at`을 사용한다.
  자식 데이터 변경 시에도 데이터를 쓰는 쪽이 제품 시각을 갱신하는 기존 계약을 따른다.

## 스키마

신규 `V18__add_product_badges.sql`에 다음을 추가한다. 구현 시 원격 변경으로 버전이 선점되면
다음 번호를 사용하고 기존 마이그레이션은 수정하지 않는다.

| 테이블 | 컬럼 | 제약/의미 |
| --- | --- | --- |
| `badge` | `code VARCHAR(50)` | PK, NOT NULL, 변경하지 않는 식별 코드 |
| | `name VARCHAR(100)` | NOT NULL, 수정 가능한 표시명, UNIQUE 없음 |
| | `created_at`, `updated_at` | TIMESTAMP NOT NULL, 기본값 한국 시각 |
| `product_badge` | `product_id BIGINT` | NOT NULL, `product(id)` FK |
| | `badge_code VARCHAR(50)` | NOT NULL, `badge(code)` FK |
| | `created_at`, `updated_at` | TIMESTAMP NOT NULL, 기본값 한국 시각 |

- `product_badge`의 PK는 `(product_id, badge_code)`다.
- 역방향 검색 인덱스 `ix_product_badge_badge_product (badge_code, product_id)`를 추가한다.
- 코드와 이름은 빈 문자열과 기본 공백 문자 포함을 거절한다. 문자열 앞·뒤·내부를 검사한다.
  DB CHECK는 `[[:space:]]`, Java는 기본 `\\s`를 사용한다. 비ASCII 공백의 DB 판정은
  DB 로케일을 따르며 모든 Unicode 공백에 대한 환경 독립적인 금지 정책은 두지 않는다.
- 코드는 문자열로 다룬다. enum, 자동 대문자화, trim 등 암묵적 변환을 도입하지 않는다.
- 코드 변경을 거부하는 `BEFORE UPDATE OF code` 트리거를 둔다. FK만으로는 연결되지 않은 배지의
  코드 변경을 막을 수 없다. 같은 코드로 갱신하는 것은 허용한다.
- FK는 삭제/수정 연쇄 동작 없이 참조 중인 배지 삭제를 거절한다. 연결 해제는 연결 행을 삭제한다.
- 표시 순서는 별도 컬럼 없이 `badge_code COLLATE "C"` 오름차순으로 고정한다.
- 운영 배지와 제품 연결을 마이그레이션에 넣지 않는다. 새 테이블이 빈 상태로 기존 제품을 조회할 수 있다.

## 도메인과 조회

- 배지는 현재 제품 표시에서만 사용하므로 `product.domain.Badge`로 시작한다.
  별도 최상위 기능 패키지나 독립 배지 목록 조회 계층을 미리 만들지 않는다.
- `Badge`는 불변 클래스로 코드·이름과 생성 시 유효성 검증을 소유한다.
  코드/이름 길이와 기본 공백 검증은 스키마와 맞춘다.
- `Product`에 불변 `List<Badge>`를 추가한다. 생성자가 방어적으로 복사하며, 배지가 없으면 빈 목록이다.
  기존 생성 호출과 테스트 fixture도 배지 목록을 명시하도록 변경한다.
- `ProductLoader.load(ids)`에서 `product_badge JOIN badge`를 제품 ID 배열로 한 번 조회한다.
  `product_id, badge_code COLLATE "C"` 순서로 읽어 제품별로 묶고 `Product`에 전달한다.
- 제품 본문 조회에 M:N JOIN을 추가하지 않는다. 배지 없는 제품도 유지하고 복수 배지가 제품을 중복시키지 않는다.
- 제품당 조회를 추가하지 않으며, 비어 있지 않은 제품 묶음당 배지 조회 한 번만 늘어난다.
  빈 ID 목록은 기존처럼 즉시 반환한다. 입력 제품 ID 순서와 중복 ID 처리도 보존한다.
- 배지 이름을 제품이나 연결 테이블에 복사하지 않고 매번 현재 `badge.name`을 읽는다.
  이름을 바꿔도 연결 PK/FK와 배지의 정렬 위치는 유지된다.

## 공개 응답

공통 `product.controller.dto.BadgeResponse`는 필수 문자열 `code`, `name`만 제공한다.
배지 목록은 응답에 항상 포함하는 배열이며, 미부착 제품은 `"badges": []`다.
배지 부착 자체가 필수라는 뜻은 아니다. 필드를 생략하거나 `null`로 내려주지 않는다.

```json
{
  "badges": [
    { "code": "DAISO", "name": "다이소" }
  ]
}
```

| DTO | 반영 경로 |
| --- | --- |
| `ProductResponse` | 제품 목록, 같은 DTO를 쓰는 위시리스트 목록 |
| `ProductDetailResponse` | 제품 상세 |
| `ProductRankingProductResponse` | 랭킹 제품 |
| `CurationProductResponse` | 일반/필터형 큐레이션의 제품 |
| `SimilarProductResponse` | 유사 제품 |
| `ProductSuggestionResponse` | 검색 제안 제품 |
| `ShelfProductInfoResponse` | 선반 제품 |

- 기존 `brand`/`brandName`을 그대로 제공하고 옆에 `badges`를 추가한다.
- ID만 주는 위시리스트 ID 목록·공유 매칭 결과, count와 필터 선택지에는 추가하지 않는다.
- 검색 대상·검색 일치 구간·필터 조건·정렬 기준은 확장하지 않는다.
- Swagger 필수 배열/필수 문자열 계약을 테스트하고 `generateApiArtifacts`로 OpenAPI와 공통 타입을 갱신한다.

### 클라이언트 계약 호환 연계

- 생성된 TypeScript 타입에서도 `badges`는 생략할 수 없는 배열이다. 기존 타입으로 제품 객체를
  만드는 fixture·mock에는 `badges: []`를 추가하고, 배지 관련 사례에는 실제 배열 값을 넣는다.
  예를 들어 `client/components/home/PopularProducts.test.tsx`의 `rankingOf`가 영향을 받는다.
- 생성 타입을 참조하는 목록·상세·랭킹·큐레이션·유사 제품·검색 제안 테스트와 mock을 확인한다.
  타입을 강제로 단언하거나 `badges`를 선택 필드로 바꿔 오류를 피하지 않는다.
- 사용자 승인에 따라 클라이언트 fixture·mock 호환 수정을 공통 생성물과 함께 반영한다.
  함께 검증되기 전까지 전체 계약 변경이 완료됐다고 판단하지 않는다.
- 연계 변경에서 `pnpm --dir client exec next typegen`, `pnpm --dir client typecheck`,
  `pnpm --dir client test`를 실행한다. 서버의 `verify.sh`는 이 클라이언트 검증을 대신하지 않는다.
- 새 필수 필드를 검증하는 클라이언트는 배지 응답을 제공하는 서버가 배포된 후 배포한다.

## 데이터 적재 범위

관리자 API는 후속 작업이다. 현재는 운영자가 DB에 직접 접속해 배지 정의와 제품 연결을 적재한다.
마이그레이션은 스키마만 생성하고 실제 운영 데이터는 포함하지 않는다. 별도 관리용 SQL,
임시 테이블·PL/pgSQL 운영 블록, 쓰기 동시성 처리와 그 전용 테스트는 이번 구현 범위에서 제외한다.
데이터 변경 시 제품 수정 시각도 갱신하는 기존 카탈로그 저장 계약은 적재하는 쪽이 따른다.

## 구현 순서와 검증

1. 마이그레이션과 실제 PostgreSQL 제약 테스트를 추가한다.
   - 동일 연결 중복, 없는 제품/배지 FK, 빈 값·공백 포함·길이 초과를 거절한다.
   - `ErdCloudSchemaTest`의 `ERD_COLUMNS`, `ERD_PRIMARY_KEYS`에 두 테이블의 컬럼 순서와 PK를
     추가한다. 이 테스트는 전체 테이블 목록을 정확히 비교하므로 신규 테스트만으로 대체하지 않는다.
   - 빈 문자열·스페이스·탭·개행 등 기본 공백 거절을 DB와 도메인에서 검증한다.
     비ASCII 공백은 도메인에서 추가로 거부하지 않아 DB가 허용한 값을 조회할 수 있게 한다.
   - 이름 중복은 허용하고, 연결 유무와 관계없이 코드 변경은 거절한다.
   - 테스트 DB에도 운영과 같은 Flyway 마이그레이션을 적용한다.
2. `Badge`, `Product`, `ProductLoader`를 연결한다.
   - 배지 없음/하나/복수, 여러 제품이 같은 배지를 공유하는 경우를 조회한다.
   - 제품 순서·페이지 경계·전체 개수 유지와 이름 변경 후 코드·연결 유지 및 현재 이름 반영을 검증한다.
   - 도메인의 방어적 복사와 입력 검증을 테스트한다.
3. 직접 DB 적재 방식을 저장 문서에 기록한다.
4. 위 일곱 응답 DTO와 API 회귀 테스트를 갱신한다.
   - 목록/상세의 빈 배열과 복수 배지 및 나머지 제품 표시 경로를 검증한다.
   - 기존 브랜드 표시가 보존되고 검색/필터/count 결과가 달라지지 않는지 확인한다.
5. `sh ./scripts/test.sh`, `./gradlew generateApiArtifacts`, `sh ./scripts/verify.sh`를 실행한다.
   생성물 드리프트가 있으면 갱신 내용을 검토한 뒤 다시 검증한다.
6. 클라이언트 호환 연계 변경의 fixture·mock 보완과 타입 검사·테스트 결과를 확인한다.
   서버 검증 성공과 클라이언트 계약 호환 확인을 별도의 완료 조건으로 남긴다.

## 구현 검증

- PostgreSQL 17의 별도 로컬 인스턴스와 한국어 UTF-8 로케일 DB에서 실제 Flyway 마이그레이션을 적용했다.
- 배지 도메인·스키마·조회 API·공개 스키마와 기존 제품 조회 회귀 테스트를 검증했다.
- OpenAPI와 공통 TypeScript 생성물을 재생성했다. 사용자 승인에 따라 클라이언트 테스트·목 데이터
  12개 파일에 `badges` 배열과 기존 배지 전달을 반영했다. UI 표시 기능은 추가하지 않았다.
- 클라이언트 Next.js 경로 타입 생성, TypeScript 검사, 변경 파일 12개의 ESLint·Prettier 검사를 통과했다.
- 클라이언트 전체 테스트: 135개 파일, 1,211개 테스트 통과. 최종 실행은
  `node node_modules/vitest/vitest.mjs run --maxWorkers=4`로 병렬 작업 수를 제한했다.
  테스트 제한 시간이나 검증 조건은 변경하지 않았다.
- 관리용 SQL과 그 전용 테스트 제거 후 `sh ./scripts/verify.sh`를 통과했다.
  생성물 드리프트가 없으며 전체 서버 테스트 1,165개가 통과했고 실패·오류·건너뜀은 0개다.
- 이번 정리에서는 클라이언트 파일과 API 계약을 변경하지 않아 클라이언트 검증은 재실행하지 않았다.
- 검증용 임시 PostgreSQL을 종료했다. 운영 DB에는 접속하거나 데이터를 적재하지 않았다.

## 코드 리뷰 및 리팩터링

- HEAD 대비 staged·unstaged·untracked 변경을 리뷰했다. 독립 검토에서도 실행 가능한 결함은 발견하지 못했다.
- 배지 도메인의 검증·불변 상태와 DTO 변환 경계는 유지했다. 별도 도메인 계층이나 컬렉션 타입을 추가하지 않았다.
- `ProductLoader`의 배지·옵션·구성품 조회를 각각 private 메서드로 분리해 `load`가 조회 조합과
  제품 조립 흐름을 보여 주도록 정리했다. SQL·조회 횟수·조회 순서·정렬·트랜잭션 경계는 유지했다.
- `badges`는 카테고리 뒤에, 카테고리가 없는 응답은 브랜드 뒤에 둔다. `Product`의 필드·생성자·
  초기화·접근자, 7개 제품 응답과 생성 호출 및 클라이언트 객체도 이 기준으로 맞췄다.
  브랜드·카테고리·배지 정보를 묶고 `updatedAt`은 마지막에 둔다. DB에서는 M:N 연결 테이블을
  유지하며 `product`에 배지 FK 컬럼을 추가하지 않는다.
  변경 후 7개 생성 응답 스키마와 클라이언트 객체 40곳의 순서를 확인했다. 서버 전체 테스트

- DB의 공백 문자 나열을 `[[:space:]]`로, Java 검사는 기본 `\\s`로 간소화했다.
  기본 공백 거절과 비ASCII 문자의 도메인 보존을 검증했다. 저장 문서에 ERD도 추가했다.

# 제품 조회 기록과 파일 저장 (#423)

## 설계

- 최신 dev `ac5dba0`에서 시작한다. 카탈로그와 별도인 `productview`가 날짜별 조회수를 소유한다.
- Service가 한국 시간 날짜를 결정하고 도메인이 제품별 long 횟수를 증가·합산한다.
  메모리 Repository가 증가와 복사를 같은 잠금으로 보호하고 독립된 복사본을 만든다.
  조회는 복사본에서 오늘 포함 days일 또는 전체 기간을 합산한다. 기록을 자동 삭제하지 않는다.
- 저장은 전용 단일 스케줄러의 Writer가 메모리 Repository를 기본 10초 fixed delay로 호출한다.
  Repository가 관리하는 변경 번호가 마지막 성공 번호와
  다를 때만 복사·직렬화·저장한다. 상태 잠금 밖에서 쓰고 성공한 복사본의 번호만 기억한다.
- 파일은 같은 디렉터리에 임시 작성·force 후 원자 교체한다. 파일 없음만 빈 상태로 복원하며
  형식 오류와 읽기 실패는 기동 실패로 처리한다. 저장 실패는 로그 후 다음 실행에서 재시도한다.
  정상 종료는 진행 중인 저장과 직렬화해 마지막 저장을 시도한다.
- #414 / PR #438의 `/opt/poudy/state/search-ranking/buckets.json`과 상위 상태 디렉터리를
  공유하고 제품 파일은 `/opt/poudy/state/product-views/daily-counts.json`으로 분리한다.
  경로와 저장 주기는 설정할 수 있다. 로컬은 `./var/product-views/daily-counts.json`이다.
- 이슈에서 명시한 배포 설정까지 수정한다. `deploy/` 수정은 이번 요청의 범위다.

## 커밋 단위

1. 날짜별 메모리 집계와 파일 저장·복원, 주기·종료 저장 및 테스트
2. 제품 존재 검증과 POST API, 회귀 테스트 및 API 생성물
3. 상태 디렉터리 권한·배포 보존 설정
4. 전체 검증에서 발견한 스케줄러 종료 대기 수정
5. 아키텍처·설정 예시·운영 및 검증 문서 (CONTRIBUTING.md에 따라 기능과 문서 분리)

## 검증

- 한국 시간 자정, days 경계·전체 합계·과거 보존, 동시 증가와 불변 복사본
- 파일 없음·손상·원자 교체·복원, 변경 없음 생략, 실패 재시도, 저장 중 추가 조회
- 204 반복 집계·404 계약·GET 부작용 없음, OpenAPI 생성물
- 서버 test.sh / verify.sh, 배포 스크립트 문법과 배포·동기화 경로 확인

## 진행

- 완료: 2026-09-12 최종 `sh ./scripts/verify.sh` 통과. 711개 테스트, 실패·오류·건너뜀 0.
  OpenAPI 드리프트, 포맷과 코드 규칙 검사를 통과했고 종료 타임아웃 로그가 없음을 확인했다.

- 최신 dev 기준 기존 test.sh 통과. 샌드박스 네트워크 제한은 권한 부여로 해결했다.
- 집계·저장·Spring 주기 및 종료 저장 테스트 통과. 8개 작업자의 8,000회 증가를 검증했다.
- API는 익명 반복 요청 204, 제품 없음 404, 잘못된 ID 400과 GET 부작용 없음을 검증했다.
- OpenAPI와 공통 TypeScript 선언을 재생성했다. 응답 DTO가 없어 api.zod.ts 내용은 동일하다.
- Ubuntu의 private mount namespace에서 임시 /opt와 계정 파일을 사용해 실제 AfterInstall을
  두 번 실행했다. 서비스 UID 쓰기, 디렉터리 poudy:poudy 0750, 읽기 전용 카탈로그와의 분리,
  애플리케이션 교체·카탈로그 교체·롤백 후 상태 파일 SHA-256 보존을 확인했다.
  실제 호스트의 /opt와 계정은 변경하지 않았다. 운영 EC2 배포·재시작은 수행하지 않았다.
- 전체 verify.sh 통과 후 예약 작업 간 간섭을 막도록 스케줄러를 분리했다.
  기존 기본 스케줄러가 별도로 유지되는지 테스트로 확인했다.
- 전체 검증의 종료 로그에서 20초 타임아웃을 발견했다. 스레드 덤프에서
  `ExecutorLifecycleDelegate.beforeExecute`에 일시정지된 작업을 기다리는 것을 확인했다.
  스케줄러의 기본 종료 동작으로 예약 작업을 취소하고, 마지막 저장은 메모리 Repository에서
  진행 중인 저장과 직렬화한다. 저장 간격 1시간과 스케줄러 일시정지 각각에서 5초 안에
  컨텍스트를 닫고 마지막 기록을 저장하는 회귀 테스트가 통과했다.

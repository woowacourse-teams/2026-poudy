# 동작 보존 리팩터링 정책

리팩터링의 성공 조건은 관찰 가능한 동작과 공개 계약을 보존하면서 책임, 불변식 또는 의존성의
소유 위치를 더 분명하게 만드는 것이다. 설계 개선과 직접 관계없는 기능 변경을 섞지 않는다.

## 기준선을 만든다

수정 전에 다음을 확인한다.

- 사용자 또는 호출자가 관찰하는 입력, 출력, 예외와 side effect
- 공개 API, 직렬화 형식, 데이터 계약과 transaction 경계
- 관련 테스트와 공식 컴파일·검증 명령
- 작업 트리의 기존 사용자 변경

현재 동작이 테스트로 충분히 고정되지 않았고 이동할 로직의 의미가 명확하지 않다면 가장 좁은
characterization test를 먼저 추가한다. 구현 세부를 고정하지 말고 외부에서 관찰되는 계약을
고정한다. 테스트 추가 자체가 큰 범위 확장이라면 수정하지 말고 차단 원인으로 보고한다.

## 작은 일관된 단계로 바꾼다

다음 순서를 기본으로 사용하되 코드 문맥에 맞게 조정한다.

1. 기존 동작을 재현하는 좁은 테스트나 기준 실행을 확보한다.
2. 상태와 불변식의 새 소유자를 정한다.
3. 기존 public entry point를 유지한 채 행동을 새 소유자로 이동한다.
4. 호출자를 한 경계씩 전환하고 각 단계에서 컴파일·테스트한다.
5. 중복 로직, 임시 adapter와 죽은 경로를 제거한다.
6. 전체 diff와 공식 검증을 다시 실행한다.

파일 수가 가장 적은 변경보다 책임 이동이 끝까지 닫히는 가장 작은 단위를 선택한다. 반쯤 이동한
책임을 구·신 구조에 동시에 남기지 않는다.

## 새 추상화를 제한한다

새 interface, base class, strategy, facade 또는 layer는 다음 근거 중 하나가 있을 때만 도입한다.

- 현재 존재하는 독립적인 변동 축을 감싼다.
- 외부 시스템과 도메인 사이의 번역 경계를 소유한다.
- 여러 호출자에 흩어진 동일한 도메인 결정을 한곳으로 모은다.
- 불변식 위반을 구조적으로 불가능하게 만든다.

단지 mock을 만들기 쉽거나, 미래 구현이 생길 수 있거나, 특정 패턴을 완성하기 위해 도입하지
않는다. 도입 후 이해해야 할 개념과 이동해야 할 파일 수가 줄지 않으면 기존 구조를 유지한다.

## 중단하고 제안으로 전환한다

다음 중 하나가 필요해지면 현재 수정 범위를 멈추고 근거, 영향과 선택지를 보고한다.

- 공개 API 또는 지원되는 동작 변경
- 데이터 마이그레이션이나 transaction 의미 변경
- 여러 모듈의 소유권을 바꾸는 아키텍처 전환
- 제품 요구나 도메인 규칙에 대한 중요한 미확정 선택
- 관련 없는 결함·보안·성능 문제 수정
- 신뢰할 수 있는 동작 보존 기준을 만들 수 없음

## 결과를 보고한다

```markdown
## Design reading
## Changes applied
## Behavioral preservation
## Verification
## What should remain unchanged
## Remaining opportunities
```

Changes applied에는 책임과 의존성이 전후에 어떻게 달라졌는지 쓴다. Behavioral preservation에는
유지한 계약과 그 근거를 쓴다. Verification에는 실행한 명령과 결과, 실행하지 못한 항목을
구분한다. Remaining opportunities에는 현재 변경과 분리해야 할 가치 있는 항목만 남긴다.

# 설계 판단 기준

원칙 이름을 위반 판정으로 사용하지 말고, 현재 구조가 만드는 비용을 설명하는 어휘로 사용한다.
모든 판단은 코드, 호출 관계, 테스트, 저장소 규칙과 현실적인 변경 시나리오에 연결한다.

## 책임과 응집도

- 한 객체가 하나의 문장으로 설명되는 목적을 가지는지 본다.
- 함께 변하고 같은 불변식을 다루는 상태와 행동이 가까이 있는지 본다.
- 서로 다른 actor나 변경 이유가 우연히 한 workflow에 묶였는지 본다.

큰 클래스가 반드시 나쁜 것은 아니다. 하나의 복잡한 정책을 온전히 소유한다면 여러 작은
클래스로 찢는 것보다 응집력이 높을 수 있다. 생성자 의존성 수만으로 분리하지 않는다.

## 캡슐화와 불변식

- 유효한 상태를 만드는 규칙과 상태 전이를 책임지는 객체가 분명한지 본다.
- 호출자가 getter로 데이터를 꺼내 같은 분기를 반복하거나 올바른 호출 순서를 기억해야 하는지 본다.
- 변경 가능한 내부 표현이 경계 밖으로 새어 나가는지 본다.

단순 전송 DTO, 영속성 projection, 읽기 모델에 행동이 없다는 이유만으로 빈약한 도메인 모델로
판정하지 않는다. 실제 도메인 규칙을 소유해야 할 객체에 로직이 없는 경우만 문제로 삼는다.

## 도메인 표현과 API

- 이름, 타입과 공개 메서드가 구현 단계보다 도메인 의도를 표현하는지 본다.
- 유효하지 않은 조합을 원시 타입과 boolean flag로 넓게 허용하는지 본다.
- orchestration과 도메인 정책이 같은 메서드 안에서 뒤섞이는지 본다.

작은 CRUD 흐름에 별도 도메인 객체나 value object를 강제하지 않는다. 새 개념이 규칙을
보호하거나 중요한 의도를 압축하지 못하면 기존 단순 구조를 유지한다.

## 결합도와 의존성 방향

- 상위 정책이 프레임워크, 저장소, 전송 형식과 같은 하위 세부를 직접 아는지 본다.
- 한 변경이 경계를 넘어 여러 구현을 동시 수정하게 하는 지식 중복이 있는지 본다.
- 객체 협력이 필요한 정보만 주고받는지, 내부 구조 전체를 노출하는지 본다.

계층 수를 늘리는 것을 의존성 역전으로 착각하지 않는다. 직접 의존이 안정적이고 교체 가능성이나
경계 의미가 없다면 유지한다.

## 추상화의 가치

추상화는 다음 중 하나를 실제로 수행할 때만 가치가 있다.

- 독립적으로 변하는 정책이나 구현을 감싼다.
- 외부 시스템과 도메인의 경계를 번역한다.
- 여러 호출자의 반복된 도메인 지식을 한 소유자로 모은다.
- 테스트 대역이 아니라 중요한 계약을 표현한다.

두 번의 유사 코드가 서로 다른 이유로 변한다면 중복을 허용한다. 단일 구현 인터페이스도 외부
경계를 표현하면 유효할 수 있지만, 이름만 바꾼 forwarding layer는 제거 후보로 본다.

## 변경 지역성과 이해 비용

- 현실적인 기능 변경을 위해 이해하고 수정해야 할 개념과 파일 수를 센다.
- 같은 정책이 validation, service, mapper, repository에 흩어졌는지 본다.
- 관련 코드를 찾기 위해 불필요한 indirection을 여러 번 건너야 하는지 본다.

줄 수 감소를 설계 개선으로 간주하지 않는다. 새 구조에서 변경 이유가 더 한곳에 모이고,
잘못된 수정을 할 수 있는 경로가 줄어드는지를 본다.

## 상속, 합성과 다형성

- 상속 관계가 진짜 대체 가능성과 안정된 공통 계약을 표현하는지 본다.
- subtype이 상위 타입의 전제조건이나 의미를 바꾸는지 본다.
- 조건 분기가 동일한 축의 정책 변화인지, 단순한 지역 제어 흐름인지 본다.

합성을 기본 후보로 보되 무조건 강제하지 않는다. 전략 객체나 visitor는 변형 축이 실제로
존재하고 분기를 제거한 가치가 객체 수 증가보다 클 때만 도입한다.

## 테스트 가능성과 우발적 복잡성

- 핵심 정책을 외부 I/O 없이 관찰할 수 있는지 본다.
- 테스트가 구현 호출 순서에 과도하게 결합되어 안전한 리팩터링을 막는지 본다.
- 전역 상태, 숨은 시간·랜덤성, service locator가 협력을 감추는지 본다.

테스트를 위해서만 production interface를 만들지 않는다. 먼저 순수한 정책 분리, 값 전달 또는
경계 adapter가 설계 자체도 개선하는지 확인한다.

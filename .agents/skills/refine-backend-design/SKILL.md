# Refine Backend Design

현재 요구와 근거 있는 변경 압력을 기준으로 설계를 읽고, 도메인 개념과 책임을 더 분명히
표현하면서 변경 영향을 좁힌다. 패턴 적용이나 원칙 준수 자체를 목표로 삼지 않는다.

작업을 시작하기 전에 [설계 판단 기준](references/design-criteria.md)을 끝까지 읽는다.
리뷰 모드이면 [리뷰 정책](references/review-policy.md)을, 수정 모드이면
[리팩터링 정책](references/refactoring-policy.md)을 추가로 끝까지 읽는다.

## 1. 권한과 범위를 확정한다

요청의 동사로 모드를 결정한다.

- 평가, 리뷰, 진단, 설명, 제안 요청은 **리뷰 모드**로 처리하고 파일을 수정하지 않는다.
- 개선, 리팩터링, 수정, 적용 요청은 **수정 모드**로 처리하고 진단 뒤 직접 수정·검증한다.
- 권한이 애매하면 리뷰 모드로 처리한다.

사용자가 지정한 대상과 목적을 우선한다. 지정이 없으면 현재 diff 또는 직접 지목된 코드에서
시작하되, 설계를 이해하는 데 필요한 호출자·피호출자·인터페이스·구현·테스트까지만 범위를
넓힌다. 변경 파일마다 가장 가까운 `AGENTS.md`와 저장소 고유 규칙을 읽는다.

정확성, 보안, 데이터 손실, API 호환성 같은 결함 판정을 이 Skill의 설계 의견에 섞지 않는다.
그 위험이 리팩터링 안전성을 막는다면 별도 위험으로 알리고, 결함 리뷰는
`$review-backend-code`의 범위로 남긴다.

## 2. 현재 설계를 재구성한다

파일이나 클래스 크기부터 평가하지 말고 다음을 한 문장씩 설명할 수 있을 때까지 실제 참조를
추적한다.

- 이 설계가 제공하는 사용자·도메인 결과
- 각 객체의 존재 이유와 소유한 책임
- 보호해야 하는 불변식과 그 소유 위치
- 입력부터 상태 변화와 출력까지의 협력 흐름
- 도메인, 애플리케이션, 인프라 경계를 가로지르는 의존성 방향
- 현재 테스트가 고정하는 관찰 가능한 동작과 공개 계약

이름, 패키지 관례 또는 프레임워크 stereotype만으로 책임을 단정하지 않는다. 코드, 호출 관계,
테스트와 저장소 규칙이 보여 주는 현재 사실을 우선한다.

## 3. 설계 마찰 후보를 만든다

[설계 판단 기준](references/design-criteria.md)의 원칙을 체크리스트처럼 전부 적용하지 않는다.
현재 설계에서 다음 중 하나가 관찰될 때만 후보를 만든다.

- 하나의 도메인 변경이 관련 없는 여러 책임과 파일을 함께 흔든다.
- 하나의 불변식을 여러 객체가 중복해서 알고 있거나 아무 객체도 보호하지 않는다.
- 행동을 소유할 객체 밖에서 데이터 조회와 분기가 반복된다.
- 상위 정책이 하위 구현 세부에 끌려간다.
- 추상화가 실제 변동성을 감싸지 않고 탐색 단계와 간접 호출만 늘린다.
- 공개 API가 도메인 의도보다 저장 방식이나 처리 순서를 노출한다.

크기, 의존성 개수, 중복 횟수 또는 사용한 패턴만으로 후보를 만들지 않는다.

## 4. 실제 변경 비용으로 검증한다

각 후보에 현재 요구 또는 저장소 근거에서 가까운 변경 시나리오를 하나 적용한다. 다음을 모두
구체적으로 설명하지 못하면 설계 finding에서 제외한다.

1. 현재 코드에서 관찰되는 구조는 무엇인가?
2. 어떤 현실적인 변경에서 이해·수정·테스트 비용이 발생하는가?
3. 그 변경이 왜 여러 책임이나 경계를 함께 건드리게 되는가?
4. 제안 구조가 그 비용을 어떻게 줄이는가?
5. 제안이 추가하는 개념, 간접 계층과 마이그레이션 비용은 무엇인가?

미래 요구를 발명하지 않는다. 가능한 대안 중 개념 수와 이동해야 할 파일 수를 실제로 줄이는
가장 작은 일관된 설계 단위를 선택한다.

## 5. 가치가 큰 개선만 선별한다

후보를 다음 순서로 정렬한다.

- **High leverage**: 책임, 불변식 또는 의존성 경계를 크게 분명하게 만든다.
- **Worthwhile**: 현재의 구체적인 이해·변경·테스트 마찰을 줄인다.
- **Optional**: 취향 또는 아직 확인되지 않은 미래 조건에 의존한다.

High leverage와 Worthwhile만 기본 결과에 포함한다. Optional은 사용자가 대안을 요청했거나
결정에 필요한 경우에만 분리해서 제시한다. 현재 구조가 적절하면 억지로 개선점을 만들지 않는다.

## 6. 요청된 모드를 수행한다

리뷰 모드에서는 [리뷰 정책](references/review-policy.md)의 근거 기준과 출력 계약을 따른다.
수정 모드에서는 우선순위가 가장 높은 설계 마찰부터 [리팩터링 정책](references/refactoring-policy.md)에
따라 수정한다.

수정 모드에서도 광범위한 아키텍처 전환, 공개 계약 변경, 데이터 모델 전환 또는 설계 목표와
무관한 기능 변경은 제안까지만 한다. 사용자가 그 확대를 명시적으로 요청한 경우에만 수행한다.

## 7. 검증하고 다시 읽는다

수정했다면 관련 컴파일과 가장 좁은 테스트부터 실행하고, 저장소의 공식 완료 검증으로 넓힌다.
실패를 우회하거나 테스트를 약화하지 않는다. 실행하지 못한 검증은 성공으로 간주하지 않는다.

마지막으로 diff를 처음 보는 리뷰어처럼 다시 읽고 다음을 확인한다.

- 관찰 가능한 동작과 공개 계약이 유지되는가?
- 책임과 불변식의 새 소유 위치가 한 곳으로 수렴하는가?
- 새 추상화가 제거한 결합보다 더 큰 탐색 비용을 만들지 않는가?
- 이전 코드, 중복 adapter 또는 임시 우회가 남지 않았는가?
- 설계 개선과 무관한 변경이 섞이지 않았는가?

## 런타임 권장

Skill은 실행 중인 모델이나 reasoning 설정을 스스로 바꾸지 못한다. 실행 환경에서 일상적인
설계 리뷰는 `gpt-5.6-sol`과 `high`, 여러 모듈·계층의 설계 판단은 `xhigh`를 시작점으로 삼는다.
`max` 또는 pro mode는 품질 차이가 중요한 고난도 리팩터링에서만 같은 대표 과제로
`xhigh` 표준 모드와 비교해 채택한다. 모델 이름을 지침에 반복하거나 “더 오래 생각하라”는
문구를 추가하지 말고, 목표·도메인 맥락·제약·필요한 근거·성공 조건을 제공한다.

# Audit Backend Harness

백엔드 하네스가 에이전트에게 더 많은 설명을 주는 데 그치지 않고, 저장소를 탐색하고
구현하고 검증하고 실패를 수정할 수 있는 환경을 제공하는지 감사한다. 파일을 수정하지
않고 저장소 근거와 실행 결과를 보고한다.

감사를 시작하기 전에 [감사 기준](references/audit-rubric.md)을 끝까지 읽는다.

## 1. 감사 유형과 경계를 정한다

사용자가 지정한 백엔드 영역과 적용되는 상위·하위 지침을 먼저 확인한다. 백엔드 루트가
명시되지 않았다면 현재 작업 위치, 빌드 경계, 지침의 적용 범위를 근거로 찾는다.

- 변경 감사: 기준 브랜치와의 diff에서 하네스 변경을 찾고 영향받는 연결까지 감사한다.
- 전체 감사: 현재 백엔드 작업을 안내하고 검증하는 하네스 표면 전체를 감사한다.
- 특정 항목 감사: 사용자가 지정한 항목과 그 입력·소비자·강제 수단을 감사한다.

감사는 읽기 전용으로 수행한다. 공식 검증이 빌드 산출물을 만들 수는 있지만 추적 파일을
바꾸는 생성 작업은 임시 복제본, dry-run 또는 변경 전후 비교가 가능한 경우에만 실행한다.

## 2. 하네스 표면을 동적으로 발견한다

현재 파일명이나 디렉터리 목록을 감사 범위로 고정하지 않는다. 적용되는 에이전트 지침과
사용자의 지정 범위를 진입점으로 삼고 참조·호출·소유 관계를 따라간다.

다음 역할을 수행하는 산출물을 발견한다.

- 작업 범위, 우선순위 또는 행동을 지시한다.
- 제품 지식, 아키텍처 불변식, 결정 또는 진행 상태를 제공한다.
- 반복 작업, 전문 절차 또는 독립 검토를 정의한다.
- 테스트, 빌드, 생성, 정적 검사 또는 완료 조건을 실행한다.
- 로컬과 원격 환경에서 규칙을 강제한다.
- 백엔드 작업의 입력, 계약, 생성물 또는 관찰 결과를 소유한다.

다음 관계를 양방향으로 추적한다.

```text
지침·지식 → 작업 절차 → 실행 명령 → 검증·강제 → 관찰 가능한 결과
      ↑                                               ↓
      └──────────── 실패 원인의 저장소 환류 ────────────┘
```

문서 링크, 명령이 호출하는 스크립트와 작업, 자동화가 실행하는 진입점, 생성물의 출력과
소비자를 끝까지 확인한다. 관계에 참여한다면 백엔드 경계 밖의 파일도 읽기 범위에
포함한다. 연결되지 않은 문서, 숨은 두 번째 진입점, 중복 기준도 기록한다.

## 3. 근거의 지위와 현재성을 판별한다

발견한 산출물을 다음 중 하나로 분류한다.

- 현재 사실: 코드, 설정, 실행 결과로 확인되는 동작
- 확정 기준: 적용되는 지침, 승인된 결정, 공식 계약과 완료 조건
- 진행 중 계획: 아직 구현되지 않은 목표와 단계
- 과거 참고: 대체됐거나 구현 계약이 아닌 자료
- 생성 결과: 권위 원천에서 재현되어야 하는 산출물

실행 결과와 현재 코드가 동작 설명보다 우선한다. 확정 기준은 진행 중 계획보다 우선한다.
계획, 예시, 과거 명세를 구현된 사실로 취급하지 않는다. 서로 충돌하면 우선순위를
추측하지 말고 충돌 자체를 발견 사항으로 남긴다.

## 4. 선언된 피드백 루프를 검증한다

하네스가 공식이라고 선언한 명령을 실제 환경에서 실행해 감사 기준의 피드백·생성·자동화
항목을 검증한다.

- 문서에 선언된 명령과 실제 실행 범위를 대조한다.
- 로컬 완료 조건, 생성물 검사와 자동화된 병합 조건을 대조한다.
- 실행 결과와 실행 전후의 의도하지 않은 변경을 기록한다.

검증을 통과시키기 위해 기준을 약화하거나 실패를 우회하지 않는다. 실행할 수 없는 항목은
성공으로 간주하지 않고 정확한 차단 원인과 미검증 범위를 기록한다.

## 5. 독립 검토로 교차 확인한다

새 서브에이전트 하나에 같은 감사 범위와 이 Skill만 제공해 독립 검토를 맡긴다.
독립 검토자로 호출된 에이전트는 이 단계를 반복하지 않는다.

- 이전 대화, 예상 결론, 의심하는 문제를 전달하지 않는다.
- 파일을 수정하지 않고 원본 근거가 있는 문제만 보고하게 한다.
- 주 감사와 독립 감사의 결과를 각각 원본에 다시 대조한다.
- 결과가 다르면 합의로 뭉개지 말고 더 강한 근거를 채택한다.

서브에이전트를 사용할 수 없다면 독립 검토를 미검증 항목으로 기록한다.

## 6. 발견 사항을 선별한다

다음 조건을 모두 만족할 때만 발견 사항으로 보고한다.

1. 저장소 위치 또는 실행 결과로 입증된다.
2. 현재 개발 흐름, 정확성, 안전성 또는 유지 비용에 구체적 영향이 있다.
3. 가장 작은 유효한 개선 방향을 설명할 수 있다.

심각도는 다음과 같이 적용한다.

- `P1`: 잘못된 구현, 범위 위반, 데이터 손상 또는 완료 검증의 무력화를 직접 유발한다.
- `P2`: 반복적인 혼선, 드리프트, 늦은 실패 또는 불필요한 유지 비용을 유발한다.
- `P3`: 영향은 제한적이지만 현재 근거가 있는 개선이 필요하다.

문체 취향, 점수, 막연한 모범 사례, 아직 발생하지 않은 확장 가능성만으로 발견 사항을
만들지 않는다.

## 7. 보고한다

발견 사항을 중요도순으로 먼저 작성한다.

```markdown
## 발견 사항

### P1 | P2 | P3 — 문제 제목

- 근거: 파일과 위치 또는 실행 결과
- 문제: 확인된 불일치나 결함
- 영향: 개발과 에이전트 작업에 미치는 영향
- 개선: 가장 작은 유효한 변경

## 유지할 요소

- 현재 목적에 맞게 작동하는 하네스와 그 근거

## 지금 추가하지 않을 요소

- 가능하지만 현재 근거가 부족한 확장과 다시 검토할 조건

## 검증 결과

- 실행한 검증과 결과
- 미검증 항목과 차단 원인
- 독립 검토와 교차 확인 결과

## 판정

적합 | 수정 필요 | 재설계 필요
```

발견 사항이 없으면 없다고 명시한다.

# 백엔드 하네스 감사 기준

이 기준은 특정 저장소 구조를 전제하지 않는다. 발견된 하네스 표면에 역할별로 적용한다.

## 1. 저장소가 기억으로 작동하는가

- 현재 제품 규칙, 아키텍처 결정, 작업 상태가 대화 기억이 아니라 저장소에 남는가?
- 현재 사실, 확정 결정, 진행 중 계획, 과거 참고 자료의 지위가 구분되는가?
- 같은 사실을 여러 문서가 중복 소유하거나 서로 다르게 설명하지 않는가?
- 코드에서 알 수 없는 중요한 이유와 제약만 기록하고 구현 세부를 선제 고정하지 않는가?
- 작업이 끝나면 계획과 문서가 실제 상태로 갱신되는가?

좋은 상태는 새 에이전트가 이전 대화를 몰라도 현재 코드와 결정 근거를 재구성할 수 있는
상태다.

## 2. 진입점과 점진적 공개가 적절한가

- 최상위 지침은 짧은 저장소 지도와 공식 작업 루프를 제공하는가?
- 상세 지식은 담당 문서나 반복 가능한 절차로 이동하고 진입점에는 링크만 남는가?
- 가까운 범위의 지침이 상위 지침을 보완하며 충돌하지 않는가?
- 실제 작업에 필요한 자료까지 자연스럽게 탐색할 수 있는가?
- 모든 작업에 불필요한 내용을 초기 컨텍스트에 강제로 넣지 않는가?

진입점의 길이 자체보다 모든 규칙이 같은 중요도로 섞여 탐색을 방해하는지를 본다.

## 3. 경계와 불변식이 명확한가

- 작업 소유권, 수정 가능 범위와 의존 방향이 명확한가?
- 코드만 보고 복구하기 어려운 핵심 불변식이 기록되어 있는가?
- 문서의 경계가 실제 빌드, 패키지, 생성물과 일치하는가?
- 미래 구조를 현재 의무처럼 고정하거나 구현 선택을 과도하게 제한하지 않는가?
- 중요한 경계 위반이 반복된다면 구조 검사나 정적 검증으로 승격됐는가?

경계 안의 구현 방식은 열어 두되 정확성, 재현성, 소유권은 명확하게 제한하는지를 본다.

## 4. 기본 작업 루프가 닫혀 있는가

다음 흐름을 저장소만으로 수행할 수 있는지 확인한다.

```text
탐색 → 계획 판단 → 구현 → 좁은 테스트 → 전체 검증 → diff 검토 → 완료
```

- 작은 변경과 실행 계획이 필요한 변경의 기준이 구분되는가?
- 기존 코드와 패턴을 먼저 탐색하도록 유도하는가?
- 동작 변경에 적절한 테스트를 요구하는가?
- 공식 완료 조건이 하나의 명확한 진입점으로 수렴하는가?
- 검증 실패를 우회하거나 삭제하는 경로가 정상 절차로 남아 있지 않은가?

## 5. 피드백이 결정적이고 재현 가능한가

- 공식 검증 명령이 깨끗한 환경에서 반복 실행 가능한가?
- 테스트, 포맷, 정적 검사, 생성물 검사가 필요한 범위를 실제로 덮는가?
- 목록과 실제 실행 항목이 일치하며 명령 간 중복이나 사각지대가 없는가?
- 로컬 완료 신호와 CI 또는 병합 조건이 같은 의미를 갖는가?
- 검증이 실패했을 때 위반 위치, 원인과 수정 방향을 알 수 있는가?
- 검증 과정이 의도하지 않은 추적 파일 변경이나 자동 커밋을 만들지 않는가?

문서로만 선언된 규칙보다 빠르고 구체적인 실행 피드백을 우선한다.

## 6. 생성과 계약의 소유권이 일치하는가

- 권위 원천과 파생 생성물이 구분되는가?
- 생성 명령, 출력 위치와 소비자가 연결되어 있는가?
- 생성물 갱신에 필요한 수정 범위가 작업 지침과 충돌하지 않는가?
- 생성 결과가 결정적이며 드리프트를 완료 전에 감지하는가?
- 생성물을 직접 편집하지 않도록 안내하고 실제 검증도 이를 보호하는가?

## 7. 계획과 결정이 실제 작업을 돕는가

- 실행 계획은 여러 경계에 걸치거나 설계 판단이 필요한 작업에만 사용하는가?
- 목표, 현재 상태, 제약, 단계, 검증, 결정과 진행 상황을 남기는가?
- 활성·완료 상태가 실제 작업 상태와 일치하는가?
- 완료된 계획에 placeholder나 미검증 완료 조건이 남아 있지 않은가?
- 확정 결정을 계획에만 묻어 두지 않고 적절한 권위 원천으로 승격하는가?

빈 구조를 채우기 위한 가짜 계획이나 구현되지 않은 진행 기록을 만들지 않는지를 본다.

## 8. 반복 절차와 전문 역할이 적절히 분리되는가

- 반복되는 전문 작업만 Skill이나 별도 절차로 분리됐는가?
- Skill의 트리거, 입력, 작업 순서, 검증과 출력이 명확한가?
- Skill이 현재 파일 목록이나 일회성 구현 세부에 과도하게 결합되지 않는가?
- 독립 검토 역할은 수정 권한과 평가 범위가 명확한가?
- 복수 에이전트가 같은 파일을 쓰며 충돌하는 구조를 기본값으로 만들지 않는가?
- 상세 절차를 최상위 지침에 다시 복제하지 않는가?

## 9. 자동화와 안전 경계가 일치하는가

- 로컬 훅, CI, 규칙과 자동화가 같은 완료 의미를 강제하는가?
- 자동 수정, 스테이징, 커밋, 푸시처럼 상태를 바꾸는 동작이 명시적으로 드러나는가?
- 자동화가 지침의 수정 범위나 사용자 승인 경계를 넘지 않는가?
- 선택적 로컬 도구가 유일한 보호 장치가 되지 않는가?
- 실패하거나 설치되지 않은 자동화가 조용히 성공 처리되지 않는가?

강한 자동화일수록 적용 범위, 실패 방식과 복구 경로를 더 명확히 요구한다.

## 10. 현재 성숙도에 맞게 최소한으로 구성됐는가

- 각 하네스 요소가 현재 위험, 반복 실패 또는 실제 작업을 다루는가?
- 같은 목적의 문서, 명령, 검사 또는 에이전트가 중복되지 않는가?
- 오래된 요소를 제거하거나 대체할 수 있는가?
- 아직 필요하지 않은 규칙, 훅, 평가, 구조 검사를 선제 추가하지 않는가?
- 새로운 기능이나 디렉터리가 생겨도 기존 파일 목록을 계속 덧붙이지 않고 관계를 통해
  발견할 수 있는가?

하네스의 크기를 성숙도로 보지 않는다. 필요한 피드백 루프가 가장 작은 구조로 닫혀
있는지를 본다.

## 11. 반복 실패가 올바르게 승격되는가

문제가 반복될 때 다음 순서로 가장 작은 단계만 추가하는지 확인한다.

```text
사건 → 지침 또는 지식 → 반복 절차 → 결정적 검증 → 자동 강제
```

- 한 번의 실수를 영구 규칙으로 과잉 일반화하지 않는가?
- 자연어 지침이 반복해서 깨지면 실행 가능한 검사로 승격하는가?
- 검사를 공식 완료 명령과 자동화에 연결하는가?
- 새 장치가 생기면 중복되거나 약해진 이전 장치를 정리하는가?
- 실패 사례가 회귀 테스트나 평가 자료로 남아 재발을 막는가?

## 12. 판정 기준

- `적합`: 공식 작업 루프와 완료 신호를 신뢰할 수 있고 현재 수정할 근거가 없다.
- `수정 필요`: 일부 충돌, 드리프트 또는 사각지대가 있지만 기존 구조 안에서 고칠 수 있다.
- `재설계 필요`: 진입점, 소유권 또는 완료 신호를 신뢰할 수 없어 부분 수정만으로 해결되지
  않는다.

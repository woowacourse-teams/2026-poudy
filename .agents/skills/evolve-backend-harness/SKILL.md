# Evolve Backend Harness

실제 개발 경험을 저장소의 더 나은 탐색·실행·검증 루프로 환류한다. 하네스를 늘리는 것
자체를 목표로 삼지 말고, 현재 개발을 방해하거나 같은 문제를 반복시키는 가장 작은 원인을
해결한다.

## 1. 개발 근거를 수집한다

사용자가 지정한 개발 범위와 적용되는 에이전트 지침을 확인한다. 다음 근거를 현재
저장소에서 수집한다.

- 최근 구현과 리팩터링의 diff 및 관련 결정
- 실패한 테스트·빌드·검증과 수정 과정
- 리뷰에서 반복된 지적과 회귀 사례
- 매번 사람이 설명하거나 수행한 절차
- 코드·문서·생성물·자동화 사이의 드리프트
- 현재 하네스의 참조·호출·강제 관계

현재 작업에서 발생한 신호와 이전부터 존재한 문제를 구분한다. 추측이나 한 번의 취향
차이만으로 하네스를 변경하지 않는다. 유효한 개선 근거가 없으면 변경하지 않는 결론을
내린다.

후보가 속한 영역의 적용 지침, 소유권과 허용된 쓰기 범위를 확인한다. 필요한 변경이
사용자가 허용한 범위 밖에 있으면 일부만 적용하지 말고 범위 확대 승인을 요청한다.

## 2. 하네스 후보를 선별한다

다음 중 하나에 해당하고 다시 발생할 가능성과 영향이 확인될 때만 후보로 채택한다.

- 중요한 제품 지식이나 결정이 대화에만 남아 있다.
- 같은 탐색·수정·검증 절차가 반복된다.
- 자연어 지침이 반복해서 깨지고 결정적으로 검사할 수 있다.
- 공식 완료 명령이 실제 완료 조건을 덮지 못한다.
- 로컬 검증과 CI·훅의 결과가 다르다.
- 실패 메시지만으로 원인과 수정 방향을 알기 어렵다.
- 소유권, 입력 또는 생성물 경계가 개발 현실과 달라졌다.
- 중복되거나 오래된 하네스가 탐색과 판단을 방해한다.

후보마다 근거, 재발 가능성, 영향, 현재 보호 수단을 기록한다. 현재 보호 수단으로 충분한
후보는 제외한다.

## 3. 가장 작은 수단을 선택한다

문제와 가장 가까운 한 곳을 권위 원천으로 선택한다.

| 확인된 필요 | 우선 수단 |
| --- | --- |
| 진입점이나 탐색 경로가 불명확함 | 가장 가까운 에이전트 지침에 짧은 지도나 링크 추가 |
| 코드만으로 알 수 없는 안정된 지식·결정 | 담당 지식 문서나 결정 기록 갱신 |
| 여러 경계에 걸친 진행 중 작업 | 실행 계획 작성 또는 갱신 |
| 반복되는 전문 절차 | Skill로 분리 |
| 기계적으로 판별 가능한 불변식 위반 | 테스트·정적 검사·스키마 검증 추가 |
| 여러 검증을 매번 따로 실행함 | 공식 완료 명령에 통합 |
| 병합 전에 반드시 막아야 하는 회귀 | 같은 완료 명령을 CI에서 강제 |
| 반복되는 생명주기·명령 안전 문제 | 충분한 근거가 있을 때만 훅이나 규칙 추가 |
| 중복·대체·노후화된 요소 | 통합하거나 제거 |

다음 승격 순서를 한 단계씩 적용한다.

```text
사건 → 지침·지식 → 반복 절차 → 결정적 검증 → 자동 강제
```

이미 뒤 단계의 수단이 문제를 충분히 막는다면 앞 단계의 중복 설명을 줄인다. 한 번에
필요한 최소한의 완결된 피드백 루프만 추가한다.

## 4. 최소 변경을 설계한다

- 새 파일을 추가하기 전에 기존 권위 원천을 갱신할 수 있는지 확인한다.
- 같은 규칙을 여러 문서와 명령에 복제하지 않는다.
- 최상위 지침에는 지도와 공통 완료 조건만 두고 상세 절차를 분리한다.
- 현재 사실, 확정 결정, 진행 중 계획과 과거 참고를 섞지 않는다.
- 미래에 필요할 수 있다는 이유만으로 구조를 미리 만들지 않는다.
- 추가한 수단이 기존 수단을 대체하면 함께 축소하거나 제거한다.
- 새 기능과 디렉터리를 파일 목록에 계속 덧붙이지 말고 관계를 통해 발견하게 한다.

여러 경계에 걸치거나 되돌리기 어려운 판단이 필요하면 적용되는 계획 규칙에 따라 실행
계획을 먼저 작성한다. 그 외에는 바로 수정한다.

## 5. 하네스를 변경한다

선택한 수단과 직접 연결된 하네스만 수정한다. 제품 동작을 변경하지 않는다. 하네스 검증에
필요한 테스트·검사·fixture는 변경할 수 있지만 기능 구현을 끼워 넣지 않는다.

- 지침, 실행 명령, 자동화와 생성물 소유권을 함께 일치시킨다.
- 새 검증은 실패 위치, 원인과 가장 가까운 수정 방향을 출력하게 한다.
- 생성 과정은 결정적이고 반복 실행 가능하게 만든다.
- 기존 사용자의 작업 흐름을 불필요하게 깨지 않는다.
- 사용자가 요청하지 않은 커밋, 푸시 또는 외부 상태 변경을 수행하지 않는다.

## 6. 피드백 루프를 검증한다

변경한 요소의 좁은 검증부터 실행한 뒤 공식 완료 명령을 실행한다.

- 문서 링크와 설정·스크립트 문법을 확인한다.
- 새 검사에 통과·실패 사례가 모두 있다면 각각 검증한다.
- 로컬 완료 조건과 자동화된 병합 조건을 대조한다.
- 생성물이 있다면 재현성과 드리프트 감지를 확인한다.
- 실행 전후 diff에서 의도하지 않은 변경을 확인한다.

검증 실패를 우회하거나 기준을 약화하지 않는다. 실패 원인을 수정하고 같은 명령을 다시
실행한다.

## 7. 독립 감사를 받는다

변경한 하네스와 영향받는 연결을 범위로 `$audit-backend-harness`를 실행한다. 감사자는
파일을 수정하지 않고 독립적으로 검토하게 한다.

- 이번 변경이 만든 `P1`과 `P2`는 수정하고 다시 검증한다.
- 범위 밖에서 발견된 기존 문제는 임의로 수정하지 않고 별도로 보고한다.
- 감사 결과를 통과시키려고 감사 기준을 낮추지 않는다.
- 수정 후 변경 범위 감사를 한 번 더 실행해 회귀가 없는지 확인한다.

## 8. 결과를 보고한다

```markdown
## 근거

- 관찰한 개발 신호와 저장소 근거

## 결정

- 변경한 이유 또는 변경하지 않은 이유
- 선택한 승격 단계

## 변경

- 추가·수정·통합·제거한 하네스

## 검증

- 실행 결과
- 독립 감사 결과
- 미검증 항목

## 다음 승격 조건

- 지금 추가하지 않은 수단과 다시 검토할 구체적 조건
```

변경하지 않았다면 빈 파일이나 계획을 만들지 말고 검토한 근거와 다음 승격 조건만
보고한다.

# Finding 정책

이 문서를 체크리스트로 사용하지 않는다. 변경에서 생긴 의심을 선별하는 정책으로 사용하고,
관련 없는 위험 영역은 조사하지 않는다.

## 위험 우선순위

1. 정확성과 동작 회귀
2. 데이터 손실과 손상
3. 보안, 인증과 인가
4. API·스키마·프로토콜 호환성
5. 동시성과 트랜잭션 정확성
6. 리소스 수명과 실패 처리
7. 현실적인 부하에서의 성능 회귀
8. 구체적인 회귀를 노출하는 테스트 공백
9. 미래 결함 위험을 실질적으로 높이는 유지보수성 문제

## 필요한 만큼만 증거를 확장한다

변경 표면에 맞는 증거만 따라간다.

| 변경 표면 | 확인할 연결 |
| --- | --- |
| API·스키마·직렬화 | 기존 소비자, 기본값, nullable, 버전과 rollout 순서 |
| 상태·영속성 | 트랜잭션 범위, 마이그레이션, 기존 데이터와 재시도 |
| 인증·인가 | 서버 강제 위치, 리소스 소유권과 테넌트 경계 |
| 비동기·외부 연동 | 멱등성, 순서, timeout, 부분 실패와 중복 전달 |
| 쿼리·컬렉션·리소스 | 입력 크기, pagination, N+1, 상한과 정리 경로 |
| 테스트 변경 | 수정 전 실패 여부, 관찰 가능한 계약과 실제 wiring |

## Finding 인정 조건

다음 조건을 모두 만족시킨다.

1. 이번 변경이 문제를 만들거나 기존 문제를 새 경로에 노출한다.
2. 지원되는 현실적인 입력이나 상태에서 실패 경로에 도달할 수 있다.
3. 정확성, 보안, 데이터, 호환성, 가용성, 성능 또는 향후 결함 위험에 의미 있는 영향이 있다.
4. 주장 전체가 코드 위치, 계약 또는 실행 결과로 뒷받침된다.
5. 영향받는 위치를 가장 좁은 줄 범위로 지정할 수 있다.
6. 작성자가 적용할 수 있는 합리적인 수정 방향이 있다.

하나라도 입증하지 못하면 더 조사한다. 그래도 입증할 수 없으면 finding을 만들지 않는다.

## 보고하지 않을 항목

- 이번 변경과 무관한 기존 문제
- 의심만 있고 구체적인 실패 조건이 없는 문제
- 개인적인 스타일·이름·주석 선호
- 포맷·import 순서와 도구가 이미 판정하는 lint 위반
- 근거 없는 추상화, 패턴 도입과 광범위한 리팩터링 제안
- 아직 요구되지 않은 미래 기능이나 가상의 확장성 문제
- 구체적인 회귀 위험이 없는 테스트 누락
- 같은 원인을 반복 설명하는 중복 finding

저장소의 명시적 불변식이 위 기본값보다 우선하지만, 위반의 도달 가능성과 영향은 여전히
입증한다.

## 우선순위

- `P1`: 정확성, 보안, 데이터 무결성 또는 호환성 실패 가능성이 높고 영향이 크다.
- `P2`: 특정 조건이나 부하에서 의미 있는 오동작 또는 신뢰성 저하가 발생한다.
- `P3`: 영향은 낮지만 구체적이며 향후 결함 위험이나 제한된 운영 실패를 만든다.

심각도를 확신도의 대용으로 사용하지 않는다. 근거가 약한 후보는 낮은 우선순위가 아니라
finding 제외 대상이다.

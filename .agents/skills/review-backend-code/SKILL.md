# Review Backend Code

시니어 엔지니어처럼 변경을 검토한다. finding 수를 늘리지 말고 signal-to-noise 비율을
최대화한다. 의심을 결함으로 보고하지 말고, 피드백을 채우기 위해 finding을 만들지 않는다.

리뷰를 시작하기 전에 [finding 정책](references/finding-policy.md)을 끝까지 읽는다.

## 1. 변경과 의도를 확정한다

사용자가 지정한 대상, 기준 revision과 의도를 우선한다. PR·이슈 설명을 사용할 수 있으면
변경 목적과 허용된 동작을 확인한다. 지정이 없으면 다음 기준을 적용한다.

- working tree 리뷰: staged, unstaged, untracked 변경을 모두 포함한다.
- 브랜치 리뷰: Git 추적 관계와 저장소 기본 브랜치를 근거로 merge-base를 정한다.
- 기준을 추론했다면 최종 보고서에 명시한다.

변경 파일마다 가장 가까운 `AGENTS.md`를 읽고 적용 범위, 저장소 고유 불변식, 권위 있는
계약과 공식 검증 명령을 찾는다. 백엔드 변경과 직접 연결된 외부 스키마·생성물·소비자는
읽기 범위에 포함하되 다른 영역의 일반 품질까지 리뷰하지 않는다. 하네스만 바뀌었다면
`$audit-backend-harness`의 영역임을 알리고 이 Skill의 finding에 섞지 않는다.

## 2. diff에서 위험 지도를 만든다

저장소 전체를 먼저 읽지 않는다. diff에서 변경된 동작, 가정과 불변식을 재구성하고 잠재적
실패 경로를 세운다. 각 후보를 확인하는 데 필요한 만큼만 다음 연결을 따라간다.

- 호출자와 피호출자
- 인터페이스와 구현
- 공개 API·스키마·프로토콜과 소비자
- 데이터 모델, 저장소와 마이그레이션
- 설정, 트랜잭션과 동시성 경계
- 관련 도메인 규칙과 테스트

파일명이나 프레임워크 관례만으로 동작을 단정하지 않는다. 정의와 참조를 검색해 실제 입력,
상태 전이, 실패 처리와 출력까지 추적한다.

## 3. 위험 순서로 조사한다

[finding 정책](references/finding-policy.md)의 위험 우선순위를 적용하되, 변경과 관련된
항목만 조사한다. 저장소 고유 규칙은 가장 가까운 `AGENTS.md`에서 가져오고 Skill에
추측해서 보충하지 않는다.

포맷, import 순서, 단순 정적 규칙처럼 결정적 도구가 맡은 영역은 도구 결과에 맡긴다.
Spotless, Checkstyle, 컴파일러, 테스트 또는 CI가 이미 정확히 설명하는 항목을 LLM finding으로
중복 보고하지 않는다.

## 4. 의심을 검증한 뒤 선별한다

각 후보를 다음 루프로 처리한다.

```text
의심 → 관련 경로 조사 → 실패 조건 검증 → finding 또는 제외
```

1. diff와 저장소 불변식에서 의심을 만든다.
2. 필요한 호출 위치, 계약과 테스트만 읽어 도달 가능성을 확인한다.
3. 이번 변경과 실패의 인과관계, 구체적인 입력·상태와 관찰 가능한 영향을 입증한다.
4. 유용하면 좁은 테스트, 빌드 또는 정적 검사를 실행한다.
5. finding 정책의 인정 조건을 모두 만족할 때만 보고한다.

기존 테스트 통과를 정확성의 충분조건으로 취급하지 않는다. 반대로 테스트가 없다는 사실만
finding으로 만들지 말고, 보호되지 않는 구체적 회귀와 현재 테스트가 놓치는 이유를
입증한다. 끝까지 입증하지 못한 의심은 finding에서 제외한다.

## 5. 읽기 전용으로 검증한다

- 검증을 통과시키려고 코드, 테스트, 설정 또는 기준을 수정하지 않는다.
- 추적 파일을 쓸 수 있는 생성 작업은 현재 작업 트리에서 실행하지 않는다. dry-run으로
  충분히 검증하거나 임시 복제본·별도 worktree에서 실행하고, 불가능하면 미검증으로
  보고한다.
- 실행하지 못한 검증을 성공으로 간주하지 않는다.
- 명시적으로 수정을 요청받지 않았다면 리뷰 뒤에도 파일을 변경하지 않는다.

중요 동작, 데이터 경계 또는 여러 계층을 바꾸는 리뷰라면 새 서브에이전트 하나에 같은
범위와 이 Skill만 제공해 독립 검토를 맡긴다. 예상 결론이나 먼저 찾은 후보를 전달하지
않고, 결과를 원본 근거에 다시 대조한다. 독립 검토자로 호출된 에이전트는 재위임하지 않는다.
서브에이전트를 사용할 수 없으면 생략 사실만 기록하고 리뷰를 계속한다.

## 6. finding부터 보고한다

심각도순으로 작성하고 각 finding은 하나의 수정 가능한 결함만 다룬다.

```markdown
## Findings

### [P1 | P2 | P3] 짧은 명령형 제목

`path/to/file:line`

문제, 구체적인 실패 조건, 이번 변경이 원인인 이유와 가장 작은 수정 방향을 간결하게
설명한다.

## Final assessment

- Verdict: correct | incorrect
- Verification performed: 실행한 검증과 결과
- Unverified risks: 실행하지 못한 검증 또는 중요한 불확실성
- Confidence: 0.0–1.0
```

실행 가능한 finding이 없으면 `No actionable findings.`라고 명시하고 `Verdict: correct`로
판정한다. 하나라도 있으면 `Verdict: incorrect`로 판정한다. confidence는 검토 범위와
근거의 완전성을 반영하며, finding 수를 늘리는 데 사용하지 않는다.

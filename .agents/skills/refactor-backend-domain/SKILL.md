# Refactor Backend Domain

도메인이 불변 상태와 판단 책임을 스스로 감추어 가지게 한다. 외부에는 내부 자료 구조가
아니라 의미 있는 행동을 제공하고, 생성·검증·집계·표현 책임은 가장 가까운 한 곳에만 둔다.
편의를 위한 중복 상태와 실제 근거가 없는 방어 로직은 만들지 않는다.

사용자의 구체적인 지시와 저장소 규칙을 이 Skill보다 우선한다. 이 Skill을 적용한다는
이유만으로 요청하지 않은 영역, API 계약 또는 외부 동작까지 바꾸지 않는다.
사용자가 설계 의도와 불편했던 이유를 설명했다면 이를 단순 선호가 아니라 이번 작업의
완료 조건으로 기록하고, 구현과 검증에서 직접 확인한다.

## 1. 요청의 진행 단계를 판별한다

다음 기준으로 바로 구현할지 구조를 먼저 제안할지 결정한다.

- 설명, 판단 또는 구조 제안만 요청했다면 파일을 수정하지 않는다.
- 사용자가 구체적인 변경 형태를 지정했거나 앞서 제안한 구조를 승인했다면 그 범위만
  구현한다.
- 책임 이동, 공개 계약 변경 또는 여러 도메인 경계에 걸친 리팩터링인데 구조가 승인되지
  않았다면 코드를 수정하기 전에 현재 문제, 책임 배치, 예상 변경 파일과 유지할 동작을
  제안하고 승인을 기다린다.
- 한 객체 내부의 명백하고 작은 캡슐화 정리라면 별도 승인 단계를 만들지 않고 진행한다.

구조 제안은 구현 세부를 길게 나열하지 않는다. 다음 판단에 필요한 내용만 제공한다.

1. 현재 어떤 객체가 어떤 책임을 잘못 갖고 있는가
2. 그 책임을 어느 객체로 옮길 것인가
3. 생성자, 정적 팩토리와 자료 구조가 어떻게 달라지는가
4. API, 예외와 데이터 계약 중 무엇을 그대로 유지하는가
5. 선택지가 둘 이상이면 각각의 실제 장단점이 무엇인가

## 2. 실제 코드에서 책임을 복원한다

대상 디렉터리에 적용되는 지침과 아키텍처 문서를 먼저 읽는다. 대상 타입만 보지 말고
생성 위치, 호출자, DTO 변환, 저장소, 관련 테스트와 공개 계약까지 필요한 범위로 추적한다.

각 상태와 로직을 다음 소유 기준으로 분류한다.

| 대상 | 책임을 둘 곳 |
| --- | --- |
| 객체 하나의 필드 조합과 판단 | 해당 도메인 객체 |
| 여러 원소 사이의 유일성·관계·탐색 | 해당 일급 컬렉션 |
| 여러 제품 등 집합을 대상으로 한 계산·집계 | 그 집합을 소유한 도메인 |
| 저장 형식 읽기와 도메인 생성 연결 | Repository |
| HTTP 요청·응답 표현과 값 복사 | DTO 변환 경계 |

어떤 타입의 ID가 결과에 등장한다는 이유만으로 그 타입에 계산 책임을 두지 않는다. 실제
계산 대상과 필요한 지식을 가진 객체를 기준으로 책임을 배치한다.

## 3. 캡슐화를 상태 노출이 아니라 행동으로 만든다

- 식별자, 불변식 또는 행동을 소유하는 핵심 도메인 객체는 현재 필드가 적더라도 일반
  클래스로 선언하고 모든 상태를 `private final`로 둔다.
- `record`는 DTO, 저장소 조회 결과처럼 데이터 전달이 주목적이고 도메인 행동을 소유하지
  않는 타입에만 사용한다. 모든 record를 기계적으로 클래스로 바꾸지 않는다.
- 공개 접근자가 있다는 이유로 외부에서 값을 꺼내 도메인 판단을 작성하지 않는다.
- 조건과 계산에 도메인 의미가 있다면 `isParent()`, `isChildOf(parent)`,
  `containsIngredient(ingredient)`처럼 해당 객체의 행동으로 표현한다.
- 새 행동은 객체 자신의 상태를 사용해 의미 있는 판단이나 변화를 수행해야 한다. 필드를
  그대로 반환하거나 외부 판단을 위한 재료만 바꾸어 노출하는 메서드는 이름이 달라도
  접근자다.

접근자가 발견되면 호출 목적을 먼저 분류한다.

| 사용 목적 | 처리 기준 |
| --- | --- |
| DTO 변환, 직렬화, Repository 연결 | 경계에 필요한 최소 접근자를 유지한다. |
| 일급 컬렉션의 인덱싱, 정렬, 집계 | 컬렉션 책임에 필요한 최소 접근자를 허용한다. |
| 호출자가 값을 꺼내 조건을 판단하거나 계산 | 판단·계산을 상태 소유자의 행동으로 옮긴다. |
| 실제 호출자나 계약이 없음 | 접근 제한자로 숨기지 말고 제거한다. |

`public` 접근자를 package-private 또는 `private`으로 낮추는 것만으로는 책임이 이동하지
않는다. 공개 도메인 타입의 의미 있는 행동도 접근자 제거를 명분으로 임의로 축소하지
않는다. 접근 제한자 변경은 호출자가 새 도메인 행동을 사용하게 되어 기존 접근자가
불필요해진 결과일 때만 수행한다. 클래스로 바꾼 뒤 기존 record 접근자를 그대로 사용하거나,
접근자 이름과 가시성만 바꾸어 외부 판단을 유지한 변경은 캡슐화 완료로 보지 않는다.

핵심 객체와 파생 상태를 함께 보관하는 보조 객체나 일급 컬렉션이 핵심 객체의 값을 꺼내
판단한다면 책임을 대신 소유하고 있는지 확인한다. 파생 상태와 행동이 핵심 객체의 생명주기와
불변식에 속하면 핵심 객체로 옮긴다. 보조 객체가 별개의 개념, 생명주기 또는 정책을 실제로
소유할 때만 분리를 유지한다.

도메인 값 동등성은 실제 사용처가 요구할 때만 구현한다. 집계 기준이 ID라면 객체 전체에
`equals`와 `hashCode`를 추가해 Map 키로 만들지 말고 안정적인 ID를 키로 사용한다.

## 4. 생성자와 정적 팩토리를 구분한다

입력값을 검증한 뒤 같은 형태로 필드에 할당하는 객체는 생성자를 사용한다.

```text
입력 검증 → 필드 할당
```

자료 구조 변환, 인덱싱, 여러 객체의 조립 또는 이름 붙일 생성 과정이 있으면 정적 팩토리를
사용한다.

```text
입력 복사 → 검증·인덱싱·조립 → 완성된 상태를 private 생성자에 전달
```

- 검증이 끝나기 전에 필드에 값을 넣지 않는다.
- 생성자에서 스트림 집계, List-to-Map 변환이나 외부 조회를 수행하지 않는다.
- 완성된 내부 상태를 호출자에게 만들게 해 캡슐화를 깨지 않는다.
- 정적 팩토리를 관례처럼 붙이지 않는다. 입력과 내부 상태가 같고 조립 과정이 없다면
  생성자를 사용한다.

## 5. 상태의 권위 원천을 하나만 둔다

같은 원소를 조회 편의를 위해 `List`와 `Map`에 동시에 보관하지 않는다. 하나의 대표 자료
구조를 선택하고 순회가 필요하면 그 구조의 view를 사용한다.

- ID 조회가 중심이면 `Map<Long, T>` 하나를 우선한다.
- 입력 순서가 계약이면 순서를 보존하는 Map 구현을 선택한다.
- 성능 최적화를 이유로 중복 상태를 추가하려면 실제 병목과 동기화 전략을 먼저 입증한다.
- 서로 다른 데이터나 서로 다른 의미를 가진 컬렉션까지 하나로 합치지 않는다.

ID로 원소 하나를 찾을 때는 Map에서 직접 조회한다. 부모부터 자식까지의 경로처럼 실제
계층 관계를 탐색할 때만 부모 참조를 재귀적으로 따라간다. 현재 데이터의 깊이가 1이라는
가정을 코드에 넣지 않되, 단순 ID 조회까지 재귀 탐색으로 바꾸지 않는다.

필드와 지역변수 이름은 `byId`, `values`, `data`, `result`처럼 구현 방식만 드러내지 않게
한다. `categories`, `tags`, `indexedTags`, `productCounts`처럼 값의 도메인 의미나 처리
단계를 드러낸다.

## 6. 필요한 불변식만 한 번 검증한다

검증마다 다음 질문에 답한다.

1. 어떤 잘못된 상태를 막는가?
2. 그 상태가 실제 도메인에서 유효할 가능성은 없는가?
3. 더 가까운 객체나 자료 구조가 이미 보장하는가?
4. 이 객체가 여러 원소를 함께 알아야만 확인할 수 있는가?
5. 실패 시점과 예외 형태를 별도로 유지할 이유가 있는가?

개별 객체의 필드 조합은 개별 객체가 검증한다. 원소 간 중복, 참조 관계처럼 여러 원소가
필요한 불변식만 일급 컬렉션이 검증한다. Repository는 저장소 형식 오류를 다루되 도메인
불변식을 중복 검증하지 않는다.

모든 가능한 이상 상태를 선제적으로 막지 않는다. 현재 데이터와 규칙으로 설명할 수 없는
검증, 미래 가능성만을 위한 검증, 자료 구조 생성 과정과 중복되는 장황한 검증은 제거한다.
다만 도메인에 필요한 오류 의미나 실패 경계를 자료 구조의 우연한 예외에 맡기지는 않는다.

## 7. 읽기 쉬운 처리 단계를 남긴다

메서드 체이닝을 무조건 한 줄로 압축하지 않는다. 조회, 필터, 집계와 변환처럼 의미가 다른
단계는 이름 있는 지역변수로 분리한다. 이름을 붙여도 새로운 의미가 생기지 않는 단순
표현식까지 기계적으로 풀어 쓰지 않는다.

주석으로 처리 순서를 설명하기 전에 변수명과 도메인 메서드로 의도를 드러낸다. 구현
자료 구조보다 업무 의미가 먼저 읽히게 한다.

## 8. DTO와 공개 계약을 분리한다

- 같은 의미의 응답 DTO를 엔드포인트마다 중복하지 않는다.
- 공유 표현은 그 개념을 정의하는 기능이 소유한다.
- 한 기능에서만 사용하는 투영은 그 기능이 소유한다.
- DTO 하나당 파일 하나를 사용한다.
- DTO 수를 줄이는 과정에서 기존 JSON 필드, 중첩 구조, 상태 코드와 예외 코드를 임의로
  바꾸지 않는다.

DTO 변환은 도메인 값을 꺼낼 수 있는 경계다. DTO 편의를 위해 도메인이 응답 구조를 알게
하거나 응답 조립 책임을 도메인에 넣지 않는다.

getter를 없애기 위해 핵심 객체에 DTO 조립, 외부 조회, 여러 카탈로그의 결합이나 다른
도메인의 정책을 주입하지 않는다. 여러 객체를 조합하는 책임은 응답 팩토리, 조회 서비스
또는 해당 조합을 나타내는 별도 도메인에 둔다. 이 책임을 핵심 객체로 옮겨야만 접근자를
없앨 수 있다면, 핵심 객체를 오염시키기보다 경계의 최소 접근자를 유지하고 이유를 남긴다.

## 9. 최소 범위로 구현한다

승인된 구조를 가장 작은 완결된 변경으로 적용한다.

1. 책임을 받을 도메인 객체를 먼저 수정한다.
2. 호출자가 새 행동이나 생성 경계를 사용하게 한다.
3. 이전 책임과 중복 상태를 제거한다.
4. 테스트를 새 책임의 소유자에게 이동하거나 추가한다.
5. 코드만으로 복구하기 어려운 책임 경계만 아키텍처 문서에 남긴다.

관련 있다는 이유만으로 인접 도메인까지 정리하지 않는다. 기존 코드의 모든 체이닝,
이름과 접근자를 한 번에 정리하지 않는다. 작업 중 더 큰 문제가 보이면 현재 변경에 반드시
필요한지 먼저 판단하고, 필요하지 않으면 보고만 한다.

## 10. 검증하고 결과를 보고한다

관련 테스트를 먼저 실행하고 저장소가 지정한 전체 완료 명령을 실행한다. 동작이나 공개
계약을 유지해야 한다면 이를 직접 확인하는 테스트를 보존하거나 추가한다. 실패한 검증을
삭제하거나 약화하지 않는다.

테스트는 접근자 반환값과 내부 컬렉션 모양보다 새 도메인 행동과 불변식을 검증한다. 접근자를
제거할 때 기존 테스트를 삭제하는 데서 끝내지 말고 같은 의미를 행동 기반 검증으로 대체한다.
불변 컬렉션을 검증할 때는 구현 타입을 확인하기보다 입력 컬렉션 변경 이후에도 도메인 행동이
안정적인지 확인한다.

완료 전에 다음 책임 이동 증거를 확인한다.

1. 변경 전 어느 호출자가 어떤 상태를 꺼내 무슨 판단이나 계산을 했는가?
2. 그 판단이나 계산을 지금 어느 객체가 소유하는가?
3. 새 메서드는 실제 행동인가, 이름만 바꾼 접근자인가?
4. 접근 제한자만 변경한 메서드가 있다면 책임 이동과 별개인 근거가 있는가?
5. 남은 접근자는 어떤 DTO, 저장소 또는 집계 경계에 필요한가?
6. getter 제거를 위해 핵심 객체가 다른 계층이나 도메인의 책임을 떠안지 않았는가?
7. 새 소유권과 불변식을 행동 기반 테스트로 검증했는가?

접근 제한자만 낮춘 변경을 책임 이동의 대체물로 사용했거나 위 질문에 답할 수 없다면
리팩터링은 완료되지 않은 것으로 판정한다.

완료 보고에는 다음 내용만 간결하게 포함한다.

- 책임과 내부 구조가 어떻게 달라졌는지
- 유지한 공개 계약
- 실행한 검증과 결과
- 승인 범위 밖이라 수정하지 않은 중요한 항목

구조 제안 단계에서는 구현을 완료한 것처럼 쓰지 않는다. 검증하지 않은 결과를 성공으로
보고하지 않는다.

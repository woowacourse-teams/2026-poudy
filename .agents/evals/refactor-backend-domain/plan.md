# 도메인 리팩터링 Skill 평가 계획

## 상태

- 상태: 활성 계획
- 시작일: 2026-08-25
- 평가 대상: `.agents/skills/refactor-backend-domain/SKILL.md`
- 기준 코드: `df94f0d4c87e4f9d2129c3c0d8fc1f23d53f4f54`
- 참고 결과: `ad56bd132746f7401db44cf096f4b8634bed5d70`
- 참고 브랜치: `refactor/category-tag-domain`

이 계획은 도메인 리팩터링 Skill이 사용자의 설계 의도를 얼마나 재현하는지 측정하고,
실패 근거를 다음 Skill 개선으로 환류하는 과정을 소유한다. 아직 구현하지 않은 평가 도구와
실행 결과를 현재 사실처럼 기록하지 않는다.

## 배경

카테고리와 태그 도메인 리팩터링은 최초 요구를 한 번에 구현한 결과가 아니다. 도메인
캡슐화, 생성자와 정적 팩토리의 구분, 검증 책임, 집계 책임, 컬렉션 구조, DTO 소유권과
가독성에 대한 반복적인 피드백을 거쳐 최종 구조가 만들어졌다.

현재 Skill은 이 과정에서 확인된 판단 기준을 일반화해 기록한 첫 버전이다. 다음을 구분해
검증해야 한다.

- 과거 작업에서 나온 기준을 같은 코드에 다시 적용하는 재현 능력
- Skill 없이 작업할 때와 비교한 실제 개선 폭
- 같은 Skill을 반복 실행했을 때의 결과 변동
- Skill 작성에 사용하지 않은 문제에도 기준을 적용하는 일반화 능력
- 점수 상승이 특정 정답 diff의 암기나 평가 기준 변경에서 온 것은 아닌지

첫 사례는 Skill 작성에 사용된 작업이므로 일반화 시험이 아니라 교정용 replay 사례다.
일반화 성능은 별도의 holdout 사례가 추가된 뒤 판단한다.

## 목표

1. 같은 입력과 실행 조건에서 Skill 유무에 따른 결과 차이를 재현 가능하게 측정한다.
2. 실제 리팩터링 결과와의 의미적 거리를 수치와 근거로 남긴다.
3. 사용자가 추가로 교정해야 했던 양과 심각도를 기록한다.
4. Skill 변경 전후의 개선과 회귀를 같은 평가 기준으로 비교한다.
5. 각 Skill 수정이 어떤 관찰된 실패를 해결하려는 것인지 추적한다.
6. replay 점수와 holdout 점수를 분리해 과적합을 드러낸다.

코드 라인이나 파일 구성이 참고 결과와 같은지를 최종 목표로 삼지 않는다. 같은 책임과
계약을 더 작은 변경으로 올바르게 구현했다면 동등하거나 더 나은 결과로 평가할 수 있다.

## 평가 원칙

### 실행과 평가를 분리한다

실행 에이전트에는 다음 정보만 제공한다.

- 기준 코드
- 동결된 사용자 요청
- 저장소 지침
- treatment일 때만 평가 대상 Skill
- 모든 조건에 동일한 승인 문구

참고 브랜치, 결정 목록, 점수 기준과 이전 실행 결과는 제공하지 않는다. 평가자는 실행이
끝난 뒤 결과 patch와 검증 기록을 기준으로 채점한다. 가능하면 실행 조건을 모르는 독립
평가자가 같은 rubric으로 교차 확인한다.

### 명시적 요구와 사후 결정을 구분한다

실제 대화에서는 일부 요구가 뒤에서 변경됐다. 최초 요청과 충돌하는 사후 결정을 숨은 정답으로
두면, 명시적 사용자 지시를 잘 따른 실행이 오히려 감점된다.

평가를 시작하기 전에 최종 대화와 참고 결과에서 결정 목록을 만들고 각 항목을 다음 중 하나로
분류한다.

- `required`: 동결된 요청과 충돌하지 않으며 반드시 재현해야 하는 의도
- `acceptable`: 같은 책임과 계약을 만족하는 허용 가능한 대안
- `excluded`: 대화 중 폐기됐거나 우연한 구현 세부라 점수에 넣지 않는 항목

동결된 요청과 충돌하는 최종 결정은 요청을 최종 의도에 맞게 고쳐 쓸지, 해당 결정을 평가에서
제외할지 먼저 선택한다. 실행 결과를 본 뒤 분류를 바꾸지 않는다.

### 관찰 가능한 과정만 기록한다

전 과정 기록에는 다음을 포함한다.

- 사용자에게 전달된 프롬프트와 승인 문구
- 에이전트가 사용자에게 보인 응답
- 실행한 도구와 명령 및 종료 결과
- 최종 working-tree patch
- 테스트와 검증 결과
- 사용자 교정과 평가자의 판정 근거

모델의 비공개 내부 추론은 수집하거나 평가 항목으로 사용하지 않는다.

### 원본 실행을 보존한다

실행 결과와 원점수는 수정하지 않는다. Skill이나 rubric이 바뀌면 새 버전과 새 실행으로
기록한다. 새 rubric으로 과거 결과를 다시 평가할 수는 있지만 기존 점수를 덮어쓰지 않고
별도 평가 버전으로 남긴다.

## 실험 조건

### 공통 조건

- 기준 커밋은 `df94f0d4c87e4f9d2129c3c0d8fc1f23d53f4f54`로 고정한다.
- 기준 커밋에서 매 실행마다 새로운 임시 Git worktree를 만든다.
- 현재 작업 트리나 참고 브랜치를 checkout으로 되돌리지 않는다.
- 이전 대화와 실행 결과를 상속하지 않는 새 Codex 실행 세션에서 각 run을 시작한다.
- 모델, reasoning effort, 도구, 권한, 프롬프트와 승인 문구를 동일하게 유지한다.
- baseline에서는 평가 대상 Skill이 사용 가능한 Skill 목록에 없음을 실행 전에 확인한다.
- treatment에서는 Skill을 절대 경로로 읽게 하고 실험 worktree의 결과 diff에는 복사하지 않는다.
- 실행 에이전트는 참고 결과와 다른 실행의 산출물을 읽지 못하게 한다.
- worktree는 실행 후 바로 삭제하지 않고 결과 수집과 검증이 끝난 뒤 정리한다.

실행 도구가 새 세션의 Skill 노출 범위를 통제하거나 확인할 수 없다면 baseline을 실행하지
않는다. Skill을 사용할 수 있었는지 알 수 없는 baseline은 비교군으로 인정하지 않는다.

### 비교군

| 조건 | 설명 |
| --- | --- |
| `baseline-v0` | 도메인 리팩터링 Skill 없이 같은 요청을 수행한다. |
| `skill-v1` | 현재 Skill을 명시적으로 적용해 같은 요청을 수행한다. |
| `skill-vN` | 관찰된 실패를 근거로 수정한 후속 Skill을 적용한다. |

파일럿은 `baseline-v0`와 `skill-v1`을 한 번씩 실행해 하네스와 기록 누락만 확인한다. 파일럿
결과는 공식 평균에 포함하지 않는다. 프로토콜이 정상화되면 각 조건을 최소 3회 실행한다.

### 상호작용

각 실행은 두 단계로 나눈다.

1. 구조 제안
2. 고정 승인 후 구현과 검증

모든 실행에 같은 승인 문구를 사용한다.

```text
제안한 구조를 기존 API 계약을 유지하는 범위에서 구현해.
관련 테스트와 프로젝트 전체 검증까지 진행해.
```

이 승인 자체는 사용자 교정으로 계산하지 않는다. 공식 실행에서는 승인 뒤 추가 피드백을
주지 않는다. 추가 피드백 없이 완료하지 못했다면 누락, 잘못된 판단 또는 차단 상태를 그대로
기록한다.

별도의 협업 비용 실험에서는 사람이 실제로 개입할 수 있다. 이 경우 구현 점수와 섞지 않고
교정 횟수, 심각도와 완료까지 걸린 turn을 별도로 비교한다.

## 평가 지표

하나의 종합 점수와 함께 모든 하위 점수를 보존한다.

### 1. 의도 일치도

동결된 `required` 결정을 가중 항목으로 나눈다.

- `TP`: 의도한 결정을 올바르게 구현했다.
- `FN`: 의도한 결정을 누락하거나 반대로 구현했다.
- `FP`: 요청하지 않은 구조 변경이나 책임을 추가했다.

```text
weighted precision = TP weight / (TP weight + FP weight)
weighted recall = TP weight / (TP weight + FN weight)
intent F1 = 2 × precision × recall / (precision + recall)
```

허용 가능한 대안은 구현 모양이 참고 결과와 달라도 TP로 평가한다. 판단 근거가 없으면 자동
채점하지 않고 평가자 검토 대상으로 남긴다.

### 2. 공개 계약과 동작 보존

- 저장소 전체 검증 성공 여부
- 관련 도메인 테스트 성공 여부
- OpenAPI와 생성 API artifact의 의도하지 않은 변경 여부
- 기존 JSON 필드와 중첩 구조 유지 여부
- 예외와 상태 코드 유지가 요구된 범위에서의 회귀 여부

전체 검증 실패는 원인을 함께 기록한다. 환경 실패와 코드 실패를 구분하되 성공으로 간주하지
않는다.

### 3. 도메인 구조 품질

- 내부 상태가 불변이고 외부 판단 로직이 도메인 행동으로 이동했는가
- 생성자와 정적 팩토리의 선택이 실제 생성 과정과 맞는가
- 개별 객체, 일급 컬렉션, 집계 객체와 Repository의 책임이 중복되지 않는가
- 같은 상태를 여러 자료 구조에 중복 보관하지 않는가
- ID 조회와 계층 탐색을 올바르게 구분하는가
- 안정적인 식별자를 집계 기준으로 사용하는가

### 4. 범위와 최소성

- 요청과 직접 관련 없는 파일을 수정하지 않았는가
- 같은 결과를 위해 불필요한 타입, 접근자, 검증이나 캐시를 추가하지 않았는가
- 제거한 책임의 이전 구현과 테스트를 함께 정리했는가
- 코드만으로 알 수 없는 결정만 문서화했는가

변경 파일 precision과 recall, 추가·삭제 라인 수, 참고 결과와의 파일 교집합을 보조 지표로
기록한다. 라인 단위 patch 일치율은 의미적 품질 점수로 사용하지 않는다.

### 5. 실행 완결성

- 필요한 코드를 실제로 구현했는가
- 책임이 이동한 위치에 테스트를 추가하거나 옮겼는가
- 좁은 테스트와 공식 전체 검증을 실행했는가
- 실패를 우회하거나 검증 기준을 약화하지 않았는가
- 최종 diff에서 의도하지 않은 변경을 확인했는가

### 6. 협업 비용

공식 무개입 실행과 별개로 다음 값을 기록한다.

- 승인 외 추가 사용자 turn 수
- 교정 항목 수와 심각도
- 되돌린 변경 수
- 최초 응답부터 검증 완료까지의 경과 시간
- 검증 재시도와 실패 원인

교정 심각도는 실행 전에 다음과 같이 고정한다.

| 점수 | 교정 종류 |
| ---: | --- |
| 1 | 이름이나 표현의 작은 수정 |
| 3 | 한 객체 안의 작은 구조 수정 |
| 7 | 책임 위치나 생성 경계의 재설계 |
| 10 | 범위 이탈, 공개 계약 파손 또는 주요 변경의 원상복구 |

## 종합 점수

`Intent Fit Index`는 다음 가중치로 계산한다.

```text
45% 의도 F1
20% 공개 계약과 동작 보존
15% 도메인 구조 품질
10% 범위와 최소성
10% 실행 완결성
```

종합 점수만으로 Skill 버전을 채택하지 않는다. 각 하위 점수, 실행 간 분산, 협업 비용과
holdout 회귀를 함께 본다.

## 기록 구조

평가 하네스를 구현할 때 다음 구조를 기본으로 사용한다. 실제 필요가 확인되지 않은 파일은
미리 만들지 않는다.

```text
.agents/evals/refactor-backend-domain/
├── plan.md
├── protocol.md
├── rubric.yaml
├── summary.csv
├── cases/
│   └── category-tag-replay/
│       ├── case.yaml
│       ├── prompt.md
│       └── decisions.yaml
└── runs/
    └── <condition>/
        └── <run-id>/
            ├── metadata.json
            ├── prompt.md
            ├── response.md
            ├── commands.log
            ├── result.patch
            ├── verification.json
            ├── score.json
            └── evaluation.md
```

각 실행의 metadata에는 최소한 다음을 기록한다.

- 실행 ID와 시작·종료 시각
- 기준 커밋과 참고 결과 커밋
- Skill 이름과 파일 content hash
- 모델과 reasoning effort
- Codex runner와 앱·CLI 버전
- 실행 시 노출된 Skill 목록과 적용된 지침 파일
- 프롬프트와 rubric 버전
- 실행 worktree 경로
- 최종 Git 상태
- 평가자와 평가 시각

worktree 경로처럼 실행마다 달라지는 값은 결과 재현의 입력이 아니라 추적 정보로만 사용한다.

## 단계별 작업

### 0. 평가 기준 동결

- [ ] 최초 요청과 후속 결정을 모아 replay용 canonical prompt를 작성한다.
- [ ] 참고 결과에서 의미 있는 결정을 추출한다.
- [ ] 각 결정을 `required`, `acceptable`, `excluded`로 분류한다.
- [ ] 항목별 가중치와 판정 근거를 `rubric.yaml`과 `decisions.yaml`에 고정한다.
- [ ] 동결된 prompt와 rubric이 참고 결과를 과도하게 암시하지 않는지 검토한다.

### 1. 최소 평가 하네스

- [ ] 기준 커밋에서 임시 worktree를 만드는 절차를 구현한다.
- [ ] Skill 미사용과 사용 조건을 동일한 실행 인터페이스로 만든다.
- [ ] 응답, 명령, patch와 검증 결과를 실행 디렉터리에 보존한다.
- [ ] 실행 에이전트가 참고 결과와 이전 실행에 접근하지 못하는지 확인한다.
- [ ] 중단된 실행도 실패 원인과 마지막 상태를 남기게 한다.

### 2. 파일럿

- [ ] `baseline-v0` 한 번을 실행한다.
- [ ] `skill-v1` 한 번을 실행한다.
- [ ] 파일럿 결과로 누락된 기록과 실행 오염만 수정한다.
- [ ] 파일럿을 근거로 의도 항목이나 가중치를 유리하게 바꾸지 않는다.
- [ ] 하네스 수정 뒤 두 조건을 다시 실행해 공식 실험 준비를 확인한다.

### 3. 공식 replay

- [ ] 각 조건을 최소 3회 독립 실행한다.
- [ ] 자동 지표와 평가자 rubric을 모두 적용한다.
- [ ] 조건별 평균, 중앙값, 범위와 표준편차를 기록한다.
- [ ] Skill 유무에 따른 점수 차이와 협업 비용 차이를 계산한다.
- [ ] 실행별 실패를 원본 patch와 명령 결과로 다시 확인한다.

### 4. Skill 개선

- [ ] 실패를 규칙 누락, 모호한 기준, 잘못된 트리거, 탐색 부족, 책임 판단 오류,
      범위 과다, 구현 누락과 검증 누락으로 분류한다.
- [ ] 반복되거나 영향이 큰 실패만 Skill 개선 후보로 선택한다.
- [ ] 실패 하나를 막는 가장 작은 지침 변경을 적용한다.
- [ ] Skill content hash를 새 버전으로 기록한다.
- [ ] 기존 replay 전체를 다시 실행해 개선과 회귀를 비교한다.
- [ ] 개선 근거가 없거나 평균만 높이고 분산·회귀가 커지면 변경을 채택하지 않는다.

### 5. Holdout 확장

- [ ] Skill 작성에 사용하지 않은 도메인 문제를 최소 두 개 선정한다.
- [ ] 올바른 적용 사례와 규칙을 적용하면 오히려 나빠지는 반례를 함께 둔다.
- [ ] replay와 같은 방식으로 입력과 rubric을 먼저 동결한다.
- [ ] Skill 개선 때마다 replay와 holdout을 함께 실행한다.
- [ ] replay만 오르고 holdout이 떨어지면 과적합으로 기록한다.

## 실패 분류

각 실패는 다음 중 하나의 주원인과 필요한 경우 보조 원인을 갖는다.

| 분류 | 뜻 |
| --- | --- |
| `missing-rule` | 필요한 판단 기준이 Skill에 없다. |
| `ambiguous-rule` | 기준은 있지만 여러 방향으로 해석된다. |
| `misrouting` | Skill이 실행되지 않거나 관련 없는 작업에 실행된다. |
| `insufficient-discovery` | 호출자, 계약이나 기존 책임을 충분히 읽지 않았다. |
| `ownership-error` | 로직이나 상태를 잘못된 객체에 배치했다. |
| `scope-expansion` | 필요한 범위를 넘어 인접 코드를 수정했다. |
| `incomplete-implementation` | 제안한 구조를 코드와 호출부에 끝까지 반영하지 않았다. |
| `verification-gap` | 테스트나 공식 완료 조건을 실행·해석하지 못했다. |
| `execution-environment` | 권한, 도구 또는 환경 문제로 실행하지 못했다. |

한 번의 실패를 새 절대 규칙으로 바로 승격하지 않는다. 같은 원인이 반복되거나 한 번이라도
영향이 큰 경우에만 Skill 변경 후보로 삼는다.

## 버전 채택 기준

후속 Skill은 다음을 모두 만족할 때 현재 버전을 대체한다.

- replay의 평균 Intent Fit Index가 하락하지 않는다.
- replay의 핵심 `required` 항목에 새 회귀가 없다.
- holdout이 있다면 평균 점수가 하락하지 않는다.
- 범위 이탈이나 공개 계약 파손이 새로 발생하지 않는다.
- 개선하려던 실패가 실제 실행에서 줄었다.
- Skill 길이 증가가 관찰된 개선에 비례한다.

조건을 만족하지 못한 변경도 실행 결과와 폐기 이유를 기록한다. 점수가 가장 높은 한 번의
실행이 아니라 반복 실행의 결과와 분산을 기준으로 채택한다.

## 검증

평가 하네스 구현 단계에서는 다음을 확인한다.

- Skill은 `quick_validate.py`를 통과한다.
- case와 rubric 파일은 정의한 schema 검증을 통과한다.
- 같은 입력에서 점수 계산은 byte-identical한 결과를 만든다.
- baseline과 treatment는 Skill 제공 여부 외에 같은 실행 조건을 사용한다.
- 실행 전후 현재 작업 트리와 참고 브랜치가 바뀌지 않는다.
- 결과 patch는 기준 커밋에 적용할 수 있다.
- 코드 결과는 해당 저장소의 공식 완료 명령으로 검증한다.
- 하네스 변경은 `$audit-backend-harness`로 독립 감사한다.

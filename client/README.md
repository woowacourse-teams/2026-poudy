# client

Next.js 프론트엔드.

## 기술 스택

| 구분          | 선택 기술                           |
| ------------- | ----------------------------------- |
| 개발 언어     | TypeScript                          |
| 프레임워크    | Next.js 16.3.0 (App Router)         |
| UI 라이브러리 | React 19.2.8                        |
| 스타일링      | Tailwind CSS 4                      |
| 패키지 매니저 | pnpm 11.21.0                        |
| 코드 품질     | ESLint 9, Prettier 3                |
| 타입 검사     | TypeScript 5                        |
| 자동 검증     | Git hook (`pre-commit`, `pre-push`) |

## 요구 사항

Node.js 22 이상, pnpm 11.21.0.

저장소를 클론한 뒤 프로젝트 루트에서 `./setup-git.sh`를 한 번 실행합니다. Git hook과 커밋 메시지 템플릿을 등록합니다.

## 설치

```bash
pnpm install
```

`client`와 `common`은 저장소 루트의 pnpm 워크스페이스로 묶여 있습니다. `client`에서 설치해도 워크스페이스 전체가 설치되며, 락파일과 `node_modules`는 저장소 루트에 생깁니다.

## 환경 변수

`.env.example`을 복사해 `.env.local`을 만듭니다. 이 파일이 없으면 API 목 서버가 켜지지 않아 화면에 데이터가 나오지 않습니다.

```bash
cp .env.example .env.local
```

| 변수                        | 설명                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_API_MOCKING`   | `enabled`일 때만 MSW 목 서버를 켭니다. 실제 API에 붙일 때는 비웁니다.                 |
| `NEXT_PUBLIC_API_BASE_URL`  | 브라우저 API 주소. 목을 쓰는 동안에는 비워 둡니다.                                    |
| `POUDY_SERVER_API_BASE_URL` | 서버 컴포넌트·런타임 sitemap 전용 주소. 운영 systemd는 `127.0.0.1:8081`을 주입합니다. |
| `NEXT_PUBLIC_ENVIRONMENT`   | `production`에서만 검색 노출을 켭니다.                                                |
| `NEXT_PUBLIC_POSTHOG_KEY`   | PostHog 프로젝트 키. 비우면 PostHog 이벤트를 보내지 않습니다.                         |
| `NEXT_PUBLIC_POSTHOG_HOST`  | PostHog 수집 주소. 비우면 같은 출처의 `/ingest` 프록시를 사용합니다.                  |

## 실행

```bash
pnpm dev
```

개발 서버가 실행되면 [http://localhost:3000](http://localhost:3000)에서 확인합니다.

## 제품 상세의 렌더링과 캐시

제품 상세는 회원별 SSR로 렌더링합니다. 공통 제품 정보는 쿠키 없이 하루 동안 캐시하고,
회원별 제품 정보(`/api/users/me/products/{productId}`)는 세션 쿠키를 전달해 캐시 없이 병렬로 조회합니다.
서버가 받은 저장 상태를 본문과 축약형 버튼의 초기값으로 사용하며, 브라우저에서 전체 저장 제품 ID를 다시 조회하지 않습니다.
제품 목록에는 저장 버튼을 표시하지 않습니다.

회원별 SSR에는 페이지 요청에 `JSESSIONID`가 포함되어야 합니다. 운영·스테이징은 같은 오리진의
`/api` 프록시를 사용합니다. 로컬에서 다른 호스트의 API에 직접 로그인하면 API의 host-only 쿠키가
페이지 서버에 전달되지 않으므로, 회원별 SSR을 확인할 때도 같은 호스트의 `/api` 프록시를 사용해야 합니다.
서버의 `Set-Cookie`가 브라우저에 전달되지 않는 SSR 조회는 `X-Poudy-SSR: true`로 표시해
앱 쿠키 연장 기회를 다음 브라우저 요청에 남깁니다.

## API 목 서버

실제 API 서버 없이 화면을 개발할 수 있도록 [MSW](https://mswjs.io)로 응답을 가로챕니다. 브라우저 워커와 Node 서버를 함께 띄우므로 서버 렌더링 중의 요청도 목으로 처리합니다.

핸들러와 데이터는 `mocks/`에 있고, 데이터 값은 `design/v1.pen`의 화면에 적힌 것을 옮겼습니다.

`public/mockServiceWorker.js`는 MSW가 만드는 파일이라 직접 고치지 않습니다. MSW 버전을 올린 뒤에는 워커를 다시 만듭니다.

```bash
pnpm run msw:init
```

## 검사

각 검사를 따로 실행할 수 있습니다.

```bash
pnpm run lint
pnpm run format:check
pnpm run typecheck
```

커밋 전에 필요한 검사를 한 번에 실행하려면 `check`를 사용합니다.

```bash
pnpm run check
```

`check`는 ESLint, Prettier, TypeScript 검사, 테스트와 production build를 순서대로 실행합니다. ESLint와 Prettier는 캐시를 사용하므로 바뀐 파일만 다시 검사합니다. 캐시는 worktree마다 `client/node_modules/.cache`에 저장하며, 도구 버전이나 Node 버전, 설정이 바뀌면 전체 파일을 다시 검사합니다. Prettier 캐시는 기본 위치와 다른 경로에 저장합니다. `--cache` 없이 Prettier를 실행하면 기본 위치의 캐시가 지워지는데, `lint-staged`가 커밋할 때마다 그렇게 실행하기 때문입니다. `design-system/lint`의 규칙 코드만 바꾸면 ESLint가 변경을 감지하지 못할 수 있으므로, 이때는 `client/node_modules/.cache`를 지우고 다시 실행합니다. CI는 캐시 없이 전체 파일을 검사합니다.

Vitest의 `domain` 프로젝트는 순수 함수를 별도 초기화 없이 검사합니다.
HTTP 목을 검증하는 `mock-*` 테스트와 나머지 테스트는 `application` 프로젝트에서 MSW와 캐시 정리를 유지합니다.
React DOM 검사 도구는 jsdom 테스트에서만 불러옵니다.
테스트는 `vmThreads` 풀에서 돌아 파일마다 jsdom을 새로 만들지 않습니다. 이 풀에서는 `window.location`을 바꿀 수 없으므로,
주소를 읽거나 옮기는 코드는 `lib/navigation/browser-location`을 거치고 테스트는 이 모듈을 목으로 바꿉니다.
이 풀은 끝난 테스트 파일의 메모리를 돌려주지 않으므로, 워커가 300MB(`vmMemoryLimit`)를 넘기면 다음 파일 전에 새로 띄웁니다.

### PR 검사 범위

- dev 대상 PR에서 `client/`, `design-system/` 바로 아래 Markdown과 `docs/`의 Markdown만 바뀌면 포맷과 로컬 링크 대상을 검사합니다.
- 코드, 설정, 생성 파일, 의존성, CI 스크립트 변경은 전체 검사를 실행합니다. main 대상 PR도 항상 전체 검사합니다.
- `Client checks`(문서·포맷·린트·타입·Storybook), `Client tests`(테스트), `Client preview`(Preview 배포)가 동시에 돌고, `Client results`가 결과를 모읍니다.
- `Client Lighthouse`는 Preview 배포가 끝난 뒤 따로 돌며 머지 조건이 아닙니다. 배포마다 고정된 `vercel.app` 주소를 재므로 PR이 머지되어 `pr-<번호>` 별칭이 떨어져도 측정을 마칩니다. 문서 검사에 추가 러너를 만들지 않습니다. 실패 또는 취소된 검사는 통과시키지 않습니다.
- 문서 링크 검사는 Markdown 링크, 이미지, 참조 링크의 로컬 파일 존재를 확인합니다. 외부 주소, 제목 앵커와 HTML 링크는 검사하지 않습니다.

테스트별 실행 결과는 `client-ci-test-files` artifact에 `vitest-report.json`으로 보관하며, 일반 PR은
댓글용 `client-ci-results` artifact에도 함께 담습니다.
`dev → main` 릴리스 PR은 Preview 배포·Lighthouse·댓글용 결과 집계를 실행하지 않습니다.
`Client checks`에서 운영 주소와 환경으로 빌드를 검증하고, 포맷·린트·타입 검사와 전체 테스트는 유지합니다.
일반 PR의 Preview 배포와 Lighthouse는 기존 조건으로 실행합니다.

문서 전용 PR은 Preview 배포와 Lighthouse를 실행하지 않습니다. 검사가 끝나면 PR의
`Client checks` 결과를 확인하고, 실패 시 `Check documentation` 로그에서 원인을 확인합니다.

파일을 수정한 뒤 포맷을 적용할 때는 다음 명령을 실행합니다.

```bash
pnpm run format
```

## Git hook

프로젝트 루트의 Git hook이 Client 변경을 검사합니다.

- `pre-commit`: Client의 staged 파일에 `lint-staged`를 실행합니다.
- `pre-push`: push 대상 커밋에 Client 변경이나 루트의 워크스페이스 설정(`pnpm-lock.yaml`, `pnpm-workspace.yaml`, `package.json`) 변경이 있으면 `pnpm run check`를 실행합니다. 여러 worktree에서 함께 push해도 검사는 한 번에 하나씩만 실행하며, 나머지 push는 앞선 검사가 끝날 때까지 기다립니다. 타입 검사는 `check`의 `typecheck`에서 실행하므로, 이 hook에서는 `next build`의 타입 검사를 건너뜁니다. 테스트 워커는 4개로 제한합니다. push를 기다리는 동안에도 에디터와 개발 서버가 메모리를 쓰고 있기 때문입니다. 워커 수를 바꾸려면 `VITEST_MAX_WORKERS`를 지정해 push합니다.

hook을 우회했거나 설치하지 않은 경우에도 push 전에 다음 명령으로 같은 검사를 실행합니다.

```bash
pnpm run check
```

## API 타입

`common/api.zod.ts`는 Server의 OpenAPI 문서에서 생성합니다. Client에서 API 타입이 필요할 때 생성된 타입을 그대로 import합니다.

```ts
import type { ProductResponse } from "@poudy/api/api.zod";
```

`@poudy/api`는 저장소 루트의 `common/`을 워크스페이스 패키지로 등록한 것입니다. `client/package.json`에 `workspace:*`로 선언되어 있어서, 설치하면 `common/`에 연결됩니다.

같은 파일에는 응답 타입과 이름이 같은 Zod 스키마도 들어 있습니다. API를 호출할 때는 이 스키마를 `apiGet`, `apiPostForm`에 넘겨 응답을 런타임에 검증합니다. 기준과 이유는 [AGENTS.md](AGENTS.md)의 「TypeScript 기준」을 참고하세요.

```ts
import { BrandOverviewResponse } from "@poudy/api/api.zod";

apiGet("/api/brands", BrandOverviewResponse);
```

API 타입 생성 방법은 [Server README](../server/README.md#api-타입-생성)를 참고하세요.

## 법정 문서

`/privacy` 개인정보 처리방침과 `/terms` 이용약관을 정적 페이지로 둡니다. Play Console 앱 콘텐츠에
등록하는 개인정보 처리방침 URL 은 로그인 없이 열리는 공개 주소여야 하고, 앱이 웹뷰라 이 두 페이지가
스토어와 앱 양쪽을 함께 맡습니다.

운영 주체와 보호책임자, 시행일은 `components/legal/operator.ts` 한 곳에 있습니다. 문서 본문은
`app/privacy/page.tsx` 와 `app/terms/page.tsx` 입니다.

### 수집 항목을 바꿀 때

파우치의 유입·로그인 전환·회원 활용 지표와 수집 계약은 [파우치 분석 문서](lib/analytics/shelf.md)에 정리했습니다.
로그인 후 PostHog는 내부 회원 번호로 만든 식별자로 로그인 전후·기기 간 기록을 연결하고,
로그아웃·탈퇴 뒤에는 식별자를 초기화합니다. 이메일·회원 프로필·파우치 평가의 구체적인 값은 새 이벤트 속성으로 보내지 않습니다.

처리방침에 적은 내용과 실제 수집이 어긋나면 개인정보보호법 위반이고, Play Console 데이터 보안
설문과도 어긋나 게시가 막힙니다. 다음을 바꾸는 작업은 처리방침 제2조·제3조를 함께 고칩니다.

- `lib/analytics/track.ts` 의 PostHog 설정, 특히 마스킹 대상과 세션 녹화
- `lib/analytics/events.ts` 의 이벤트 속성
- 서버로 새로 보내는 값
- 서버가 검색어, 제품 조회처럼 이용 행동을 별도 파일이나 로그에 집계하는 값과 보유 기간

### 회원 정보와 서버 저장함

카카오·Google 소셜 로그인은 제공자와 소셜 계정 식별자, 인증된 이메일을 서버에 저장합니다.
회원 프로필은 닉네임·선택한 프로필 사진·성별·나이대·피부 타입(건성·지성·복합성)과 민감성 피부 여부이며, 회원 저장함은
회원 번호·제품 번호·저장 시각을 서버에 보관합니다. 파우치(`user_shelf_product`)는 회원 번호·제품 번호·
사용 상태·평가(잘 맞았는지, 수분감·유분감)·등록 시각을, `user_shelf_analysis_ingredient`는 회원별
성분 분석의 직전 결과를 보관합니다. 저장함과 파우치에서 제품을 빼면 행을 지우지 않고 뺀 시각(`deleted_at`)만
남겨 되돌릴 수 있게 하고, 탈퇴 후 회원 파기 때 함께 지웁니다. 나만의 필터(`user_my_filter_ingredient`)는
회원이 고른 성분을 보관합니다. 최근 검색어와 필터 조건은
브라우저에 남습니다. 로그아웃이나 사이트 데이터 삭제는 서버 저장함 삭제와 다릅니다.

탈퇴하면 세션을 종료하고 회원 기능을 중지합니다. 계정·프로필·저장함·파우치는 복구 요청 처리를 위해
30일 보관하고 운영 환경의 `UserRetentionService`가 매일 한국 시간 03:40에 삭제합니다.
회원 행 삭제 시 저장함과 파우치, 성분 분석 결과도 `ON DELETE CASCADE`로 삭제됩니다. 복구 요청 자체는 보관 기간을
연장하지 않으며, 운영자가 파기 전에 복구를 완료해야 합니다.

파우치 평가 이력(이슈 #817)은 파우치에 제품을 담거나 평가를 고칠 때마다 한 줄씩 쌓입니다. 파우치에서 빼거나
프로필만 바꿀 때는 기록하지 않습니다. 한 줄에는 제품 번호, 사용 상태, 평가(잘 맞았는지, 수분감·유분감),
그 시점의 성별·나이대·피부 타입·민감성 피부 여부를 값으로 복사하고, 같은 프로필로 남긴 최신 평가인지
표시하며, 기록 시각은 날짜까지만 둡니다. 분석에는 회원·제품·프로필마다 최신 평가 하나만 씁니다. 회원으로
있는 동안에는 파우치에서 빼도 이력이 남습니다. `UserRetentionService`가 회원 행을 지울 때 이력은
`ON DELETE SET NULL`로 회원 번호만 끊기고, 최신 평가 표시를 포함한 나머지는 개인을 알아볼 수 없는 통계
자료로 남아 제품 평가 분석(유수분 분석 개선)에 쓰입니다. 처리방침은 이 구조를 근거로 "회원 번호를 지운 뒤에는 특정 회원의 기록을 찾을 수 없다"고
안내합니다(제2조·제3조·제7조·제8조). 기록 시각을 시각 단위로 늘리거나, 한 사람의 기록끼리 묶는 키를
두거나, 전성분 같은 값을 함께 저장하면 이 안내가 사실과 어긋나므로 처리방침을 함께 고칩니다.

루틴(`routine`, `routine_product`)은 회원 번호·이름·메모·공개 여부·아침과 저녁 제품을, 루틴 좋아요와
댓글(`routine_like`, `routine_comment`)은 누른·쓴 회원 번호와 내용을 보관합니다. 공개 루틴과 그 댓글은 로그인하지
않은 이용자에게도 보이고, 작성자의 닉네임·프로필 사진·피부 타입(건성·지성·복합성)이 함께 표시됩니다. 민감성 피부
여부와 성별·나이대는 공개 응답에 넣지 않습니다. 공개 루틴을 가져가면 "작성자 닉네임 - 루틴 이름"과 메모·제품을
복사한 사본이 원본과 연결 없이 남으므로, 작성자가 탈퇴해 파기돼도 사본은 지워지지 않습니다. 탈퇴한 회원의 루틴과
좋아요·댓글은 바로 공개 목록에서 빠지고, 회원 파기 때 `ON DELETE CASCADE`로 삭제됩니다(이슈 #1160).
공개 응답에 넣는 작성자 정보나 가져오기 때 복사하는 값을 바꾸면 처리방침 제2조·제3조·제7조·제8조를 함께 고칩니다.

서버 오류 기록(이슈 #890)은 백엔드 로그 가운데 오류를 남긴 줄입니다. 웹 서버의 journald에는 오류 메시지와
스택까지 14일·200MB 한도로 남고, 모니터링 서버(Loki)에는 Alloy가 각 로그의 첫 줄(시각, 레벨, 기능, 앱이 쓴
메시지)만 7일 보관합니다. 첫 줄에는 회원 번호와 제품·의견 번호 같은 식별 번호만 쓰고 예외 메시지나 사용자 입력은
넣지 않습니다. `deploy/monitoring/alloy`의 로그 필터나 서버의 로그 메시지 규칙을 바꾸면 처리방침 제2조·제3조·제7조·
제8조의 서버 오류 기록 안내를 함께 확인합니다.

수집 항목·보유 기간·탈퇴와 복구 동작을 바꾸면 처리방침 제1조부터 제3조, 제7조부터 제10조와 이용약관 제2조부터 제4조,
Play Console 데이터 보안 설문을 함께 확인합니다. 문서별 시행일은 `operator.ts`, 개정 이력은
각 페이지에서 관리합니다. 개인정보 처리방침의 코드상 시행일은 2026년 11월 9일이며, 개정 이용약관은
2026년 12월 9일 시행 예정으로 표시합니다. 약관의 7일·30일 사전 안내 기준에 맞춰 이번 개정은
30일의 안내 기간을 확보합니다. 처음에는 10월 12일 안내 시작을 전제로 11월 11일에 시행할 예정이었지만, 루틴과
게시물 조항(이슈 #1160)을 더하면서 새로 더한 조항도 30일을 안내하도록 11월 9일 공개를 기준으로 시행일을
12월 9일로 옮겼습니다. 실제 공지가 늦어지면 공지 시작일로부터 최소 30일 뒤로 `operator.ts`의 약관 시행일을
조정해야 합니다.
`/terms`는 `components/legal/CurrentTerms.tsx`의 10월 4일 적용본을 기본으로 보여 주고,
`ScheduledTerms.tsx`의 개정 예정본은 닫힌 `details`에서 펼쳐볼 수 있도록 제공합니다.
10월 4일 적용본은 Git 커밋 `2f3bb50b`의 본문을 보존했으며, 과거 본문의 시행일과 운영자 정보는
현재 설정 변경의 영향을 받지 않도록 고정했습니다. 시행 시 `terms/page.tsx`의 기본 본문을
개정본으로 전환하고 사전 안내와 시행 예정 표기를 실제 시행 상태로 갱신합니다. 이 저장소 변경만으로 공지가 완료된 것으로 보지 않습니다.

개인정보 처리방침의 11월 9일 개정안은 루틴 안내를 추가하고 분석 도구와 문의 알림의 설명을 실제 처리에 맞춥니다.
실제 공개가 늦어지면 배포 전에 `operator.ts`의 개인정보 처리방침 시행일을 공개·적용 일정에 맞춥니다. 11월 8일까지의
개정 이력은 날짜를 고정해 두었으므로 새 시행일을 바꿔도 과거 이력이 함께 바뀌지 않습니다.

2026년 10월 12일 점검에서는 프로필 입력 시 하나 이상 선택하는 화면 조건과 마이페이지의 직접 수정,
위시리스트 명칭, 로그아웃·탈퇴·소셜 연결 해제의 차이를 반영했습니다. 웹 세션(1일 미사용·7일 절대 만료),
앱 세션(60일 미사용), 가입·중복 가입 안내·복구용 임시 세션(10분 미사용), 운영 서버의 세션 파일 보관과
재시작 유예(5분), 마지막 로그인 제공자의 로컬 저장도 실제 구현과 대조했습니다.
DB 백업은 [DB 운영 문서](../deploy/postgresql-ec2.md)의 S3 객체 생성 후 30일 만료 설정을 반영했습니다.
만료 후 실제 삭제는 비동기로 이루어지므로 정확히 30일째 삭제가 완료된다고 안내하지 않습니다.
운영 DB 삭제 후 백업에 남는 기간은 탈퇴 계정 복구를 위한 30일과 별개이며, 백업 보관으로 계정 복구 기간이
연장되지는 않습니다. 서버의 임시 덤프는 업로드 성공 시 삭제되지만 실패하면 남을 수 있고 S3 만료 규칙도
적용되지 않습니다.

2026년 10월 12일 운영자가 전달한 DB EC2 SSM 조회 결과에서도 백업 스크립트는 검사·업로드 성공 뒤에만
임시 덤프를 삭제하며, 실패하면 `set -e`로 종료되는 것을 확인했습니다. 조회 당시 `/var/backups/poudy`에는
파일이 없었습니다. `/etc/cron.daily`, `/etc/tmpfiles.d`, `/etc/systemd/system`에서 `poudy` 또는
`/var/backups`를 검색한 결과 백업 서비스·타이머만 발견됐고, `/etc/cron.d`는 존재하지 않았습니다.
이 확인 범위에서는 실패한 임시 덤프의 자동 삭제 설정을 찾지 못했습니다. 임시 덤프의 삭제 기한과
장애 복원 시 이미 삭제한 개인정보를 다시 제거하는 절차는 별도 운영 조치가 필요하며, 구현된 것으로
처리방침에 기재하지 않았습니다.

이번 점검은 [korean-privacy-terms의 privacy-kr 스킬](https://github.com/kimlawtech/korean-privacy-terms/blob/d8934d79a258e1427f1a6ad0247c100c01f3b3b8/skills/privacy-kr/SKILL.md)의
항목별 기준을 사용했습니다. 한국어 이용약관 템플릿이 비어 있어 기존 약관과 해당 스킬의
`ftc-standard-terms.md`를 대조했고, 무료 정보 서비스에 맞게 결제·배송 조항은 추가하지 않았습니다.
기존 TSX 문서와 디자인을 유지하며 [개인정보위의 2026.4 작성지침 개정 안내](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=&nttId=12021)도 확인했습니다.

### 인기 검색어와 인기 제품 집계

인기 검색어는 상품 검색 결과가 있는 정규화 검색어를 UTC 10분 구간별로 합산합니다. 최근 완결된
7일을 순위에 사용하고 직전 구간과 비교하므로 각 제출 기록은 계산에 최대 7일 20분 사용합니다.
기간을 벗어난 구간은 다음 상태 저장에 성공하면 집계 파일에서 제거됩니다. 모든 제품 검색은 별도
서버 검색 기록에도 남으며, 이 기록은 journald의 14일·200MB 한도 가운데 먼저 도달하는 기준에 따라
오래된 순서로 삭제됩니다.

제품 상세 화면이 표시되면 `ProductViewRecorder`가 제품 번호를 서버로 보냅니다. 서버는 제품 번호,
한국 날짜와 조회 횟수만 집계 파일에 두고 이용자·세션·IP 주소 식별자를 함께 저장하지 않습니다.
새로고침과 재방문은 각각 집계하며, 이 통계는 인기 제품 제공을 위해 서비스 운영 기간 동안 보관하고
서비스가 종료되거나 집계를 폐기할 때 파일을 삭제합니다. 제품 조회 요청의 주소와 IP 주소는 별도의
접속 기록 보유 기준을 따릅니다.

두 집계의 항목이나 기간을 바꿀 때에는 처리방침 제1조부터 제3조, 제7조부터 제9조, 이용약관의 순위
기준과 한계, 아래 Play Console 데이터 보안 표를 함께 고칩니다. 실제 Play Console 설문 변경은 배포
전에 수동으로 제출합니다. 인기 검색어 수집 호출을 클라이언트에 연결할 때에는 변경된 처리방침의
시행일 이후에 배포합니다.

다음 이벤트를 PostHog로 수집합니다.

  `popular_keyword_used`, `popular_keywords_expanded`, `skin_type_selected`, `ranking_category_changed`,

- 목록과 조건 조작 — `product_list_viewed`, `filter_applied`, `filter_reset`, `sort_applied`,
  `product_list_scrolled`, `empty_result_shown`, `filter_conflict_shown`
- 제품 진단 — `product_unsaved`, `ingredient_viewed`, `ingredient_condition_toggled`, `error_occurred`, 세션 녹화
- 상세 탐색 시간 — `detail_active_time_recorded`
- 웹에서 앱 설치 유입 — `app_install_clicked`, `app_install_landed`, `app_store_redirected`

앱 설치 유입은 [웹 → 앱 설치 유입 및 Google Play 이동](https://us.posthog.com/project/562550/insights/gpX6nbg5)에서
최근 30일 횟수를 경로별로 확인합니다. 운영 환경·`poudy.site` 조건과 프로젝트 테스트 계정 제외를 적용합니다.

| 이벤트                 | 의미                          | `source`                                           |
| ---------------------- | ----------------------------- | -------------------------------------------------- |
| `app_install_clicked`  | QR 링크 또는 상단 배너를 누름 | `qr_click`, `install_banner`                       |
| `app_install_landed`   | QR 주소가 브라우저에 도착함   | `qr_scan`, `qr_click`, `unknown`                   |
| `app_store_redirected` | Google Play로 보내기 직전     | `qr_scan`, `qr_click`, `install_banner`, `unknown` |

QR 그림에는 `/open-app?source=qr_scan`, 클릭 링크에는 `/open-app?source=qr_click`을 담습니다.
Android intent는 앱이 없을 때 `/open-app?source=…&store=google_play`를 거친 뒤 스토어로 보냅니다.
그래서 클릭 자체를 스토어 이동으로 세지 않으며, 스토어 fallback에서는 QR 도착을 다시 세지 않습니다.
표시가 없는 기존 QR·직접 방문은 `unknown`으로 남기고 QR 스캔으로 추정하지 않습니다.

이벤트는 외부 이동 전에 비콘으로 전송합니다. 초기 SDK 준비를 최대 1초 기다리되, 로딩 실패나 지연이
이동을 막지는 않습니다. 추적 거부·전송 실패는 집계에서 빠질 수 있습니다. 앱이 이미 설치되어 App Links가
바로 앱을 여는 QR 스캔은 웹 집계에 포함되지 않습니다. 다른 기기로 찍은 QR은 웹 방문자와 같은 사람으로
연결하지 않습니다. 스토어 이동은 Google Play의 로딩 완료나 설치 완료를 뜻하지 않으며 배포 이후부터만 수집합니다.

`detail_active_time_recorded`는 제품 상세와 성분 상세에서 사용자가 실제로 화면을 본 시간을 기록합니다.
탭이 보이고 창에 포커스가 있으며 마지막 입력 후 60초가 지나지 않은 동안에만 시간을 누적합니다.
`$prev_pageview_duration`은 숨은 탭과 자리를 비운 시간까지 포함하므로 활성 체류시간 지표로 쓰지 않습니다.
30초마다, 그리고 탭이 가려지거나 경로가 바뀌거나 화면을 떠날 때 직전 전송 이후에 늘어난 시간만
`active_seconds`로 보냅니다. 따라서 여러 이벤트의 `active_seconds`를 더해도 같은 시간이 두 번 집계되지 않습니다.

서비스 전체 활성 시간(#900)은 `AnalyticsProvider`가 공통 영역에서 측정합니다.
브라우저의 `useEffect`가 실행되고 지연 로딩한 PostHog SDK가 준비된 뒤 시작하므로,
서버 렌더링과 프리페치는 방문으로 기록하지 않습니다. 기존 SDK 지연 로딩은 유지합니다.

| 이벤트                         | 의미                                                       |
| ------------------------------ | ---------------------------------------------------------- |
| `service_session_started`      | 화면이 보이고 포커스를 가진 SDK 세션에서 한 번 기록한 방문 |
| `service_active_time_recorded` | 전체 화면의 활성 시간 증가분과 세션 누적 시간              |
| `service_active_time_reached`  | 같은 세션에서 활성 10·30·60초에 도달한 시점                |

활성 조건은 상세 측정과 같습니다. 전체 합계에는 `service_active_time_recorded.active_seconds`만
더하고 상세 이벤트를 함께 더하지 않습니다. 경로가 바뀌면 이전 경로로 증가분을 정산하며,
이벤트의 경로에는 검색어와 해시를 넣지 않습니다. 30초 주기로 증가분을 보내고,
10초 도달 이벤트는 주기 전송을 기다리지 않고 별도로 보냅니다.

실제 `$session_id`별 누적 값을 `localStorage`에 저장해 경로 이동과 새로고침 뒤에도 이어 셉니다.
SDK의 세션 변경 알림을 받아 세션을 구분하며 SDK 세션 ID를 매초 조회하지 않습니다.
1초 타이머로 메모리에서 활성 시간과 도달 여부를 확인합니다. 시간은 타이머 실행 횟수가 아닌
실제 경과 시간으로 계산하며, 저장소의 누적 값은 측정 시작, 10·30·60초 도달과 주기 전송,
경로 이동·탭 전환 때만 읽고 씁니다. 도달 이벤트는 타이머가 정상적으로 실행될 때
최대 약 1초 늦게 기록할 수 있습니다.
Web Locks를 지원하는 브라우저에서는 포커스를 가진 탭이 잠금을 잡고 측정해 여러 탭의 중복을 막습니다.
지원하지 않거나 잠금 접근이 거절되면 브라우저 포커스로 측정 탭을 구분합니다.
저장소 접근이 막히면 기존 저장 도구의 메모리 대체 경로를 쓰므로 새로고침 이후의 누적 보존은 제한됩니다.

[서비스 전체 활성 체류시간 대시보드](https://us.posthog.com/project/562550/dashboard/2248210)에
같은 세션의 방문→10초→30초→60초 퍼널, 일별 합계(간격을 주로 변경 가능), 사용자·세션별 합계를 둡니다.
신규 이벤트는 배포 이후부터 수집하며 리플레이와 기존 상세 지표를 과거 값으로 섞지 않습니다.
사용자·세션별 표의 사용자 30일 합계는 세션 행에 반복되므로 그 열을 행끼리 다시 합산하지 않습니다.
이벤트 보관 기간은 녹화의 30일 보관 기간과 별개인 제품 분석 이벤트 정책을 따릅니다.

큐레이션 캐러셀은 `home_section_viewed.section = curation`으로 실제 섹션 노출을 기록하고,
`curation_slide_viewed`로 가운데 카드가 바뀐 시점과 `transition = manual | autoplay`를 남깁니다.
[큐레이션 노출→수동 넘김 퍼널](https://us.posthog.com/project/562550/insights/7FSy0f6p)은 직접 조작만
집계합니다. 큐레이션 상세 화면이 생기기 전에는 `curation_opened`를 보내지 않습니다.

캐러셀 첫 장의 서비스 가이드는 큐레이션이 아니므로 `curation_slide_viewed`와 `curation_opened`를 보내지
않고, 두 이벤트의 `position`도 가이드를 뺀 큐레이션 목록 안에서 셉니다. 가이드를 누르면
`service_guide_opened`를 남기고, 서비스 소개(`/about`)는 `page_viewed.page = about`으로 집계합니다.

### 거부 방법

처리방침 제9조는 로그인 쿠키와 분석용 저장소를 구분합니다. 쿠키·사이트 데이터 차단은
식별자 저장을 제한하지만 분석 요청 자체의 중단을 보장하지 않습니다. 분석 수집 중단 방법은
추적 안 함 설정 또는 이메일 처리정지 요청이며, 앱 웹뷰에는 브라우저 설정 화면이 없습니다.

다만 `/ingest` 프록시가 추적 차단기를 우회하므로, 안내가 빈말이 되지 않도록 `track.ts` 에서
`respect_dnt` 를 켜 브라우저가 보낸 거부 신호를 직접 지킵니다. 프록시를 유지하는 한 이 설정도
함께 유지해야 합니다.

추적 안 함 설정은 PostHog에만 적용됩니다. 서비스 요청, 접속 기록, 서버 검색
기록과 인기 검색어·제품 조회수 집계는 이 설정으로 중단되지 않습니다. 집계 파일에는 이용자 식별자를
함께 저장하지 않으므로 이미 합산된 특정 이용자의 기여분을 찾아 분리할 수도 없습니다.

맞춤형 광고를 시작하면 이 판단이 바뀝니다. 그때는 거부 수단을 따로 만들고 제9조를 다시 씁니다.

### 개인정보 처리방침 점검 (2026년 11월 8일)

이번 변경은 현재 동작을 설명하는 문구에 한정합니다. 수집 범위·보관 설정·로그인·문의·알림 흐름은 바꾸지 않습니다.
추가 동의나 수집 제한이 필요한지는 기존 서비스의 목적과 처리 범위, 실제 계약을 먼저 확인해 판단합니다.

#### 확인하고 반영한 내용

- [Poudy PostHog 프로젝트](https://us.posthog.com/project/562550)의 설정을 읽어
  `session_recording_retention_period = 30d`, `capture_console_log_opt_in = true`,
  `capture_performance_opt_in = true`를 확인했습니다. 설정은 변경하지 않았습니다.
- 화면 조작 기록에 포함되는 콘솔 메시지와 네트워크 요청 주소·성능 정보를 처리방침 제1·2·3·5·6조에 반영했습니다.
  검색어와 필터 조건이 요청 주소에 있으면 함께 기록될 수 있습니다. 이 기록의 30일 보관과 별도로,
  분석 이벤트와 Person 프로필의 실제 삭제 설정은 아래 확인 목록에 남깁니다.
- `PendingImage`의 업로드 유효 기간은 24시간이고, 정리 대상 선정에는 10분 유예가 더해집니다.
  `PendingImageCleanupService`는 기본 5분 주기로 실행하며 실패한 삭제는 다시 시도합니다.
  문의에 연결하지 않은 이미지를 정확히 24시간 안에 지운다고 안내하던 제2·3조를 정정했습니다.
- `logout`·`withdraw`의 분석 식별자 초기화와 이미 전송한 기록의 삭제가 별개임을 제7조에 설명했습니다.
  제3조의 보관 기간을 늘리거나 새로운 삭제 연동을 추가하지 않았습니다.
- 보유 기간 표를 ‘처리 업무·법적 근거·보유 기간·보관 이유’로 나눴습니다. 이용자가 요청한 서비스 제공에는
  기존 안내의 제15조 제1항 제4호를 항목별로 표시했습니다. 안정성 확보·분석 등에 기존에 안내한 같은 항 제6호는
  적용 요건이 확인 중임을 함께 적어 확정된 근거와 구분했습니다. 문의 90일을 제21조의 법정 기간처럼 읽을 수 있던
  표현은 고쳤으며, 조문이 각 보관 일수를 정하는 것은 아니라고 설명했습니다.
- 탈퇴 후 복구 지원을 위한 보관, 선택 피부 정보, 백업 사본과 제품 요청 처리 후 장기 이력 보관에는 확인되지 않은
  조문을 새로 배정하지 않았습니다. 표에 확인 중이라고 표시하고, 실제 처리 근거를 확인할 항목으로 남깁니다.
  평가 이력은 기존 법적 근거 설명을 참조하도록만 연결했으며 보유 기간·보관 이유·파기·권리행사 설명을 유지했습니다.
- `/ingest` 프록시 설명을 PostHog로 한정했습니다. Google Analytics 태그까지 자사 주소로 전송한다고
  읽힐 수 있던 제9조의 표현을 정정했습니다.
- 로그인 안내에서 이용약관 동의와 개인정보 처리방침 확인을 구분했습니다. 가입 조건과 API 호출은 그대로입니다.

- Discord 알림의 본문 제거·관리자 링크 전환 또는 메시지 자동 삭제
- 백업 임시 사본 자동 삭제·복원 후 재삭제 절차와 푸시 토큰 등록·해제·파기 동작 변경

위 변경이 필요하다고 판단되면 기존 기능에 미치는 영향과 현재 기능을 유지할 수 있는 대안을 먼저 보고합니다.

### 개인정보 처리방침 점검 (2026년 11월 9일)

#1154에서 코드, PostHog 설정과 데이터, AWS 콘솔을 처리방침과 대조했습니다. 확인 결과는
[이슈 댓글](https://github.com/woowacourse-teams/2026-poudy/issues/1154#issuecomment-6730441687)에 있고, 여기에는 이후
작업에서 지켜야 할 기준과 팀이 정한 처리 방향을 남깁니다.

#### PostHog

- 프로젝트 설정의 IP 익명화(`anonymize_ips`)가 꺼져 있어 이벤트마다 IP 주소가 남습니다. Person 프로필에는 IP로 추정한
  시도·시군구·우편번호·위도·경도, 처음·최근 화면 주소, 이전 사이트 주소, User-Agent 원문, utm 값과 광고 클릭 ID가
  붙습니다. 처리방침 제2조의 "기기와 브라우저 정보"와 "유입 정보"가 이 항목을 안내합니다. IP 저장을 끄려면 팀원 제외
  필터 가운데 IP 기준 필터를 다른 기준으로 바꾸고 처리방침도 함께 고칩니다.
- 무료 플랜이라 이벤트는 1년, 녹화는 30일 보관합니다. Person 프로필과 속성은 이벤트 보관 기간과 관계없이 지울 때까지
  남으므로 아래 절차로 정리합니다.
- 화면 녹화는 입력값과 `data-private`를 붙인 영역(저장함 목록, 관리자 복구 화면)만 가립니다. 프로필의 피부 정보, 파우치
  평가, 마이페이지 이메일, 루틴과 댓글은 녹화에 담길 수 있고, 처리방침 제2조가 이를 안내합니다. 가리는 범위를 바꾸면
  이 안내도 고칩니다.
- 처리정지를 요청한 이용자의 수집을 막는 기능은 이번에 다루지 않았습니다.

#### PostHog Person 정리 절차

처리방침 제3조는 분석용 식별자와 이에 붙은 정보를 마지막으로 이용한 날로부터 1년이 지난 뒤 분기마다 하는 정리 작업에서
지운다고 안내합니다. 분기 첫 주에 다음을 합니다.

1. PostHog SQL 화면에서 최근 1년 동안 이벤트가 없는 Person을 찾습니다. 이벤트가 모두 만료된 Person은 `last_seen`이
   비어 있으므로 함께 잡힙니다. `not in` 하위 쿼리로 쓰면 PostHog가 events 표를 두 번 묶다가 실패합니다.

   ```sql
   select p.id
   from persons p
   left join (select person_id, max(timestamp) as last_seen from events group by person_id) e on e.person_id = p.id
   where e.last_seen is null or e.last_seen < now() - interval 365 day
   ```

2. 찾은 Person을 Persons 화면이나 [PostHog 데이터 삭제 안내](https://posthog.com/docs/privacy/data-storage)의 API로 지웁니다.
3. 정리한 날짜와 지운 Person 수를 운영 기록에 남깁니다.

가장 오래된 Person이 2026년 8월에 생겼으므로 첫 정리 대상은 2027년 8월부터 생깁니다.

#### 문의 알림

Discord 알림에는 유형, 접수 시각, 접수 ID, 정정 대상 제품과 관리자 화면 주소만 보냅니다(`server/ARCHITECTURE.md`).
이용자가 쓴 내용이 Discord로 넘어가지 않으므로 처리방침에서 Discord를 수탁자와 국외 이전 대상에서 뺐습니다. 이 변경
전에 보낸 메시지에는 문의 본문과 화면 주소가 남아 있으므로, 이번 개정을 공개하기 전에 Discord 채널의 기존 메시지를
지웁니다. 알림에 이용자가 쓴 값을 다시 넣으면 처리방침 제2조·제5조·제6조를 함께 고칩니다.

#### 그 밖의 결정

- 공식 전화번호는 두지 않고 이메일 접수처만 유지합니다.
- 개정할 때 변경 전후 비교표는 만들지 않고, 제13조의 개정 이력으로 바뀐 내용을 안내합니다.
- 실패한 백업의 임시 덤프는 운영에서 지우도록 고칩니다. 고친 뒤 처리방침 제7조의 임시 사본 문장을 지웁니다.

### 닉네임과 프로필 사진

가입에서는 닉네임과 사진을 묻지 않습니다. 가입하면 서버가 만든 기본 닉네임을 쓰고, 마이페이지 상단의 프로필 영역에서
`/my-page/profile` 편집 화면으로 들어가 바꿉니다. 닉네임은 공백·특수문자 없이 한글·영문·숫자 2~15자입니다. 형식 오류는
입력이 멈춘 뒤 보여 주고, 형식이 맞을 때만 중복 확인 API를 불러 사용할 수 있을 때 저장을 엽니다. 확인 뒤 저장 응답의 중복은 다시
안내합니다.

사진은 선택 즉시 기존 프로필 이미지 API로 업로드하고, 저장할 때 받은 ID를 프로필에 연결합니다. 브라우저가 읽을 수 있는
JPEG·PNG는 서버와 같게 가운데를 정사각형으로 잘라 512px 이하로 줄이며 HEIC는 서버 처리를 사용합니다. 고른 사진은 바로 보여 주고, 업로드가 끝날 때까지 그 위에
진행 표시를 띄우며 저장을 막습니다. 업로드에 실패하면 사진에 실패를 표시하고, 사진을 누르면 같은 파일을 다시 올립니다. 선택을 바꾸거나
취소한 뒤 이전 업로드가 끝나도 그 결과를 붙이지 않습니다. 미리보기 URL은 선택 변경·삭제·화면 종료 때 반환합니다.

닉네임·사진 저장에는 기존 피부 정보도 함께 보내 기존 값을 보존합니다. 닉네임·사진·피부 정보 수정은 서버의 회원별 1분 5회
요청 제한을 공유하며, 실패한 입력은 화면에 남깁니다.

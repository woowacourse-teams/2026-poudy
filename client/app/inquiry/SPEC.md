## 화면 형식

이슈는 채팅처럼 한 번에 한 가지씩 묻는 흐름을 제안했지만, 디자인은 게시판 등록 형식으로 확정됐습니다. 한 화면에 필요한 항목을 모두 펼쳐 두고 마지막에 한 번 제출합니다.

채팅 형식을 쓰지 않는 이유는 이 API가 한쪽으로만 흐르기 때문입니다. 채팅 모양은 사용자가 메시지를 여러 번 나눠 보내도록 유도하는데, 이 화면의 전송 버튼은 문의를 접수하는 버튼이어서 한 번 누르면 끝납니다. 채팅처럼 짧게 나눠 보내면 이어서 쓰려던 내용을 잃고, `content`의 최소 길이인 10자에 걸려 거절당하기도 합니다.

게시판 형식에서는 제출 버튼이 화면마다 하나뿐이므로 이런 문제가 생기지 않습니다. 사용자가 전체 분량을 미리 파악할 수 있고, 필수 항목과 선택 항목도 한눈에 구분됩니다.

모든 프레임은 390 × 1046 크기이며, 상단 바와 스크롤 본문, 하단 고정 제출 버튼으로 구성됩니다.

디자인과 다르게 구현하는 부분이 한 곳 있습니다. S13c에는 제목만 있고 설명 문구가 없는데, 이슈가 확인한 뒤 반영한다는 뜻을 분명히 전하라고 요구하므로 제목 아래에 설명을 함께 둡니다.

S13b의 브랜드 입력에는 안내 문구가 없습니다. 선택 사항이라는 점은 문구 대신 제출 버튼이 활성화되는 동작으로 드러냅니다.

## 라우팅

경로를 두 개 둡니다. 일반 문의와 제품 정보 정정은 묻는 내용과 진입 경로가 서로 다르기 때문입니다.

```
/inquiry                                 일반 문의
/inquiry?from=/products/123              일반 문의, 문의를 연 화면이 있는 경우
/inquiry/products/123                    제품 정보 정정
```

| 경로                            | 화면                  | 파일                                        |
| ------------------------------- | --------------------- | ------------------------------------------- |
| `/inquiry`                      | S13, S13a, S13b, S13c | `app/inquiry/page.tsx`                      |
| `/inquiry/products/[productId]` | S13e                  | `app/inquiry/products/[productId]/page.tsx` |

제품 정보 정정에는 쿼리 파라미터를 두지 않습니다. 대상 제품이 경로에 있으므로 문의를 연 화면도 `/products/{productId}`로 만들어 쓸 수 있습니다. 이 화면은 제품 상세에서만 들어오기 때문입니다.

경로를 나누면 주소만 보고도 무엇을 하는 화면인지 알 수 있고, 제품 ID를 검증하는 코드도 따로 두지 않아도 됩니다. 존재하지 않는 제품은 동적 세그먼트를 처리하는 기존 방식대로 404가 됩니다.

일반 문의의 `from`은 파라미터로 남습니다. 어느 화면에서든 들어올 수 있어서 경로로 표현할 수 없습니다.

| 파라미터 | 담는 값               | 없을 때          |
| -------- | --------------------- | ---------------- |
| `from`   | 문의를 연 화면의 경로 | `/`를 전송합니다 |

`from`은 진입할 때 정해져서 끝까지 바뀌지 않습니다. 화면 안에서 사용자가 고르는 유형은 상태로만 관리하며 주소를 바꾸지 않습니다.

파라미터는 사용자가 수정할 수 있으므로 받은 값을 그대로 믿지 않습니다. `from`이 우리 화면의 경로인지 확인하고, 어긋나면 `/`를 담습니다.

### 진입 경로에 따라 화면이 달라집니다

`/inquiry`로 들어오면 S13처럼 유형 버튼을 보여 줍니다. 떠 있는 문의하기 버튼으로 들어오는 경우가 여기에 해당하며, 무엇을 문의할지 아직 정해지지 않았으므로 유형부터 고르게 합니다.

`/inquiry/products/[productId]`로 들어오면 S13e처럼 유형 버튼을 아예 그리지 않습니다. 제품 상세 화면의 제품 정보 정정 링크가 여기에 해당합니다. 이미 고른 것을 다시 고르게 할 이유가 없고, 다른 유형으로 바꿀 수 있게 열어 두면 정정하러 온 사용자가 엉뚱한 유형으로 접수하게 됩니다.

버튼을 흐리게 하거나 잠그지 않고 그리지 않습니다. 대신 화면 제목이 무엇을 하는 화면인지 알려 줍니다. S13e의 제목은 `제품 정보가 정확하지 않나요?`입니다.

이 화면은 `DATA_CORRECTION` 유형으로 고정해서 전송하며, `path`에는 `/products/{productId}`를 담습니다.

### 단계

| 단계      | 화면                  | 다음 단계 |
| --------- | --------------------- | --------- |
| 작성      | S13, S13a, S13b, S13e | 접수 완료 |
| 접수 완료 | S13c                  | 끝        |

작성 화면에서 유형을 고르면 그 아래 입력 항목이 나타납니다. 화면이 바뀌는 것이 아니라 같은 화면에서 항목이 늘어납니다.

S13d는 첨부한 이미지를 크게 보는 화면이며 작성 화면 위에 겹쳐서 나타나므로 단계로 두지 않습니다.

### 입력하던 내용은 저장하지 않습니다

새로고침하면 입력하던 내용과 첨부한 이미지는 사라집니다. 이번 범위에서는 초안을 저장하지 않습니다.

문의 내용은 최대 2000자여서 주소에 담을 수 없습니다. 길이 제한에 걸릴 뿐만 아니라 사용자가 적은 내용이 주소창과 브라우저 기록에 남습니다. 저장소에 담아 두는 방법도 있지만 이슈가 요구한 사항이 아니며, 만료 처리와 이미지 복원 같은 문제가 뒤따릅니다. 실제로 필요한지는 사용해 본 뒤에 판단합니다.

### 문의를 연 화면의 경로

`FeedbackRequest`의 `path` 필드는 필수이며 1자에서 500자까지 허용합니다. 진입점 링크를 누르는 시점에 그 화면이 자신의 경로를 알고 있으므로, 그때 값을 확보해서 `from` 파라미터에 담습니다.

주소에 담긴 조건도 함께 보냅니다. 어떤 조건을 걸고 있었는지 알아야 오류를 재현할 수 있고, 어떤 조합에서 문의가 나오는지도 함께 볼 수 있습니다.

| 문의를 연 화면                      | 전송하는 값                         |
| ----------------------------------- | ----------------------------------- |
| `/products?include=123&exclude=789` | `/products?include=123&exclude=789` |
| `/products/123`                     | `/products/123`                     |
| `/search?q=수분크림`                | `/search?q=수분크림`                |

`path` 는 500자까지만 허용하므로, 조건이 길어 넘치면 조건을 버리고 경로만 남깁니다. 조건은 있으면 좋은 정보이고 경로는 없으면 안 되는 정보입니다.

조각 식별자(`#`)는 브라우저 안에서만 쓰이므로 보내지 않습니다.

접수를 마치고 돌아갈 때도 이 값을 씁니다. 조건을 떼면 필터를 걸어 둔 목록에서 문의를 연 사람이 조건이 풀린 목록으로 돌아가게 됩니다.

이 방식은 처리방침의 수집 항목과 맞물립니다. 조건을 담는 방식을 바꾸면 방침도 함께 고쳐야 합니다.

### 내부에서 사용하는 이름

서버가 정한 필드 이름인 `path`만으로는 무엇의 경로인지 알기 어려우므로, 클라이언트 내부에서는 `originPath`라고 부르고 전송하기 직전에 `path`로 옮겨 담습니다. 매핑하는 자리에는 서버 필드 이름이 `path`라는 사실을 주석으로 남깁니다.

```ts
sendFeedback({ type, content, originPath, imageIds });
```

전송 함수는 인자를 객체로 받습니다. 순서대로 나열하면 `content`와 `originPath`가 모두 문자열이어서 두 값이 뒤바뀌어도 타입 검사를 통과하기 때문입니다.

### 화면 밖 요소

하단 내비게이션은 `components/ui/bottom-navigation-path.ts`가 허용 목록으로 판별하기 때문에, `/inquiry`는 목록에 없어서 자동으로 노출되지 않습니다. 레이아웃은 수정하지 않습니다.

상단 바는 `components/ui/TopBar.tsx`의 `variant="sub"`가 디자인의 뒤로가기 버튼과 제목 구성에 부합합니다. 디자인에 포함된 닫기 버튼은 `right` 슬롯에 배치합니다.

## API 연동

`lib/api/client.ts`에는 현재 `apiGet` 함수만 있으므로, `apiPost` 함수와 multipart 형식으로 전송하는 함수를 새로 추가합니다. 기존의 `ApiError` 클래스와 `reportError` 함수가 정해 놓은 규약은 그대로 따릅니다.

이미지는 `POST /api/feedback/images`로 먼저 업로드해서 `imageIds`를 받고, 그 값을 `POST /api/feedback`의 본문에 함께 실어 보냅니다.

| 엔드포인트                   | 본문                                  | 성공 | 오류               |
| ---------------------------- | ------------------------------------- | ---- | ------------------ |
| `POST /api/feedback`         | `type`, `content`, `path`, `imageIds` | 204  | 400, 429, 500      |
| `POST /api/feedback/images`  | `images`                              | 201  | 400, 413, 429, 500 |
| `POST /api/product-requests` | `productName`, `brandName`            | 202  | 400, 429, 500      |

`path`를 받는 스키마는 `FeedbackRequest` 하나뿐이므로 제품 등록 요청에는 경로를 보내지 않습니다.

413 오류는 이미지 업로드 단계에서만 발생하므로 그 자리에서만 처리합니다. 전송하는 동안에는 버튼을 비활성화해서 중복 요청을 차단하고, 전송에 성공하면 입력한 내용과 첨부한 이미지를 모두 비웁니다.

접수 완료 화면에는 제목 `문의를 접수했어요` 아래에 `보내주신 내용을 확인해 반영할게요`를 함께 보여 줍니다. 제목만으로는 접수됐다는 사실만 전할 뿐, 확인한 뒤 반영한다는 뜻이 빠집니다.

반영 시점을 약속하는 문구는 쓰지 않습니다. `POST /api/product-requests`는 202를 돌려주며 스키마에 제품 등록 완료를 뜻하지 않는다고 적혀 있습니다. 접수만 된 것이고 실제 반영은 운영이 따로 판단하므로, `빠른 시일 내에`처럼 시점을 약속하면 지키지 못합니다.

## 입력 제약

화면에 제약을 안내하되, 안내에 그치지 않고 실제로 지켜지도록 막습니다.

| 항목        | 제약                          | 근거                                     |
| ----------- | ----------------------------- | ---------------------------------------- |
| 문의 내용   | 10자 이상 2000자까지          | `FeedbackRequest.content`                |
| 제품명      | 1자 이상 200자까지            | `ProductRegistrationRequest.productName` |
| 브랜드      | 100자까지이며 선택 사항입니다 | `ProductRegistrationRequest.brandName`   |
| 이미지 크기 | 장당 5MB까지                  | 디자인 문구와 개인정보처리방침           |
| 이미지 개수 | 다섯 장까지                   | `imageIds`의 최대 개수                   |
| 이미지 형식 | JPG와 PNG, HEIC               | 서버가 받는 형식입니다                   |

문의 내용은 2000자를 넘겨 입력할 수 없도록 막고, 디자인의 `0 / 2,000` 자리에 현재 길이를 보여 줍니다. 입력 글자는 세 곳 모두 14px 로 보입니다.

10자에 미치지 못하면 제출 버튼을 누를 수 없습니다. 서버가 400으로 거절할 요청을 미리 막고, 최소 길이를 채워야 한다는 사실도 함께 알립니다.

이미지는 `File.size`로 크기를 확인해 5MB를 넘으면 업로드하지 않고 그 자리에서 알립니다. 파일을 고르는 시점에 판단할 수 있으므로 서버에 보내 볼 필요가 없습니다.

다만 이 검사는 서버 검증을 대신하지 않습니다. 5MB를 계산하는 기준이 서버와 다를 수 있고 multipart로 감싸면 전송 크기가 원본보다 커지므로, 경계에 걸친 파일은 서버에서 413으로 거절될 수 있습니다. 413 처리는 그대로 유지합니다.

### 아이폰의 HEIC 형식

서버가 JPEG 와 PNG, HEIC 를 받습니다. HEIC 는 서버가 JPEG 로 다시 저장합니다. 388번 이슈로 지원이 더해졌습니다.

아이폰은 기본 설정에서 사진을 HEIC 로 저장하므로, `accept` 에 HEIC 를 넣어 사진 보관함과 파일 앱 어느 쪽에서 고르든 그대로 올릴 수 있게 합니다. 변환은 서버가 맡으므로 클라이언트에서 바꾸지 않습니다.

다만 브라우저는 HEIC 를 그리지 못합니다. 첨부와 전송에는 지장이 없지만 미리보기가 빈 칸이 되므로, 그리지 못할 때만 사진이 있다는 표시로 자리를 채웁니다. 전체화면에서는 미리 보여 줄 수 없다는 사실과 첨부는 됐다는 사실을 함께 적습니다.

서버는 파일 이름이나 선언된 형식이 아니라 실제 바이트로 판별합니다. 클라이언트의 `accept` 와 형식 검사는 사용자가 엉뚱한 파일을 고르는 것을 미리 막아 주는 장치일 뿐, 서버 검증을 대신하지 않습니다.

### 입력이 멈춘 뒤에 알립니다

잘못은 글자마다 알리지 않고 입력이 멈춘 뒤에 알립니다. 열 자를 채우는 동안 붉은 글씨가 따라다니면 재촉받는 느낌을 줍니다. 기존 `useDebouncedValue`를 그대로 씁니다.

아직 아무것도 적지 않은 칸은 잘못으로 보지 않습니다. 화면에 들어오자마자 붉은 글씨가 깔리면 처음 온 사람에게는 자기가 뭘 잘못한 것처럼 보입니다.

잘못이 있으면 설명 자리를 대신 씁니다. 제품명 칸은 평소 `용량이나 버전이 있다면 함께 적어주세요`를 보여 주다가 잘못이 생기면 그 자리에 잘못을 보여 줍니다. 둘을 함께 쌓지 않습니다.

자리는 미리 잡아 둡니다. 잘못이 나타나도 아래 항목이 밀리지 않습니다. 다만 비어 있을 때 한 줄이 그대로 남으면 아래와 사이가 유독 벌어지므로, 자리의 절반만 흐름에 두고 나머지는 아래 여백에 겹칩니다.

## 업로드 상태

이미지 업로드는 문의 전송과 별개로 진행되므로, 업로드가 끝나지 않은 상태에서 전송하면 `imageIds`가 빠진 채로 접수됩니다. 이를 막기 위해 업로드하는 동안 화면을 다음과 같이 다룹니다.

- 업로드하는 동안 해당 이미지에 진행 중임을 나타내는 표시를 보여 줍니다
- 첨부한 이미지가 모두 `imageIds`를 받기 전까지 제출 버튼을 누를 수 없습니다
- 업로드하는 동안에는 그 이미지를 삭제할 수 없습니다

업로드 중인 이미지를 삭제할 수 없게 막는 이유는, 삭제한 뒤에 응답이 도착하면 이미 화면에서 사라진 이미지의 `imageIds`를 들고 있게 되어 상태가 어긋나기 때문입니다.

디자인 S13a의 세 번째 썸네일이 이 상태를 보여 줍니다. 반투명하게 덮고 가운데에 진행 표시를 두며, 삭제 버튼을 두지 않습니다.

업로드에 실패한 이미지는 삭제할 수 있어야 합니다. 실패한 이미지를 지우지 못하면 제출 자체가 막혀서 문의를 보낼 수 없게 됩니다.

## 문의 유형별 화면 구성

유형에 따라 묻는 내용과 안내 문구가 달라집니다.

| 유형                        | `type`            | 유형 버튼 | 입력 항목      | 이미지 |
| --------------------------- | ----------------- | --------- | -------------- | ------ |
| 오류를 발견했어요           | `BUG_REPORT`      | 있음      | 문의 내용      | 선택   |
| 개선하고 싶은 점이 있어요   | `IMPROVEMENT`     | 있음      | 문의 내용      | 선택   |
| 그 밖의 문의가 있어요       | `OTHER`           | 있음      | 문의 내용      | 선택   |
| 등록하고 싶은 제품이 있어요 | 해당 없음         | 있음      | 제품명, 브랜드 | 없음   |
| 제품 정보가 정확하지 않아요 | `DATA_CORRECTION` | 없음      | 제보 내용      | 선택   |

`/inquiry`의 유형 선택 화면에는 네 가지만 보입니다. `DATA_CORRECTION`은 `/inquiry/products/[productId]` 경로에서만 사용하므로 목록에 두지 않습니다. 대상 제품이 정해져야 의미가 있는 유형이어서 제품 없이 고를 수 있게 두면 어느 제품에 대한 제보인지 알 수 없습니다. 이슈가 이 유형을 화면에 두지 않는다고 정한 것과도 어긋나지 않습니다.

유형마다 라벨과 입력 칸 안내 문구가 다릅니다. 라벨 아래에 따로 질문을 두지 않고, 안내 문구가 그 역할을 대신합니다.

| 유형              | 라벨      | 입력 칸 안내 문구                                                               |
| ----------------- | --------- | ------------------------------------------------------------------------------- |
| `BUG_REPORT`      | 문의 내용 | 예를 들어 어느 화면에서 무엇을 누르셨는지 적어주시면 도움이 돼요.               |
| `IMPROVEMENT`     | 문의 내용 | 지금 어떤 점이 아쉬운지 함께 적어주시면 도움이 돼요.                            |
| `OTHER`           | 문의 내용 | 궁금하거나 알리고 싶은 내용을 적어주세요.                                       |
| `DATA_CORRECTION` | 제보 내용 | 성분이나 용량, 가격 중 무엇이 다른지 실제 정보와 함께 적어주시면 확인이 빨라요. |

`BUG_REPORT`와 `DATA_CORRECTION`의 문구는 디자인 S13a와 S13e에 있는 것을 그대로 씁니다. `IMPROVEMENT`와 `OTHER`는 디자인에 없어서 같은 기준으로 새로 적었으므로, 디자인이 나오면 그에 맞춥니다.

제품 등록 요청은 `POST /api/product-requests`를 호출하며 이미지를 첨부하지 않습니다. 제품명과 브랜드를 각각 한 줄 입력으로 받습니다.

민감한 정보에 대한 안내는 자유 입력을 받는 화면에 공통으로 보여 줍니다. 제품 등록 요청 화면에는 대신 제품 정보 안내를 둡니다.

필수 항목에만 별표를 붙입니다. 선택 항목에는 아무 표시도 두지 않으며, 별표가 없다는 사실이 선택이라는 뜻입니다.

브랜드가 선택 사항이라는 점은 문구로 설명하지 않고 동작으로 보여 줍니다. 브랜드를 비워 두어도 제출 버튼이 활성화되므로 쓰지 않아도 된다는 사실이 드러납니다.

## 목 핸들러

`mocks/handlers.ts`에 POST 핸들러 세 개를 추가합니다. 현재 등록된 핸들러는 모두 GET이므로 이번에 추가하는 핸들러가 첫 POST 핸들러입니다.

```
POST /api/feedback         → 204
POST /api/feedback/images  → 201, imageIds 반환
POST /api/product-requests → 202
```

429 오류와 413 오류의 안내 문구를 실제로 확인할 수 있도록, 특정한 입력을 넣으면 해당 오류가 발생하도록 유도하는 경로도 함께 마련합니다.

## 진입점

### 떠 있는 문의하기 버튼

화면 오른쪽 아래에 원형 버튼을 띄웁니다. 스크롤해도 자리를 지키며, 문의하기 화면을 뺀 모든 화면에 나타납니다. 문의는 어느 화면에서든 생기므로 화면을 가리지 않습니다.

`components/ui/BottomNavigationSlot.tsx`와 같은 방식으로 만듭니다. 경로를 보고 보여 줄지 판단하는 컴포넌트를 `app/layout.tsx`에 두며, 하단 내비게이션 옆에 나란히 놓습니다.

```tsx
{children}
<BottomNavigationSlot />
<InquiryButtonSlot />
```

`/inquiry`로 시작하는 경로에서는 모두 숨깁니다. 제품 정보 정정 화면도 포함합니다. 이미 문의하기 안에 있는데 같은 곳으로 들어가는 버튼을 둘 이유가 없고, 버튼을 누르면 쓰던 내용이 사라지기 때문입니다.

### 하단 내비게이션과 겹치지 않게 둡니다

하단 내비게이션은 `sticky bottom-0`이며 레이아웃 흐름 안에 있습니다. 떠 있는 버튼은 흐름 밖에 두므로 내비게이션이 밀어내지 못합니다. 겹치지 않도록 위치를 직접 계산해야 합니다.

| 화면                        | 버튼 위치                         |
| --------------------------- | --------------------------------- |
| 하단 내비게이션이 있는 화면 | 내비게이션 높이만큼 위로 올립니다 |
| 하단 내비게이션이 없는 화면 | 화면 아래에 붙입니다              |

어느 쪽인지는 `isBottomNavigationPath`가 이미 판단하고 있으므로 그 함수를 그대로 씁니다. 판단 기준을 두 곳에 두면 한쪽만 고쳐져 어긋납니다.

버튼은 `fixed`가 아니라 `sticky`로 둡니다. 넓은 화면에서 본문은 폭이 제한되어 가운데 놓이는데, `fixed`로 두면 뷰포트 오른쪽에 붙어 본문 밖으로 나갑니다. 하단 내비게이션이 `sticky`로 흐름 안에 있는 것과 같은 이유입니다.

흐름 안에 두면 자리를 차지하므로 높이를 0으로 두고 버튼만 위로 끌어올립니다.

기기의 안전 영역도 고려합니다. 하단 내비게이션이 없는 화면에서 버튼이 화면 맨 아래에 붙으면 홈 인디케이터에 가립니다.

버튼은 하단 내비게이션보다 위에 겹쳐야 하므로 `z-20`보다 높은 값을 줍니다.

### 누른 화면의 주소를 담습니다

버튼이 `from` 값을 채웁니다. 누른 시점의 주소를 조건까지 담아 `/inquiry?from=...` 형태로 넘깁니다.

이 진입점은 링크입니다. 다른 화면으로 가는 것이므로 새 탭으로 열거나 주소를 미리 보는 길을 막지 않습니다.

다만 조건은 `href` 에 담지 않고 누르는 순간 붙입니다. 그려질 때 `useSearchParams` 로 읽으면 이 버튼이 레이아웃에 있어 모든 화면이 Suspense 경계를 요구하고, 미리 만들어 두는 화면까지 무너집니다.

| 상황           | 넘기는 값                  |
| -------------- | -------------------------- |
| 눌러서 이동    | 경로와 조건                |
| 새 탭으로 열기 | 경로만 (`href` 에 담긴 값) |

새 탭으로 여는 중이면 `preventDefault` 를 하지 않고 브라우저에 맡깁니다. 그때는 조건이 빠지는데, 조건까지 담으려면 그려질 때 읽어야 해서 감수합니다.

제품 상세 화면에서 눌러도 일반 문의로 보냅니다. 떠 있는 버튼은 무엇이든 문의한다는 뜻이므로 유형을 미리 정하지 않습니다.

### 제품 정보 정정 링크

자리가 이미 마련돼 있습니다. `components/product/ProductDetail.tsx`의 `Source` 컴포넌트에 다음 주석이 남아 있습니다.

```tsx
{
  /* 정보 수정 제안은 받을 곳이 아직 없어 화면에서 감춘다. */
}
```

이제 받을 곳이 생기므로 이 자리에 `정보 수정 제안 ›` 링크를 넣고 주석을 지웁니다. 디자인 S05의 `상품 정보 출처 안내` 콜아웃에도 같은 문구가 그려져 있습니다.

링크는 `/inquiry/products/{productId}`로 보냅니다. 이 링크가 있어야 `DATA_CORRECTION` 유형에 닿을 수 있습니다.

콜아웃은 `브랜드 공식 전성분을 기준으로 정리했어요. 제품 리뉴얼에 따라 실제 표기와 다를 수 있어요.`라고 알리는 자리입니다. 정보가 실제와 다를 수 있다고 말하는 바로 그 자리에서 수정을 제안받으므로 맥락이 이어집니다.

떠 있는 버튼과 역할이 다릅니다. 떠 있는 버튼은 어느 화면에서든 문의를 여는 곳이고, 이 링크는 지금 보고 있는 제품의 정보가 틀렸다고 알리는 곳입니다.

### 디자인

떠 있는 버튼은 v1.pen에 아직 없어 기존 변수로 구현했습니다. 디자인이 나오면 그에 맞춥니다.

배경은 `$ui-brand-soft`, 아이콘은 `$ui-brand`를 쓰고 원형으로 둡니다. 배경이 연해 흰 본문에 묻히므로 퍼짐 없는 1px 그림자를 겹쳐 테두리를 겸합니다. `--shadow-app-frame`이 쓰는 방식과 같습니다.

아이콘은 말풍선 안에 물음표를 둔 모양입니다. 봉투는 받은 편지함으로 읽혀 답장이 온 것처럼 보이고, 홈 하단의 메일 보내기 링크와도 겹칩니다.

화면 낭독기를 쓰는 사람을 위해 버튼에 이름을 붙입니다.

## 테스트

주변 코드의 관례에 따라 각 파일 옆에 `*.test.tsx` 파일을 함께 둡니다. `describe`와 `it`으로 묶고 동작을 한국어로 서술하며, 조회는 역할 기준으로 수행하고 상호작용은 `userEvent`로 작성합니다.

### 유형 선택

- 유형을 고르기 전에는 입력 항목을 보여 주지 않는다
- 유형을 고르기 전에는 제출 버튼을 누를 수 없다
- 유형을 고르면 해당 입력 항목이 나타난다
- 유형을 바꾸면 이전 유형의 입력 항목이 사라진다
- 제품 등록 요청을 고르면 제품명과 브랜드 입력이 나타난다
- 유형 선택 화면에 `DATA_CORRECTION`은 나타나지 않는다

### 입력과 제출 버튼의 상태

- 입력이 비어 있으면 제출 버튼을 누를 수 없다
- 공백만 입력하면 제출 버튼을 누를 수 없다
- 10자 미만을 입력하면 제출 버튼을 누를 수 없고 최소 길이를 안내한다
- 10자를 채우면 제출 버튼을 누를 수 있다
- 2000자를 넘겨 입력할 수 없다
- 입력한 길이가 글자 수 표시에 반영된다

### 전송 동작

- 제출하면 `type`, `content`, `path`를 담아 `POST /api/feedback`을 호출한다
- 내부에서 사용한 `originPath` 값이 요청 본문에서는 `path` 필드로 전달된다
- 전송하는 동안 제출 버튼을 비활성화한다
- 전송이 끝나기 전에 버튼을 두 번 눌러도 요청은 한 번만 나간다
- 전송에 성공하면 접수 완료 화면을 보여 준다
- 접수 완료 화면은 답변을 약속하는 문구를 담지 않는다
- 확인을 누르면 문의를 연 화면으로 돌아간다
- 문의를 연 화면이 없으면 홈으로 보낸다

### 쿼리 파라미터

- `from`에 담긴 경로를 `path` 필드로 전송한다
- `from`이 없으면 `/`를 전송한다
- `from`이 우리 화면의 경로가 아니면 `/`를 전송한다
- 주소에 담긴 조건도 함께 전송한다
- 조건이 길어 500자를 넘으면 경로만 전송한다
- 화면에서 유형을 골라도 주소는 바뀌지 않는다

### 이미지 첨부

- 이미지를 첨부하면 미리보기에 나타난다
- 다섯 장을 첨부하면 첨부 버튼을 비활성화한다
- 다섯 장을 넘겨 선택하면 다섯 장까지만 받는다
- 첨부한 이미지를 삭제하면 미리보기에서 사라지고 첨부 버튼이 다시 활성화된다
- 첨부한 이미지를 누르면 전체화면으로 볼 수 있다
- 전체화면에서 삭제하면 목록에서도 사라진다
- 이미지를 먼저 업로드해서 받은 `imageIds`를 문의 전송에 함께 담는다
- 5MB를 넘는 이미지는 업로드를 시도하지 않고 그 자리에서 알린다
- HEIC 파일도 첨부할 수 있다
- 사진이 아닌 파일은 받지 않는다
- 브라우저가 그리지 못하는 사진은 미리보기 자리를 표시로 채운다
- 제품 등록 요청에서는 이미지를 첨부할 수 없다

### 업로드 상태

- 업로드하는 동안 진행 중임을 나타내는 표시를 보여 준다
- 업로드가 끝나지 않으면 제출 버튼을 누를 수 없다
- 여러 장 중 한 장이라도 업로드 중이면 제출 버튼을 누를 수 없다
- 모든 이미지가 `imageIds`를 받으면 제출 버튼을 누를 수 있다
- 업로드하는 동안에는 그 이미지를 삭제할 수 없다
- 업로드에 실패한 이미지는 삭제할 수 있다
- 업로드에 실패한 이미지를 지우면 제출할 수 있다

### 제품 정보 정정

- 제품 상세의 `정보 수정 제안`을 누르면 `/inquiry/products/123`으로 간다
- `/inquiry/products/123`으로 들어오면 유형 버튼이 나타나지 않는다
- 경로의 제품 ID로 제품의 이름과 브랜드를 보여 준다
- 대상 제품을 사용자가 바꿀 수 없다
- 라벨이 `제보 내용`으로 나타난다
- `DATA_CORRECTION` 유형으로 전송한다
- `path`에 `/products/123`을 담아 전송한다

### 오류 처리

- 이미지 업로드가 413으로 실패하면 용량 때문이라고 안내한다
- 이미지 업로드가 429로 실패하면 잠시 뒤 다시 시도해 달라고 안내한다
- 문의 전송이 429로 실패하면 다른 오류와 구분되는 문구를 보여 준다
- 전송에 실패하면 입력한 내용을 지우지 않는다
- 전송에 실패한 뒤 다시 전송할 수 있다

### 떠 있는 문의하기 버튼

- 문의하기 화면이 아니면 버튼을 보여 준다
- `/inquiry`에서는 버튼을 보여 주지 않는다
- `/inquiry/products/123`에서도 버튼을 보여 주지 않는다
- 누르면 누른 화면의 경로를 `from`에 담아 이동한다
- 누른 화면의 조건도 `from`에 담는다
- 하단 내비게이션이 있는 화면에서는 그 위로 올라간다

### 제품 등록 요청

- 제품명과 브랜드를 담아 `POST /api/product-requests`를 호출한다
- 브랜드를 입력하지 않고 등록을 요청할 수 있다
- 브랜드가 비어 있어도 제출 버튼이 활성화된다
- 제품명이 비어 있으면 제출할 수 없다
- 접수됐다는 안내와 확인 후 반영한다는 안내를 함께 보여 준다
- 반영 시점을 약속하는 문구를 보여 주지 않는다

## 법적 고지 문서와의 관계

392번 PR 이 이 기능에 맞춰 처리방침과 이용약관을 고쳤습니다. 화면을 손볼 때는 두 문서도 함께 봐야 합니다.

| 문서     | 이 기능과 맞물리는 곳                                                                    |
| -------- | ---------------------------------------------------------------------------------------- |
| 처리방침 | 문의 내용과 첨부 이미지, 문의를 연 화면의 경로를 수집 항목으로 적었습니다                |
| 처리방침 | 첨부 형식을 JPEG·PNG·HEIC 로 적고, 받은 파일을 JPEG 나 PNG 로 다시 저장한다고 밝혔습니다 |
| 이용약관 | 제7조 이용자 제출물에 권리 귀속과 삭제 근거를 두었습니다                                 |

`path` 를 담는 방식도 방침에 그대로 적혀 있습니다. `검색어와 선택한 조건이 주소에 담겨 있으면 함께 저장됩니다` 라고 되어 있어 구현과 일치합니다. 이 규칙을 바꾸면 방침도 함께 고쳐야 합니다.

## 확인이 필요한 사항

### 처리방침의 이메일 항목이 실제와 다릅니다

`app/privacy/page.tsx`의 69번째 줄이 수집 항목에 `답변을 받을 이메일 주소(적지 않고 보내실 수 있습니다)`를 적고 있습니다. 그러나 `common/api.zod.ts`의 `FeedbackRequest`와 `ProductRegistrationRequest` 어디에도 이메일 필드가 없고, 화면에도 이메일을 받는 자리가 없습니다.

392번 PR 이 방침을 손보면서 `path` 와 HEIC 는 반영했지만 이 항목은 그대로 두었습니다. 수집하지 않는 항목이 수집 항목으로 적혀 있는 상태이므로, 방침에서 지우거나 이메일 필드를 두는 쪽으로 정해야 합니다.

172번째 줄과 281번째 줄, 328번째 줄도 이메일을 받는다는 전제로 쓰여 있어 함께 봐야 합니다.

## 구현하며 정한 것

### 쿼리 파라미터는 서버 컴포넌트가 읽습니다

`from` 을 `useSearchParams` 로 읽으면 Suspense 경계를 요구해 빌드가 멈춥니다. 떠 있는 버튼은 레이아웃에 있어 모든 화면이 영향을 받으므로, 미리 만들어 두는 화면까지 함께 무너집니다.

그래서 `page.tsx` 가 `searchParams` 로 받아 `InquiryScreen` 에 넘깁니다. 값을 고르는 일은 서버가 맡고 화면은 정해진 값을 받기만 합니다.

### 버튼 색은 상태로 나눕니다

`disabled:` 변형만 두면 켜진 상태에도 꺼진 색이 남습니다. 켜짐과 꺼짐을 조건으로 나눠 각각의 색을 직접 적습니다.

### 목 응답도 스키마 검사를 받습니다

`lib/domain/mock-schema.test.ts` 가 모든 핸들러를 검사하고 있어, 새로 추가한 POST 세 개도 함께 검사하도록 넓혔습니다. 응답에 내용이 없는 곳은 상태 코드만 봅니다.

### 파일 구성이 조금 늘었습니다

`lib/**` 에 함수 길이 제한이 있어 업로드 상태를 두 자리로 나눴습니다.

| 파일                           | 역할                                          |
| ------------------------------ | --------------------------------------------- |
| `lib/domain/attached-image.ts` | 첨부 파일을 받을지 판단하고 상태를 계산합니다 |
| `lib/domain/origin-path.ts`    | 문의를 연 화면의 경로를 다듬습니다            |
| `lib/hooks/usePreviewUrls.ts`  | 미리보기 주소를 만들고 되돌려줍니다           |

### 오류 문구는 누른 버튼 바로 위에 둡니다

전송 실패는 본문 끝이 아니라 고정 버튼 영역 안, 제출 버튼 바로 위에 보여 줍니다. 본문 끝에 두면 입력 항목이 적은 화면에서 버튼과 멀어져, 눌러 놓고도 왜 안 됐는지 눈에 들어오지 않습니다.

문구는 한 줄에 들어가는 길이로 맞춥니다. 폭이 좁아 서른 자를 넘기면 두 줄이 되는데, 버튼 바로 위라 줄 수가 달라지면 버튼이 오르내려 눌리는 자리가 흔들립니다.

같은 까닭으로 문의와 제품 등록 요청이 같은 문구를 씁니다. 무엇을 보냈는지는 화면이 이미 말해 주므로 문구에서 되풀이하지 않습니다.

### 첨부 실패는 썸네일 안에 겹칩니다

실패 표시를 썸네일 아래에 두면 그만큼 자리를 차지해 목록이 들쭉날쭉해집니다. 썸네일 안쪽 하단에 겹쳐 두어 자리를 차지하지 않게 합니다.

### iOS 확대를 막습니다

iOS Safari 는 초점이 간 입력의 `font-size` 가 16px 보다 작으면 화면을 저절로 키우고, 입력에서 빠져나와도 키운 채로 둡니다.

검색 입력(`.search-field-input`)이 쓰는 방식을 그대로 따릅니다. `font-size` 는 16px 로 두고 `scale(0.875)` 로 보이는 크기만 14px 로 줄입니다. viewport 에 `maximum-scale` 을 거는 방법과 달리 사용자가 손가락으로 넓히는 확대는 그대로 살아 있습니다.

문의 내용 입력을 13px 에서 14px 로 올려 제품명·브랜드와 통일했습니다. 배율이 같아져 `.inquiry-input` 하나로 세 입력을 모두 덮습니다.

여러 줄 입력이라 기준점만 다릅니다. 검색은 `left center` 이지만 문의 내용은 `left top` 입니다. 가운데를 기준으로 하면 줄이 늘 때마다 첫 줄의 자리가 흔들립니다.

### 접수를 마치면 문의를 연 화면으로 돌아갑니다

확인을 누르면 돌아갈 곳을 세 단계로 고릅니다.

| 순서 | 조건                  | 동작               |
| ---- | --------------------- | ------------------ |
| 1    | `from` 이 있음        | 그 경로로 옮깁니다 |
| 2    | 없고 방문 기록이 있음 | 뒤로 갑니다        |
| 3    | 둘 다 없음            | 홈으로 보냅니다    |

`from` 을 먼저 보는 까닭은 이 값이 문의를 시작한 자리를 그대로 담고 있기 때문입니다. 방문 기록은 문의 화면에 오기까지 거친 자리를 가리키므로, 중간에 다른 화면을 들렀다면 시작한 곳과 어긋납니다.

기록이 없는데 `router.back()` 을 부르면 사이트 밖으로 나갑니다. 주소로 바로 들어와 문의를 보낸 경우가 그렇습니다. `TopBar` 가 뒤로가기에 쓰는 `hasInSiteHistory` 로 같은 판단을 합니다.

옮길 때는 `replace` 를 씁니다. 기록을 늘리지 않아 옮긴 뒤 뒤로 가도 접수 화면으로 돌아오지 않습니다.

### 체크는 눈에 맞춰 조금 내립니다

접수 완료의 체크는 1000ms 동안 획이 그려지듯 나타나며 크기는 38px 입니다. 원형 배경은 64px 입니다.

체크는 아래로 뻗은 획이 짧고 위로 올라가는 획이 길어, 자를 대고 가운데에 두면 위로 떠 보입니다. 1.5px 내려 눈에 맞춥니다.

### 빌드는 API 주소가 있어야 지나갑니다

`next build` 는 `/brands` 처럼 미리 만드는 화면을 그리며 서버에서 API 를 부릅니다. MSW 는 서버가 뜰 때 `instrumentation.ts` 로 붙는데, 빌드의 사전 생성은 서버가 아니라 빌드 워커라 그 함수가 불리지 않습니다. 그래서 목이 없고 실제 요청이 나갑니다.

`client/.env.example` 이 이 사정을 알고 `NEXT_PUBLIC_API_BASE_URL` 에 스테이징 주소를 적어 두었습니다. 사본이 오래돼 이 값이 비어 있으면 빌드가 멈추므로, 그럴 때는 `.env.example` 을 다시 복사합니다.

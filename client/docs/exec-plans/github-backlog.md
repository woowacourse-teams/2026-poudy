# GitHub 이슈·PR 작성 대기 목록

> GitHub 장애로 올리지 못한 이슈와 PR 을 기록해 둔다. 복구되면 이 문서 순서대로 올린다.
>
> **현재 상태**: 브랜치 5 개를 로컬에 쌓아 두었다. push 와 PR 만 남았다.
> 처음에는 11 개로 나누려 했으나 커밋 재배치가 불가능해 5 개로 바꿨다.
> 사유는 아래 `브랜치를 5 개로 나눈 이유` 를 본다.

## 남은 확인 사항

- **ISR 되돌리기**: `/categories`, `/brands` 는 목 서버가 빌드 시점에 뜨지 않아
  `force-dynamic` 으로 두었다. 실제 API 에 붙일 때 `revalidate` 로 바꾼다.
- **없는 제품 404 상태 코드**: 화면은 404 페이지를 보여 주지만 응답 상태는 200 이다.
  데이터를 기다린 뒤 `notFound()` 를 부르면 스트리밍이 이미 시작돼 상태를 바꾸지 못한다.
  색인에는 `noindex` 가 붙어 문제되지 않지만, 상태 코드가 필요하면 별도로 다룬다.
- **비슷한 제품(S05)**: API 가 없어 아직 넣지 않았다.

## 올리는 순서

1. 이슈를 먼저 만들어 번호를 받는다
2. 브랜치를 push 한다
3. PR 을 stacked 로 만든다. 각 PR 의 base 는 앞 PR 의 브랜치다
4. PR 본문의 `Close #N` 에 1 번에서 받은 번호를 넣는다

앞 PR 이 머지되면 뒤 PR 의 base 를 `dev` 로 바꾼다.

## 브랜치를 5 개로 나눈 이유

처음 계획은 화면 단위 stacked PR 11 개였다. 작업이 한 브랜치(`feat/client-assets`)에
68 커밋으로 쌓인 뒤 나누려 했으나, 커밋 순서를 바꾸는 방식은 모두 실패했다.

**측정한 사실**

- 68 커밋 중 38 개가 두 영역 이상을 동시에 고친다.
  `ff2ba90` 은 카테고리 · 상세 · 목록 · 저장함 · 검색 5 개 영역을 한 번에 고친다.
- `IngredientSearchPanel.tsx` 와 `ProductDetail.tsx` 는 각각 9 개 커밋이 건드린다.
  여러 번에 걸쳐 다듬어져서 중간 커밋을 건너뛰면 문맥이 어긋난다.
- 성분·필터 커밋 10 개만 골라 cherry-pick 한 결과 **8 개가 충돌**했다.
  선행 커밋 3 개를 넣고 다시 해도 13 개 중 6 개가 충돌했다.

**그래서 시간순 경계선만 다시 그었다.** cherry-pick 없이 브랜치 포인터만 옮기므로
충돌이 구조적으로 발생하지 않는다. 커밋 메시지와 이력은 그대로 남는다.

**남는 한계**

- PR 5 가 44 커밋 2,690 줄로 크다. 더 쪼개려면 위 충돌을 감수해야 한다.
  리뷰어에게는 `v1.pen 대조 반영` 이라는 하나의 성격으로 설명한다.
- PR 5 가 앞 PR 이 만든 파일을 다시 고친다. 실제 작업 순서가 그랬던 결과라
  어떤 분할로도 없앨 수 없다.

**경계를 정할 때 주의한 점**

PR 1 의 끝을 Vitest 설정 커밋에 두었더니 첫 테스트가 들어오는 커밋 직전이라
`No test files found` 로 CI 가 깨졌다. 도메인 함수와 그 테스트가 같은 PR 에
들어가도록 경계를 뒤로 옮겼다. 경계를 바꿀 때는 그 지점에서 `pnpm run check` 를 돌린다.
